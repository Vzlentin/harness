# harness reference

The behaviour of the `harness` CLI, the `subagent` tool, the Pi extension and the host. The [README](../README.md) has the install.

## Commands

Spawn with a descriptive name using the default model and thinking level (see [Tool](#tool)):

```sh
harness spawn --name review --prompt "Review the current diff independently"
```

Spawn prints `Spawned <name> (<handle>)` and `State: <state>`, the state of the child (see `status`): `busy` for a new child, and the current state when a spawn with the same key repeats. Names appear in the parent UI. Generated handles remain the stable identifiers used by management commands.

Override the model configuration when needed:

```sh
harness spawn \
  --provider openai-codex \
  --model gpt-5.4-mini \
  --thinking low \
  --prompt "Find the relevant implementation"
```

Provide multiple prompt fragments and files. The first message holds the text of each file, then `Task:` and the prompts:

```sh
harness spawn \
  --file /tmp/spec.md \
  --prompt "Implement this specification" \
  --prompt "Run the targeted tests"
```

Restrict tools with `--tools`, a comma-separated list. Without it, a child gets `read`, `write`, `edit`, `bash`, `subagent`, `todo`, `codemode`, and the tools of the host's entries (see [Limits](#limits)). A child at the depth limit gets no `subagent` and no `workflow`, but keeps `todo` (see [Push](#push)). An unknown tool name is an error:

```sh
harness spawn --tools read,bash --prompt "Investigate the failure"
```

A child lives until its spawner stops it or ends (see [Agent life](#agent-life)). `--parley <slug>` gives it the label of a parley, and `--item <id>` the label of a work item. These labels need an entry that checks their label kind, such as the projects entry: without one, the spawn fails with `no loaded entry checks the label kind "<kind>"`. A spawn takes one of them: with both, or one twice, it fails with `A spawn serves one thing: give --parley or --item once`. An `--item` that is not an integer from 1 fails with `Invalid item id: <id>`:

```sh
harness spawn --parley agent-life --prompt "Run the parley"
harness spawn --item 3 --prompt "Do the work item"
```

Manage a run by its generated handle:

```sh
harness status a1b2c3
harness rename a1b2c3 "error handling review"
harness send a1b2c3 "Focus on error handling"
harness send a1b2c3 --follow-up "Then summarize"
harness wait a1b2c3
harness stop a1b2c3
harness stop --conversation 42
harness list
harness query a1b2c3 "Which files did it change?"
harness attach a1b2c3
harness inspect a1b2c3
```

- `status` prints `<name> (<handle>): <state> (<provider>/<model>, <thinking>)`. The state is `busy`, `idle`, `error` when the last turn failed, or `ended` after a `stop`, or when the children library ended the child, such as a subagent under a workflow session whose run ended. After an abort from a mirror session, the state is `idle`. An ended child stays `ended`, also while its children hold it, until a `send` resumes it. A child that is not ended is also `busy` while one of its notify children holds it (see [Push](#push)), at any depth, so `status`, `list`, `wait`, the widget and a mirror session show it as `busy` until its subtree is quiet.
- `send` prints `Prompted`, `Steered`, or `Queued follow-up for`, then the child. A `send` to an ended child resumes it: it runs a new turn with its whole history. A steer goes in after the current tool round. A follow-up starts after the current answer. The verb comes from the child's own turn: a child that only its children hold is `Prompted`.
- `wait` waits until the child answers its last message, up to `--timeout` seconds (default 1800), and prints `<handle> finished`, a blank line, and the answer. When the spawn or an earlier `send` has an answer that no `wait` gave, it prints `<n> unread answers, oldest first.`, a blank line, and each answer after a line `--- Answer <i> of <n> ---`, the last one last. An earlier turn that failed gives `(no answer: <error>)`. A steer shares the answer of the turn it went into, so that answer comes once. A failed or aborted last turn is an error: after an abort, it prints `<handle> was aborted`. The error gives the earlier unread answers in the same form, and does not give the failed turn twice. Each `wait` marks these answers read. A message sent while a `wait` runs stays unread for the next `wait`. Input from a mirror session is not counted. While its children hold the child, `wait` waits too, and when a push starts a turn of the child meanwhile, `wait` gives the answer of that turn. While a `wait` runs, the host pushes no answer of that child. A `wait` for a turn whose answer a push already gave prints `<handle> finished`, a blank line, and `No new answers: the last answer came as a message.`. A second `wait` without a push between still gives the last answer again. A `wait` for an ended child, or for a child that ends while the `wait` runs, fails with `The child <id> ended: send a message to resume it`. When the host closes, a running `wait` fails with `The host is closing`.
- `stop` stops the work of the child and of the children it spawned, and ends them. They keep their handle, their record and their conversation, and their state is `ended`. It marks each request of these children read, so they hold no caller, and an answer that no `wait` or push gave is not pushed. A repeated `stop` finishes a stop that a crash interrupted. A `send` resumes an ended child; a note leaves it ended. A `spawn` that comes again with the request ID of an ended child gives that child and sends nothing. A name is a label and not a key: a `spawn` with a new request ID and the name of an ended child starts a new child with that name, and the ended child stays ended. `stop --conversation <id>` stops the conversation whose ID is `<id>`. The caller `cli`, a command from a terminal that is not an agent (`PI_SESSION_ID` is not set), can stop any conversation of the host that works, by handle or by conversation ID: the child of any caller, a conversation of the children library with no record of a child, such as a session of a workflows run, and the host agent with the handle `agent`. A conversation with no record of a child and the host agent are not ended: the stop aborts their turn, as Esc does, and keeps the conversation and its entries. It prints `Stopped <conversation id>` or `Stopped agent`. The owner of the conversation gets the failure of an aborted turn, such as a task that then fails, and the host agent stays and takes the next input. Another caller can stop only a child that it spawned (see [Host](#host) for the details and the errors). With more arguments, or with a first argument that starts with `--` and is not `--conversation`, it prints the usage.
- `list` prints one line per child of the current caller, the ended ones too: `<name> (<handle>)  <state>  <provider>/<model>  <thinking>`.
- `attach` opens the child in Pi in this terminal, and `attach --conversation <id>` a conversation of the children library (see [Open in Pi](#open-in-pi)). `--side` after the target opens it in a new herdr-app pane to the right of the caller. Without an ID, with an argument after the target other than one `--side`, or with a first argument that starts with `--` and is not `--conversation`, it prints the usage.
- `inspect` serves a web page that shows the child live and sends what you type to it (see [Inspect](#inspect)).
- `query <handle> <question>` prints the answer of a model to one question about the child, and `query --conversation <id> <question>` about a conversation of the children library, such as a session of a workflows run. The words after the target are the question. It is the action `query` of the tool (see [Tool](#tool)). Without a target or a question, or with a first argument that starts with `--` and is not `--conversation`, it prints the usage.

### Host agent

Each host has an agent, a conversation in the host that you talk to directly:

```sh
harness web
harness main
```

`harness <host>` opens the agent of the host in Pi in this terminal (see [Open in Pi](#open-in-pi)). It starts the host when none runs. A single word that is not `main`, a host or a command prints the usage. A `--host` before it is an error: `harness <host> takes no --host`.

- The agent works in the host directory, or in the home directory for `main`. Its system prompt, tools and bash env are the same as a child's in that directory (see [Host](#host)). Its bash commands get `PI_SESSION_ID`, the agent's conversation ID.
- When it is first opened, the agent gets Pi's default model (`defaultProvider` and `defaultModel` in Pi's `settings.json`) when it has a login, else the first model with a login, and Pi's `defaultThinkingLevel` (default `medium`), or the nearest level that the model has. Without a model with a login, Pi does not start and `harness <host>` prints `No model for the <host> agent: log in to a provider and set a default model in Pi (defaultProvider and defaultModel)`. A mirror session changes its model and thinking level as for a child.
- The children that the agent spawns have the agent as their parent: `harness list` with `PI_SESSION_ID` set to the agent's conversation ID shows them. The agent gets the answers of these children as input (see [Push](#push)). Its own state ignores its children.
- Esc stops only the agent's turn. The children that it spawned keep running.
- The agent keeps its conversation across host restarts. `status`, `send`, `wait`, `rename` and `list` do not know the agent: it is not a subagent. `harness stop agent` from a terminal that is not an agent aborts its turn, as Esc does, and the agent stays; an agent caller cannot stop it.
- Before each `input` request to the handle `agent`, the host catches the agent up. It keeps what the agent has seen in a `harness.seen` document of the agent's conversation, version 2: `{ mainSha, catchups, hooks, entry? }`, the head of the default branch, the count of catch-up entries, what each catch-up hook of the entries said the agent saw, by hook kind, and the catch-up entry that is not written yet. A version 1 document loses its `lastTaskId` and `pending`, and its hooks start with nothing seen. The catch-ups of the agent run one at a time. A repeated input, whose request ID the conversation already has, gets no catch-up. The host then reads, in the host directory, read only:
  - The default branch: the target of `refs/remotes/origin/HEAD` without `origin/`, else `main`, and its local head `refs/heads/<branch>`. Outside a Git repository, or without that branch, there are no commits and no warning. With a head in `mainSha`, the commits are those of `git log <mainSha>..<head>`, newest first. When the head does not contain `mainSha` (`git merge-base --is-ancestor` fails), as after a force-push, a change of `origin/HEAD`, or a `mainSha` that the repository no longer has, there are no commits, the entry tells it, and `mainSha` becomes the head, with no warning. When Git fails, the host writes a warning and keeps `mainSha`.
  - The catch-up hooks of the entries, in load order (see the entries below). The host calls `run(harness, seen)` of each hook with the host's harness and the `seen` that the hook returned at the last catch-up, or `undefined` the first time. The hook returns `{ seen, lines, data? }`: the `seen` to keep in `hooks[<kind>]`, the lines for the agent, none when nothing is new, and the data of these lines. A hook that throws or returns another shape gives the warning `catch-up: <kind>: <message>` and keeps its last `seen`, and the catch-up goes on.
  - The first time, with no `harness.seen` yet, the host only records the current state, and adds no entry. When nothing is new, it adds no entry.
  - Else it records the new state with `catchups + 1` and the planned entry in one commit, then adds one passive entry of the kind `harness.catchup` before the input, with the request ID `catchup:<catchups + 1>`, then removes the planned entry from the document. A catch-up first writes a planned entry that an earlier catch-up left, such as after a crash or a failed write; its request ID makes a repeat add nothing. The entry is a user message with the line `Catch-up since your last input.`, then the lines of each hook, then the branch name and each new commit as `<short sha> <subject>`, then a line when the branch no longer contains `mainSha`. Its `data` is `{ commits?, reset?, hooks? }` with the same facts: `commits` is `{ branch, commits: [{ sha, subject }] }`, `reset` is `{ branch, from, head }`, the old and the new head, and `hooks` has the `data` of each hook that gave lines, by hook kind. A missing field is left out.
  - A failure of the catch-up is a warning: the input always goes through.

### Hosts

Each host has its own process, store and children. A host is a name and a directory:

```sh
harness create web --cwd ~/Dev/web
harness hosts
```

- `create <name> --cwd <dir>` prints `Created <name> (<dir>)`, where `<dir>` is the real path of the directory. A relative `--cwd` is relative to the current directory. The name has 1 to 32 characters: `a-z` first, then `a-z`, `0-9` or `-`. It cannot be `main` or a command name (`spawn`, `status`, `rename`, `send`, `wait`, `stop`, `list`, `query`, `tree`, `todo`, `attach`, `host`, `create`, `hosts`, `inspect` or `page`); `addHost` of `@vzlentin/harness/hosts` refuses these names too, with `A host cannot have the name <name>`, and `COMMAND_NAMES` gives the command names. A name that exists, and a directory that does not exist, are errors.
- `hosts` prints `<name>  <dir>` for each host, in creation order, then `main`.
- `--version` prints the version of the package. It takes no argument and no `--host`.

The hosts are in `$XDG_CONFIG_HOME/harness/hosts.json` (default `~/.config/harness/hosts.json`), an object of name to directory. `create` saves the real path of the directory; a hand-written file can have another absolute path. A command that reads the file fails when a name does not follow the rule of `create` or a directory is not an absolute path.

The state of a host stays in `$XDG_STATE_HOME/harness/<host>/` (see [Host](#host)).

A command goes to the host of `--host <name>`, which must come before the command (`harness --host carrefour list`), then of `HARNESS_HOST`, then of the current directory: the host with the longest directory that is the current directory or contains it. Only the first argument can be `--host`: after the command, `--host` is an argument of the command, such as the `--host <ip>` of `inspect` and `page`. The old flag `--project` as the first argument is an error, `harness takes --host <name>, not --project`; after the command, `--project` is a plain argument. Harness ignores `HARNESS_PROJECT`. The comparison uses the real paths of the current directory and of each host directory, so a path through a symbolic link finds the same host as its real path; a path that does not exist is compared as written. Without a match, the host is `main`, which has no directory. When two hosts have the same real directory, the first one created wins. An unknown host name is an error: `Unknown harness host: <name>`. The tool finds its host in the same way, from `HARNESS_HOST` and the current directory of their process. `connect` and `request` of `@vzlentin/harness/client` take a `host` option; without it, the host comes from `HARNESS_HOST` and the current directory. They fail with `HostUnreachableError` when no host answers: no host could start, the connection closed before the reply, the host was closing, or the host has another protocol version. An abort keeps its own reason, and another error that the host replies is a plain `Error`. The CLI passes `--host` in this option and does not set `HARNESS_HOST`, so the Pi of `harness attach` and a host that the CLI starts do not get it.

The caller is `PI_SESSION_ID`, or `cli` when it is not set. `list` shows only the caller's children. The CLI and the tool refuse to `send` to, `rename`, or `stop` a child of another caller; only the caller `cli` can `stop` the child of any caller. A mirror session does not check the caller, because the host socket is for one user: it can show, send to, and abort the child of any caller. It sends text with an `input` request, stops a turn with an `abort` request, and changes the model or the thinking level with a `configure` request. None of these requests has a caller.

`openChildTab` of `@vzlentin/harness/herdr` opens a child in Pi in a new herdr-app tab, in the space of the hc terminal of the caller. It reads the labels of that terminal with `hc get --json <HC_TERMINAL_ID>`, then runs `hc run --bg --keep --no-parent --cwd <cwd> [--name <name>] --label herdr.space=<space> -- <command>`, in the child's working directory. herdr-app shows a terminal with a `herdr.space` label in that space, in a new tab, and does not move the focus. The command is `[env XDG_STATE_HOME=<state> XDG_CONFIG_HOME=<config>] <node> <cli> --host <host> attach <handle>`, where `<cli>` is `dist/cli.js` of the install, or `src/cli.ts` of a checkout: `harness attach` with this Node and this install's CLI, so it does not need `harness` on `PATH`, on the host of the caller. hc gives the program the environment of the hc server, so `env` gives it each of `XDG_STATE_HOME` and `XDG_CONFIG_HOME` that is set for the caller; without both, there is no `env`. The name is `<name>` of the child (or its handle) in lowercase, with `-` in place of each character other than `a-z`, `0-9`, `-` and `_`, without the characters before the first letter or digit, and cut to 32 characters. When nothing is left, or when the name has the shape of an hc terminal ID (`t`, a digit from 1 to 9, then digits and the letters of `bcdfghjkmnpqrstvwxyz`, such as `t7`), there is no `--name`. Before `hc run`, it rejects with `Not in an hc terminal: HC_TERMINAL_ID is not set`, with `hc get gave no labels: <output>`, or with `The hc terminal <id> has no herdr.space label` when the label is missing or empty. When an `hc` call fails, it rejects with the stderr of `hc`, or with the reason that the call failed; when a live terminal has the name, that is the `name_taken` error of hc.

`openConversationPane` of `@vzlentin/harness/herdr` opens a children library conversation in Pi in herdr-app, in the conversation's working directory. It takes the conversation as a `ChildInfo`, a place, and the environment. For a conversation, `ChildInfo` gives the same ID in `handle` and in `conversation`. It runs `hc run` as `openChildTab` does, with the name from `<key>` and the command `[env ...] <node> <cli> --host <host> attach --conversation <id>`, on the host of the caller. With `{ space }`, the terminal gets `--label herdr.space=<space>`, and it does not read the labels of the caller: herdr-app opens a new tab in that space. With `{}`, the terminal gets the `herdr.space` label of the caller: a new tab in the space of the caller. With `{ side: true }`, the terminal gets the `herdr.space` and the `herdr.tab` labels of the caller: herdr-app splits the last pane of the tab of the caller to the right. Without `space`, it rejects before `hc run` as `openChildTab` does, also with `The hc terminal <id> has no herdr.tab label` for `{ side: true }`. When an `hc` call fails, it rejects with the stderr of `hc`, or with the reason that the call failed.

### Todos

Each agent and each run keeps a list of todos (see the `todo` request in [Host](#host)). A todo can have an optional `ask`, the ID of the ask that the todo `Save to the vault` belongs to (see [Asks and parleys](#asks-and-parleys)). Only the host sets it, and the line of a todo does not show it:

```sh
harness todo add Move the config to vite.config.ts
harness todo set 1 doing
harness todo
harness todo list --handle a1b2c3
harness todo sort
```

- `harness todo [list | add <text> | set <id> <state> [--text <text>] | sort]` sends one `todo` request, or for `sort` one `classify-todos` request. Without a word, the action is `list`. The options can come before or after the words.
- `add` adds a todo with the words after it, joined with a space, as `send` does with its message. `set` sets the state of the todo `<id>` to `open`, `doing`, `done` or `dropped`, and its text to the `--text` value when it is given.
- Without a target option, the list is the list of the caller, `PI_SESSION_ID` or `cli` (see [Hosts](#hosts)). One target option gives another list: `--handle <handle>` the list of a child, or of the host agent with `agent`; `--conversation <id>` the list of a conversation that the children library opened; `--task <key>` the list of the task of a `start`. The host agent keeps a list of its own, as any agent: `--handle agent` gives it.
- `add` and `set` print the line of the todo. `list` prints the line of each todo, in ID order, or `No todos` for an empty list. A line is `<mark> <id> <text>`, with the mark of the state: `○` open, `◉` doing, `✓` done, `✗` dropped. A text with a line break prints as it is.
- The command refuses a state that is not one of the four with `Invalid todo state: <state>`, an ID that is not an integer from 1 with `Invalid todo id: <id>`, an unknown option, such as `--hosts-list`, with `Unknown todo argument: <option>`, and an empty `add` text with `add requires text`, before it sends the request. The other errors come from the host, such as `The text of a todo is empty` and `Unknown todo: <id>` (see [Host](#host)). An unknown word, more words than the action takes, `add` or `set` without its words, `--text` without `set`, two `--text` options and two target options print the usage.
- The command runs as a call of `runTodoTool(args, scope, target)` of `@vzlentin/harness/tool`, the runner of the todo tool. `args` are the parameters of the tool, `{ action, text?, id?, state? }`. `target` is the list, as the `todo` request takes it (`ListTarget` of `@vzlentin/harness/protocol`): `{ handle }`, `{ conversation }`, `{ key }`, or `{}` for the list of the caller. The command gives the target of its target option. The `todo` tool gives `{}`, the list of its caller. The runner refuses an `add` without `text`, or a `set` without `id` or `state`, with `<action> requires <argument>`. Its result is the text that the command prints, and `{ action, value }`, where `value` is the reply of the host: the todo for `add` and `set`, and `{ todos }` for `list`. The `todo` tool of the host runs `runAgentTodoTool(args, scope)` of `@vzlentin/harness/tool`, which runs this runner on `{}` and, for `add` and `set`, takes its text from a `list` call (see [Tool](#tool)).
- `sort` asks the classifier of the todos (see `classify-todos` in [Host](#host)). Without a target option, it asks about the list that an entry gives, such as the open work items of the projects entry, with their titles as their texts, and without such an entry it fails with `classify-todos needs a list: no loaded entry gives one`; a target option gives a list, as for the other actions, and it asks about the open todos of that list. It prints one line for each answer, in ID order, as `<id>  needs you: yes|no  repeats: <id>|none`, or `No open items` without a target option and `No open todos` with one when there is none. The errors come from the host, such as `No classifier: log in to <provider> or set todoClassifier`.

### Tree

`harness tree [--json]` sends one `tree` request (see [Host](#host)), and starts the host when none runs:

```sh
harness tree
harness tree --json
```

- It prints one line for each node, parents first: two spaces for each level, then `<mark> <name>  <state>  <n> open`, where `<n>` counts the todos of the node in the state `open`. The mark is `◉` for `busy` and `running`, `○` for `idle` and `pending`, `✓` for `ended` and `completed`, and `✗` for `error`, `failed` and `aborted`.
- `--json` prints the reply, `{ nodes }`, as one JSON line. Another argument prints the usage.
- A started task that did not end has its child tasks and their conversations under it. A started task that ended has only its own node, and only while it is one of the 50 newest started tasks.

## Open in Pi

`harness attach <handle>` opens a child in Pi in the current terminal, `harness attach --conversation <id>` opens a conversation that the children library opened, such as a child of a task, and `harness <host>` opens the agent of the host. They start the host when none runs, and check the target before Pi starts: an unknown handle is an error, `Unknown subagent: <handle>`, an unknown conversation or a root is an error, `Unknown conversation: <id>`, and so is a host agent without a model. Then they run `pi --harness <host>` for the host agent, `pi --harness <host> --harness-child <handle>` for a child, or `pi --harness <host> --harness-conversation <id>` for a conversation, which opens a mirror session (see [Mirror sessions](#mirror-sessions)), and exit with the exit code of Pi. They run the `pi` of `PATH` without the `node_modules/.bin` folders; without one, the error is `pi is not on PATH. Install Pi to open the agent`. That Pi needs the extension of the package (see [Pi extension](#pi-extension)). Closing Pi never changes the child.

`harness attach (<handle> | --conversation <id>) --side` in an hc terminal (`HC_TERMINAL_ID` is set) does not start Pi in this terminal. It checks the target as above, then runs `hc run --bg --keep --no-parent` with the `herdr.space` and `herdr.tab` labels of the caller's hc terminal, so herdr-app shows the target in a new pane to the right in the caller's tab. That terminal runs `harness --host <host> attach <target>`, without `--side`, in the cwd of the target. The command exits with 0 when `hc run` succeeds. When the caller's terminal has no `herdr.space` or `herdr.tab` label, it fails with `The hc terminal <id> has no <label> label` and starts no terminal. When an `hc` call fails, it fails with the stderr of `hc`. Both exit with 1. Outside an hc terminal, `--side` runs Pi in this terminal, as without it.

In every terminal, the mirror session reports the state of the agent to the terminal with the Program Status Protocol (OSC 7501), through Pi's `setProgramStatus`, with `app: "harness"`. It reports when it starts and at each change of the state or of the message. While the session connects again to the host, the state is `blocked`, with the message `<title> (connecting again)`. On an open connection, a busy agent is `working`, an agent whose last request failed is `error`, and an idle agent after a turn is `done`, with the title as the message, until its next turn. An aborted turn also ends in `done`. `done` stays while the session connects again: an idle agent on the connection that opens again is `done`. An error, an ended agent and a connection that failed end `done`. All other cases are `idle`: an idle agent before its first turn in the session, an ended agent, the connection before the first one opens, and a connection that failed. The message is the title of the agent (the name or the handle of a child, `<key>` for a conversation, `<host> agent` for the host agent). Before the first connection, a child has its handle and a conversation its ID. A rename changes the title. For `error`, the message is the first line of the `errorMessage` of the last assistant message with `stopReason: "error"`, trimmed, or `Error` when there is none. When a dialog of Pi ends (`ui_prompt_end`), Pi writes its own state, so the session reports its state one more time, also when it did not change. When Pi leaves the mirror session, it reports `idle` with the title one more time.

## Inspect

`harness inspect` serves a web page that shows a conversation of a host live, as a mirror session does in Pi (see [Mirror sessions](#mirror-sessions)), and sends what you type to it:

```sh
harness inspect a1b2c3
harness inspect --conversation 42
harness --host web inspect --tailscale
```

- `harness inspect [<handle> | --conversation <id>] [--port <n>] [--host <ip> | --tailscale]` listens on the port of `--port`, else of `HARNESS_INSPECT_PORT`, else 7501, or on a free port with `0`. An invalid `HARNESS_INSPECT_PORT` is an error, `Invalid HARNESS_INSPECT_PORT: <value>`; `--port` wins over it. It prints one URL for each address that it listens on, `http://<address>:<port>/`, with the target in the query: `?host=<host>&handle=<handle>` for a child, `?host=<host>&conversation=<id>` for a conversation, and `?host=<host>` for the handle `agent` and for `--host <name>` before the command without a target. The host is the host of the command (see [Hosts](#hosts)). Without a target and without `--host <name>` before the command, the URL has no query, and the page shows the picker. The command runs until SIGINT or SIGTERM, then closes its connections.
- It listens on `127.0.0.1` only. `--host <ip>` listens on that address only, so it listens on `0.0.0.0` only with `--host 0.0.0.0`. `--host` takes an IP address or `localhost`, because the routes refuse another name in the `Host` header (see below); another host is an error: `The host must be an IP address or localhost: <host>`. `--tailscale` listens on `127.0.0.1` and on each IPv4 address that `tailscale ip -4` gives, on the same port. Both `--host` and `--tailscale` is an error: `Use --host or --tailscale, not both`. When `tailscale ip -4` fails, the error is `tailscale ip -4 failed: <stderr>`, and without an IPv4 address in its output, `tailscale ip -4 gave no IPv4 address`. `--port` takes an integer from 0 to 65535; another value is an error, `--port must be an integer from 0 to 65535`. An unknown option is an error, `Unknown inspect argument: <option>`, and two targets print the usage.
- With `host` in its query, the page shows the target: the host agent, the child of `handle`, or the conversation of `conversation`. Without `host`, it shows the picker: each host, then `main`, with its directory, and the host agent and the children of each running host, each with a link that has its title, as in a mirror session, then its state and its model as in the header. A host that does not run has only a link to its agent, `agent`, and opening it starts the host. A running host without a target to show has the line `the host runs, with no target to show`.
- The header has the title of the agent, as in a mirror session, its model and thinking level, as `<provider>/<model> • <thinking>`, its state (`busy`, `idle`, `error` or `ended`), and the connection (`connecting`, `open`, `reconnecting`, or `failed: <reason>`). The title of the page is `<title> · harness inspect`.
- The transcript has the user messages, the typed inputs (`harness.typed`) among them, the answers with their thinking, folded, each tool call with its arguments and its result, folded, with an error result in the error colour, the output of a running tool, the passive notes, catch-ups and digests, `[compaction]` with its summary, and `[new context]`.
- The footer has what the agent does, as Pi's working indicator says it, each queued message as `Steer: <first line>` or `Follow-up: <first line>`, and the usage: `↑` input, `↓` output, `R` cache read, `W` cache write and `$` cost, each when it is not zero, then `ctx <tokens>`, the context of the last answer of the active transcript. The page knows no context window, so it shows no percent. Below is a message box. While the agent is idle, `Send` starts a new turn. While it works, `Steer` and `Follow-up` queue the message, and `Stop` aborts the turn. Enter sends, Shift+Enter adds a line, Alt+Enter queues a follow-up while the agent works, and Esc stops the turn while the agent works. On the page of `harness inspect`, Esc works wherever the focus is. On a page that mounts only the view, Esc works while the focus is in the view, such as after a click in the transcript. A conversation of the children library takes a message only while it works, always as a steer: it has no `Follow-up`, and the box is off while it is idle. A message that the server refuses stays in the box, with `not sent: <error>`.
- The page puts all text in as text, never as HTML, so the output of an agent cannot run in it.

`@vzlentin/harness/inspect` gives the routes, so that another server, such as `workflows web`, can serve them on its own port. A server that mounts the handler also serves the pages of `harness page` (see [Pages](#pages)). `createInspectHandler({ start? })` gives a handler `(req, res) => Promise<boolean>`, which is false for a request that is not one of these routes. `startInspectServer({ hosts?, port?, start? })` serves the page at `/` and the routes, with one server for each address of `hosts` (default `127.0.0.1`), all on one port (default 7501, or the free port of the first address for 0), and gives `{ urls, close() }`. It refuses a host that is not an IP address or `localhost` before it listens, with `The host must be an IP address or localhost: <host>`. `close()` also closes the open connections. `resolveBindHosts({ host?, tailscale? })` gives the addresses of the CLI options, and refuses such a `host` with the same error. The routes are:

- `GET /assets/inspect.js` and `GET /assets/inspect.css`: the browser files, from the `web/` folder of the package, with no other dependency. `inspect.js` exports `mountInspect(container, { host, handle?, conversation? }, { onTitle? })`, which shows the target in `container` and gives `{ interrupt(), close() }`, and `mountPage(container)`, the page of `/`, which gives `{ close() }`. `onTitle(title)` runs each time that the title of the agent changes. `interrupt()` stops the turn while the agent works and gives true; otherwise it does nothing and gives false. The view listens to its keys on its own root, and a click in the transcript gives the focus to the view. `mountPage` also listens to Esc on the document, and gives to `interrupt()` each Esc that the view did not take. Each rule of `inspect.css` selects only elements with a class that starts with `inspect`, or elements below `.inspect` (the view), `.inspect-picker` (the picker) or `.inspect-page` (the page of `/`), so the view does not change the page that mounts it.
- `GET /api/inspect/hosts`: `{ hosts: [{ name, dir }, ..., { name: "main" }] }`, in creation order.
- `GET /api/inspect/targets?host=<name>`: `{ host, running, targets }`. `running` tells whether the host runs. `targets` has the info of the host agent, then the children of the caller of the server process, in that host, each with `title`, its title as in a mirror session. The caller is `PI_SESSION_ID`, or `cli`, as for `harness list`. When that host does not run, `running` is false, `targets` is empty, and the route does not start the host. The agent is not in `targets` when its watch fails, such as without a model.
- `GET /api/inspect/stream?host=<name>[&handle=<handle> | &conversation=<id>]`: Server-Sent Events (`text/event-stream`) from a mirror of the target. Each event is one `data:` line with a frame `{ status, title, child, view, summary }`: the status of the mirror, the title of the agent (its handle or conversation ID before the first connection), its info, its whole conversation view, and `{ statusText, queued, usageTotals, lastAnswerUsage }`. `child`, `view` and `summary` are not there before the first connection, and `lastAnswerUsage` is not there before an answer. One frame comes at once, then one after each change. When the client reads more slowly than the frames come, only the newest frame waits. When the mirror fails, such as for an unknown child, the last frame has `status: { kind: "failed", reason }`, the stream ends, and the page does not connect again. When the client closes the connection, the mirror closes.
- `POST /api/inspect/input` with `{ host, handle?, conversation?, message, followUp? }` sends an `input` request with a new request ID, and `POST /api/inspect/abort` with `{ host, handle?, conversation? }` sends an `abort` request. Each replies `{ ok: true }`.
- `GET /api/inspect/asks?host=<name>&parley=<slug>` sends `parley read { slug }` to the entry that serves the request type `parley`, such as the projects entry, and replies with its reply, `{ parley, asks }`, with the asks in every state. Without such an entry, the route gets 400 with `no loaded entry serves request type "parley"`.
- `POST /api/inspect/answers` with `{ host, parley, answers: [{ n, answer, label?, words? }] }` writes the answers of the user to the asks of the parley `parley`. Each answer names its ask by `n`, its number in the parley; an answer with `slug` or `id` gets 400. The route checks the answers as `ask answer` does, then sends one `ask answer { caller: "page", answers, user: true }`, with `slug` set to `parley` in each answer, and replies with the write. An answer by `slug` needs an entry that serves the parley asks: without one, the route gets 400 with `no loaded entry serves parley asks`. The caller `page` is never an asker, so each asker gets its delivery. The answers count as the answers of the user, with the limit of the mark (see [Asks and parleys](#asks-and-parleys)).
- `GET /pages/<slug>/<file>`: the files of a page of `harness page`, with the script of the Send in an HTML file whose query has a target (see [Pages](#pages)).
- Without `handle` and `conversation`, the target is the host agent, as with the handle `agent`. A stream, an input, an abort, and a read or a write of asks start the host when it does not run. With `start: false`, they do not: all but the stream then fail with `The harness host <host> is not running`.
- A request that is not valid gets 400 with `{ error }`: a query or a body that does not match, such as `Invalid query: must have required properties host`, `Give handle or conversation, not both`, `The message is empty`, `Unknown harness host: <name>`, a POST that is not `application/json` (`The body must be application/json`), and a body that is not JSON (`The body is not JSON`) or is longer than 1 MiB (`The body is longer than 1 MiB`). An error of the host gets 500 with `{ error }`, such as `<key> takes input only while it works`. On the routes of the asks and the answers, a refusal of the host gets 400 with `{ error }`, such as `Unknown parley: <slug>`, `Ask <id> is dropped: it takes no answer` or `Ask <id> takes a, b or own`, and the write changes nothing; a host that does not run or does not answer gets 500. Another path under `/api/inspect/` gets 404.
- Each route under `/api/inspect/` and `/pages/` gets 403 when the `Host` header is not an IP address or `localhost`, so that the DNS name of another site that points at the server (DNS rebinding) cannot reach the routes. This refuses a Tailscale MagicDNS name too: use the address. The routes have no login: each client that reaches the address can read and steer the agents of the user. `127.0.0.1` keeps them on this machine, and `--tailscale` on the tailnet.

### Pages

`harness page` copies an HTML page, such as the classic page of a parley, to the pages of the inspect routes, and prints its link. The Send of the page posts its answer line to an agent, which takes it as a message:

```sh
harness page /tmp/parley-demo --slug demo
harness page /tmp/parley-demo --slug demo a1b2c3 --tailscale
```

- `harness page <folder> --slug <slug> [<handle> | --conversation <id>] [--port <n>] [--host <ip> | --tailscale]` copies the page to `$XDG_STATE_HOME/harness/pages/<slug>/` (default `~/.local/state/harness/pages/<slug>/`). The slug is lowercase words of letters and digits, joined with hyphens, as the parley skill gives it. The copy has the regular files at the top level of `<folder>` whose names do not start with `.`. It skips folders and symbolic links. It replaces the earlier copy of the slug. A copy that fails, such as for a file that it cannot read, keeps the earlier copy of the slug.
- The Send posts to the target of the arguments. Without a target, the command sends a `whoami` request with the caller `PI_SESSION_ID` to the host (see `host.sock` in [Host](#host)): a child gets its own handle. The host agent, and a caller that the host does not run, such as a Pi session, get the host agent. The host comes from `--host <name>` before the command, `HARNESS_HOST` or the working directory. The command does not start the host.
- It prints one link for each address, as `harness inspect` does: `http://<address>:<port>/pages/<slug>/` with the query of the target, `?host=<host>&handle=<handle>`, `?host=<host>&conversation=<id>`, or `?host=<host>` for the host agent. The addresses come from `--host` and `--tailscale` as for `harness inspect`, and the port without `--port` is `HARNESS_INSPECT_PORT`, else 7501, as for `harness inspect`. It tries a TCP connection to each address for 1 s. When no address listens, it starts `harness inspect --port <port>`, with `--host <ip>` or `--tailscale` as the command got them, detached, with the state folder `$XDG_STATE_HOME/harness` as its working directory and its output appended to `$XDG_STATE_HOME/harness/inspect.log`. It tries each address every 100 ms, for up to 10 s, until each one listens, and then prints the links and one line on stderr, `harness inspect runs as pid <pid>; log <log>`. The server runs until a signal stops it. When the server exits or does not listen in time, the command fails with `harness inspect did not start: <exit>; see <log>`, where the exit is `code <n>`, `signal <name>`, `error <message>` or `no server listens after 10 s`. When only some addresses listen, the command starts no server, and the line of each address where nothing listens ends with `  (no server listens: harness inspect serves the pages)`. Each server that mounts the inspect routes serves the pages, such as `harness inspect` on the same port.
- These errors stop the command with code 1 before the copy, so the earlier copy stays: the usage for a missing folder or `--slug`, two targets or an extra word; `Unknown page argument: <option>`; `The slug must be lowercase words with hyphens: <slug>`; `No index.html in <folder>` when `<folder>/index.html` is not a regular file; `Give <handle> or --conversation <id>: PI_SESSION_ID is not set`; `The harness host <host> is not running`; and, as for `harness inspect`, the errors of `--port` and of `HARNESS_INSPECT_PORT`, of a `--host` that is not an IP address or `localhost` (`The host must be an IP address or localhost: <host>`), of both `--host` and `--tailscale`, and of `tailscale ip -4`.
- `GET /pages/<slug>/<file>` serves the file of the copy, and `GET /pages/<slug>/` serves `index.html`. The content type comes from the extension: `.html` `text/html; charset=utf-8`, `.svg` `image/svg+xml`, `.css` `text/css; charset=utf-8`, `.js` `text/javascript; charset=utf-8`, `.png` `image/png`, `.json` `application/json; charset=utf-8`, and `application/octet-stream` for another file. Each reply has `cache-control: no-cache`.
- An HTML file whose query has `host`, `handle` or `conversation` gets one script before its first `</head>`, in any case. A file without `</head>` goes as it is. The query takes the target as the stream route does, so `?host=<host>` alone is the host agent. The script defines `window.sendPrompt(text)`, which the Send button of an artifacts page calls. It posts `{ host, handle, message }` or `{ host, conversation, message }` to `POST /api/inspect/input`, so an idle child or host agent starts a turn with the message. At its first call, it adds one line to the body of the page, at the top centre, in a 16px font. A call with the same text as the last post that succeeded posts nothing and sets the line to `already sent ✓`. Another call adds a layer that covers the page, dims it by 8% and blocks clicks, sets the line to `sending…` and posts. A call while a post runs does nothing. When both the post and a 400 ms delay end, the layer goes and the line shows `sent ✓`, or `not sent: <reason>`, where the reason is the `error` of the reply, its HTTP status, or the error of the request. A failed post does not change the last text that succeeded. The script also defines two calls for the parley whose slug is the slug of the page, so a page answers only its own parley. `window.readAsks()` gets `GET /api/inspect/asks` with the host of the query, and resolves to `{ parley, asks }`, or rejects with the `error` of the reply, its HTTP status, or the error of the request. `window.sendAnswers(answers)` posts `{ host, parley, answers }` to `POST /api/inspect/answers`, where each answer is `{ n, answer, label?, words? }`, so the asks are answered at Send, with no answer line. It shares the line and the layer of `sendPrompt`, and the same rules: a call while a post runs does nothing and resolves to undefined, and a call with the same answers, as JSON text, as the last post that succeeded posts nothing, sets the line to `already sent ✓`, and resolves to the write of that post. It resolves to the write of the host when the post succeeds, and to undefined when it fails. The script itself is ASCII. The target and the slug go into the script as JSON with each `<` escaped, so they cannot end the script. Another file, and an HTML file with no target in its query, go as their bytes.
- The route gives 404 with `{ error: "Not found: <method> <path>" }` for a method that is not GET, a path that is not `/pages/<slug>/<file>`, a slug that is not valid, a file name that does not percent-decode, a decoded file name with `/` or `..` or a leading `.`, and a file that does not exist or that is a folder. An HTML file with a query that is not valid gets 400 with `{ error }`, as the stream route does, such as `Unknown harness host: <name>` or `Give handle or conversation, not both`.

## Host

The children of a host run in one process, `harness --host <name> host` (default `main`). The host takes its name only from `--host`, not from `HARNESS_HOST`. The first command that needs it starts it in the background, and tries to connect for 10 s. A started host that exits with code 0 found the lock held by another host, such as one that closes after its idle time: the command then starts a host again, at most once per second. A started host that exits in another way fails the command at once with `The harness host exited with <code N or signal S>; see <host.log>`. When the started host still runs after 10 s, the command fails with `The harness host (pid <pid>) is still starting: it can wait up to 60 s for the lock of durable.sqlite. Run the command again soon; see <host.log>`; otherwise with `Could not start the harness host; see <host.log>`. It exits after 5 minutes with no connection, no running work, no busy entry, such as the projects entry while it compresses the memory, and no command other than `list`, `status`, `answers`, `tree`, `watch-tree`, `classify-todos`, a `todo` or `ask` request with the action `list` or `read`, and a request of an entry type whose `passive` rule is true for it. A connection with an open `answers` request does not count. An open mirror session and an open `watch-tree` are connections, and a live started task is running work, so each keeps the host running. A task that no loaded entry can run, such as one of an entry that was removed, is not running work, and neither is a task that waits only on such tasks. The host waits up to 60 s for the lock of `durable.sqlite`, so a client that reads the file, such as the workflows CLI, does not make it fail. The wait is synchronous: while it lasts, the host answers no request. When the host closes, it stops listening, stops each running request, such as a `wait` or an `answers` request, which then fails with `The host is closing`, and waits until the replies of all requests are written. A request that comes while the host closes fails with `The host is closing` and does not run. The host then closes the connections.

On macOS, the host holds the Mac awake while it has active work: while `wake().active` of pi-durable is true, which means a task can run now or runs. Parked work, such as a sleep that is not due or a task that waits for a child, does not count. The hold is `caffeinate -s -w <host pid>`, so it works only on AC power, and it ends with the host. The host reads `wake().active` every 5 s, and does not wait for a commit: active work can start or end without a commit, such as a sleep that falls due or the wake recompute after a failed migration, and `wake()` is synchronous and reads from memory. The host releases the hold 30 s after the last read with active work, so the release comes 30 to 35 s after the work ends. Work that comes back within the 30 s keeps the same hold. The close of the host releases the hold. When `caffeinate` cannot start, the host writes one warning, `caffeinate cannot start: <message>`, to `host.log`, and tries no more. Other systems get no hold.

The host keeps its degraded states in memory, and gives them to its entries with the `degraded` handle (see the entries below), so an entry can show them to a client. A state is `{ kind, line, since }`: its kind, a line for the user, and the time of its start in epoch milliseconds. The host keeps one state for each kind and cause. A state starts when its cause starts and ends when its cause ends. A cause that continues keeps its `since` and takes the new line. A source that writes a warning to `host.log` writes it for its state too, and the `gate-classifier` and `no-classifier` states write none. `DEGRADED_KINDS`, `DegradedKind` and `DegradedState` of `@vzlentin/harness/protocol` give the kinds and the schema. An entry, such as the projects entry, starts the states of the kinds `gate-classifier`, `approve-tell` and `digest-failed` through its `degraded` handle, and the host starts the others. The kinds, their causes, their lines and their ends:

- `gate-classifier`: the classifier of the gate of an entry failed after the entry found its model. The line is the reason of the held call, such as `The classifier <provider>/<id> failed: <message>`. It ends at the next gate call whose classifier answers. It has no warning.
- `no-classifier`: one for each setting, such as `todoClassifier` or the `gateClassifier` of an entry, when the setting has no classifier model with a credential. The line is `No classifier: log in to <provider> or set <setting>`. It ends when a `classify-todos` request, or a call of the entry, finds the model. It has no warning.
- `package-skipped`: one for each `package.json` that the host skipped at its start, with the line of its warning. It ends with the host.
- `entry-skipped`: one for each entry of `entries.json` with no module, with the line `The entry <name> has no module at <path>; the host skips it`. It ends with the host.
- `push-failed`: one for each delivery whose last push failed and waits, the answers of a child (its handle) or an answer of the user (`user-answer:<id>`). The line is `The push of <key> failed: <message>`, and the warning is the message. It ends when a push of the delivery works, or when the record of the child or the answer goes.
- `approve-tell`: one for each approved action of an entry whose tell to its agent failed. The line is `The tell of approved action <id> failed: <message>`, and the warning is the message. It ends when the approved command runs through the gate of the entry.
- `answer-waits`: one for each asker with answers of the user and nowhere to push them: it is not a conversation of the host and has no open `answers` request. The line is `The answers of the user wait for <asker>, which has no answers request open`. It ends when the asker gets a place for its answers, or when no answer waits for it. It has no warning.
- `awake-failed`: `caffeinate` cannot start, with the line of its warning. It stays, because the host tries no more.
- `catch-up-failed`: a catch-up of the host agent failed (the line `catch-up: <message>`), a catch-up hook threw (one for each hook kind, `catch-up: <kind>: <message>`), an input hook of an entry threw (one for each hook kind, the cause `input:<kind>` and the line `input: <kind>: <message>`), or Git failed (`catch-up: git: <message>`). Each ends at the next catch-up, call of the hook or read of Git that works.
- `digest-failed`: one for each conversation whose digest of an entry failed, with the line `digest: <message>`. It ends at the next digest of the conversation that works or has nothing to write.
- `resources-failed`: one for each directory whose project instructions and skills failed to load, with the line `<cwd>: <message>; no project instructions or skills`. It ends at the next load of the directory that works.

A pi-durable report and a failed pass of a watch are events, not states: a report is a warning in `host.log`, and a failed pass ends its connection with no warning. A `bash` call that the default limit stops is not a state: the model sees it in the result of the tool. Only a client sees the states where the host does not answer: no host, a host of another protocol, a store that the host cannot read, and an entry that stops the start of the host.

The host keeps its state in `$XDG_STATE_HOME/harness/<host>/` (default `~/.local/state/harness/<host>/`):

- `durable.sqlite`: the children's conversations and records, the started tasks, the lists of todos, the asks, and the host agent, which is the store's root conversation. A host opens a store with the `harness.terms` and `harness.parts` documents of an older version, and does not read them. Work that a host stop interrupts continues when the host starts again. A host refuses a `durable.sqlite` from a version before the children library: stop the old host, remove the file and run the command again. A host opens a `durable.sqlite` from an older version with the children library, and keeps its children and their records. A child that an older host marked `rlm` loads as any child. A child of a store from before `serves` has no label. The records of the children have version 7, with the labels of each child. A host reads records of version 5 or 6, with or without the projects entry, as records of version 7 with the labels of what each child served that the record names: an open parley or a contract gives `parley:<slug>`, and a spawner, a todo or an item gives no label. A record that does not have the fields of its version stops the open with `subagent.children of version <version> is invalid: <path> <message>`. The record keeps no `serves` and no end of what it served. The document `harness.task-labels` keeps the labels of each started task by `start` key. The document `harness.worker-refs` keeps the result references of each worker that a `report` named: `agents` by handle and `tasks` by `start` key.
- `lock.sqlite`: one host at a time.
- `host.sock`: the socket the CLI and the extension connect to. The protocol has version 44. A `spawn` request has `provider` and `model` only when the spawn itself gives them, and the caller's own model in `callerProvider` and `callerModel`, next to its level in `callerThinking`; the host picks the model and the level (see [Tool](#tool)). A `whoami` request `{ caller }` replies `{ handle? }`: `agent` when the caller is the conversation ID of the host agent, and the handle of the child whose conversation ID it is. Another caller, such as a Pi session, `cli` or a conversation of a task, gets `{}`, with no handle. `harness page` sends it (see [Pages](#pages)). The `spawn` and `send` requests have `notify`, a boolean: false turns off the push of the answers of that request (see [Push](#push)). A `spawn` request can have `labels`, a list of labels, and `serves`, the work of the child: `{ parley: <slug> }` or `{ item: <id> }`, each with no other key, so a slug of digits only is never an item ID. A `serves` of another shape fails with `Invalid spawn request: serves: <rule>`. A label is a text that is not empty, and its kind is the text before its first `:`. `serves` gives the label `parley:<slug>` or `item:<id>`. The labels of the child are `labels`, then the label of `serves`, each once, fixed at the spawn in the record of the child. Before the commit that creates the child, the host checks each label with the check of its kind, and refuses the spawn with the reason of the first label that it refuses: each entry checks the kinds that it gives, such as the projects entry the kinds `parley` and `item` (see the entries below). A kind with no check fails with `no loaded entry checks the label kind "<kind>"`, so `serves` needs an entry that checks `parley` or `item`. A spawn that comes again with the same request ID checks nothing. The info of a child has `labels` when it has one, and `refs`, the references that `report` stored for it, when it has one. The host agent and a conversation of the children library with no record of a child have none (see [Agent life](#agent-life)). An `answers` request `{ caller }` waits until the host pushes answers to `caller` (see [Push](#push)), and replies with them: `{ source: "child", handle, name?, text, failed }` for the answers of a child, `{ source: "ask", ask, text }` for the answer of the user to an ask of the caller with no parley, `{ source: "parley", parley, asks, text }` for the answers of the user to asks of the caller in a parley, which the entry that serves the parley asks groups, and `{ source: "entry", key, text }` for a delivery of an entry (see the entries below). A newer `answers` request of the same caller replaces the older one, which then fails with `A newer answers request of the same caller replaced this one`. It needs a connection of its own, because the replies of a connection come in request order. The `watch` reply is `{ view, child }`. Each event of a watch is `{ change, child }` after a commit to the conversation, or `{ change: {}, child }` after a rename, an end or a resume of the conversation. A change gives the parts of the view that the commit changed, as whole values, so a client needs no chord: `entries` is `{ from, items }`, the entries from index `from` on; `docs` has each document that changed, by kind, and `null` for a document that was removed; `conversation` is the conversation record. After a watch that fell behind, the change is `{ view }`, the whole view. When the conversation has a list of todos (see the `todo` request below), the `docs` of the reply and of each `{ view }` have it, under `harness.todos`. Each change of the list, the first `add` included, gives one event `{ change: { docs: { "harness.todos": <list> } }, child }`, with the whole list. A watch that fell behind gives only the newest list. A `configure` request `{ handle, provider?, model?, thinking? }` replies with the child, and refuses an unknown model and a thinking level that the model does not have. It takes no `conversation`. After a `watch` reply, each event of the watch is a `{ "event": ... }` line, and every other line is a reply, in request order. The host checks each request line against the schema of its type, or against the schema of the entry that serves its type (see the entries below). Extra keys are allowed. A line of a type that neither the host nor a loaded entry serves fails with `no loaded entry serves request type "<type>"`, and a line without a string `type` with `Invalid request`. A line that does not match the schema of its type fails with `Invalid <type> request: <path>: <rule>`. `<path>` is the path of the first wrong field, with no leading slash, such as `asks/0/options/1/label`. `<rule>` is `required` for a missing field, `not allowed` for a key that the type refuses, and else the description of the schema of the field, such as `plain text, no backticks or **` for a plain text (`PLAIN_RULE` of `@vzlentin/harness/protocol`), or the message of TypeBox, such as `must be >= 1`. For example, a `spawn` needs a `cwd` that is not empty, and its `thinking` is one of pi-ai's `MODEL_THINKING_LEVELS`, as is the `thinking` of `configure`. When the type has a schema for the `action` of the line, the error comes from a schema of that action. When a line from the host is not valid, the client cannot match it to its request: it ends the connection, and rejects each waiting request with `The harness host sent an invalid reply: <line>`. A client refuses a host with another version, and the host refuses the `hello` of a client with another version, with the same message. The `hello` reply is `{ version, pid, entries }`: `entries` has the version of the protocol of each entry that gives one, by its name, such as `{ "projects": 1 }`, and is `{}` when no entry gives one. The protocol of the host has version 44. The host does not refuse a `hello` with `external: true`: it replies with its own version, and the external client checks that version itself. A `hello` with `external: false` or without `external` gets the exact check. When the host is older, stop it with `kill <pid>` and run the command again. When the client is older, reload Pi with `/reload`, or use the CLI of the host's install. The `watch`, `input`, `note`, `abort`, `configure` and `todo` requests take the handle `agent` for the host agent; its info is a child with the handle `agent` and the name `<host> agent`. Other requests refuse it as an unknown subagent. A `stop` request `{ caller }` with a handle or `{ conversation }` ends the child and the children it spawned, and replies `{ handle, name? }`, with the handle of the child. The caller `cli` can stop any child; another caller fails with `Subagent <handle> belongs to another session` for a child of another caller by handle, and with `The conversation <id> is not a child of this caller` by conversation ID. For the caller `cli`, a conversation of the children library with no record of a child, such as a conversation of a task, and the handle `agent` are not ended: the host aborts their turn, as an `abort` does, keeps the conversation and its entries, and replies `{ handle }`, with the conversation ID or `agent`. The owner of the conversation gets the failure of an aborted turn, such as a task whose turn then fails, and the host agent stays and takes the next input. Another caller fails with `Unknown subagent: agent` for the handle `agent`. A root, an unknown ID, or text that is not an ID fails with `Unknown conversation: <id>`. The host places the message of an `input` request as an entry of the kind `harness.typed`, whatever its target, and the message of a `send` as a `pi.user` entry. The model reads both as user messages. The gate of the projects entry reads only the `harness.typed` entries as the words of the user. `input` is the request of the clients of the user, such as a mirror session, the inspect page and Orda. The host cannot tell who holds the socket, so an `input` from any client counts as typed by the user: this is the limit of the mark. The `watch`, `input`, `note` and `abort` requests also take `{ conversation }` in place of `{ handle }`: the ID of a conversation that the children library opened, of any owner, such as a child of a task. A request with both keys fails with `Invalid <type> request: conversation: not allowed`. Its info has `handle` and `conversation` set to the ID, and the child's key as `name`, so its title and its label are `<key>`. An ended conversation is `ended`. It takes `input` only while it works, always as a steer, so the reply verb is `Steered`; an idle conversation refuses it with `<key> takes input only while it works`. A root, an unknown ID, or text that is not an ID gives `Unknown conversation: <id>`. The info of a conversation without a model fails with `The conversation <id> has no model`, and without a working directory with `The conversation <id> has no working directory`. A `note` request `{ requestId, text, kind?, data? }` with a handle or `{ conversation }` adds a passive user message `text` to the conversation's transcript, as an entry of the kind `kind` (default `harness.note`) with `data`. It starts no turn: an idle conversation places it at once, and the model reads it with the next input; a busy one places it at its next boundary, so the model reads it on its next request. An abort keeps a note that was placed. Its request ID is in the scope `note:`, apart from the IDs of `input`, and a repeated ID, also after a host restart, adds nothing. A kind that starts with `pi.`, and the kind `harness.typed`, which only an `input` gives, fail with `Invalid note request: kind: <rule>`. The reply is `{ child }`, with no verb. A note to an ended child is placed and leaves it ended; the next input resumes the child with the note in its history. An unknown handle fails with `Unknown subagent: <handle>`. When the children library ends the child while the note is admitted, the note stays in the transcript of the ended child, and the request succeeds. A `send` in that case fails with `The child <id> ended during the submit`, and its input is aborted. A conversation takes a note in any state, and an ended one stays ended.
- `host.log`: the host's output.

The host reads Pi's settings as a Pi session in the host directory (the home directory for `main`) reads them: the settings and packages of the `.pi/settings.json` of that directory count only when Pi trusts the project there, with the saved trust (see the project skills below). They give the host agent its default model, and the packages of the entries. The host loads two kinds of entries when it starts. First, the `piDurable` entries of the packages in Pi's settings, such as pi-ipython: a package lists its entry modules in its `package.json`, as `{ "piDurable": { "extensions": ["./durable/index.ts"] } }`. Second, the entries in `$XDG_CONFIG_HOME/harness/entries.json` (default `~/.config/harness/entries.json`), an object of entry name to the absolute path of a module, for packages that are not Pi packages, such as workflows. A package sets its entry there with `setEntry(name, module)` of `@vzlentin/harness/entries`, which is true when it changed the file. `setEntry` and `create` hold the lock file `<file>.lock`, with their process ID, while they change `entries.json` or `hosts.json`, so processes that change the file at the same time keep each other's change. A lock with no process ID, or whose process does not run, is removed; after 5 s with a lock of a live process, they fail with `Could not lock <file>: another process holds <file>.lock. Remove it if no harness command runs`. A host that runs already loads a new or changed entry only after it starts again. Missing packages are skipped, not installed. An entry of `entries.json` whose module does not exist, such as one of an uninstalled package, is skipped with the warning `The entry <name> has no module at <path>; the host skips it`. A package whose `package.json` is not a JSON object, or has a `piDurable` field that is not valid, gives a warning and is skipped. Node does not strip types under `node_modules`, so the host loads a TypeScript entry there through jiti. It calls the default export of each entry with `{ durable, ai, events, children, place, stateDir, host, cwd, settings, scope, tell, liveWorkers, asks, todos, degraded, warn, classifier, deliver, workers, stop, stopAfterTurn, labelledTasks, workersChange, labelChild, endedChild }`: the host's pi-durable and pi-ai modules, one event bus that all entries share (the host listens on it for the kernel starts and the cells of pi-ipython, see [Tools bridge](#tools-bridge)), the children library, and the host's `place` (store, models, tools and the names of the uninherited extensions) for `children.open`. The other handles are the same object for each entry: `stateDir`, the state directory of the host; `host` and `cwd`, the name and the directory of the host; `settings`, Pi's settings as the host reads them; `scope`, the scope of the tools of the hosted conversations, whose `send(request, signal)` serves a request in the host process: a typed request of a core type by the host, with no check of its schema, and a request of another type by its entry, after the check of its schema as for a line of the socket, with the value of the reply. It fails for a type that no loaded entry serves with `no loaded entry serves request type "<type>"`, and for a watch type with `A <type> watch needs a connection`. `sendToHost` of `@vzlentin/harness/tool` sends both kinds of request through the socket in the same way; `tell(caller, input)`, which sends an input to `caller` when it is a conversation of the host, after its input hooks, resumes an ended conversation, and does nothing for another caller; `liveWorkers()`, the live workers of each label, as `workers(label)` gives them; `asks`, the asks of the store for the parleys of an entry, with `read(reader, context)`, every ask as `{ asks }`, `open(reader, context)`, the open asks as `{ asks }`, `inCommit(tx)`, every ask in the commit `tx`, which the writes in `tx` change, and the writes `add(tx, asks, by, at)`, `answer(tx, answers, confirms, by, author, root, group)`, `drop(tx, id, by)`, `note(tx, id, note, by)`, `take(tx, ids, by)`, which makes `by` the asker of the open asks of `ids` and removes their answers that wait for their askers, `load(tx, asks)`, which adds the asks of a store file, and `changed(change)`, whether `change`, a change of a commit, can change an ask; `todos`, the lists of todos of the store, with `has(reader, id, context)`, whether the conversation `id` has a list, `draft(tx, id)`, the list of the conversation `id` in the commit `tx`, `read(reader, id, context)`, the list of the conversation `id`, empty when it has none, `callers(reader, storage, context)`, the list of each caller that has one as `{ caller, todos }`, by caller, which the scan of `storage` finds, `changed(change, id)`, whether `change`, a change of a commit, can change the list of the conversation `id` or the list of a caller, and `load(tx, root, todos, callerTodos)`, which writes the lists of a store file. The reads of `asks` and `todos` take any reader of the store, the writes take the `Tx` of a commit of the entry, so they go in one commit with the writes of the entry, and need no open host; `degraded`, the degraded states of the host, with its kinds only; `warn`, which writes a warning to `host.log`; and `classifier`, with `model(key)`, the classifier model of the setting `todoClassifier` or `gateClassifier` as the host finds it, with its `no-classifier` state, and `ask(model, context, signal)`, the answers of the model; and `deliver({ key, to, text })`, which queues `text` for `to`, once for each `key` (see [Push](#push)). `to` is the conversation ID of the host agent, of a child, or of another conversation of the children library, which gets the text as input, or a Pi session of the host (a caller that opened an `answers` request), which gets it in the reply of its `answers` request. `deliver` throws `The host is not open yet` until the host is open, `<to> is not a conversation or a Pi session of the host` for another `to`, as an `UnknownDeliveryTarget` of `@vzlentin/harness/entry-api`, whose `name` is `UnknownDeliveryTarget`, and `Invalid delivery: it needs a key, a to and a text` for another shape. A delivery whose key waits in the queue for `to`, or that `to` already took, adds nothing, also after a restart. `workers(label)` gives the live workers of the label: `{ kind: "agent", handle, conversation, state }` for a child of the host with the label that did not end, with the state `running` while it is busy and `idle` while it is idle or failed, then `{ kind: "task", key, state: "running" }` for a started task with the label that is not terminal. `stop(worker)` ends a child with the children that it spawned, as a `stop` request does, and aborts a task; it does nothing for a child that is already ended or a task that is terminal. `stopAfterTurn(worker)` stops an agent worker as `stop` does, after the turn that it runs: at the first commit that ends its turn, or at once when it runs no turn; it rejects when the session closes first. `labelledTasks()` gives the keys of the started tasks of each label, in any state of the task. `workersChange(change)` is true when `change`, a change of a commit of the store, can change a live worker of a label: a change of a child, of the record of a child, of the started tasks or of the labels of the tasks, or a task that ends; it reads nothing, so a store watch of an entry can call it. `labelChild(conversation, label)` adds `label` to the labels of the child whose conversation ID is `conversation`, once and with no check of the label, and gives whether the host has such a child: it is for the move of an old store, whose labels the record does not name. `endedChild(conversation)` gives whether `conversation` is a child of the host that ended. `workers`, `stop`, `stopAfterTurn`, `tell`, `liveWorkers`, `labelledTasks`, `labelChild` and `endedChild` throw `The host is not open yet` until the host is open. The entries load before the host opens its store, so `place.store` is usable only once the host is open, which means inside tasks. An entry returns `{ extensions, uninherited?, tasks?, catchUp?, input?, answeredAsk?, reported?, agentEnded?, requests?, labels?, protocol?, open?, busy?, ask?, classifyList?, close }`. The host installs its own extensions first, then those of the MCP servers, then those of the entries, in load order. The host installs `extensions` and `tasks`, and refuses to start when two entries give a task with the same name. `uninherited` lists the names of extensions that no child inherits from the agent of its owner, such as the memory extension of the projects entry, which only the host agent has: at any depth and also as a depth root, `children.open` removes them from the `extensions` of the child's `AgentDoc`. An entry that returns no `tasks` loads as before. `catchUp` is a catch-up hook of the host agent, `{ kind, run }`, with a `kind` that is not empty (see [Host agent](#host-agent)); the host refuses to start when two entries give a hook of the same kind, with `The entries <module> and <module> both give the catch-up hook <kind>`. `input` is an input hook, `{ kind, run }`, with a `kind` that is not empty; the host refuses to start when two entries give a hook of the same kind, with `The entries <module> and <module> both give the input hook <kind>`. Before each input of any conversation that the host hosts, the host agent, a child or another conversation of the children library, the host calls `run({ conversation, head, write })` of each input hook, in load order. This covers the inputs of the requests (`spawn`, `send` and `input`) and the inputs that the host pushes (the answers of children, the answers of the user, and the deliveries of the entries, such as the approve of a held action). Before an `input` to the host agent, the hooks run after its catch-up: `conversation` is the conversation ID, and `head` the ID of the newest head marker of its context (a `pi.compaction` or a `pi.reset`), or undefined. `write({ key, kind, text, data? })` writes one passive user entry of the kind `kind` with the text `text` and `data`, with the request ID `input:<hook kind>:<key>`, so a repeat after a crash adds nothing. A second `write` in one call, and a `write` of another shape, throw. A hook that throws gives the warning `input: <kind>: <message>` and the degraded state `catch-up-failed` of the cause `input:<kind>`, which its next call that works ends, and the input goes through. `answeredAsk(event, { signal })` gets each answer that an `ask answer` writes, as `{ key, ask }`: `key` is `answer:<n>`, from a count that never goes down, and `ask` the answered ask. The commit of the answers always queues their events in the document `harness.ask-events`, so a restart loses none. The host gives the events once it is open, oldest first, one at a time, to the handler of each entry in load order, such as the handler of the projects entry, which makes the contracts of the parleys, and removes each one after every handler resolves. When a handler throws, the host writes a warning, the later handlers do not get the event, and the host gives that event again only after its next start. When the host closes, `signal` aborts, the host does not wait for the handler, and the event stays for the next start: each handler gets it again, so a handler must do nothing for a key that it already handled. `reported(event)` gets each `report` (see the task requests below), as `{ worker, labels, refs, caller }`: `worker` is `{ kind: "agent", handle }` or `{ kind: "task", key }`, `labels` its labels, `refs` the references of this report, repeats included, and `caller` the caller of the report. After the commit of the report, the host runs the handler of each entry in load order, such as the rule of the items of the projects entry, and replies after them. When one throws, the request fails with its error, the later handlers do not run, and the references stay stored. The host keeps no queue of reports: a repeat of the report runs them again, so a handler must do nothing for a report that it already handled. `agentEnded(event)` gets each child of the host that ends, as `{ conversation }`, its conversation ID: a child that a `stop` request, the `stop` handle, the end of its spawner or the end of an ancestor ends. After the end, the host runs the handler of each entry in load order; a handler that throws is a warning in `host.log`, and the later handlers still run. A child can end twice, such as after a resume, so a handler must do nothing for an end that it already handled. The host keeps no queue of these events: an entry that must see every end checks the children that ended at its `open`, with `endedChild`. `requests` lists the request types that the entry serves on the socket. Each is `{ type, schema, passive, handle }` or `{ type, schema, passive, watch }`, with exactly one of `handle` and `watch`: `type` is not empty, `schema` is a TypeBox schema that each line of the type must match, and `passive(request)` is true when the line does not count as activity for the idle exit. A line that does not match the schema fails with `Invalid <type> request: <path>: <rule>`, as a line of the host does. `handle(request, { signal })` gives the reply. `watch(request, { signal, emit, drained, end })` gives the state, which is the reply, and needs a connection (`A <type> watch needs a connection`). After the reply, each `emit(event)` becomes one `{ "event": ... }` line, in order, and the events that come before the reply wait for it. `emit` is false when the socket holds the line until it drains, and `drained()` resolves once it drained, so a watch of a slow client waits. `end()` ends the connection after the reply and the events before it. `signal` aborts when the socket or the host closes. The host refuses to start when two entries serve the same type, with `The entries <module> and <module> both serve the request type <type>`, and when an entry serves a type of the host, with `The entry <module> serves the request type <type>, which the host owns`. `labels` lists the label kinds that the entry checks, each `{ kind, check }`, with a `kind` that is not empty. Before a spawn or a first start with a label of the kind, the host calls `check(label)`, which throws the reason when it refuses the label. The host refuses to start when two entries check the same kind, with `The entries <module> and <module> both check the label kind <kind>`. `protocol` is `{ name, version }`, with a name that is not empty and an integer version from 1, which the `hello` reply gives; the host refuses to start when two entries give the same name, with `The entries <module> and <module> both give the protocol <name>`. `open({ harness, root, storage })` runs once the store, the root conversation and the workers are there, before the push, the sessions and the resume of the tasks; an entry that fails its open stops the host start. `busy()` is true while the entry has work that keeps the host from its idle exit. `ask(request, { signal, author })` serves the `ask` requests in place of the host, with `author(request)`, which gives the author of the answers of the `ask answer` request `request` as the host works it out (see `ask answer`), and which the entry calls only for an `answer`; without it, the host serves the plain asks (see [Asks and parleys](#asks-and-parleys)). `classifyList()` gives the list of `classify-todos` without `list`. At most one entry gives `ask`, and at most one `classifyList`: the host refuses to start when two do, with `The entries <module> and <module> both give the handler of the ask requests` or `The entries <module> and <module> both give the list of classify-todos`. An entry that returns another shape stops the host start with `The entry <module> returned an invalid result: <path> <message>`, such as `/extensions must be array`. In each of these refusals, the entries loaded before it close.

A host has the rules, the gate, the parleys, the work items, the digest and the memory of the host agent only with the projects entry. The projects entry is a package of its own, and loads as any external entry: from `piDurable.extensions` of an installed Pi package, or from `entries.json`. A host without it runs, with no gate, no rules, no digest and no tools of the projects entry. It answers a request of a projects type, such as `parley` or `item`, with `no loaded entry serves request type "<type>"`. It serves the `ask` requests itself, with no parley: a round with `parley`, and an ask by `slug` and `n`, fail with `no loaded entry serves parley asks`. It answers, drops and notes an ask that serves a parley by its ID as any other ask, and keeps its `parley` as data that it does not read. A `classify-todos` without `list` fails with `classify-todos needs a list: no loaded entry gives one`.

A client starts and follows the tasks of the entries with four requests, and reports the results of a worker with a fifth:

- `start { kind, input, key, version?, labels? }` creates a task of the kind `kind`, with the input `input`, and replies with its info `{ key, id, kind, version, status, outcome? }`. `version` is the version on the task's record: the version of the entry's task definition that last ran or migrated the task. It shows which version of the entry the host used for this task, not which version the host has loaded now. `outcome` is there only when the task is terminal. The key is the client's own name for the task. A repeated `start` with a known key gives the first task, and its new input is ignored. It refuses another kind with `The task <key> is a <kind> task, not <kind>`. An unknown kind gives `Unknown task kind: <kind>`. With `version`, a host whose loaded definition of the kind has another version creates nothing and gives `This host has version <n> of <kind>, not <version>: stop the host so it starts again with the installed version`, for a first and a repeated `start`. The task gets the labels of `labels`, then the label of `input.serves` when the input has a `serves` of the shape of a spawn (`{ parley: <slug> }` or `{ item: <id> }`), each once. A first `start` checks them as a spawn does (see `host.sock`), before it creates anything, and refuses with the reason of the first label that a check refuses; the commit that creates the task writes them. A repeated `start` checks no label and keeps the labels of the first. Before it creates the task, `start` sets up the host agent, so a child that the task opens without a model takes the agent's; when the agent has no model, the task still starts.
- `task { key }` replies with the info of the task.
- `wait-task { key }` waits until the task is terminal, and replies with its info, with the outcome. To follow the status during the run, poll `task`.
- `abort-task { key }` aborts the task and the work that it owns, such as the turns of its children, and replies with the info.
- `report { caller, refs, handle? | key? }` stores the result references `refs` of a worker, such as `commit:<sha>`, and replies `{ refs }` with all the references of the worker, each once, in the order of their first report. `refs` has at least one reference, each a text that is not empty. The worker is the child `handle`, the started task `key`, in any state, or, with neither, the child whose conversation is the caller. A line with both keys fails with `Invalid report request: key: not allowed`. An unknown handle fails with `Unknown subagent: <handle>`, and the host agent or another caller with no `handle` and no `key` with `The caller is no worker of this host: give handle or key`. The host does not check that the reporter is live, and does not read the references. After the commit of the references, the `reported` handler of each entry runs, in load order, such as the rule of the items of the projects entry (see the entries above). The info of a task, and the `run` node of a started task, have `refs` when the task has one.

The other requests refuse a key that no `start` gave with `Unknown task: <key>`. The host keeps each key and its task in `durable.sqlite`, and no request removes a key, so the key map only grows. A started task is a background task of the root conversation, so an abort of the host agent (Esc in its mirror session) does not reach it. A task that a host stop interrupts continues when the host starts again. The children that tasks open are not in `list`. workflows starts the task `n` of the run `<runId>`, from 1, with the key `wf:<runId>#<n>`, and writes the asks of the run with the asker `workflows:<runId>`.

A todo is a line of intent with a state: `{ id, text, state, ask? }`, where `state` is `open`, `doing`, `done` or `dropped`, and `ask` is the ID of the ask that the todo `Save to the vault` belongs to (see [Asks and parleys](#asks-and-parleys)). No `todo` request sets `ask`: the host sets it on the todo `Save to the vault`, and the replies give it. The host keeps lists of todos in `durable.sqlite`, in three places. Each conversation has one list, as its document `harness.todos`: the host agent, a child, or a conversation that the children library opened. Each task that `start` created has one list, keyed by its task ID: it is not a document of the task, so it stays after the task ends. Each caller that is not a conversation of the host, such as a Pi session or `cli`, has one list, keyed by the caller. A `todo` request `{ caller, action, ... }` reads or changes one list:

- `add { text }` adds a todo with the state `open` and the next ID of the list (1, 2, 3 and so on), and replies with the todo. The text stays as it is given.
- `set { id, state, text? }` sets the state of the todo `id`, and its text when `text` is given, and replies with the todo.
- `list` replies with `{ todos }`, in ID order. A list that was never changed is empty.

The list is the one of the target of the request: a handle, with `agent` for the host agent; `{ conversation }`, the ID of a conversation that the children library opened; `{ key }`, the key of a `start`; or, with none of them, the list of the caller. When the caller is the conversation ID of the host agent or of a conversation that the children library opened, such as a child of this host, the list of the caller is the list of that conversation, as for the parent of a `spawn`. The request does not check that the caller spawned the child of a handle, and it does not set up the host agent, so it works when the agent has no model. A `{ key }` target takes `add` and `set` also after the task ends, and a `{ conversation }` target also when the conversation is ended. A request with two targets fails with `Invalid todo request: <field>: not allowed`, where `<field>` is the second one in the order `handle`, `conversation`, `key`. A state that is not one of the four fails with `Invalid todo request: state: <rule>`, and an `id` that is not an integer from 1 with `Invalid todo request: id: <rule>`. A text that is empty or has only white space fails with `The text of a todo is empty`, an unknown ID with `Unknown todo: <id>`, an unknown handle with `Unknown subagent: <handle>`, a conversation that the children library did not open, the root included, with `Unknown conversation: <id>`, and an unknown key with `Unknown task: <key>`. A request that fails does not change the list. The `watch` of a conversation gives its list, and an event for each change of it (see `host.sock`). `harness todo` sends this request (see [Todos](#todos)).

`@vzlentin/harness/todo` gives the tasks of an entry the same lists and the same rules, with no socket: the schemas `Todo` and `TodoState` and their types, `TODO_STATES`, `TODO_MARKS` (the mark of each state in the line of a todo), `TODO_LIST_KIND` (`"harness.todos"`, the kind of the list of a conversation in the `docs` of a watched view), `TASK_TODO_LIST_KIND` (`"harness.task-todos"`, the kind of the lists of the started tasks), the schemas `TodoAnswer` and `ClassifyReply` of the reply of `classify-todos` and their types, the types `TodoList` and `TodoOwner` (`{ kind: "conversation", id }`, `{ kind: "task", id }` or `{ kind: "caller", caller }`), and six functions. `todoLine(todo)` gives the line of a todo as `harness todo` prints it, `<mark> <id> <text>` (see [Todos](#todos)), and `answerLine(answer)` the line of an answer as `harness todo sort` prints it. `addTodo(tx, owner, text)` and `setTodo(tx, owner, { id, state, text? })` change the list of `owner` in the commit `tx` of the caller, such as a commit of the runtime of a task, and give the todo. For an empty text or an unknown ID, they throw the error of the request, and a commit that does not catch it changes nothing. `readTodos(reader, owner, context)` gives the list from a reader such as the harness or the runtime of a task. `watchTodos(harness, id, context)` gives a chord watch of the list of the conversation `id`: its value is the list, or `null` while the conversation has none, and each stored commit that changes the list gives a call, the first `add` included. An abort of `context` or the close of the harness ends it. A task changes its own list with `{ kind: "task", id: runtime.taskId }`, also in the commit that makes it terminal.

A `classify-todos` request `{ list?, ids? }` asks a classifier model of Pi about the todos in the state `open` of a list, and stores nothing. `list` is `{ handle }`, with `agent` for the host agent, `{ conversation }` or `{ key }`, as for the `todo` request. Without `list`, it asks about the list that an entry gives (`classifyList`), such as the work items of the projects entry, and without such an entry it fails with `classify-todos needs a list: no loaded entry gives one`. `ids` are the IDs of the todos to ask about; without it, every open todo. A todo of `ids` that is not open gets no answer, and an ID that is not in the list fails with `Unknown todo: <id>`. The classifier is `todoClassifier` in Pi's settings, as `<provider>/<id>`, read again at each request, from the global settings and the settings of a trusted project; the default is `typesafe/jev-latest`. When its provider has no credential in Pi, or has no classifier model with that ID, the request fails with `No classifier: log in to <provider> or set todoClassifier`, before it reads the list, so a client keeps the order of the adds. Each todo gets one call of pi-ai's `classify`, with `{ todo: { id, text }, earlier }` as the state, where `earlier` are the todos with a lower ID, in any state, and two questions: `needsYou`, a bool, true when the todo needs a call that only the user can make, which counts as yes from a probability of 0.5; and, when `earlier` is not empty, `repeats`, a choice of `none` or the ID of one todo of `earlier` that it repeats. A call that does not end with the stop reason `stop` fails the request with `The classifier <provider>/<id> failed: <errorMessage>`. The reply is `{ answers: [{ id, needsYou, repeats? }] }`, in ID order, where `repeats` is the ID that the classifier chose, absent for `none`. `harness todo sort` sends it (see [Todos](#todos)).

A `tree` request `{}` replies `{ nodes }` with the nodes of the host, each parent before its children, and the siblings in ID order. pi-durable takes the IDs of the tasks and the conversations from one counter, so ID order is creation order. A node is `{ id, parent?, kind, name, state, todos, labels?, refs? }`: `parent` is the `id` of the node above, absent for a root; `kind` is `agent` or `run`; `todos` is the whole list of the node (see the `todo` request), in ID order; `labels` are the labels of a child by handle that has one, as its info gives them. The host agent, a conversation that a task owns and a `run` node have none. `refs` are the references that `report` stored for a child by handle or a started task, when it has one. The text of `harness tree` does not show them. The nodes are:

- The host agent: `id` `agent`, no parent, the name `<host> agent`, and the state `busy`, `idle` or `error` of its info. It needs no model.
- Each child by handle: `id` its handle, the name of the child or its handle, and the state that `status` gives. Its parent is the node of its caller: `agent`, the handle of a child, or `conversation:<id>` for a conversation of the children library. A child whose caller is not a conversation of the host, such as a Pi session or `cli`, is a root. A child whose caller is a conversation of the children library that is not in the tree is not in the tree either.
- Each task that `start` created: `id` `task:<key>`, `kind` `run`, no parent, and the name `<kind> <key>`.
- Each task in the root conversation of a kind that the entries give, whose owner task is a started task that did not end or a task under one, such as a child task of a started task: `id` `task:<task ID>`, `kind` `run`, the node of its owner as its parent, and the name `<kind> <task ID>`.
- Each conversation of the children library that a started task that did not end owns, or that a task under one owns: `id` `conversation:<id>`, the node of the task as its parent, the key of the conversation as its name, and the state `busy`, `idle`, `error` or `ended` of its info.

The kind of the other nodes is `agent`. The state of a `run` node comes from its task: `pending`; `running` for a task that runs, waits, sleeps or completes; and for a terminal task the status of its outcome, `completed`, `failed` (also for an orphaned or faulted task) or `aborted`. The list of a `run` node is the list of its task. A started task that ended keeps only its `run` node, and the node is left out when its ID is lower than the ID of the 50th newest task that `start` created. Under a started task that did not end, a node that ended (a terminal task, or an ended conversation) is left out when its ID is lower than that ID, and so are the nodes under it. An ended child by handle is left out by the same test. With fewer than 50 started tasks, no node is left out for its age. The host reads the tasks and the conversations of the tree from the store with no write transaction. `harness tree` sends this request (see [Tree](#tree)).

A `watch-tree` request `{}` replies as `tree` does, then sends `{ "event": { nodes } }` with the nodes that are new or changed, in tree order, and `{ "event": { removed } }` with the IDs of the nodes that went, each only when it is not empty. When a started task ends, `removed` gives the nodes that were under it. The host builds the tree again after each commit that can change a node, and compares it with what the client has: a change of a list of todos, of the records of the children by handle, of the started tasks, of the result references of the workers, of a conversation of the children library or of the last request of the host agent; any change of a submission; the start and the end of a run of a conversation; and a new task of a kind of the entries, or such a task whose node state changed. The builds run one at a time, and the commits during a build give one more. A slow client does not hold up the host: when a write must wait for the socket to drain, only that watch waits, and its next `nodes` event has every node. A build that fails ends the connection, so the client opens a new watch. A request without a connection fails with `A tree watch needs a connection`. `TreeNode`, `TreeReply` and `TreeEvent` of `@vzlentin/harness/protocol` are the TypeBox schemas of a node, of the reply and of an event.

A host of an older harness, with no host names, kept its state in `$XDG_STATE_HOME/harness/`. To keep its children, stop that host, then move `durable.sqlite` and its `-wal` and `-shm` files into `main/` before the `main` host starts.

A child's bash commands get `PI_SESSION_ID` (the child's conversation ID), `PI_PROVIDER`, `PI_MODEL`, `PI_REASONING_LEVEL`, and `HARNESS_HOST`, so a child can spawn its own children with its own model and thinking level when the subagent settings do not set them (see [Tool](#tool)), in the same host, down to the depth limit (see [Push](#push)). After a `configure`, the next commands get the new model and thinking level. In a host other than `main` whose directory has a `.optmem` folder, they also get `MEMORY_DIR`, the path of that folder. Otherwise they get no `MEMORY_DIR`, not even the host's own. The rule uses the host directory, not the child's working directory. Children survive `/reload`. When a Pi session ends, the host ends its children and the children they spawned (see [Pi extension](#pi-extension)). `harness stop` ends a child and the children it spawned, by handle or with `--conversation <id>`; a `send` resumes one. For the host agent and a conversation with no record of a child, such as one of a task, it aborts the turn and keeps the conversation.

A child's system prompt starts with the section `rules`, before the project instructions. It has Pi's four tool-use rules, the same for every conversation: `- Use read to examine files instead of cat or sed.`, `- Use edit for targeted changes; batch changes to one file in a single call.`, `- Use write only for new files or complete rewrites.` and `- Use codemode to batch independent tool calls (Promise.allSettled), chain them, or filter large output, instead of many separate calls.`, one per line. Then it has what a Pi session in the child's working directory gets: the `AGENTS.md` or `CLAUDE.md` of the agent directory and of the working directory and its parents, the skills, and the working directory. User skills always load. Project skills (`.pi/skills`, and `.agents/skills` in the working directory and its parents) load only for a trusted project: a directory without project resources, then the decision saved with `/trust`, then the `defaultProjectTrust` setting, where `ask` counts as not trusted. A trust decision that a Pi session made for itself without saving it does not reach its children; when the tool spawns in such a session, it adds `The child gets no project skills (.pi/skills, .agents/skills): this project is trusted for this Pi session only, and children see only the trust saved for future sessions. To give children project skills, run /trust and choose Trust.` to its output. The host checks the trust on every model request, so a decision saved later applies from the next request. The host reads the instructions and skills of a directory once per trust decision and keeps them until it exits. It skips packages that are not installed. When the instructions or skills of a directory fail to load, the child gets none for that request, the host writes a warning, and the next request tries again. A child that the children library opens with `overlay` in its spec, a map of path to content, sees that content in place of the disk. A relative path is relative to the child's working directory, lexically; without a working directory, a relative path makes `open` fail with `The overlay key <path> is relative, and the child has no working directory`. A string replaces the file, and `null` removes it. The overlay changes the instructions and the skills that Pi loaded, and the `read` tool, which gives `ENOENT` for a removed file. A `SKILL.md` path that is not on disk adds a skill. A skill whose content has no description is not loaded, as in Pi, and for a name that two skills use, the first one wins. An overlay adds no instructions file. The other tools see the disk. A child that is opened with a parent that has an overlay gets that overlay, at every depth, also through the `subagent` tool. The child's own paths win, compared after they are resolved, and its own skill comes first when two skills have the same name. A child without an overlay and without an overlaid parent saves no overlay. The overlay is set when the child is created: a second `open` of its key keeps the first one.

### MCP servers

The host connects the MCP servers of Pi's config, and the `codemode` scripts of its conversations (the children, the host agent and the workflows sessions) call their tools as `tools.mcp__<server>__<tool>(args)`, as in Pi. The model never gets an MCP tool as a tool of its own: only scripts call them.

- The servers are those of `mcp.json` in Pi's agent directory, and of `.pi/mcp.json` of the host directory when Pi trusts the project there, with the saved trust. One set serves the whole host. The rules are Pi's: a project entry replaces the global entry of the same name, and a project entry with no `command`, `url` or `type` sets only `enabled`, `exposure` and `toolExposure` of the global entry. Only the global file can set `auth`. A stdio server runs in the host directory, or in its `cwd` relative to it.
- A value that Pi resolves as `${VAR}`, `$VAR` or `!command`, in `headers`, `env` or `oauth.clientSecret`, stops that server, with the warning `MCP config: <file>: server "<name>": <field> uses ${VAR}, $VAR or !command, which the harness host does not resolve` in `host.log`. The other errors of the files are warnings of the same form.
- `exposure` and `toolExposure` work as in Pi. A `direct` tool is in the `codemode` section. A `codemode` or `deferred` tool is not: a script finds it with `searchTools()`, and the section `mcp_servers` names each server with such tools, with the first line of its `description` or of its instructions. Each server is a codemode namespace `mcp__<server>`, also before it connects: the `codemode` section lists it, and `describeNamespace("mcp__<server>")` gives its tools, the same first line as its description, and its instructions. A `hidden` tool does not exist for the host.
- The servers connect in the background when the host starts. A script that names a server, by a word that contains `mcp__<server>`, first waits for its connection. A script that uses `searchTools`, `describeNamespace`, `describeTool` or `ALL_TOOLS` waits for the connections of all servers. The tools of a script are fixed when its call starts, so a script whose server connected during the wait fails with `MCP server "<name>" connected while the script started. Run the script again.`
- A script that names a server that needs sign-in or failed tries to connect it once more, so a sign-in done in Pi applies with no restart of the host. When the server still needs sign-in, the script fails with Pi's message `MCP server "<name>" requires sign-in. Run /mcp to sign in.`, or `Run /login <provider>` for a server with `auth`. A server that failed gives `MCP server "<name>" failed to connect: <message>`. The host writes the same lines to `host.log`.
- The host never signs in. It uses the OAuth state that Pi keeps in `mcp-auth.json` of Pi's agent directory, under Pi's key `mcp__<server>|<url>` and Pi's lock of the file, and refreshes the tokens under Pi's refresh lock, so Pi and the host do not sign each other out. A server with `auth` gets the token of its provider from the host's models.
- MCP problems are warnings in `host.log`, not degraded states. The host closes the connections when it closes, after the store.

### Asks and parleys

An ask is a question that someone put to the user, with his answer. The host keeps the asks in its store (see [Host](#host)), in the document `harness.asks` of `durable.sqlite`, and it is their one writer. An ask names its asker, and its parley when it has one. A parley is a group of asks with a frame, which ends as a contract. The entry that serves the parley asks, such as the projects entry, keeps the parleys and serves the `ask` requests in place of the host (`ask` of the entries in [Host](#host)). Without such an entry, the host serves the plain asks, which this section describes.

An ask is `{ id, title, kind?, tension?, options?, plan?, view?, parley?, note?, asker, state, answer?, label?, words?, author?, at, by }`:

- `id` is the next ID of the one list of asks of the host.
- `title` is the question. `kind` is `your call` or `my call`. `options` is a list that is not empty of `{ key, label, gains?, costs? }`: `key` is one lowercase letter, unique in the ask, and `gains` and `costs` are lists of texts that are not empty. `plan` is the key of the option that the asker proposes. `view` is a text that explains the ask, in Markdown.
- `parley` is `{ id, n }`: the ID of its parley, and its number in that parley, 1, 2, 3 and so on. The entry that serves the parley asks sets it. The host stores it and does not read it.
- `note` is the ID of the note of the ask in the vault: the `id` of the front matter of that note, kept as it is given. Only `ask note` sets it.
- `asker` is the caller of the round that wrote it, or the caller that the entry that serves the parley asks made its asker.
- `state` is `open`, `answered` or `dropped`. An open ask takes an answer and a drop. An answered ask takes a new answer, which replaces `answer`, `label` and `words` as one unit. A dropped ask takes nothing. `askTransition(state, event)` of `@vzlentin/harness/protocol` gives the state after an `answer` or a `drop`, or `undefined`.
- Only an answered ask has `answer`: the key of one of its options, `ok`, or `own`. `own` needs `label`, the short name of the answer of the user. `words` are the exact words of the user, a list of texts that is not empty, in Markdown.
- Only an answered ask has `author`, the author of its last answer: `{ kind: "user" }`, `{ kind: "hosted", conversation }` for the agent of a conversation of the host, with its conversation ID, or `{ kind: "agent", caller }` for another agent, which the host knows only by its caller, such as the session ID of a Pi session. A new answer writes its own author. A note keeps it.
- `at` is the time of its last change, and `by` the caller of that change.

The answer of an ask with options is the key of an option or `own`. The answer of an ask with no options and no parley is `own`. The entry that serves the parley asks also takes `ok` for the read-back of a parley, an ask of the parley with no options.

`title`, `tension`, each label, and each text of `gains` and `costs` are plain text: at least one character that is not white space, with no backtick and no `**`.

The requests have an `action`, and each write has a `caller`. A request names one ask as `{ id }`, its ID, or as `{ slug, n }`, its number `n` in the parley `slug`; a request with keys of both fails with `Invalid ask request: <key>: not allowed`. A round with `parley`, and an ask by `{ slug, n }`, need an entry that gives an `ask` handler, such as the projects entry: without one, they fail with `no loaded entry serves parley asks`. The reply of a write of asks is `{ parleys, asks, items? }`, from the commit of the write. On the plain asks, `parleys` is empty, there is no `items`, and `asks` has the asks that the write added or changed, in ID order. An entry that serves the parley asks gives each parley that the write changed in `parleys`, as `{ parley, asks }`, and each item that the write added in `items`, as `{ id, title }`.

- `ask round { caller, asks }` writes one or more asks, with the state `open` and the caller as their asker, and replies with the write.
- `ask answer { caller, answers, user? }` writes one or more answers `{ id, answer, label?, words? }` in one write, each of another ask, and replies with the write. The host sets the `author` of each answer: `{ kind: "user" }` when `user` is `true`, else `{ kind: "hosted", conversation }` when the caller is the host agent or a conversation of the children library, else `{ kind: "agent", caller }` with the caller. The host cannot tell who holds the socket, so an `ask answer` with `user: true` from any client counts as the answers of the user, as for `input`: this is the limit of the mark. A caller that is not a conversation of the host and sends no mark, such as `cli`, `orda` or `<store>:<id>`, is written as `agent` with that caller.
- `ask drop { caller, id }` drops an open ask, and replies with the write.
- `ask note { caller, id, note }` sets `note`, the ID of the vault note of the ask (not a `note` request of a child), and replies with the ask. In the same write, it sets the todo `Save to the vault` of the ask to `done` (see below), unless that todo is `done` or `dropped`: a dropped todo stays dropped. The ask can be in any state. A second note replaces the first, and no request removes it. It sets `at` and `by`, and keeps `asker`. An answer or a drop keeps the note. Only the asker of the ask sends it: another caller fails with `Ask <id> was asked by another caller: only its asker records its note`.
- `ask read { id }` replies with the ask, in any state.
- `ask list` replies with `{ asks }`, the open asks.

No request removes an ask. A request that fails changes nothing. The checks inside one request run at the request: an empty list of asks or of answers, an option key used twice, a `plan` that is not a key of the options, two answers of one ask, a text that is not plain, and a `note` that is empty or blank fail with `Invalid ask request: <path>: <rule>`, such as `Invalid ask request: asks/0/options/1/label: plain text, no backticks or **` for a label with a backtick. An answer `own` without `label` fails with `Invalid ask request: answers/<n>/label: required`, and an `ask note` without `note` with `Invalid ask request: note: required`. The checks against the store fail with:

- `Unknown ask: <id>`.
- `Ask <id> has two answers in one write`.
- `Ask <id> takes <keys> or own`, such as `Ask 3 takes a, b or own`, and `Ask <id> takes own` for an ask with no options.
- `Ask <id> is dropped: it takes no answer`, and `Ask <id> is <state>: only an open ask drops`.
- `Ask <id> was asked by another caller: only its asker records its note`, for an `ask note` from a caller that is not the asker of the ask.

`Ask`, `Parley`, `AskRef`, `AskWrite`, `AskList` and `ParleyAsks` of `@vzlentin/harness/protocol` are the TypeBox schemas of an ask, a parley, the name of an ask and the replies.

The `ask answer` request also queues the answers for their askers, in the same write, in the document `harness.user-answers` of the store, so a restart loses none. It queues one delivery for each asker and parley of the answered asks, with the text that the entry that serves the parley asks gives, and one delivery for each answered ask with no parley, with the line of the ask, then each of the words of the user on its own line. Each delivery ends with the line `<mark> <id> <text>` of each todo `Save to the vault` that the same write added for one of its asks (see below). An ask whose asker is the caller of the answer gets no delivery. Each delivery has an ID from a counter that never goes down. The host pushes them (see [Push](#push)).

When the host has a vault, the `ask answer` request also adds, in the same write, the todo `Save to the vault: <title>` to the list of the asker of each answered ask (see the `todo` request in [Host](#host)), with the first line of the title of the ask, and with `ask`, the ID of the ask. The list of the asker is the list of the host agent when the asker is its conversation ID, the list of a conversation that the children library opened when the asker is its ID, and the list of the caller when the asker is a Pi session that the host knows. One ask gives one todo: the host keeps, in the document `harness.save-todos` of the store, the ID of each ask that has its todo and the list that holds it, so a second answer or a changed answer adds none, whatever the state of the todo. The host has a vault when `VAULT` of its environment is set and names a folder that exists; it reads this at each answer, and without a vault no ask gets a todo. With a vault, these asks get no todo: the read-back of a parley, which the entry that serves the parley asks names, an ask with a `note`, and an ask whose asker has no list, such as a session of a workflows run or `cli`. `ask note` reads a list only when that document says the list holds the todo of the ask, so a note creates no list.

### Push

When a child finishes, the host sends its unread answers to its caller, so the caller does not need `wait`. A request of a `spawn` or `send` with `notify: false` is quiet: its answer is not pushed alone, and it does not hold the caller. A child is done when its own turn ended and none of its children has an unread notify request, at any depth: until then, it holds its caller. The host checks this after each commit that can end a turn or change a record of a child, at host start, at the end of a `wait` or a `send`, and when an `answers` request opens or its reply is written. For a done child, it takes the unread answers as `wait` gives them, marks them read, and delivers them:

- The text is the answers in the form of `wait`, cut as `wait` cuts them (see [Limits](#limits)), without its first line `<handle> finished` and the blank line after it. When the last turn failed or was aborted, `failed` is true and the text is the error of `wait`, such as `<handle> failed: overloaded` or `<handle> was aborted`.
- A caller that is a conversation of the host (a child, the host agent, or another conversation of the children library, such as one of a workflow task) gets the input `subagent <name> (<handle>) finished` (`subagent <handle> finished` for a child without a name), or `failed` in place of `finished` when `failed` is true, a blank line and the text: a new turn when it is idle, a follow-up when it works. Its request ID is `push:<handle>:<read>`, so a push that runs again after a restart does not repeat. The input reaches the caller before the child stops holding it.
- Any other caller, such as a Pi session, gets the answers as the reply to its open `answers` request, oldest child first. These answers become read only once the reply is written to the socket. When the write fails, or the connection closes first, they stay unread, for a later `answers` request or a `wait`; a `wait` that runs meanwhile waits until the write ends. Without an open request, the answers stay unread too. When the host stops after it wrote the reply and before it marked the answers read, the next `answers` request gives them again.
- When a push of a child fails, such as a conversation that cannot be found or a caller that refuses the input, the host writes a warning and skips that child for 1 s, then for twice as long after each failure in a row, up to 60 s. A timer pushes again when the wait ends, also without a new commit. A push of the child that ends without an error resets the wait. While a child of a caller waits after a failed push, the later children of that caller wait too, so the answers keep their order.
- A turn that a mirror session started sends nothing up: when the last request is mirror input, the answer that goes up is the one of the caller's last request.

The host pushes the queued answers of the user to their askers (see [Asks and parleys](#asks-and-parleys)) in the same checks, after each commit that changes the queue, with the same destinations and the same waits after a failed push, oldest delivery first, after the answers of the children of the same caller. They differ from the answers of a child in these points:

- A delivery is `{ source: "ask", ask, text }` for an ask with no parley: the ID of the ask and the text of the queue. It is `{ source: "parley", parley, asks, text }` for the asks of a parley: the slug of the parley, the IDs of the answered asks, and the text of the queue. The input, and the text of the Pi message, is `the user answered ask <id>` or `the user answered the parley <slug>`, a blank line and the text.
- A conversation of the host gets it as input with the request ID `user-answer:<id>`, a new turn when it is idle and a follow-up when it works. The delivery leaves the queue after the input is sent.
- In the reply of an `answers` request, a delivery leaves the queue once the reply is written. When the write fails, or the connection closes first, it stays for a later request. When the host stops after it wrote the reply and before it removed the delivery, the next `answers` request gives it again. Without an open request, such as a Pi session that is closed, the answers stay in the queue.
- A delivery to an ended conversation of the host resumes it, as a `send` does: the answers of the user, a delivery of an entry, such as the approval of a held action, and the answers of its children. A conversation with no record, such as a child of a task, resumes too, and the delivery does not change its last request. When the children library ends the conversation while the delivery is admitted, the delivery is aborted and fails. The unread answers of an ended child go only to the reply of an open `answers` request, such as the answers of the children of a Pi session that ended: as input, they would resume an ended conversation. A busy turn that the end aborted gives `<handle> was aborted`, with `failed` true.
- The wait after a failed push is kept for each delivery. A delivery that waits, or a child of the same caller that waits after a failed push, makes the later deliveries of that caller wait too.
- A turn that a delivered answer starts sends nothing up to the caller of the asker, as for mirror input.

The host pushes the deliveries of the entries (see the entries in [Host](#host)), queued in the document `harness.deliveries`, in the same checks, after each commit that changes the queue, after the answers of the children and of the user of the same caller, oldest first, with the same waits after a failed push. A conversation of the host gets the text as input, with the request ID `delivery:<key>`, a new turn when the conversation is idle and a follow-up when it works, and the delivery leaves the queue after the input is sent. A caller with an open `answers` request, such as a Pi session, gets `{ source: "entry", key, text }` in the reply, and the delivery leaves the queue once the reply is written, as an answer of the user does; the document keeps its key for that caller, so the same key adds nothing later. A Pi session without an open request gets its deliveries when it opens one.

Before each push that goes to a conversation of the host as input, the answers of a child, an answer of the user, or a delivery of an entry, such as the approve of a held action, the input hooks of the entries run, as before the input of a request (see the entries in [Host](#host)), the digest of the projects entry among them. A push gets no catch-up.

The depth of the subagent tree is the setting `agentDepthLimit` in Pi's global `settings.json`, an integer of at least 1, default 4. The host reads it again at each spawn, and it applies to the new trees: a child of a child keeps the limit of its tree. A deeper spawn fails with `Nested subagents are disabled`. A tree that a library caller of the children library starts without a limit, such as one of workflows, keeps the limit of 2, also for the spawns of the `subagent` tool in it. A library caller can open a child as a depth root (`depthRoot`): it stays under its tree parent, for the end and the viewer, and starts a new depth budget at depth 0 with its own `limit`, such as a session that a script opens in code. With `depthParent`, a child takes the depth budget of that conversation in place of its tree parent's: one deeper, with its limit; a conversation that the library did not open counts as depth 0. A child at the limit of its depth budget is a leaf: it gets no `subagent` and no `workflow` tool, also when `--tools` names them, so a model call to `subagent` there gives `Tool subagent is not available`. A call of `tools.subagent` in its IPython kernel gives the same error (see [Tools bridge](#tools-bridge)).

The default model and thinking level of a spawn are the settings `subagentModel` and `subagentThinkingLevel` in Pi's global `settings.json`. `subagentModel` is `<provider>/<model>`, split at the first `/`, as `subagentModel: "openai-codex/gpt-5.4-mini"`. `subagentThinkingLevel` is one of pi-ai's thinking levels. The host reads them again at each spawn, so a change applies to the next spawn without a restart. Each key works alone: a key that is missing or not valid, such as a model without `/`, counts as absent, and the caller's value applies. They apply to every spawn of the `subagent` tool and the CLI, at every depth. A model that the host does not know fails the spawn with `Unknown model: <provider>/<model>`. The children that a library opens, such as the roles of workflows, do not use them.

### Agent life

A child lives until its spawner stops it or ends: a `stop` request ends the child and the children that it spawned, and so does the end of the Pi session that spawned it (see [Pi extension](#pi-extension)). The host agent, `cli`, a conversation of a task and a `<store>:<id>` caller never end a child by their end. A child whose todos are all done keeps running.

A worker is a child of the host or a started task with a label (see `host.sock` and `start` in [Host](#host)). The labels of a child come from the `labels` and the `serves` of its spawn, and those of a task from the `labels` and the `input.serves` of its first `start`. The host stores the labels. A child with labels is a live worker while it did not end; a task while it is not terminal. A label kind needs a loaded entry that checks it. An entry can act on the workers through the `workers`, `stop` and `stopAfterTurn` handles (see the entries in [Host](#host)).

## Limits

- Children get only `read`, `write`, `edit`, `bash`, `subagent`, `todo`, `codemode`, and the tools of the host's entries (see [Host](#host)). Their `codemode` scripts also call the tools of the MCP servers of the host, which the model does not get as tools (see [MCP servers](#mcp-servers)). They get no Pi extensions. A child at the depth limit also gets no `subagent` and no `workflow`, and keeps `todo` (see [Push](#push)). `codemode` runs JavaScript that calls the other tools of the child, as Pi's `codemode` does. A script that a host stop interrupts continues when the host starts again.
- A `bash` call of a hosted conversation (a child, the host agent, or a workflows session) that sets no `timeout` stops after 300 seconds. Its result keeps the output so far, and its error is `Command stopped after 300 seconds: it set no timeout. Set a timeout to run longer.` A call that sets a `timeout` runs with it, also above 300 seconds; when it fires, the error stays `Command timed out after <timeout> seconds`. The `timeout` parameter of `bash` says `Timeout in seconds (optional, default 300 seconds)`. A `bash` call of a `codemode` script gets the same default: the `await` of the script rejects with the line, and the script gets no output. Two cases lose output or keep running: a command that pipes into `tail` shows nothing when it stops, because `tail` prints only at its end, and a process that `setsid` starts leaves the process group, so the stop does not end it.
- A change to `AGENTS.md` or to a skill reaches children only after the host restarts.
- `wait` and a push (see [Push](#push)) cut each answer of a child, and each failure text, to 256 KiB in UTF-8, on a character boundary. They then add the line `[The answer was cut at 256 KiB]`. When they give several answers, they cut each one. The answer stored in the child's conversation stays whole: the caller reads it there with `watch`, `harness attach <handle>` or the transcript of `harness inspect`.
- A query reads at most 256 KiB in UTF-8 of the transcript of its conversation: the last part, from a character boundary, of a longer one. Its answer then starts with the line `[The conversation is longer than 256 KiB: this answer reads only its last 256 KiB]`.
- `--file` gives text only; images are not attached.
- The CLI sends each `spawn` once and has no `key`. If the host stops during a `spawn` and you run the command again, there can be two children.

## Tool

The `subagent` tool does what the CLI does, with one `action` and its arguments:

| `action`         | Arguments                                                                                              |
| ---------------- | ------------------------------------------------------------------------------------------------------ |
| `spawn`          | `name`, `provider`, `model`, `thinking`, `cwd`, `tools`, `prompts`, `files`, `key`, `notify`, `serves` |
| `send`           | `handle`, `message`, `followUp`, `key`, `notify`                                                       |
| `wait`           | `handle`, `timeout` (seconds, default 1800)                                                            |
| `status`, `stop` | `handle`                                                                                               |
| `rename`         | `handle`, `name`                                                                                       |
| `list`           | none                                                                                                   |
| `query`          | `handle`, `question`                                                                                   |

`tools`, `prompts`, and `files` are arrays. `serves` is `{ parley: <slug> }` or `{ item: <id> }`, as on the socket: it gives the child the label of that work (see [Agent life](#agent-life)). The label needs an entry that checks its kind, such as the projects entry: without one, the spawn fails with `no loaded entry checks the label kind "<kind>"`. A relative `cwd` or file path is relative to the caller's working directory. A caller without a working directory cannot spawn. The text result is the output of the same CLI command. The structured result is `{ action, value }`, and the tool declares its schema, where `value` is the host's reply: the child for `spawn`, `status`, and `rename`, `{ verb, child }` for `send`, `{ answer }` for `wait` and `query`, the children for `list`, and `{ handle, name }` for `stop`. A child is `{ handle, name, state, provider, model, thinking, cwd, labels }`, where `state` is `busy`, `idle`, `error` or `ended`, `cwd` is its working directory, and `labels` are its labels, such as `item:<id>`, when it has one.

A spawn without `provider` and `model` uses `subagentModel` in Pi's global `settings.json`, else the caller's model. A spawn with only one of `provider` and `model` takes the other from the caller, not from the setting. A spawn without `thinking` uses `subagentThinkingLevel`, else the caller's level, in both cases clamped to the nearest level that the model has. When no source gives a model, the spawn fails with `No provider specified and the caller has no model` or `No model specified and the caller has no model`. A spawn refuses a `thinking` that the model does not have with `<provider>/<model> has no thinking level <level>`. The CLI refuses a `--thinking` that is not one of pi-ai's levels with `Invalid thinking level: <level>`. The tool's parameter schema takes only pi-ai's levels, so Pi refuses another value before the call. On the socket, such a `thinking` fails with `Invalid spawn request: thinking: must be equal to one of the allowed values`. A `spawn` or `send` that comes again with the same `key` finds the first one and does not repeat it. Without `key`, the call is the key. Each caller has its own keys. When the call is aborted, for example with Esc, a `wait` stops; the child continues.

When a child finishes, its answer comes to the caller as a message that starts a turn (see [Push](#push)). `notify: false` on a `spawn` or a `send` turns off the message for the turns of that call; the answers then come only with `wait`. The CLI has no flag for it. The tool description tells the model to use `wait` only when it needs the answer in the same turn. Its last line says that, with the `ipython` tool, a cell has `tools`, which runs the tools of the conversation, `subagent` too, as `await tools.<name>(**args)`, and that `print(tools.__doc__)` lists them and `print(tools.<name>.__doc__)` gives the arguments of one (see [Tools bridge](#tools-bridge)).

`query` asks a model one `question` about the conversation of the child `handle`, so that the caller learns what the child did without its transcript in its context. The host sends a `query` request `{ caller, question }` with a handle or `{ conversation }`, and replies `{ answer }`; the text result is the answer. The model gets one user message: the transcript between `<transcript>` and `</transcript>`, then `Question: <question>`. The transcript has the model messages of the entries of the conversation, oldest first, separated by a blank line: each message of the user role as `User: <text>`, the notes, digests and summaries too; each text of the assistant as `Assistant: <text>`; and each tool call as `Tool call <name>: <arguments as JSON>`. It has no thinking, no tool output and no image. It is at most 256 KiB (see [Limits](#limits)). A query writes no entry, writes nothing in the store and starts no turn, so it works on a child that is busy or idle. The caller `cli`, a command from a terminal that is not an agent (`PI_SESSION_ID` is not set), can query any child, `agent` and any conversation of the children library, also after a `stop`, with `--conversation <id>`. Another caller, an agent, can query only a child that it spawned, also after a `stop`: a child of another caller with `Subagent <handle> belongs to another session`, a conversation ID that is not one of its children with `The conversation <id> is not a child of this caller`, and `agent` with `Only a terminal that is not an agent can query the host agent`. The model is the setting `queryModel` in Pi's settings, `<provider>/<model>` as `subagentModel`, read again at each query from the global settings and the settings of a trusted project; else `subagentModel` in Pi's global settings; else Pi's default model (`defaultProvider` and `defaultModel`). A key that is not valid counts as absent. A query fails with one line: `No model for a query: set queryModel, subagentModel or a default model in Pi`, `Unknown model: <provider>/<model>`, `No credential for <provider>: log in to <provider> or set queryModel`, or `The query model <provider>/<id> failed: <errorMessage>` for a call that does not end with the stop reason `stop`.

`subagent` calls in one message run one after another, in message order, so a `wait` after a `send` waits for the answer to that message. A round with a `subagent` call runs all of its tool calls in order, `bash` and `read` included.

The CLI runs `spawn`, `status`, `rename`, `send`, `wait`, `stop`, `list` and `query` as calls of the same tool, and `todo` as a call of the runner of the todo tool (see [Todos](#todos)). There are two other adapters of the `subagent` tool:

- In Pi, the extension `@vzlentin/pi-agents` gives the tool (see [Pi extension](#pi-extension)). The caller is the session ID, the same as `PI_SESSION_ID` for the CLI, so `harness list` in that session shows the tool's children. When the session runs a pi virtual model, its model, which a spawn inherits, is the physical model of its latest response since its latest model change (see [Pi extension](#pi-extension)).
- In another pi-durable host, the entry `@vzlentin/harness/durable-entry` gives the tool. The caller is `<store>:<conversation ID>`, where `<store>` is a random ID that the store keeps. A call that runs again after the host restarts uses the same key, so its spawn or send does not repeat. Such a host gets the answers only with `wait`: it opens no `answers` request.

The children get the tool too. Their caller is their conversation ID, as for their bash commands.

The `todo` tool keeps a list of todos (see [Todos](#todos)). It takes one `action` and its arguments: `add` with `text`, `set` with `id`, `state` and an optional `text`, and `list`. The list is the caller's own: the host agent has its own list, as any agent. The text result is the whole list after the call: the line of each todo, or `No todos`, for each action. The host adds todos to the list by itself, such as the todo `Save to the vault`, so the line of one todo would hide them; `harness todo` prints the line of the todo for `add` and `set`. The structured result is `{ action, value }`, where `value` is the reply of the host: the todo `{ id, text, state }` for `add` and `set`, and `{ todos }` for `list`. The description of the tool also tells when to keep a list, in this sentence after its first line: `Use it for each task of 3 steps or more: add one todo for each step before you start, set a todo to doing when you start its step, and to done when the step is finished.` The tool declares the schema of this result. The host gives the tool to the host agent and to each child, also at the depth limit. The call runs in the host process, as a call of the `subagent` tool does, and its caller is the conversation ID, so the list is the list of that conversation. A call that a host restart interrupts does not run again. It ends with `Tool todo was interrupted and may have partially run`, so an `add` is never made twice, and `list` shows whether it was made. The entry `@vzlentin/harness/durable-entry` does not give the tool. In Pi, the extension `@vzlentin/pi-agents` gives the tool too, with the session ID as the caller (see [Pi extension](#pi-extension)).

## Tools bridge

In the host and in interactive Pi, a cell of the IPython kernel of a conversation or of a session has `tools`: the tools of that conversation, as coroutines, as a `codemode` script has them (see [Tools bridge in Pi](#tools-bridge-in-pi) for Pi). The client is `python/harness_tools.py` of `@vzlentin/harness`. It uses the standard library only, and needs Python 3.9 or later. It has no copy of a tool schema: the text of the tools comes from the server.

- `await tools.<name>(**args)` runs the tool `<name>` of the conversation of the cell with `args`, as the cell gives them, `None` included. The bridge adds no argument and has no default of its own: a `tools.subagent(action="spawn", ...)` without `notify` sends the answer of the child as a message, as a spawn of the model does (see [Push](#push)), and `notify=False` turns it off. The tool checks the arguments against its schema.
- A call gives the structured output of the tool when the tool declares a schema for it, else the text of its output. A success of a tool with a schema that gives no structured output raises with `Tool <name> gave no structured output`.
- A refused or failed call raises `ToolError`, a `RuntimeError`, with the error text: the text of the schema check, such as `Validation failed for tool "subagent": ...`, `Tool <name> is not available` for a tool that the conversation does not have, or the error of the tool. The error of the tool is the text of its output, else the text of its error diagnostics, else `Tool <name> failed`. A result that the tool marks as an error always raises, also when it has a structured output. `from harness_tools import ToolError` gives the class.
- `print(tools.__doc__)` gives the use of `tools`, then the line `- <name>: <first line of the description>` for each tool that a cell can call. `print(tools.<name>.__doc__)` gives the description of the tool and the JSON Schema of its arguments. Each read asks the server for the list.
- A cell cannot call `ipython`: the kernel is busy with the cell, so the call would never start. The list does not have it, and a call fails with `A cell cannot run ipython: its kernel is busy with the cell`.
- A cell cannot call the internal tools of pi-durable's code mode, whose names start with `pi.codemode.`, such as `pi.codemode.models.classify`, nor a deferred tool, which a tool search must load. Code mode leaves them out of the tools that it lists to a script. The list does not have them, and a call fails with `Tool <name> is not available`, as for a tool that the conversation does not have.
- Each call opens its own connection, so `asyncio.gather` of several calls runs them at the same time. A cancelled call closes its connection, which stops the request in the server. In Pi, this also aborts the tool call. In the host, the tool call continues until it ends or its cell ends: the host cannot abort a nested call before its cell ends.

A call runs as a nested call of the `ipython` call of its cell, as a call of a `codemode` script runs inside the script. It runs only while its cell runs. A call while no cell of its kernel runs, such as a call from a thread after its cell returned, fails with `No cell of this kernel runs: tools runs a tool only while a cell runs`. When a cell ends, its calls that still run stop and fail with `The cell ended: tools runs a tool only while a cell runs`. A kernel runs one cell at a time, so a call goes to the oldest open cell of its kernel.

The host listens on three events of pi-ipython on the event bus of its entries:

- `ipython:cell-start` with `{ conversationId, api, context }`, before a cell runs. The host opens the cell. A call of the cell runs as `api.executeTool(name, args, context)`, so pi-durable checks the arguments against the schema of the tool, runs the `beforeTool` hooks on it, such as the gate of the projects entry, and aborts the call when the cell ends, not before. A tool with a schema keeps no text of its output, so its error is the text of its error diagnostics. The tools of the list are the `callable` tools of the agent of the conversation, read at each request. The host serves each conversation that has the `ipython` tool, a leaf too: a leaf has no `subagent` tool, so `tools.subagent` there fails with `Tool subagent is not available`, and its other tools run.
- `ipython:cell-end` with `{ conversationId }`, after the cell ends, also when it fails. The event does not name the cell, so the host ends the oldest open cell of the conversation. A cell that ends before an older cell of the same conversation would end the wrong cell. pi-ipython runs the cells of a kernel one at a time, so this does not occur.
- `ipython:kernel-starting` with `{ conversationId, env, startupCode, waitFor }`, before each kernel start, restarts included. On the first cell of a conversation, it comes after `ipython:cell-start`. In a promise that it gives to `waitFor`, the host starts a server for that kernel start.

A payload of another shape gives a warning, and does nothing else: `The ipython:cell-start event has an invalid payload; its cell gets no tools`, `The ipython:cell-end event has an invalid payload; its cell keeps its tools` or `The ipython:kernel-starting event has an invalid payload; its kernel gets no tools`. The server of a kernel start:

- The server is a Unix socket, `kernel.sock`, in a new directory `/tmp/harness-tools-<random>` with mode 0700. The short path keeps the socket under the 104-byte limit of macOS.
- It has a random secret token.
- The host sets `HARNESS_TOOLS_SOCKET` and `HARNESS_TOOLS_TOKEN` in the `env` of the payload, never in its own environment. The client reads them at each call.
- The host adds the startup code: it puts the folder of the client first on `sys.path`, then binds `tools`.
- A new kernel start of the same conversation replaces its server. The old server stops its requests, and the host removes its directory.
- When the server cannot start, the kernel start fails. A kernel start after the kernel servers close, while the host closes, fails with `The host is closing`: the host keeps its listener until the entries close.
- When the host closes, it stops the requests of each kernel server with `The host is closing`, before the entries close. It then closes the servers and removes their directories.
- A request line on a kernel socket that is longer than 16 MiB before its newline gets the reply `{ ok: false, error: "Invalid tools request: the line is longer than 16 MiB" }`, and runs nothing. The server then ends the connection, and reads and ignores the data that follows. This bound is for the transport only: it stops a line that has no end. The client sends the line as UTF-8 JSON, with each character as it is, so a character counts its UTF-8 bytes. The JSON escapes count in the line, such as `\n`, `\"` and a lone surrogate, which goes as its escape.

Each connection carries one request, one JSON line, of one of two shapes. `{ token, name, args }` runs the tool `name` with the object `args`. `{ token, list: true }` asks for the tools that a cell can call, as a list of `{ name, description, parameters }`. A line has only the fields of its shape. The server replies with one line, `{ ok: true, value }` or `{ ok: false, error }`, then ends the connection. A line that is not JSON or does not have the token of the server fails with `Invalid tools token` and runs nothing. A line of another shape fails with `Invalid tools request: <path> <message>`, the first error of the shape that it names: the list shape when it has `list`, else the call shape. Examples are `Invalid tools request: /name must be string`, and `Invalid tools request: /args schema is false` for a list line with `args`.

The calls of a cell are not replayed. The `ipython` tool of pi-ipython is not replay-safe, so a host restart does not run a cell again: its call ends with `Tool ipython was interrupted and may have partially run`, and pi-durable abandons the nested calls of the bridge that did not end. A call that ended before the restart keeps its effect, such as a spawned child, and does not run again. The bridge gives no key, so the nested calls of a cell take the keys `1`, `2` and so on, in the order that the cell makes them.

No system prompt has a section about `tools`. The last line of the description of the `subagent` tool names `tools`, `print(tools.__doc__)` and `print(tools.<name>.__doc__)` (see [Tool](#tool)). A leaf has no `subagent` tool, so no text tells its model about `tools`, but its kernel has them.

### Tools bridge in Pi

In interactive Pi, the extension `@vzlentin/pi-agents` (see [Pi extension](#pi-extension)) serves the bridge to the IPython kernel of the session, with the client, the servers and the startup code of the host. The kernel runs in Pi, and the calls of a cell run in Pi, as nested calls of the call of the cell.

- The extension listens on `pi.events`, from the start of the session to its end. In Pi, pi-ipython emits `ipython:kernel-starting` with `{ env, startupCode, waitFor }`, without `conversationId`, `ipython:cell-start` with `{ toolCallId, ctx }`, where `ctx` is the tool context of the call of the cell, and `ipython:cell-end` with `{ toolCallId }`. A payload of another shape shows its warning, the text of the host, as a notification, and does nothing else.
- In a promise that it gives to `waitFor`, the extension starts a server for that kernel start, as the host does: a Unix socket `kernel.sock` in a new directory `/tmp/harness-tools-<random>`, with a random secret token. It sets `HARNESS_TOOLS_SOCKET` and `HARNESS_TOOLS_TOKEN` in the `env` of the payload, never in the environment of Pi, and adds the startup code. A new kernel start, such as a restart, replaces the server: the old server stops its requests, and the extension removes its directory. When the server cannot start, the kernel start fails.
- A call of a cell runs as `ctx.executeTool(name, args, { signal })`, so Pi checks the arguments against the schema of the tool and runs the hooks of the session on it. The signal aborts when the request stops: when the cell cancels the call, or the cell ends. Its value is the `structuredContent` of the result when the tool declares an `outputSchema`, else the text of its content. A result with `isError` raises with its text, else `Tool <name> failed`: Pi keeps no diagnostics of a nested call. The tools of the list are `ctx.tools`. `ipython:cell-end` ends the cell of its `toolCallId`, and aborts the signal of its calls that still run.
- The `subagent` tool of the session sends its requests to the host. So `tools.subagent` gives the children of the session, the subagents widget and `/subagent` show them, and a child spawned without `notify: false` sends its answer to the session as a message.
- At the session end, the extension stops the requests of the server with `The host is closing`, closes the server and removes its directory. A later request of the kernel cannot reach a server, because its socket is gone. The children of the session end 30 s later, unless the session opens its `answers` request again (see [Pi extension](#pi-extension)).

## Pi extension

The Pi extension is the npm package `@vzlentin/pi-agents`, from the `pi/` folder of this repository: the `subagent` tool, the `/subagent` command, the subagents widget, the messages with the answers of the children and the answers of the user to the asks of the session, the `todo` tool, `/todo`, the todo widget, `/vc`, the mirror sessions (see [Mirror sessions](#mirror-sessions)), the tools bridge in the IPython kernels of the session (see [Tools bridge in Pi](#tools-bridge-in-pi)), and the `subagent` skill, `pi/skills/subagent/SKILL.md`, which tells the agent how to use the tool and the `harness` CLI. The `pi` manifest of the package lists the extension and the `skills/` folder. `/subagent` lists the children of the session, with the lines of `list`, and opens the one that you select in Pi, in a new herdr-app tab (see `openChildTab`); outside an hc terminal (`HC_TERMINAL_ID` is not set), it shows `Run in another terminal: harness attach <handle>`. When the tab does not open, it shows `Could not open a herdr-app tab: <reason>. Run in another terminal: harness attach <handle>`. The extension has the same version as harness. It has no copy of harness: `@vzlentin/harness` at that version is a dependency of `@vzlentin/pi-agents`, and the extension loads its `dist/` modules, so it starts the host of that install. It resolves each module from its own folder, as `@vzlentin/harness/<name>`, with the `exports` of the package. These `exports` give the public modules of the package, and only them: `answers`, `bridge`, `checkpoint`, `children`, `classifier-answers`, `client`, `degraded`, `doc-family`, `durable-entry`, `entries`, `entry-api` (the types of the entry API, `src/host/entries.ts`), `herdr`, `host`, `hosts`, `inspect`, `label-checks`, `lock`, `mirror`, `model-choice`, `overlay`, `passes`, `protocol`, `respond`, `store-watch`, `tasks`, `todo`, `tool`, `trust` and `view-state`, and `package.json`. When Pi loads the extension, it also puts the `.bin` folder of the `node_modules` folder that holds `@vzlentin/harness` last on the `PATH` of Pi's process, so the agents find `harness`. It goes last because the folder also holds the commands of other dependencies, such as an older `pi`, which must not hide the user's own. It first removes that folder from `PATH`, so each load leaves it there once. When one of the `dist/` modules does not load, such as in a checkout without `npm run build`, Pi shows that the extension failed to load.

The model and the thinking level that a spawn of the `subagent` tool inherits from the session, when its arguments and the settings give none (see [Tool](#tool)), are the session's own or, when the session runs a pi virtual model (`api` `pi-virtual`), the physical model and the thinking level of the latest response that the branch of the session records after its latest model change; a failed or aborted response does not count, as it can name the virtual model, and a response without a thinking level leaves the selected one. A response before the latest model change answered on the model that the session left. A virtual model names no physical model the host could run, so a session that recorded no such response inherits no model: the host picks `subagentModel`, and the spawn fails with the errors of [Tool](#tool) when no setting gives one.

With a UI, the subagents widget below the editor shows a dim header line `subagents`, then one line with the children of the session, `<name or handle>:<state>`, five at most, then `+<n>` for the others; it reads them every second and does not start the host. A busy child is in the warning colour, an idle child in the success colour and a child in error in the error colour. The widget leaves out the ended children. Without children that are not ended, or when no host runs (see [Host](#host): it exits after 5 idle minutes), the widget is hidden. When the host fails the request, it shows only `subagents: <first line of the error>` in the error colour, with no header.

The `todo` tool of the extension has the parameters, the description, the text result and the structured result of the `todo` tool of the host (see [Tool](#tool)), the whole list after each call, and runs the runner of the `todo` tool of the host, `runAgentTodoTool` of `@vzlentin/harness/tool`, on the caller's own list. The call goes to the host with `sendToHost`, so it starts the host when none runs. The caller is the session ID, so the list is the list of the session, which the host keeps under the session ID (see the `todo` request in [Host](#host)). `harness todo` in the bash of the session has the session ID in `PI_SESSION_ID`, so it gives the same list. Each call opens its own connection, so calls at the same time could reach the host out of order: a round with a `todo` call runs all of its tool calls in order, as for the `subagent` tool, so the todos of one message get their IDs in message order.

`/todo <text>` adds a todo to the list of the session, through the same runner and with the session ID as the caller. It starts the host when none runs, then refreshes the todo widget at once. With a UI, it notifies the line of the todo. `/todo` without text asks `New todo`; a cancel, or an answer that is empty or has only white space, adds nothing and shows nothing. The text loses the white space at its ends. Without a UI, the command prints the line of the todo, or `Usage: /todo <text>` on stderr without text. In a mirror session, the todo widget shows the list of the mirrored agent, not the list of the session, so `/todo` adds nothing and shows the error `harness: /todo does not work in a mirror session`. An error is the notification `harness: <error>`, or that line on stderr with no UI.

`/vc`, and its shortcut `ctrl+shift+y`, open the visual copy of the transcript, only in Pi's interactive mode; in another mode, it shows `/vc requires interactive mode`. The shortcut keeps the text of the editor, which a typed `/vc` replaces. The view selects the blocks of the agent messages (a paragraph, a list item, a code block, a quote, a table, a Mermaid diagram) and the images of the tool results. `j`/`k` move by block, `{`/`}` by message, `v` and `V` select a range or a message, `/` and `?` search, `n`/`N` go to the next and the previous match, `w` selects the inline code, `y` copies and `Y` copies the raw Markdown, Esc leaves the range, then the view, and `q` leaves the view. A single code block gives its code without the fences, a single quote its text without the markers, a diagram an image of it (`Y` its source) and an image the image (`Y` its file path). Images and diagrams go on the clipboard with `osascript` on macOS, with `wl-copy` or `xclip` on Linux, and with Windows PowerShell on Windows and WSL; the text copy uses Pi's clipboard. A copy shows `Copied <n> lines: <first line>`, `Copied image`, `Copied path: <path>` or `Copied diagram image (<size>)`, and a copy that fails shows `Copy failed: <error>`.

With a UI, the todo widget above the editor shows the list of the agent of the session while that list has an open or a doing todo: a dim header line `todos <done>/<total>`, such as `todos 3/10`, then one line for each open and doing todo, in ID order, as `harness todo list` prints it. The total counts the open, doing and done todos, not the dropped ones. The done and dropped todos do not show. The widget has at most 10 lines: with more than 9 open and doing todos, it shows the first 8, then a dim `+<n> more`. Each line starts with one space, and a line wider than the terminal is cut at its width with `…`. Otherwise the widget is hidden. In a session that is not a mirror session, the agent is the session itself. Its list has no watch, so the widget reads it as the subagents widget reads the children: every second, without starting the host, so it is hidden when no host runs. It also reads it at once after each `todo` call of the session and each `/todo` addition, before the call or command ends. When the host fails the request, it shows only `todos: <first line of the error>` in the error colour, with no header. The extension sets each of the two widgets one time at the session start, as a component, also in a mirror session: Pi moves a widget that is set again to the end of its side. A change of the lines draws the component again, and a hidden widget draws no line. So of these two widgets, only the todo widget is above the editor, and the subagents widget stays below it. A mirror session also has its status area above the editor, below the todo widget (see [Mirror sessions](#mirror-sessions)). Pi draws these components only in its interactive mode: an RPC client does not get the widgets. A `todo` request with the action `list` does not keep the host running (see [Host](#host)). In a mirror session, the widget shows the list of the mirrored agent (see [Mirror sessions](#mirror-sessions)).

Each Pi session keeps one `answers` request open to the host, on a connection of its own, with the session ID as the caller (see [Push](#push)). For each delivery, Pi shows a custom message with the same text as the input of a push to a conversation of the host, and the delivery as its details: of the type `subagent-answer` for the answers of a child, `user-answer` for the answers of the user to asks of the session, and `entry-delivery` for a delivery of an entry, whose text is the text of the delivery. The message starts a turn, as a follow-up when Pi works. At the session start, with or without a UI, the extension opens the request. It starts the host only when the session has a result of the `subagent` tool or of the `parley` tool, so a session that spawned children or asked the user gets the answers that came while Pi was closed. When the host closes the connection, the extension connects again at once, after 2 s and after 5 s, then every 5 s until a try connects. When no host runs at the session start, it tries every 5 s. When a connection closes less than 10 s after it opened, the next try is after 5 s. Only the first try at the session start can start a host. A caller that opened an `answers` request is a Pi session for the host, which keeps it in the document `subagent.sessions` of the store. When a session has no open `answers` connection for 30 s, the session ends: the host ends its children and the children they spawned, as a `stop` does, and keeps the unread answers of its own children, which the session gets when it opens an `answers` request again. A busy child gives `<handle> was aborted`. No child runs again until a `send` resumes it. `/reload` opens the request again within the 30 s, so it keeps the children; a quit, and Pi's `new`, `resume` and `fork`, close it, so the children of the old session end. A host that starts gives each saved session 30 s from its start: a session whose request does not come back in that time ends. A host that closes ends no session. `cli`, and a caller that never opened an `answers` request, keep their children. When Pi fails to show an answer, the extension shows the error as a notification, `Could not show an answer: <error>`, and the next answers still come. At the session end, it closes the connection.

### Mirror sessions

A mirror session is a Pi session that shows a child or the agent of a host (see [Host agent](#host-agent)) in Pi's own chat, and sends what you type to it. The agent runs in the host, so it continues when Pi closes. Below, the agent is the child or the host agent that the session shows. The mirror sessions work only in Pi's interactive mode. In another mode, a session with a `harness-mirror` entry, or a Pi with one of the `--harness` flags, fails at the session start with `harness: a mirror session works only in Pi's interactive mode`, and Pi's own agent does not take its input.

- `/harness <host>` opens a new Pi session that mirrors the agent of `<host>`, which is `main` or a host name. An unknown host is an error: `harness: Unknown harness host: <name>`. The command completes the host names. Without a host, it asks for one in the list `Harness host`, with one line `<name>  <dir>` for each host: the host of Pi's working directory first (as for a command), then the other hosts, then `main` with `~`. When `main` is the only host, it opens `main` and does not ask. Esc cancels.
- `pi --harness <host>` mirrors the agent of the host in the session that Pi starts with, `pi --harness <host> --harness-child <handle>` mirrors a child of the host, and `pi --harness <host> --harness-conversation <id>` mirrors a conversation of the children library (see [Open in Pi](#open-in-pi)). Both `--harness-child` and `--harness-conversation` is an error: `harness: use --harness-child or --harness-conversation, not both`. Without `--harness`, or with an empty host, the host is the one of `HARNESS_HOST` and Pi's working directory. It refuses a session with messages, such as one of `--continue`: `harness: --harness needs a new session, not one with messages`. A session that is already a mirror session keeps its target, and at the startup Pi shows `harness: the --harness flags are not used: the session is already a mirror session`.
- The session has the title of the agent as its name, `<name> (<handle>)`, `<key>` for a conversation, or `<host> agent`, and follows a rename. It holds one custom entry, `harness-mirror`, with the target `{ host, handle }`, or `{ host, conversation }` for a conversation, and Pi draws the conversation of the agent in place of that entry: the newest entries of the conversation when the session attaches, then each new entry, which it adds below the others. It uses Pi's message and tool components and Pi's theme (adapted from the attach view of [mavam/pi-agents](https://github.com/mavam/pi-agents)): the user messages, the typed inputs (`harness.typed`) among them, the answers with their thinking, and a Pi tool card for each call of `read`, `bash`, `edit` and `write`, with its output while it runs. Other tools get Pi's generic card. A compaction shows `[compaction]` and its summary, and a reset shows `[new context]`, where they occur in the conversation; the entries before them stay. The first line is `harness │ <title> │ <working directory>`. Pi saves a session only when it has a message, so it does not save a mirror session and `/resume` does not list it; run `/harness` again to open it.
- A message that you send goes to the agent: a new turn when it is idle, a steer when it works. Pi's own agent does not run. While the agent works, Esc aborts its turn, and the queued messages go back to the editor, steers first; Alt+Enter (`app.message.followUp`) queues the text as a follow-up. Before the connection opens and while the session connects again, Alt+Enter also sends the text as a follow-up, which waits for the connection. A conversation of the children library takes a message only while it works, always as a steer, also with Alt+Enter; when it is idle, the message goes back to the editor with `harness: not sent: <key> takes input only while it works`. The extension uses its own editor in the session for these keys.
- Above the editor, Pi's working indicator shows what the agent does (`Working...`, `Running <tool>...`, `Compacting (<reason>)...` or `Retrying (attempt <n>): <error>`), and each queued message shows as `Steer: <first line>` or `Follow-up: <first line>`.
- Above the editor, above the working indicator, the todo widget (see [Pi extension](#pi-extension)) shows the list of todos of the agent, from the view of the watch (`harness.todos` in its `docs`, see `host.sock` in [Host](#host)), while it has an open or a doing todo. Its lines follow each change of the view, and the widget is drawn again only when they change. It is set one time, before the status area of the session, so it stays above that area. It shows the list of the last view also while the session connects again and after it failed. It does not show the list of the local Pi session. It goes away when the session ends.
- The answers of the agent follow Pi's `hideThinkingBlock` setting: Ctrl+T (`app.thinking.toggle`) hides and shows their thinking, as for Pi's own messages.
- The last line above the editor is `<title> • <usage> • <context>`, without the parts that are empty. The usage has the sums of the agent's model requests and tool results, as Pi's footer shows its own: `↑` input, `↓` output, `R` cache read, `W` cache write and `$` cost, each when it is not zero, and the cost also when Pi uses a subscription for the model, with `(sub)`. The context is `<percent>%/<window>`: the context of the last answer of the agent's active transcript (after its last compaction or reset) that did not abort or fail, against the context window of its model, when Pi knows the model. Pi's footer stays as it is, for the local Pi session: Pi's own footer, or the footer of an extension.
- Pi's model and thinking level follow the agent's. A model that you select in Pi (`/model`, Ctrl+P) and a thinking level (Shift+Tab) go to the agent with a `configure` request. A refused change gives an error, and Pi goes back to the agent's model. The model that Pi takes from the agent is not a request. When Pi does not take the agent's model, Pi shows an error: `harness: Pi has no login for <provider>/<model>` without a login for it, or the error of Pi. When the agent changes its model while Pi takes the previous one, Pi then takes the new one. A conversation of the children library refuses each change, without a request, with `harness: A conversation of the children library keeps its model and thinking level`.
- When the host closes the connection, the session connects again, which starts a new host when none runs. It shows `Connecting again to the harness host...` above the editor. It tries three times: at once, after 2 s, and after 5 s. When all tries fail, the session shows `The harness host closed the connection. Connecting again failed: <error>`. When the host closes a connection that was opened again less than 10 s before, the session does not connect again and shows `The harness host closed the connection. Run /reload to attach again`. When the child is stopped, the session stays open and shows the state `ended`; a message resumes the child. When the connection closes, each tool card that runs shows `Interrupted: no connection to the harness host`. `/reload` attaches again, and starts the host when none runs. `/new` and `/resume` leave the mirror session; the agent keeps running.
- A message that you send while the session connects waits for the connection. When the connection closes before the host answers a message, the message goes again on the next connection with the same request ID, so the agent gets it once. A message that does not reach the agent, because the host refuses it or the session fails first, goes back to the editor, after the text there, and Pi shows `harness: not sent: <reason>`. A message that went to the host on a connection that closed before the host answered, when the session then fails, may be with the agent: it does not go back to the editor, so that a send again does not give it twice. It stays in the history of the editor, and Pi shows `harness: maybe sent: <reason>. The text is in the history of the editor`.
- Images are not sent: the agent gets only the text, with the warning `harness: the images are not sent; the agent gets only the text`. Pi does not expand skill commands and prompt templates for the agent. Pi's own session commands act on the local Pi session, which has no messages: `/compact` fails with `Nothing to compact (session too small)`, `/fork` gives `No messages to fork from`, `/tree` shows `No entries found`, and `/export` fails with `Nothing to export yet - start a conversation first`.
