# harness reference

The behaviour of the `harness` CLI, the `subagent` tool, the Pi extension and the host. The [README](../README.md) has the install.

## Commands

Spawn with a descriptive name using the default model and thinking level (see [Tool](#tool)):

```sh
harness spawn --name review --prompt "Review the current diff independently"
```

Spawn prints `Spawned <name> (<handle>)` and `State: <state>`, the state of the child (see `status`): `busy` for a new child, and the current state when a spawn with the same key repeats. Names appear in the parent UI. Generated handles remain the stable identifiers used by management commands.

Override the model configuration when needed:

```sh
harness spawn \
  --provider openai-codex \
  --model gpt-5.4-mini \
  --thinking low \
  --prompt "Find the relevant implementation"
```

Provide multiple prompt fragments and files. The first message holds the text of each file, then `Task:` and the prompts:

```sh
harness spawn \
  --file /tmp/spec.md \
  --prompt "Implement this specification" \
  --prompt "Run the targeted tests"
```

Restrict tools with `--tools`, a comma-separated list. Without it, a child gets `read`, `grep`, `find`, `ls`, `write`, `edit`, `bash`, `subagent`, `todo`, `thread`, `rule`, `term`, `part`, `codemode`, and the tools of the host's entries (see [Limits](#limits)). A child at the depth limit gets no `subagent` and no `workflow`, but keeps `todo`, and its IPython kernel has no `rlm` (see [Push](#push)). An unknown tool name is an error:

```sh
harness spawn --tools read,bash --prompt "Investigate the failure"
```

Manage a run by its generated handle:

```sh
harness status a1b2c3
harness rename a1b2c3 "error handling review"
harness send a1b2c3 "Focus on error handling"
harness send a1b2c3 --follow-up "Then summarize"
harness wait a1b2c3
harness stop a1b2c3
harness list
harness attach a1b2c3
harness inspect a1b2c3
```

- `status` prints `<name> (<handle>): <state> (<provider>/<model>, <thinking>)`. The state is `busy`, `idle`, `error` when the last turn failed, or `closed` when the children library closed the child outside `stop`, such as a subagent under a workflow session whose run ended. After an abort from a mirror session, the state is `idle`. A closed child stays `closed`, also while its children hold it. A child that is not closed is also `busy` while one of its notify children holds it (see [Push](#push)), at any depth, so `status`, `list`, `wait`, the widget and a mirror session show it as `busy` until its subtree is quiet.
- `send` prints `Prompted`, `Steered`, or `Queued follow-up for`, then the child. A steer goes in after the current tool round. A follow-up starts after the current answer. The verb comes from the child's own turn: a child that only its children hold is `Prompted`.
- `wait` waits until the child answers its last message, up to `--timeout` seconds (default 1800), and prints `<handle> finished`, a blank line, and the answer. When the spawn or an earlier `send` has an answer that no `wait` gave, it prints `<n> unread answers, oldest first.`, a blank line, and each answer after a line `--- Answer <i> of <n> ---`, the last one last. An earlier turn that failed gives `(no answer: <error>)`. A steer shares the answer of the turn it went into, so that answer comes once. A failed or aborted last turn is an error: after an abort, it prints `<handle> was aborted`. The error gives the earlier unread answers in the same form, and does not give the failed turn twice. Each `wait` marks these answers read. A message sent while a `wait` runs stays unread for the next `wait`. Input from a mirror session is not counted. While its children hold the child, `wait` waits too, and when a push starts a turn of the child meanwhile, `wait` gives the answer of that turn. While a `wait` runs, the host pushes no answer of that child. A `wait` for a turn whose answer a push already gave prints `<handle> finished`, a blank line, and `No new answers: the last answer came as a message.`. A second `wait` without a push between still gives the last answer again. A `wait` for a closed child, or for a child that closes while the `wait` runs, fails with `The child <id> is closed`. When the host closes, a running `wait` fails with `The host is closing`.
- `stop` stops the work of the child and of the children it spawned, and removes them. A `spawn` that comes again with the request ID of a stopped child spawns a new child, with a new handle, and sends the prompt to it. A repeat of that `spawn` gives the new child.
- `list` prints one line per child of the current caller: `<name> (<handle>)  <state>  <provider>/<model>  <thinking>`. The line of an RLM child (see [RLM limits](#rlm-limits)) ends with `  rlm`.
- `attach` opens the child in Pi in this terminal, and `attach --conversation <id>` a conversation of the children library (see [Open in Pi](#open-in-pi)). Without an ID, or with more arguments, it prints the usage.
- `inspect` serves a web page that shows the child live and sends what you type to it (see [Inspect](#inspect)).

### Project agent

Each project has an agent, a conversation in its host that you talk to directly:

```sh
harness web
harness main
```

`harness <project>` opens the agent of the project in Pi in this terminal (see [Open in Pi](#open-in-pi)). It starts the host when none runs. A single word that is not `main`, a project or a command prints the usage. A `--project` before it is an error: `harness <project> takes no --project`.

- The agent works in the project directory, or in the home directory for `main`. Its system prompt, tools and bash env are the same as a child's in that directory (see [Host](#host)). Its bash commands get `PI_SESSION_ID`, the agent's conversation ID.
- When it is first opened, the agent gets Pi's default model (`defaultProvider` and `defaultModel` in Pi's `settings.json`) when it has a login, else the first model with a login, and Pi's `defaultThinkingLevel` (default `medium`), or the nearest level that the model has. Without a model with a login, Pi does not start and `harness <project>` prints `No model for the <project> agent: log in to a provider and set a default model in Pi (defaultProvider and defaultModel)`. A mirror session changes its model and thinking level as for a child.
- The children that the agent spawns have the agent as their parent: `harness list` with `PI_SESSION_ID` set to the agent's conversation ID shows them. The agent gets the answers of these children as input (see [Push](#push)). Its own state ignores its children.
- Esc stops only the agent's turn. The children that it spawned keep running.
- The agent keeps its conversation across host restarts. `status`, `send`, `wait`, `rename`, `stop` and `list` do not know the agent: it is not a subagent, and it cannot be stopped.
- Before each `input` request to the handle `agent`, the host catches the agent up. It keeps what the agent has seen in a `harness.seen` document of the agent's conversation, version 2: `{ mainSha, catchups, hooks, entry? }`, the head of the default branch, the count of catch-up entries, what each catch-up hook of the entries said the agent saw, by hook kind, and the catch-up entry that is not written yet. A version 1 document loses its `lastTaskId` and `pending`, and its hooks start with nothing seen. The catch-ups of the agent run one at a time. A repeated input, whose request ID the conversation already has, gets no catch-up. The host then reads, in the project directory, read only:
  - The default branch: the target of `refs/remotes/origin/HEAD` without `origin/`, else `main`, and its local head `refs/heads/<branch>`. Outside a Git repository, or without that branch, there are no commits and no warning. With a head in `mainSha`, the commits are those of `git log <mainSha>..<head>`, newest first. When the head does not contain `mainSha` (`git merge-base --is-ancestor` fails), as after a force-push, a change of `origin/HEAD`, or a `mainSha` that the repository no longer has, there are no commits, the entry tells it, and `mainSha` becomes the head, with no warning. When Git fails, the host writes a warning and keeps `mainSha`.
  - The catch-up hooks of the entries, in load order (see the entries below). The host calls `run(harness, seen)` of each hook with the host's harness and the `seen` that the hook returned at the last catch-up, or `undefined` the first time. The hook returns `{ seen, lines, data? }`: the `seen` to keep in `hooks[<kind>]`, the lines for the agent, none when nothing is new, and the data of these lines. A hook that throws or returns another shape gives the warning `catch-up: <kind>: <message>` and keeps its last `seen`, and the catch-up goes on.
  - The first time, with no `harness.seen` yet, the host only records the current state, and adds no entry. When nothing is new, it adds no entry.
  - Else it records the new state with `catchups + 1` and the planned entry in one commit, then adds one passive entry of the kind `harness.catchup` before the input, with the request ID `catchup:<catchups + 1>`, then removes the planned entry from the document. A catch-up first writes a planned entry that an earlier catch-up left, such as after a crash or a failed write; its request ID makes a repeat add nothing. The entry is a user message with the line `Catch-up since your last input.`, then the lines of each hook, then the branch name and each new commit as `<short sha> <subject>`, then a line when the branch no longer contains `mainSha`. Its `data` is `{ commits?, reset?, hooks? }` with the same facts: `commits` is `{ branch, commits: [{ sha, subject }] }`, `reset` is `{ branch, from, head }`, the old and the new head, and `hooks` has the `data` of each hook that gave lines, by hook kind. A missing field is left out.
  - A failure of the catch-up is a warning: the input always goes through.

### Projects

Each project has its own host, store and children. A project is a name and a directory:

```sh
harness create web --cwd ~/Dev/web
harness projects
```

- `create <name> --cwd <dir>` prints `Created <name> (<dir>)`, where `<dir>` is the real path of the directory. A relative `--cwd` is relative to the current directory. The name has 1 to 32 characters: `a-z` first, then `a-z`, `0-9` or `-`. It cannot be `main` or a command name; `addProject` of `@vzlentin/harness/projects` refuses these names too, with `A project cannot have the name <name>`, and `COMMAND_NAMES` gives the command names. A name that exists, and a directory that does not exist, are errors.
- `projects` prints `<name>  <dir>` for each project, in creation order, then `main`.
- `--version` prints the version of the package. It takes no argument and no `--project`.

The projects are in `$XDG_CONFIG_HOME/harness/projects.json` (default `~/.config/harness/projects.json`), an object of name to directory. A command that reads the file fails when a name does not follow the rule of `create` or a directory is not an absolute path.

A command goes to the project of `--project <name>`, which must come before the command (`harness --project carrefour list`), then of `HARNESS_PROJECT`, then of the current directory: the project with the longest directory that is the current directory or contains it. Without a match, the project is `main`, which has no directory. When two projects have the same directory, the first one created wins. An unknown project name is an error: `Unknown harness project: <name>`. The tool finds its project in the same way, from `HARNESS_PROJECT` and the current directory of their process. `connect` and `request` of `@vzlentin/harness/client` take a `project` option; without it, the project comes from `HARNESS_PROJECT` and the current directory. The CLI passes `--project` in this option and does not set `HARNESS_PROJECT`, so the Pi of `harness attach` and a host that the CLI starts do not get it.

The caller is `PI_SESSION_ID`, or `cli` when it is not set. `list` shows only the caller's children. The CLI and the tool refuse to `send` to, `rename`, or `stop` a child of another caller. A mirror session does not check the caller, because the host socket is for one user: it can show, send to, and abort the child of any caller. It sends text with an `input` request, stops a turn with an `abort` request, and changes the model or the thinking level with a `configure` request. None of these requests has a caller.

`openChildTab` of `@vzlentin/harness/herdr` opens a child in Pi in a new herdr-app tab, in the space of the hc terminal of the caller. It reads the labels of that terminal with `hc get --json <HC_TERMINAL_ID>`, then runs `hc run --bg --keep --no-parent --cwd <cwd> [--name <name>] --label herdr.space=<space> -- <command>`, in the child's working directory. herdr-app shows a terminal with a `herdr.space` label in that space, in a new tab, and does not move the focus. The command is `[env XDG_STATE_HOME=<state> XDG_CONFIG_HOME=<config>] <node> <cli> --project <project> attach <handle>`, where `<cli>` is `dist/cli.js` of the install, or `src/cli.ts` of a checkout: `harness attach` with this Node and this install's CLI, so it does not need `harness` on `PATH`, on the project of the caller. hc gives the program the environment of the hc server, so `env` gives it each of `XDG_STATE_HOME` and `XDG_CONFIG_HOME` that is set for the caller; without both, there is no `env`. The name is `<name>` of the child (or its handle) in lowercase, with `-` in place of each character other than `a-z`, `0-9`, `-` and `_`, without the characters before the first letter or digit, and cut to 32 characters. When nothing is left, or when the name has the shape of an hc terminal ID (`t`, a digit from 1 to 9, then digits and the letters of `bcdfghjkmnpqrstvwxyz`, such as `t7`), there is no `--name`. Before `hc run`, it rejects with `Not in an hc terminal: HC_TERMINAL_ID is not set`, with `hc get gave no labels: <output>`, or with `The hc terminal <id> has no herdr.space label` when the label is missing or empty. When an `hc` call fails, it rejects with the stderr of `hc`, or with the reason that the call failed; when a live terminal has the name, that is the `name_taken` error of hc.

`openConversationPane` of `@vzlentin/harness/herdr` opens a children library conversation in Pi in herdr-app, in the conversation's working directory. It takes the conversation as a `ChildInfo`, a place, and the environment. For a conversation, `ChildInfo` gives the same ID in `handle` and in `conversation`. It runs `hc run` as `openChildTab` does, with the name from `<key>` and the command `[env ...] <node> <cli> --project <project> attach --conversation <id>`, on the project of the caller. With `{ space }`, the terminal gets `--label herdr.space=<space>`, and it does not read the labels of the caller: herdr-app opens a new tab in that space. With `{}`, the terminal gets the `herdr.space` label of the caller: a new tab in the space of the caller. With `{ side: true }`, the terminal gets the `herdr.space` and the `herdr.tab` labels of the caller: herdr-app splits the last pane of the tab of the caller to the right. Without `space`, it rejects before `hc run` as `openChildTab` does, also with `The hc terminal <id> has no herdr.tab label` for `{ side: true }`. When an `hc` call fails, it rejects with the stderr of `hc`, or with the reason that the call failed.

### Todos

Each agent and each run keeps a list of todos (see the `todo` request in [Host](#host)):

```sh
harness todo add Move the config to vite.config.ts
harness todo set 1 doing
harness todo
harness todo --project-list add "Archive librlm and pi-rlm"
harness todo list --handle a1b2c3
harness todo sort
```

- `harness todo [list | add <text> | set <id> <state> [--text <text>] | sort]` sends one `todo` request, or for `sort` one `classify-todos` request. Without a word, the action is `list`. The options can come before or after the words.
- `add` adds a todo with the words after it, joined with a space, as `send` does with its message. `set` sets the state of the todo `<id>` to `open`, `doing`, `done` or `dropped`, and its text to the `--text` value when it is given.
- Without a target option, the list is the list of the caller, `PI_SESSION_ID` or `cli` (see [Projects](#projects)). One target option gives another list: `--handle <handle>` the list of a child, or of the project agent with `agent`; `--conversation <id>` the list of a conversation that the children library opened; `--task <key>` the list of the task of a `start`; `--project-list` the list of the project, which is the list of the project agent, the same as `--handle agent`.
- `add` and `set` print the line of the todo. `list` prints the line of each todo, in ID order, or `No todos` for an empty list. A line is `<mark> <id> <text>`, with the mark of the state: `○` open, `◉` doing, `✓` done, `✗` dropped. A text with a line break prints as it is.
- The command refuses a state that is not one of the four with `Invalid todo state: <state>`, an ID that is not an integer from 1 with `Invalid todo id: <id>`, an unknown option with `Unknown todo argument: <option>`, and an empty `add` text with `add requires text`, before it sends the request. The other errors come from the host, such as `The text of a todo is empty` and `Unknown todo: <id>` (see [Host](#host)). An unknown word, more words than the action takes, `add` or `set` without its words, `--text` without `set`, two `--text` options and two target options print the usage.
- The command runs as a call of `runTodoTool(args, scope, target)` of `@vzlentin/harness/tool`, the runner of the todo tool. `args` are the parameters of the tool without `list`, `{ action, text?, id?, state? }`. `target` is the list, as the `todo` request takes it (`ListTarget` of `@vzlentin/harness/protocol`): `{ handle }`, `{ conversation }`, `{ key }`, or `{}` for the list of the caller. The command gives the target of its target option, and `--project-list` gives `{ handle: "agent" }`. The `todo` tool gives `todoToolTarget(args)` of `@vzlentin/harness/tool`: `{ handle: "agent" }` for `list: "project"`, and `{}` without `list`. The runner refuses an `add` without `text`, or a `set` without `id` or `state`, with `<action> requires <argument>`. Its result is the text that the command prints, and `{ action, value }`, where `value` is the reply of the host: the todo for `add` and `set`, and `{ todos }` for `list`. The `todo` tool of the host runs the same runner (see [Tool](#tool)).
- `sort` asks the classifier of the todos about the open todos of a list (see `classify-todos` in [Host](#host)). Without a target option, the list is the list of the project; a target option gives another list, as for the other actions. It prints one line for each answer, in ID order, as `<id>  needs you: yes|no  repeats: <id>|none`, or `No open todos` when the list has none. The errors come from the host, such as `No classifier: log in to <provider> or set todoClassifier`.

### Tree

`harness tree [--json]` sends one `tree` request (see [Host](#host)), and starts the host when none runs:

```sh
harness tree
harness tree --json
```

- It prints one line for each node, parents first: two spaces for each level, then `<mark> <name>  <state>  <n> open`, where `<n>` counts the todos of the node in the state `open`. The mark is `◉` for `busy` and `running`, `○` for `idle` and `pending`, `✓` for `closed` and `completed`, and `✗` for `error`, `failed` and `aborted`.
- `--json` prints the reply, `{ nodes }`, as one JSON line. Another argument prints the usage.

## Open in Pi

`harness attach <handle>` opens a child in Pi in the current terminal, `harness attach --conversation <id>` opens a conversation that the children library opened, such as a child of a task, and `harness <project>` opens the agent of the project. They start the host when none runs, and check the target before Pi starts: an unknown handle is an error, `Unknown subagent: <handle>`, an unknown conversation or a root is an error, `Unknown conversation: <id>`, and so is a project agent without a model. Then they run `pi --harness <project>` for the project agent, `pi --harness <project> --harness-child <handle>` for a child, or `pi --harness <project> --harness-conversation <id>` for a conversation, which opens a mirror session (see [Mirror sessions](#mirror-sessions)), and exit with the exit code of Pi. They run the `pi` of `PATH` without the `node_modules/.bin` folders; without one, the error is `pi is not on PATH. Install Pi to open the agent`. That Pi needs the extension of the package (see [Pi extension](#pi-extension)). Closing Pi never changes the child.

In every terminal, the mirror session reports the state of the agent to the terminal with the Program Status Protocol (OSC 7501), through Pi's `setProgramStatus`, with `app: "harness"`. It reports when it starts and at each change of the state or of the message. While the session connects again to the host, the state is `blocked`, with the message `<title> (connecting again)`. On an open connection, a busy agent is `working`, an agent whose last request failed is `error`, and an idle agent after a turn is `done`, with the title as the message, until its next turn. An aborted turn also ends in `done`. `done` stays while the session connects again: an idle agent on the connection that opens again is `done`. An error, a closed agent and a connection that failed end `done`. All other cases are `idle`: an idle agent before its first turn in the session, a closed agent, the connection before the first one opens, and a connection that failed. The message is the title of the agent (the name or the handle of a child, `<key>` for a conversation, `<project> agent` for the project agent). Before the first connection, a child has its handle and a conversation its ID. A rename changes the title. For `error`, the message is the first line of the `errorMessage` of the last assistant message with `stopReason: "error"`, trimmed, or `Error` when there is none. When a dialog of Pi ends (`ui_prompt_end`), Pi writes its own state, so the session reports its state one more time, also when it did not change. When Pi leaves the mirror session, it reports `idle` with the title one more time.

## Inspect

`harness inspect` serves a web page that shows a conversation of a host live, as a mirror session does in Pi (see [Mirror sessions](#mirror-sessions)), and sends what you type to it:

```sh
harness inspect a1b2c3
harness inspect --conversation 42
harness --project web inspect --tailscale
```

- `harness inspect [<handle> | --conversation <id>] [--port <n>] [--host <ip> | --tailscale]` listens on port 7501, or on a free port with `--port 0`. It prints one URL for each address that it listens on, `http://<address>:<port>/`, with the target in the query: `?project=<project>&handle=<handle>` for a child, `?project=<project>&conversation=<id>` for a conversation, and `?project=<project>` for the handle `agent` and for `--project <name>` without a target. The project is the project of the command (see [Projects](#projects)). Without a target and without `--project`, the URL has no query, and the page shows the picker. The command runs until SIGINT or SIGTERM, then closes its connections.
- It listens on `127.0.0.1` only. `--host <ip>` listens on that address only, so it listens on `0.0.0.0` only with `--host 0.0.0.0`. `--host` takes an IP address or `localhost`, because the routes refuse another name in the `Host` header (see below); another host is an error: `The host must be an IP address or localhost: <host>`. `--tailscale` listens on `127.0.0.1` and on each IPv4 address that `tailscale ip -4` gives, on the same port. Both `--host` and `--tailscale` is an error: `Use --host or --tailscale, not both`. When `tailscale ip -4` fails, the error is `tailscale ip -4 failed: <stderr>`, and without an IPv4 address in its output, `tailscale ip -4 gave no IPv4 address`. `--port` takes an integer from 0 to 65535; another value is an error, `--port must be an integer from 0 to 65535`. An unknown option is an error, `Unknown inspect argument: <option>`, and two targets print the usage.
- With `project` in its query, the page shows the target: the project agent, the child of `handle`, or the conversation of `conversation`. Without `project`, it shows the picker: each project, then `main`, with its directory, and the project agent and the children of each running host, each with a link that has its title, as in a mirror session, then its state and its model as in the header. A project whose host does not run has only a link to its agent, `agent`, and opening it starts the host. A running host without a target to show has the line `the host runs, with no target to show`.
- The header has the title of the agent, as in a mirror session, its model and thinking level, and `rlm` for an RLM child, as `<provider>/<model> • <thinking> • rlm`, its state (`busy`, `idle`, `error` or `closed`), and the connection (`connecting`, `open`, `reconnecting`, or `failed: <reason>`). The title of the page is `<title> · harness inspect`.
- The transcript has the user messages, the answers with their thinking, folded, each tool call with its arguments and its result, folded, with an error result in the error colour, the output of a running tool, the passive notes, catch-ups and digests, `[compaction]` with its summary, and `[new context]`.
- The footer has what the agent does, as Pi's working indicator says it, each queued message as `Steer: <first line>` or `Follow-up: <first line>`, and the usage: `↑` input, `↓` output, `R` cache read, `W` cache write and `$` cost, each when it is not zero, then `ctx <tokens>`, the context of the last answer of the active transcript. The page knows no context window, so it shows no percent. Below is a message box. While the agent is idle, `Send` starts a new turn. While it works, `Steer` and `Follow-up` queue the message, and `Stop` aborts the turn. Enter sends, Shift+Enter adds a line, Alt+Enter queues a follow-up while the agent works, and Esc stops the turn while the agent works. On the page of `harness inspect`, Esc works wherever the focus is. On a page that mounts only the view, Esc works while the focus is in the view, such as after a click in the transcript. A conversation of the children library takes a message only while it works, always as a steer: it has no `Follow-up`, and the box is off while it is idle. A message that the server refuses stays in the box, with `not sent: <error>`.
- The page puts all text in as text, never as HTML, so the output of an agent cannot run in it.

`@vzlentin/harness/inspect` gives the routes, so that another server, such as `workflows web`, can serve them on its own port. A server that mounts the handler also serves the pages of `harness page` (see [Pages](#pages)). `createInspectHandler({ start? })` gives a handler `(req, res) => Promise<boolean>`, which is false for a request that is not one of these routes. `startInspectServer({ hosts?, port?, start? })` serves the page at `/` and the routes, with one server for each address of `hosts` (default `127.0.0.1`), all on one port (default 7501, or the free port of the first address for 0), and gives `{ urls, close() }`. It refuses a host that is not an IP address or `localhost` before it listens, with `The host must be an IP address or localhost: <host>`. `close()` also closes the open connections. `resolveBindHosts({ host?, tailscale? })` gives the addresses of the CLI options, and refuses such a `host` with the same error. The routes are:

- `GET /assets/inspect.js` and `GET /assets/inspect.css`: the browser files, from the `web/` folder of the package, with no other dependency. `inspect.js` exports `mountInspect(container, { project, handle?, conversation? }, { onTitle? })`, which shows the target in `container` and gives `{ interrupt(), close() }`, and `mountPage(container)`, the page of `/`, which gives `{ close() }`. `onTitle(title)` runs each time that the title of the agent changes. `interrupt()` stops the turn while the agent works and gives true; otherwise it does nothing and gives false. The view listens to its keys on its own root, and a click in the transcript gives the focus to the view. `mountPage` also listens to Esc on the document, and gives to `interrupt()` each Esc that the view did not take. Each rule of `inspect.css` selects only elements with a class that starts with `inspect`, or elements below `.inspect` (the view), `.inspect-picker` (the picker) or `.inspect-page` (the page of `/`), so the view does not change the page that mounts it.
- `GET /api/inspect/projects`: `{ projects: [{ name, dir }, ..., { name: "main" }] }`, in creation order.
- `GET /api/inspect/targets?project=<name>`: `{ project, running, targets }`. `running` tells whether the host of the project runs. `targets` has the info of the project agent, then the children of the caller of the server process, in that host, each with `title`, its title as in a mirror session. The caller is `PI_SESSION_ID`, or `cli`, as for `harness list`. When that host does not run, `running` is false, `targets` is empty, and the route does not start the host. The agent is not in `targets` when its watch fails, such as without a model.
- `GET /api/inspect/stream?project=<name>[&handle=<handle> | &conversation=<id>]`: Server-Sent Events (`text/event-stream`) from a mirror of the target. Each event is one `data:` line with a frame `{ status, title, child, view, summary }`: the status of the mirror, the title of the agent (its handle or conversation ID before the first connection), its info, its whole conversation view, and `{ statusText, queued, usageTotals, lastAnswerUsage }`. `child`, `view` and `summary` are not there before the first connection, and `lastAnswerUsage` is not there before an answer. One frame comes at once, then one after each change. When the client reads more slowly than the frames come, only the newest frame waits. When the mirror fails, such as for an unknown child, the last frame has `status: { kind: "failed", reason }`, the stream ends, and the page does not connect again. When the client closes the connection, the mirror closes.
- `POST /api/inspect/input` with `{ project, handle?, conversation?, message, followUp? }` sends an `input` request with a new request ID, and `POST /api/inspect/abort` with `{ project, handle?, conversation? }` sends an `abort` request. Each replies `{ ok: true }`.
- `GET /pages/<slug>/<file>`: the files of a page of `harness page`, with the script of the Send in an HTML file whose query has a target (see [Pages](#pages)).
- Without `handle` and `conversation`, the target is the project agent, as with the handle `agent`. A stream, an input and an abort start the host of the project when none runs. With `start: false`, they do not: an input and an abort then fail with `The harness host of <project> is not running`.
- A request that is not valid gets 400 with `{ error }`: a query or a body that does not match, such as `Invalid query: must have required properties project`, `Give handle or conversation, not both`, `The message is empty`, `Unknown harness project: <name>`, a POST that is not `application/json` (`The body must be application/json`), and a body that is not JSON (`The body is not JSON`) or is longer than 1 MiB (`The body is longer than 1 MiB`). An error of the host gets 500 with `{ error }`, such as `<key> takes input only while it works`. Another path under `/api/inspect/` gets 404.
- Each route under `/api/inspect/` and `/pages/` gets 403 when the `Host` header is not an IP address or `localhost`, so that the DNS name of another site that points at the server (DNS rebinding) cannot reach the routes. This refuses a Tailscale MagicDNS name too: use the address. The routes have no login: each client that reaches the address can read and steer the agents of the user. `127.0.0.1` keeps them on this machine, and `--tailscale` on the tailnet.

### Pages

`harness page` copies an HTML page, such as the classic page of a parley, to the pages of the inspect routes, and prints its link. The Send of the page posts its answer line to an agent, which takes it as a message:

```sh
harness page /tmp/parley-demo --slug demo
harness page /tmp/parley-demo --slug demo a1b2c3 --tailscale
```

- `harness page <folder> --slug <slug> [<handle> | --conversation <id>] [--port <n>] [--host <ip> | --tailscale]` copies the page to `$XDG_STATE_HOME/harness/pages/<slug>/` (default `~/.local/state/harness/pages/<slug>/`). The slug is lowercase words of letters and digits, joined with hyphens, as the parley skill gives it. The copy has the regular files at the top level of `<folder>` whose names do not start with `.`. It skips folders and symbolic links. It replaces the earlier copy of the slug. A copy that fails, such as for a file that it cannot read, keeps the earlier copy of the slug.
- The Send posts to the target of the arguments. Without a target, the command sends a `whoami` request with the caller `PI_SESSION_ID` to the host of the project (see `host.sock` in [Host](#host)): a child gets its own handle, and the project agent gets `agent`. The command does not start the host.
- It prints one link for each address, as `harness inspect` does: `http://<address>:<port>/pages/<slug>/` with the query of the target, `?project=<project>&handle=<handle>`, `?project=<project>&conversation=<id>`, or `?project=<project>` for the project agent. The addresses come from `--host` and `--tailscale` as for `harness inspect`, and the port is 7501 without `--port`. The command starts no server. It tries a TCP connection to each address for 1 s, and when nothing listens there, the line ends with `  (no server listens: harness inspect serves the pages)`. Each server that mounts the inspect routes serves the pages, such as `harness inspect` on the same port.
- These errors stop the command with code 1 before the copy, so the earlier copy stays: the usage for a missing folder or `--slug`, two targets or an extra word; `Unknown page argument: <option>`; `The slug must be lowercase words with hyphens: <slug>`; `No index.html in <folder>` when `<folder>/index.html` is not a regular file; `Give <handle> or --conversation <id>: PI_SESSION_ID is not set`; `The harness host of <project> is not running`; the error of `whoami`, such as for a Pi session or a conversation of a workflow; and, as for `harness inspect`, the errors of `--port`, of a `--host` that is not an IP address or `localhost` (`The host must be an IP address or localhost: <host>`), of both `--host` and `--tailscale`, and of `tailscale ip -4`.
- `GET /pages/<slug>/<file>` serves the file of the copy, and `GET /pages/<slug>/` serves `index.html`. The content type comes from the extension: `.html` `text/html; charset=utf-8`, `.svg` `image/svg+xml`, `.css` `text/css; charset=utf-8`, `.js` `text/javascript; charset=utf-8`, `.png` `image/png`, `.json` `application/json; charset=utf-8`, and `application/octet-stream` for another file. Each reply has `cache-control: no-cache`.
- An HTML file whose query has `project`, `handle` or `conversation` gets one script before its first `</head>`, in any case. A file without `</head>` goes as it is. The query takes the target as the stream route does, so `?project=<project>` alone is the project agent. The script defines `window.sendPrompt(text)`, which the Send button of an artifacts page calls. It posts `{ project, handle, message }` or `{ project, conversation, message }` to `POST /api/inspect/input`, so an idle child or project agent starts a turn with the message. At its first call, it adds one line to the body of the page, at the top centre, in a 16px font. A call with the same text as the last post that succeeded posts nothing and sets the line to `already sent ✓`. Another call adds a layer that covers the page, dims it by 8% and blocks clicks, sets the line to `sending…` and posts. A call while a post runs does nothing. When both the post and a 400 ms delay end, the layer goes and the line shows `sent ✓`, or `not sent: <reason>`, where the reason is the `error` of the reply, its HTTP status, or the error of the request. A failed post does not change the last text that succeeded. The script itself is ASCII. The target goes into the script as JSON with each `<` escaped, so a target cannot end the script. Another file, and an HTML file with no target in its query, go as their bytes.
- The route gives 404 with `{ error: "Not found: <method> <path>" }` for a method that is not GET, a path that is not `/pages/<slug>/<file>`, a slug that is not valid, a file name that does not percent-decode, a decoded file name with `/` or `..` or a leading `.`, and a file that does not exist or that is a folder. An HTML file with a query that is not valid gets 400 with `{ error }`, as the stream route does, such as `Unknown harness project: <name>` or `Give handle or conversation, not both`.

## Host

The children of a project run in one host process, `harness --project <name> host` (default `main`). The host takes its project only from `--project`, not from `HARNESS_PROJECT`. The first command that needs it starts it in the background, and tries to connect for 10 s. A started host that exits with code 0 found the lock held by another host, such as one that closes after its idle time: the command then starts a host again, at most once per second. A started host that exits in another way fails the command at once with `The harness host exited with <code N or signal S>; see <host.log>`. When the started host still runs after 10 s, the command fails with `The harness host (pid <pid>) is still starting: it can wait up to 60 s for the lock of durable.sqlite. Run the command again soon; see <host.log>`; otherwise with `Could not start the harness host; see <host.log>`. It exits after 5 minutes with no connection, no running work, and no command other than `list`, `status`, `answers`, `tree`, `watch-tree`, `watch-project`, `classify-todos`, a `todo`, `person`, `rule`, `term` or `part` request with the action `list`, and a `thread` request with the action `list` or `read`. A connection with an open `answers` request does not count. An open mirror session, an open `watch-tree` and an open `watch-project` are connections, and a live started task is running work, so each keeps the host running. A task that no loaded entry can run, such as one of an entry that was removed, is not running work, and neither is a task that waits only on such tasks. The host waits up to 60 s for the lock of `durable.sqlite`, so a client that reads the file, such as the workflows CLI, does not make it fail. The wait is synchronous: while it lasts, the host answers no request. When the host closes, it stops listening, stops each running request, such as a `wait` or an `answers` request, which then fails with `The host is closing`, and waits until the replies of all requests are written. A request that comes while the host closes fails with `The host is closing` and does not run. The host then closes the connections.

The host keeps its state in `$XDG_STATE_HOME/harness/<project>/` (default `~/.local/state/harness/<project>/`):

- `durable.sqlite`: the children's conversations and records, the started tasks, the lists of todos, the store of the project (persons, threads and their messages, rules, terms, parts and held actions), and the project agent, which is the store's root conversation. Work that a host stop interrupts continues when the host starts again. A host refuses a `durable.sqlite` from a version before the children library: stop the old host, remove the file and run the command again. A host opens a `durable.sqlite` from an older version with the children library, and keeps its children and their records.
- `lock.sqlite`: one host at a time.
- `host.sock`: the socket the CLI and the extension connect to. The protocol has version 21. A `spawn` request has `provider` and `model` only when the spawn itself gives them, and the caller's own model in `callerProvider` and `callerModel`, next to its level in `callerThinking`; the host picks the model and the level (see [Tool](#tool)). A `whoami` request `{ caller }` replies `{ handle }`: `agent` when the caller is the conversation ID of the project agent, and the handle of the child whose conversation ID it is. Another caller, such as a Pi session, `cli` or a conversation of a task, fails with `The caller <caller> is not a child or the project agent of this host`. `harness page` sends it (see [Pages](#pages)). The `spawn` and `send` requests have `notify`, a boolean: false turns off the push of the answers of that request (see [Push](#push)). An `answers` request `{ caller }` waits until the host pushes answers to `caller` (see [Push](#push)), and replies with them, `[{ handle, name?, text, failed }]`. A newer `answers` request of the same caller replaces the older one, which then fails with `A newer answers request of the same caller replaced this one`. It needs a connection of its own, because the replies of a connection come in request order. The `watch` reply is `{ view, child }`. Each event of a watch is `{ change, child }` after a commit to the conversation, `{ change: {}, child }` after a rename, or `{ stopped: true }`, which comes after the events of the commits before the stop and one event with the whole view, `{ view }`. A change gives the parts of the view that the commit changed, as whole values, so a client needs no chord: `entries` is `{ from, items }`, the entries from index `from` on; `docs` has each document that changed, by kind, and `null` for a document that was removed; `conversation` is the conversation record. After a watch that fell behind, the change is `{ view }`, the whole view. When the conversation has a list of todos (see the `todo` request below), the `docs` of the reply and of each `{ view }` have it, under `harness.todos`. Each change of the list, the first `add` included, gives one event `{ change: { docs: { "harness.todos": <list> } }, child }`, with the whole list. A watch that fell behind gives only the newest list. A `configure` request `{ handle, provider?, model?, thinking? }` replies with the child, and refuses an unknown model and a thinking level that the model does not have. It takes no `conversation`. After a `watch` reply, each event of the watch is a `{ "event": ... }` line, and every other line is a reply, in request order. The host checks each request line against the schema of its type. Extra keys are allowed. A line of an unknown type fails with `Unknown request: <type>`, and a line without a string `type` with `Invalid request`. A line that does not match the schema of its type fails with `Invalid <type> request: <field> is required` for a missing field, `<field> is not allowed` for a key that the type refuses, and `<field> is not valid` for a wrong value: for example, a `spawn` needs a `cwd` that is not empty, and its `thinking` is one of pi-ai's `MODEL_THINKING_LEVELS`, as is the `thinking` of `configure`. When a line from the host is not valid, the client cannot match it to its request: it ends the connection, and rejects each waiting request with `The harness host sent an invalid reply: <line>`. A client refuses a host with another version, and the host refuses the `hello` of a client with another version, with the same message. When the host is older, stop it with `kill <pid>` and run the command again. When the client is older, reload Pi with `/reload`, or use the CLI of the host's install. The `watch`, `input`, `note`, `abort`, `configure` and `todo` requests take the handle `agent` for the project agent; its info is a child with the handle `agent` and the name `<project> agent`, and its watch never sends `stopped`. Other requests refuse it as an unknown subagent. The info of an RLM child (see [RLM limits](#rlm-limits)) has `kind: "rlm"` in each reply and watch event that gives it, such as those of `spawn`, `send`, `status`, `rename`, `list` and `watch`. The info of another child, of the project agent and of a `{ conversation }` target has no `kind`. The `watch`, `input`, `note` and `abort` requests also take `{ conversation }` in place of `{ handle }`: the ID of a conversation that the children library opened, of any owner, such as a child of a task. A request with both keys fails with `Invalid <type> request: conversation is not allowed`. Its info has `handle` and `conversation` set to the ID, and the child's key as `name`, so its title and its label are `<key>`. A closed conversation is `closed`, and its watch never sends `stopped`. It takes `input` only while it works, always as a steer, so the reply verb is `Steered`; an idle conversation refuses it with `<key> takes input only while it works`. A root, an unknown ID, or text that is not an ID gives `Unknown conversation: <id>`. The info of a conversation without a model fails with `The conversation <id> has no model`, and without a working directory with `The conversation <id> has no working directory`. A `note` request `{ requestId, text, kind?, data? }` with a handle or `{ conversation }` adds a passive user message `text` to the conversation's transcript, as an entry of the kind `kind` (default `harness.note`) with `data`. It starts no turn: an idle conversation places it at once, and the model reads it with the next input; a busy one places it at its next boundary, so the model reads it on its next request. An abort keeps a note that was placed. Its request ID is in the scope `note:`, apart from the IDs of `input`, and a repeated ID, also after a host restart, adds nothing. A kind that starts with `pi.` fails with `Invalid note request: kind is not valid`. The reply is `{ child }`, with no verb. A closed child fails with `The child <id> is closed`, and an unknown handle with `Unknown subagent: <handle>`. When the close comes while the note is admitted, the note stays in the transcript of the closed child, which never runs again, and the request still fails. A `send` in that case fails the same way, and its input is aborted. A conversation takes a note while it is idle or busy; a closed one fails with `The conversation <id> is closed`.
- `host.log`: the host's output.

The host reads Pi's settings as a Pi session in the project directory (the home directory for `main`) reads them: the settings and packages of the project's `.pi/settings.json` count only when the project is trusted, with the saved trust (see the project skills below). They give the project agent its default model, and the packages of the entries. The host loads two kinds of entries when it starts. First, the `piDurable` entries of the packages in Pi's settings, such as pi-ipython: a package lists its entry modules in its `package.json`, as `{ "piDurable": { "extensions": ["./durable/index.ts"] } }`. Second, the entries in `$XDG_CONFIG_HOME/harness/entries.json` (default `~/.config/harness/entries.json`), an object of entry name to the absolute path of a module, for packages that are not Pi packages, such as workflows. A package sets its entry there with `setEntry(name, module)` of `@vzlentin/harness/entries`, which is true when it changed the file. `setEntry` and `create` hold the lock file `<file>.lock`, with their process ID, while they change `entries.json` or `projects.json`, so processes that change the file at the same time keep each other's change. A lock with no process ID, or whose process does not run, is removed; after 5 s with a lock of a live process, they fail with `Could not lock <file>: another process holds <file>.lock. Remove it if no harness command runs`. A host that runs already loads a new or changed entry only after it starts again. Missing packages are skipped, not installed. An entry of `entries.json` whose module does not exist, such as one of an uninstalled package, is skipped with the warning `The entry <name> has no module at <path>; the host skips it`. A package whose `package.json` is not a JSON object, or has a `piDurable` field that is not valid, gives a warning and is skipped. Node does not strip types under `node_modules`, so the host loads a TypeScript entry there through jiti. It calls the default export of each entry with `{ durable, ai, events, children, place }`: the host's pi-durable and pi-ai modules, one event bus that all entries share (the host listens on it for the kernel starts of pi-ipython, see [RLM](#rlm)), the children library, and the host's `place` (store, models and tools) for `children.open`. The entries load before the host opens its store, so `place.store` is usable only once the host is open, which means inside tasks. An entry returns `{ extensions, tasks?, catchUp?, close }`. The host installs `extensions` and `tasks`, and refuses to start when two entries give a task with the same name. An entry that returns no `tasks` loads as before. `catchUp` is a catch-up hook of the project agent, `{ kind, run }`, with a `kind` that is not empty (see [Project agent](#project-agent)); the host refuses to start when two entries give a hook of the same kind, with `The entries <module> and <module> both give the catch-up hook <kind>`. An entry that returns another shape stops the host start with `The entry <module> returned an invalid result: <path> <message>`, such as `/extensions must be array`, and the entries loaded before it close.

A client starts and follows the tasks of the entries with four requests:

- `start { kind, input, key, version? }` creates a task of the kind `kind`, with the input `input`, and replies with its info `{ key, id, kind, version, status, outcome? }`. `version` is the version on the task's record: the version of the entry's task definition that last ran or migrated the task. It shows which version of the entry the host used for this task, not which version the host has loaded now. `outcome` is there only when the task is terminal. The key is the client's own name for the task. A repeated `start` with a known key gives the first task, and its new input is ignored. It refuses another kind with `The task <key> is a <kind> task, not <kind>`. An unknown kind gives `Unknown task kind: <kind>`. With `version`, a host whose loaded definition of the kind has another version creates nothing and gives `This host has version <n> of <kind>, not <version>: stop the host so it starts again with the installed version`, for a first and a repeated `start`. Before it creates the task, `start` sets up the project agent, so a child that the task opens without a model takes the agent's; when the agent has no model, the task still starts.
- `task { key }` replies with the info of the task.
- `wait-task { key }` waits until the task is terminal, and replies with its info, with the outcome. To follow the status during the run, poll `task`.
- `abort-task { key }` aborts the task and the work that it owns, such as the turns of its children, and replies with the info.

The other requests refuse a key that no `start` gave with `Unknown task: <key>`. The host keeps each key and its task in `durable.sqlite`, and no request removes a key, so the key map only grows. A started task is a background task of the root conversation, so an abort of the project agent (Esc in its mirror session) does not reach it. A task that a host stop interrupts continues when the host starts again. The children that tasks open are not in `list`, and neither is a subagent that the library closed outside `stop`, such as one under a workflow session whose run ended.

A todo is a line of intent with a state: `{ id, text, state }`, where `state` is `open`, `doing`, `done` or `dropped`. The host keeps lists of todos in `durable.sqlite`, in three places. Each conversation has one list, as its document `harness.todos`: the project agent, a child, or a conversation that the children library opened. Each task that `start` created has one list, keyed by its task ID: it is not a document of the task, so it stays after the task ends. Each caller that is not a conversation of the host, such as a Pi session or `cli`, has one list, keyed by the caller. A `todo` request `{ caller, action, ... }` reads or changes one list:

- `add { text }` adds a todo with the state `open` and the next ID of the list (1, 2, 3 and so on), and replies with the todo. The text stays as it is given.
- `set { id, state, text? }` sets the state of the todo `id`, and its text when `text` is given, and replies with the todo.
- `list` replies with `{ todos }`, in ID order. A list that was never changed is empty.

The list is the one of the target of the request: a handle, with `agent` for the project agent; `{ conversation }`, the ID of a conversation that the children library opened; `{ key }`, the key of a `start`; or, with none of them, the list of the caller. When the caller is the conversation ID of the project agent or of a conversation that the children library opened, such as a child of this host, the list of the caller is the list of that conversation, as for the parent of a `spawn`. The request does not check that the caller spawned the child of a handle, and it does not set up the project agent, so it works when the agent has no model. A `{ key }` target takes `add` and `set` also after the task ends, and a `{ conversation }` target also when the conversation is closed. A request with two targets fails with `Invalid todo request: <field> is not allowed`, where `<field>` is the second one in the order `handle`, `conversation`, `key`. A state that is not one of the four fails with `Invalid todo request: state is not valid`, and an `id` that is not an integer from 1 with `Invalid todo request: id is not valid`. A text that is empty or has only white space fails with `The text of a todo is empty`, an unknown ID with `Unknown todo: <id>`, an unknown handle with `Unknown subagent: <handle>`, a conversation that the children library did not open, the root included, with `Unknown conversation: <id>`, and an unknown key with `Unknown task: <key>`. A request that fails does not change the list. The `watch` of a conversation gives its list, and an event for each change of it (see `host.sock`). `harness todo` sends this request (see [Todos](#todos)).

`@vzlentin/harness/todo` gives the tasks of an entry the same lists and the same rules, with no socket: the schemas `Todo` and `TodoState` and their types, `TODO_STATES`, `TODO_MARKS` (the mark of each state in the line of a todo), `TODO_LIST_KIND` (`"harness.todos"`, the kind of the list of a conversation in the `docs` of a watched view), `TASK_TODO_LIST_KIND` (`"harness.task-todos"`, the kind of the lists of the started tasks), the schemas `TodoAnswer` and `ClassifyReply` of the reply of `classify-todos` and their types, the types `TodoList` and `TodoOwner` (`{ kind: "conversation", id }`, `{ kind: "task", id }` or `{ kind: "caller", caller }`), and six functions. `todoLine(todo)` gives the line of a todo as `harness todo` prints it, `<mark> <id> <text>` (see [Todos](#todos)), and `answerLine(answer)` the line of an answer as `harness todo sort` prints it. `addTodo(tx, owner, text)` and `setTodo(tx, owner, { id, state, text? })` change the list of `owner` in the commit `tx` of the caller, such as a commit of the runtime of a task, and give the todo. For an empty text or an unknown ID, they throw the error of the request, and a commit that does not catch it changes nothing. `readTodos(reader, owner, context)` gives the list from a reader such as the harness or the runtime of a task. `watchTodos(harness, id, context)` gives a chord watch of the list of the conversation `id`: its value is the list, or `null` while the conversation has none, and each stored commit that changes the list gives a call, the first `add` included. An abort of `context` or the close of the harness ends it. A task changes its own list with `{ kind: "task", id: runtime.taskId }`, also in the commit that makes it terminal.

A `classify-todos` request `{ list?, ids? }` asks a classifier model of Pi about the todos in the state `open` of a list, and stores nothing. `list` is `{ handle }`, with `agent` for the project agent, `{ conversation }` or `{ key }`, as for the `todo` request; without it, the list is the list of the project. `ids` are the IDs of the todos to ask about; without it, every open todo. A todo of `ids` that is not open gets no answer, and an ID that is not in the list fails with `Unknown todo: <id>`. The classifier is `todoClassifier` in Pi's settings, as `<provider>/<id>`, read again at each request, from the global settings and the settings of a trusted project; the default is `typesafe/jev-latest`. When its provider has no credential in Pi, or has no classifier model with that ID, the request fails with `No classifier: log in to <provider> or set todoClassifier`, before it reads the list, so a client keeps the order of the adds. Each todo gets one call of pi-ai's `classify`, with `{ todo: { id, text }, earlier }` as the state, where `earlier` are the todos with a lower ID, in any state, and two questions: `needsYou`, a bool, true when the todo needs a call that only the user can make, which counts as yes from a probability of 0.5; and, when `earlier` is not empty, `repeats`, a choice of `none` or the ID of one todo of `earlier` that it repeats. A call that does not end with the stop reason `stop` fails the request with `The classifier <provider>/<id> failed: <errorMessage>`. The reply is `{ answers: [{ id, needsYou, repeats? }] }`, in ID order, where `repeats` is the ID that the classifier chose, absent for `none`. `harness todo sort` sends it (see [Todos](#todos)).

The host keeps the store of the project in `durable.sqlite`: the persons that the user talks with, the threads of messages with them, the rules and the terms of the project, the parts of the vault that explain them, and the tool calls that the gate held (see the `gate` request below). Each list is one document of the session: `harness.persons`, `harness.threads`, `harness.rules`, `harness.terms`, `harness.parts` and `harness.held`. The state of each message out is in the document `harness.outbox`, because an entry cannot change. A person, a rule, a term, a part and a held action have the next ID of their list, 1, 2, 3 and so on. A thread is an ownerless conversation, and its ID is the ID of the conversation. A message is an entry of the kind `harness.message` in the conversation of its thread, with the message as its `data`, without its state, and no model message, and its ID is the ID of the entry. A thread is not a node of the tree. An author, `from` or `saidBy`, is the ID of a person or `"user"`. Every time is in epoch milliseconds. Each write, `message log`, `message mark`, `rule set`, `term set`, `part add` and `part check`, has a `caller`, as a `todo` request has: the conversation ID of a hosted agent, a Pi session ID, or another text. The host keeps it in `by` of the object that the write adds or changes. Each request has an `action`, and each reply of a list is in ID order:

- `person add { name }` adds a person `{ id, name }`, and replies with it. `person list` replies with `{ persons }`.
- `thread add { topic, persons }` adds a thread `{ id, topic, persons, last? }` with one or more persons, in a new conversation, and replies with it. `last` is the latest `at` of its messages, absent while it has none. `thread list` replies with `{ threads }`. `thread read { id }` replies with `{ thread, messages }`, the messages oldest first.
- `message log { caller, thread, from, direction, at?, text }` adds a message `{ id, thread, from, direction, state, at, text, by }` to the thread, and replies with it. `direction` is `in` or `out`. The host sets `state`: `received` for `in`, `draft` for `out`. `at` defaults to the time of the write. A message `in` from a person of the thread is a reply to each message out of the thread in the state `draft` or `sent` whose `at` is not later than its own: in the same commit, a draft becomes `sent`, and a sent message `answered`. One message moves each of them one step only. A pasted message that is older than the draft moves nothing.
- `message mark { caller, message, state }` sets the state of the message out `message`, and replies with it. `state` is `sent` (the user sent it, such as after a copy), `draft` (it was not sent after all) or `dropped`. A draft takes `sent` and `dropped`, and a sent message takes `draft`. Another mark fails with `Message <id> is <state>: it cannot become <state>`, and a mark of a message in with `Message <id> is a message in: only a message out has a mark`. The states of a message out are `draft`, `sent`, `answered` and `dropped`; `messageTransition(state, event)` of `@vzlentin/harness/protocol` gives the state after a mark or a reply, or `undefined`.
- `rule set { caller, saidBy, source, ... }` without `id` adds a rule `{ id, name, kind, value, status, saidBy, source, replaces?, at, by }` with `name`, `kind` (`conduct` or `domain`), `value`, and `status` (`open`, `decided` or `retired`, default `open`). With `replaces`, the rule that it replaces becomes `retired` in the same commit, with the `at` and the `by` of the write, and keeps its own `saidBy` and `source`. With `id`, it changes the rule `id`: its `name`, `kind`, `value` and `status` when they are given, and always its `saidBy`, `source` and `by`. A retire is a change to the status `retired`. `at` is the time of the last change. The reply is the rule. `rule list { kind?, status? }` replies with `{ rules }`, only those of the kind `kind` and of the status `status` when they are given.
- `term set { caller, saidBy, source, ... }` without `id` adds a term `{ id, name, meaning, avoid, saidBy, source, at, by }` with `name`, `meaning` and `avoid?`, the words not to use (default none). With `id`, it changes the `name`, `meaning` and `avoid` that are given, and always its `saidBy`, `source`, `at` and `by`. The reply is the term. `term list` replies with `{ terms }`.
- `part add { caller, kind, path, rules, terms }` adds a part `{ id, kind, path, rules, terms, checked, stale, by }` that explains the rules and the terms with these IDs, and replies with it. `kind` is `diagram`, `table`, `example` or `widget`, and `path` is its file in the vault. `checked` is the time of the write, and `stale` is false. `part check { caller, id }` sets `checked` to the time of the write, `stale` to false and `by` to the caller, and replies with the part. `part list { rule?, term? }` replies with `{ parts }`, only those that explain the rule `rule` or the term `term` when they are given.

A change of a rule or a term, also a retire or a replace, makes each part that lists its ID stale. A new rule or term makes no part stale. `source` is the ID of a message. A write without `caller`, and a `set` without `saidBy` or `source`, fails with `Invalid <type> request: <field> is required`. A rule `set` with `id` and `replaces` fails with `A change of a rule cannot replace a rule: set replaces on a new rule`. An unknown ID fails with `Unknown person: <id>`, `Unknown thread: <id>`, `Unknown message: <id>`, `Unknown rule: <id>`, `Unknown term: <id>` or `Unknown part: <id>`, for the persons of a thread, an author, a source, a rule that a new rule replaces, and the rules and the terms of a part too. An empty `name`, `topic`, `text`, `value`, `meaning` or `path`, or a thread with no person, fails with `Invalid <type> request: <field> is not valid`. A request that fails changes nothing.

A `watch-project` request `{}` replies with the whole store, `{ persons, rules, terms, threads, parts, held }`, each list in ID order. Each thread has `waits` too: its messages in the state `draft` or `sent`, oldest first. The other messages of a thread come from `thread read`. The host reads the store again after each commit that changes a person, a rule, a term, a thread, a message, the state of a message, a part or a held action, and compares it with what the client has. It then sends one `{ "event": { persons, rules, terms, threads, parts, held, removed } }` with the objects that are new or changed, and in `removed` the IDs of each kind of the objects that went. Every list is there, empty when nothing of its kind changed, because the persons, the rules, the terms, the parts and the held actions share the IDs 1, 2, 3. A read that changes nothing sends no event. The reads run one at a time, and the commits during a read give one more read and one more event. A read gets the messages only of the threads that are new or that got a message since the last read, and the states of the messages at each read. A slow client does not hold up the host: when a write must wait for the socket to drain, only that watch waits, and its next event has every object. A read that fails ends the connection, so the client opens a new watch. A request without a connection fails with `A project watch needs a connection`. `ProjectState`, `ProjectThread` and `ProjectEvent` of `@vzlentin/harness/protocol` are the TypeBox schemas of the reply, of a thread with its waits and of an event.

A `digest` request `{ caller }` replies with `{ text }`, the digest of `caller`, and records it in the document `harness.digests` as the last digest of the caller. The digest has two lines: `waiting on: ` and each message out of the project in the state `draft` or `sent`, as `<persons> (<topic>, sent <day> <month> <HH:MM>)` or `<persons> (<topic>, draft not sent)`, with the names of the persons of its thread and the time of its last change of state in UTC, such as `Sam (own-brand C+P, sent 12 Nov 14:22)`; then `held: ` and each held action of the caller in the state `held`, as `<id> <tool>: <reason>`. The items are joined with `·`, and an empty list is `none`. The reply is `{}` when the text is the text of the last digest of the caller, and when the caller never got a digest and has no item. The host gives each hosted agent its digest the same way, as a passive user entry of the kind `harness.digest` with `data` `{ waits, held }`, the IDs of the messages and of the held actions, before an `input` to it (after the catch-up of the project agent), a `send` to a child, and the first message of a spawned child. The entry has the request ID `digest:<count>:<hash>`, the count of digests of the caller and a hash of the text, and goes before the record, so a repeat after a crash adds nothing. A failure is the warning `digest: <message>` in `host.log`, and the input goes through. The digest is not a part of the catch-up: a catch-up comes only before an input to the project agent, and its hooks do not know the agent. The input of an approve, a push of answers and a conversation of a `durable-entry` host get no digest; the next input gives it.

A `gate` request `{ requestId, caller, tool, arguments, messages }` checks the tool call of the agent `caller`, the tool `tool` with the JSON object `arguments`, against the conduct rules of the project in the status `decided`. `messages` are the last messages of the user in the conversation of the caller, oldest first. The reply is `{ runs: true }`, or `{ runs: false, held }` with the held action. The command of a call is the `command` of a `bash` call, and `<tool> <arguments as JSON>` for another tool. The host goes through these steps, in order:

1. A call of `read`, `grep`, `find` or `ls`, or of the `list` or `read` action of `thread`, `rule`, `term` or `part`, runs, with no question.
2. When an approved action of the same caller, tool and command ran for no call, or for the call `requestId`, the call runs, and the action keeps `ran: { requestId, at }`. So an approved command runs one time, and the same call again, such as a hook after a host restart, runs again. The host finds the action and marks it in one commit, so of two calls of the command at the same time, one runs, and the other goes on to the next steps.
3. A held or dropped action of the same caller and `requestId` is the reply again, with no question.
4. With no decided conduct rule, the call runs.
5. Step 1 asks the classifier one bool question, `writes`, with the state `{ command }`: whether the command writes to a system outside this machine that other people see or use, or changes a decided rule. A probability of 0.5 or less runs the call.
6. Step 2 asks one choice question, `rule`, with the state `{ action, last_user_messages }`, the command and `messages`: which rule the action breaks most clearly. The choices are `none` and the ID of each decided conduct rule, as `<name>: <value>`. The domain rules are not choices. `none` runs the call. Another choice holds it.

The host holds a call as a held action `{ id, requestId, agent, tool, command, rule?, reason, state, at, by }`: `agent` is the caller, `command` is the command as it runs, `rule` is the ID of the rule that it breaks, and `reason` is `It breaks rule <id> <name>: <value>`. `state` is `held`, `approved` or `dropped`. `at` is the time of the last change, and `by` the caller of that change. When the classifier has no credential, has no model with that ID, fails, or gives no answer, the host holds the call with no `rule` and the error as the `reason`, such as `No classifier: log in to openrouter or set gateClassifier` or `The classifier <provider>/<id> failed: <errorMessage>`, so a call never runs unchecked. The classifier is `gateClassifier` in Pi's settings, as `<provider>/<id>`, read again at each request, as `todoClassifier` is; the default is `openrouter/typesafe/jev-1.14`. When the reply is `{ runs: true }` for a call that the gate checks (not a read), each draft that the command names as `draft:<id>`, such as in the shell comment `# draft:12`, becomes `sent`, with the caller as `by`. Another ID changes nothing, and a gate of the same call again finds the draft sent. A `held` request `{ action, caller, id }` with the action `approve` or `drop` sets the held action `id` to `approved` or `dropped`, with `by` the caller, and replies with it. An action that is not held fails with `Held action <id> is <state>, not held`, and an unknown ID with `Unknown held action: <id>`. An approve tells the agent of the action when it is a conversation of the host, with a follow-up input that starts a turn: `The user approved held action <id>: <command>. Call it again: it runs one time with no question.` A delivery that fails is a warning in `host.log`, and the action stays approved. A Pi session gets no input. `GateReply`, `HeldAction` and `HELD_STATES` of `@vzlentin/harness/protocol` are the schema of the reply, the schema of a held action and its states.

A `tree` request `{}` replies `{ nodes }` with the nodes of the project, each parent before its children, and the siblings in ID order. pi-durable takes the IDs of the tasks and the conversations from one counter, so ID order is creation order. A node is `{ id, parent?, kind, name, state, todos }`: `parent` is the `id` of the node above, absent for a root; `kind` is `agent` or `run`; `todos` is the whole list of the node (see the `todo` request), in ID order. The nodes are:

- The project agent: `id` `agent`, no parent, the name `<project> agent`, and the state `busy`, `idle` or `error` of its info. It needs no model.
- Each child by handle: `id` its handle, the name of the child or its handle, and the state that `status` gives. Its parent is the node of its caller: `agent`, the handle of a child, or `conversation:<id>` for a conversation of the children library. A child whose caller is not a conversation of the host, such as a Pi session or `cli`, is a root. A child whose caller is a conversation of the children library that is not in the tree is not in the tree either.
- Each task that `start` created: `id` `task:<key>`, `kind` `run`, no parent, and the name `<kind> <key>`.
- Each task in the root conversation of a kind that the entries give, whose owner task is in the tree, such as a child task of a started task: `id` `task:<task ID>`, `kind` `run`, the node of its owner as its parent, and the name `<kind> <task ID>`.
- Each conversation of the children library that a task of the tree owns: `id` `conversation:<id>`, the node of the task as its parent, the key of the conversation as its name, and the state `busy`, `idle`, `error` or `closed` of its info.

The kind of the other nodes is `agent`. The state of a `run` node comes from its task: `pending`; `running` for a task that runs, waits, sleeps or completes; and for a terminal task the status of its outcome, `completed`, `failed` (also for an orphaned or faulted task) or `aborted`. The list of a `run` node is the list of its task. A node that ended (a terminal task, or a closed child or conversation) is left out when its ID is lower than the ID of the 50th newest task that `start` created, and so are the nodes under it. With fewer than 50 started tasks, no node is left out. `harness tree` sends this request (see [Tree](#tree)).

A `watch-tree` request `{}` replies as `tree` does, then sends `{ "event": { nodes } }` with the nodes that are new or changed, in tree order, and `{ "event": { removed } }` with the IDs of the nodes that went, each only when it is not empty. The host builds the tree again after each commit that can change a node, and compares it with what the client has: a change of a list of todos, of the records of the children by handle, of the started tasks, of a conversation of the children library or of the last request of the project agent; any change of a submission; the start and the end of a run of a conversation; and a new task of a kind of the entries, or such a task whose node state changed. The builds run one at a time, and the commits during a build give one more. A slow client does not hold up the host: when a write must wait for the socket to drain, only that watch waits, and its next `nodes` event has every node. A build that fails ends the connection, so the client opens a new watch. A request without a connection fails with `A tree watch needs a connection`. `TreeNode`, `TreeReply` and `TreeEvent` of `@vzlentin/harness/protocol` are the TypeBox schemas of a node, of the reply and of an event.

A host from before the projects kept its state in `$XDG_STATE_HOME/harness/`. To keep its children, stop that host, then move `durable.sqlite` and its `-wal` and `-shm` files into `main/` before the `main` host starts.

A child's bash commands get `PI_SESSION_ID` (the child's conversation ID), `PI_PROVIDER`, `PI_MODEL`, `PI_REASONING_LEVEL`, and `HARNESS_PROJECT`, so a child can spawn its own children with its own model and thinking level when the subagent settings do not set them (see [Tool](#tool)), in the same project, down to the depth limit (see [Push](#push)). After a `configure`, the next commands get the new model and thinking level. In a project other than `main` whose directory has a `.optmem` folder, they also get `MEMORY_DIR`, the path of that folder. Otherwise they get no `MEMORY_DIR`, not even the host's own. The rule uses the project directory, not the child's working directory. Children survive `/reload` and the end of the parent Pi session. `harness stop` removes a child and the children it spawned permanently.

A child's system prompt has what a Pi session in the child's working directory gets: the `AGENTS.md` or `CLAUDE.md` of the agent directory and of the working directory and its parents, the skills, and the working directory. User skills always load. Project skills (`.pi/skills`, and `.agents/skills` in the working directory and its parents) load only for a trusted project: a directory without project resources, then the decision saved with `/trust`, then the `defaultProjectTrust` setting, where `ask` counts as not trusted. A trust decision that a Pi session made for itself without saving it does not reach its children; when the tool spawns in such a session, it adds `The child gets no project skills (.pi/skills, .agents/skills): this project is trusted for this Pi session only, and children see only the trust saved for future sessions. To give children project skills, run /trust and choose Trust.` to its output. The host checks the trust on every model request, so a decision saved later applies from the next request. The host reads the instructions and skills of a directory once per trust decision and keeps them until it exits. It skips packages that are not installed. When the instructions or skills of a directory fail to load, the child gets none for that request, the host writes a warning, and the next request tries again. A child that the children library opens with `overlay` in its spec, a map of path to content, sees that content in place of the disk. A relative path is relative to the child's working directory, lexically; without a working directory, a relative path makes `open` fail with `The overlay key <path> is relative, and the child has no working directory`. A string replaces the file, and `null` removes it. The overlay changes the instructions and the skills that Pi loaded, and the `read` tool, which gives `ENOENT` for a removed file. A `SKILL.md` path that is not on disk adds a skill. A skill whose content has no description is not loaded, as in Pi, and for a name that two skills use, the first one wins. An overlay adds no instructions file. The other tools see the disk. A child that is opened with a parent that has an overlay gets that overlay, at every depth, also through the `subagent` tool. The child's own paths win, compared after they are resolved, and its own skill comes first when two skills have the same name. A child without an overlay and without an overlaid parent saves no overlay. The overlay is set when the child is created: a second `open` of its key keeps the first one.

### Push

When a child finishes, the host sends its unread answers to its caller, so the caller does not need `wait`. A request of a `spawn` or `send` with `notify: false` is quiet: its answer is not pushed alone, and it does not hold the caller. A child is done when its own turn ended and none of its children has an unread notify request, at any depth: until then, it holds its caller. The host checks this after each commit that can end a turn or change a record of a child, at host start, at the end of a `wait` or a `send`, and when an `answers` request opens or its reply is written. For a done child, it takes the unread answers as `wait` gives them, marks them read, and delivers them:

- The text is the answers in the form of `wait`, without its first line `<handle> finished` and the blank line after it. When the last turn failed or was aborted, `failed` is true and the text is the error of `wait`, such as `<handle> failed: overloaded` or `<handle> was aborted`.
- A caller that is a conversation of the host (a child, the project agent, or another conversation of the children library, such as one of a workflow task) gets the input `subagent <name> (<handle>) finished` (`subagent <handle> finished` for a child without a name), or `failed` in place of `finished` when `failed` is true, a blank line and the text: a new turn when it is idle, a follow-up when it works. Its request ID is `push:<handle>:<read>`, so a push that runs again after a restart does not repeat. The input reaches the caller before the child stops holding it.
- Any other caller, such as a Pi session, gets the answers as the reply to its open `answers` request, oldest child first. These answers become read only once the reply is written to the socket. When the write fails, or the connection closes first, they stay unread, for a later `answers` request or a `wait`; a `wait` that runs meanwhile waits until the write ends. Without an open request, the answers stay unread too. When the host stops after it wrote the reply and before it marked the answers read, the next `answers` request gives them again.
- When a push of a child fails, such as a conversation that cannot be found or a caller that refuses the input, the host writes a warning and skips that child for 1 s, then for twice as long after each failure in a row, up to 60 s. A timer pushes again when the wait ends, also without a new commit. A push of the child that ends without an error resets the wait. While a child of a caller waits after a failed push, the later children of that caller wait too, so the answers keep their order.
- A turn that a mirror session started sends nothing up: when the last request is mirror input, the answer that goes up is the one of the caller's last request.

The depth of the subagent tree is the setting `agentDepthLimit` in Pi's global `settings.json`, an integer of at least 1, default 4. The host reads it again at each spawn, and it applies to the new trees: a child of a child keeps the limit of its tree. A deeper spawn fails with `Nested subagents are disabled`. A tree that a library caller of the children library starts without a limit, such as one of workflows, keeps the limit of 2, also for the spawns of the `subagent` tool in it. A library caller can open a child as a depth root (`depthRoot`): it stays under its tree parent, for close and the viewer, and starts a new depth budget at depth 0 with its own `limit`, such as a session that a script opens in code. With `depthParent`, a child takes the depth budget of that conversation in place of its tree parent's: one deeper, with its limit; a conversation that the library did not open counts as depth 0. A child at the limit of its depth budget is a leaf: it gets no `subagent` and no `workflow` tool, also when `--tools` names them, so a model call to `subagent` there gives `Tool subagent is not available`. Its IPython kernel has no `rlm` (see [RLM](#rlm)).

The default model and thinking level of a spawn are the settings `subagentModel` and `subagentThinkingLevel` in Pi's global `settings.json`. `subagentModel` is `<provider>/<model>`, split at the first `/`, as `subagentModel: "openai-codex/gpt-5.4-mini"`. `subagentThinkingLevel` is one of pi-ai's thinking levels. The host reads them again at each spawn, so a change applies to the next spawn without a restart. Each key works alone: a key that is missing or not valid, such as a model without `/`, counts as absent, and the caller's value applies. They apply to every spawn of the `subagent` tool, the CLI and `rlm`, at every depth. A model that the host does not know fails the spawn with `Unknown model: <provider>/<model>`. The children that a library opens, such as the roles of workflows, do not use them.

## Limits

- Children get only `read`, `grep`, `find`, `ls`, `write`, `edit`, `bash`, `subagent`, `todo`, `thread`, `rule`, `term`, `part`, `codemode`, and the tools of the host's entries (see [Host](#host)). They get no MCP tools and no Pi extensions. A child at the depth limit also gets no `subagent`, no `workflow` and no `rlm`, and keeps `todo`, `thread`, `rule`, `term` and `part` (see [Push](#push)). `codemode` runs JavaScript that calls the other tools of the child, as Pi's `codemode` does. A script that a host stop interrupts continues when the host starts again.
- A change to `AGENTS.md` or to a skill reaches children only after the host restarts.
- The children that `rlm` spawns have more limits: how many are live, the size of their requests, the time of a turn, the size of an answer, and the model requests of a tree at the same time (see [RLM limits](#rlm-limits)).
- `--file` gives text only; images are not attached.
- The CLI sends each `spawn` once and has no `key`. If the host stops during a `spawn` and you run the command again, there can be two children.

## Tool

The `subagent` tool does what the CLI does, with one `action` and its arguments:

| `action`         | Arguments                                                                                    |
| ---------------- | -------------------------------------------------------------------------------------------- |
| `spawn`          | `name`, `provider`, `model`, `thinking`, `cwd`, `tools`, `prompts`, `files`, `key`, `notify` |
| `send`           | `handle`, `message`, `followUp`, `key`, `notify`                                             |
| `wait`           | `handle`, `timeout` (seconds, default 1800)                                                  |
| `status`, `stop` | `handle`                                                                                     |
| `rename`         | `handle`, `name`                                                                             |
| `list`           | none                                                                                         |

`tools`, `prompts`, and `files` are arrays. A relative `cwd` or file path is relative to the caller's working directory. A caller without a working directory cannot spawn. The text result is the output of the same CLI command. The structured result is `{ action, value }`, and the tool declares its schema, where `value` is the host's reply: the child for `spawn`, `status`, and `rename`, `{ verb, child }` for `send`, `{ answer }` for `wait`, the children for `list`, and `{ handle, name }` for `stop`. A child is `{ handle, name, state, provider, model, thinking, cwd, kind }`, where `state` is `busy`, `idle`, `error` or `closed`, `cwd` is its working directory, and `kind` is `rlm` for an RLM child (see [RLM limits](#rlm-limits)) and absent for the other children.

A spawn without `provider` and `model` uses `subagentModel` in Pi's global `settings.json`, else the caller's model. A spawn with only one of `provider` and `model` takes the other from the caller, not from the setting. A spawn without `thinking` uses `subagentThinkingLevel`, else the caller's level, in both cases clamped to the nearest level that the model has. When no source gives a model, the spawn fails with `No provider specified and the caller has no model` or `No model specified and the caller has no model`. A spawn refuses a `thinking` that the model does not have with `<provider>/<model> has no thinking level <level>`. The CLI refuses a `--thinking` that is not one of pi-ai's levels with `Invalid thinking level: <level>`. The tool's parameter schema takes only pi-ai's levels, so Pi refuses another value before the call. On the socket, such a `thinking` fails with `Invalid spawn request: thinking is not valid`. A `spawn` or `send` that comes again with the same `key` finds the first one and does not repeat it. Without `key`, the call is the key. Each caller has its own keys. When the call is aborted, for example with Esc, a `wait` stops; the child continues.

When a child finishes, its answer comes to the caller as a message that starts a turn (see [Push](#push)). `notify: false` on a `spawn` or a `send` turns off the message for the turns of that call; the answers then come only with `wait`. The CLI has no flag for it. The tool description tells the model to use `wait` only when it needs the answer in the same turn. Its last line says that, with the `ipython` tool, the kernel also has `rlm`, a client for the same children, and that `print(rlm.__doc__)` prints its API and its limits (see [RLM](#rlm)).

`subagent` calls in one message run one after another, in message order, so a `wait` after a `send` waits for the answer to that message. A round with a `subagent` call runs all of its tool calls in order, `bash` and `read` included.

The CLI runs `spawn`, `status`, `rename`, `send`, `wait`, `stop` and `list` as calls of the same tool, and `todo` as a call of the runner of the todo tool (see [Todos](#todos)). There are three other adapters of the `subagent` tool:

- In Pi, the extension `@vzlentin/pi-agents` gives the tool (see [Pi extension](#pi-extension)). The caller is the session ID, the same as `PI_SESSION_ID` for the CLI, so `harness list` in that session shows the tool's children.
- In another pi-durable host, the entry `@vzlentin/harness/durable-entry` gives the tool. The caller is `<store>:<conversation ID>`, where `<store>` is a random ID that the store keeps. A call that runs again after the host restarts uses the same key, so its spawn or send does not repeat. Such a host gets the answers only with `wait`: it opens no `answers` request.
- In an IPython kernel of the host or of interactive Pi, `rlm` gives the actions of the tool as coroutines (see [RLM](#rlm)). The caller is the conversation of the kernel, or the Pi session, as for the tool of that conversation or session.

The children get the tool too. Their caller is their conversation ID, as for their bash commands.

The `todo` tool keeps a list of todos (see [Todos](#todos)). It takes one `action` and its arguments: `add` with `text`, `set` with `id`, `state` and an optional `text`, and `list`. Each action also takes `list: "project"`, for the list of the project, which is the list of the project agent. Without `list`, the list is the caller's own. The text result is the output of `harness todo` for the same call: the line of the todo for `add` and `set`, and the line of each todo, or `No todos`, for `list`. The structured result is `{ action, value }`, where `value` is the reply of the host: the todo `{ id, text, state }` for `add` and `set`, and `{ todos }` for `list`. The tool declares the schema of this result. The host gives the tool to the project agent and to each child, also at the depth limit. The call runs in the host process, as a call of the `subagent` tool does, and its caller is the conversation ID, so without `list` the list is the list of that conversation. A call that a host restart interrupts does not run again. It ends with `Tool todo was interrupted and may have partially run`, so an `add` is never made twice, and `list` shows whether it was made. The entry `@vzlentin/harness/durable-entry` does not give the tool. In Pi, the extension `@vzlentin/pi-agents` gives the tool too, with the session ID as the caller (see [Pi extension](#pi-extension)).

The `thread`, `rule`, `term` and `part` tools read and change the store of the project (see [Host](#host)). Each takes one `action` and its arguments, and sends the requests of that object:

| Tool     | `action` | Arguments                                                                                  |
| -------- | -------- | ------------------------------------------------------------------------------------------ |
| `thread` | `list`   | none                                                                                       |
| `thread` | `read`   | `thread`                                                                                   |
| `thread` | `log`    | `thread`, `from`, `text`, `at`                                                             |
| `thread` | `draft`  | `thread`, `text`                                                                           |
| `thread` | `mark`   | `message`, `state`                                                                         |
| `rule`   | `set`    | `saidBy`, `source`, and `name`, `kind`, `value`, `status`, `replaces`, or `id` and changes |
| `rule`   | `list`   | `kind`, `status`                                                                           |
| `term`   | `set`    | `saidBy`, `source`, and `name`, `meaning`, `avoid`, or `id` and changes                    |
| `term`   | `list`   | none                                                                                       |
| `part`   | `add`    | `kind`, `path`, `rules`, `terms`                                                           |
| `part`   | `list`   | `rule`                                                                                     |

- `log` adds a message `in` from the person `from`, with `at` when it is given. `draft` adds a message `out` from `user`, at the time of the write, so its state is `draft`. `mark` sends `message mark`. The description of `thread` tells the agent to put `draft:<id>` in the command of a call that sends a draft. `rule set` and `term set` without `id` add a rule or a term, and with `id` change it, as the `rule` and `term` requests do. `part add` takes no rules or no terms as an empty list.
- The runner refuses a call without an argument that the action needs with `<action> requires <argument>`, before it sends a request: `read`, `log` and `draft` without `thread`, `log` without `from`, `log` and `draft` without `text`, `mark` without `message` or `state`, a `set` without `saidBy` or `source`, a new rule without `name`, `kind` or `value`, a new term without `name` or `meaning`, and `add` without `kind` or `path`. The other errors come from the host (see [Host](#host)).
- The text result has one line for each object. An author is `user`, or a person as `<name> (<id>)`, such as `Sam (1)`, or `person <id>` when the person has no name in the reply of `person list`. A thread is `<id> <topic> with <persons>: last message <time>`, or `no messages` in place of the time, with its persons as authors. A message is `<id> <time> <author> (<state>): <text>`. A rule is `<id> <name> (<kind>, <status>): <value> [said by <author> in message <source>; replaces <id>]`, without `; replaces <id>` when it replaces none. A term is `<id> <name>: <meaning> [avoid <words>; said by <author> in message <source>]`, without `avoid <words>; ` when it has none. A part is `<id> <kind> <path> [rules <ids>; terms <ids>; checked <time>]`, with `none` for no IDs, and ` stale` at the end when it is stale. A time is in ISO 8601, in UTC. `thread read` gives the line of the thread, then the line of each message, oldest first, or `No messages`. `thread list` gives the line of each thread, or `No threads`; `rule list`, `term list` and `part list` give `No rules`, `No terms` and `No parts` for no objects. Each call, except a `part` call, also sends a `person list` request, for the names.
- The structured result is `{ action, value }`, where `value` is the reply of the host: the object for `log`, `draft`, `mark`, `set` and `add`, `{ thread, messages }` for `read`, and `{ threads }`, `{ rules }`, `{ terms }` or `{ parts }` for `list`. Each tool declares the schema of this result, with the schemas `Thread`, `Message`, `Rule`, `Term` and `Part` of `src/protocol/project.ts`.
- The host gives the tools to the project agent and to each child, also at the depth limit. A call runs in the host process, and its caller is the conversation ID, which the host keeps in `by` of each object that the call writes. The requests have no request ID, so a call that a host restart interrupts does not run again. It ends with `Tool <name> was interrupted and may have partially run`, so a message is never logged twice. The entry `@vzlentin/harness/durable-entry` does not give the tools. In Pi, the extension `@vzlentin/pi-agents` gives the tools too (see [Pi extension](#pi-extension)).

The host gates each tool call of the project agent and of each child, the nested calls of `codemode` included, with the `beforeTool` hook of pi-durable. The hook sends a `gate` request (see [Host](#host)) with the request ID `gate:<task ID>`, the conversation ID as the caller, and the texts of the last 3 user messages of the conversation, such as the inputs and the answers of children, not the notes. A call of a read tool sends no request. A held call does not run: its result is the error `Tool call blocked: Held as action <id>: <reason>`, and the agent goes on. A request that fails blocks the call with its error. When the user approves the action, the agent gets the input of the approve, and its next call of the same command runs one time with no question. The entry `@vzlentin/harness/durable-entry` does not gate its calls.

## RLM

In the host and in interactive Pi, the IPython kernel of a conversation or of a session has `rlm`: a client with the actions of the `subagent` tool, as coroutines (see [RLM in Pi](#rlm-in-pi) for Pi). The client is `python/harness_rlm.py` of `@vzlentin/harness`. It uses the standard library only, and needs Python 3.9 or later.

- `await rlm.spawn(prompt, *, context=None, name=None, files=None, model=None, thinking=None, cwd=None)` gives the child as a dict `{ handle, name, state, provider, model, thinking, cwd, kind }`, with `kind` set to `rlm`. The first message of the child is the message of the tool's `spawn` with `prompts: [prompt]`, then `context`, when given, in a `<context>` block: `Task:\n<prompt>\n\n<context>\n<context text>\n</context>`. `context` must be text: other values raise `RlmError` before the call reaches the host. `model` is a model ID of the caller's provider, or `<provider>/<model>`: the client gives the text before the first `/` as the tool's `provider`, so a model ID with a `/` needs its provider in front. Without `model` or `thinking`, the host applies the subagent settings as for the tool (see [Tool](#tool)). A relative `cwd` or file path resolves against the caller's working directory.
- `await rlm.send(handle, message, *, follow_up=False)` gives `{ verb, child }`.
- `await rlm.wait(handle, timeout=1800)` gives the answer text, as the `wait` value of the tool. `timeout` is a whole number of seconds, at least 1, as for the tool.
- `await rlm.status(handle)` and `await rlm.rename(handle, name)` give the child. `await rlm.list()` gives the children of the caller. `await rlm.stop(handle)` gives `{ handle, name }`.
- Each `handle` argument takes the handle text or a child dict that a call gave.
- A refused or failed call raises `RlmError`, a `RuntimeError`, with the error text of the host. `from harness_rlm import RlmError` gives the class.
- Each call opens its own connection, so `asyncio.gather` of several calls runs them at the same time. A cancelled call, such as one of an interrupted cell, closes its connection, which stops its request in the host, such as a `wait`. The child continues.

The host listens on `ipython:kernel-starting` on the event bus of its entries. pi-ipython emits it before each kernel start, restarts included, with `{ conversationId, env, startupCode, waitFor }`. A payload of another shape gives a warning, and its kernel gets no `rlm`. In a promise that it gives to `waitFor`, the host reads the lineage of the conversation. A conversation without lineage, such as the project agent, is at depth 0. A conversation at the limit of its depth budget is a leaf (see [Push](#push)): the host adds nothing, so its kernel has no `rlm`. For any other conversation, the host starts a server for that kernel start:

- The server is a Unix socket, `kernel.sock`, in a new directory `/tmp/harness-rlm-<random>` with mode 0700. The short path keeps the socket under the 104-byte limit of macOS.
- It has a random secret token.
- The host sets `HARNESS_RLM_SOCKET` and `HARNESS_RLM_TOKEN` in the `env` of the payload, never in its own environment. The client reads them at each call.
- The host adds the startup code: it puts the folder of the client first on `sys.path`, binds `rlm`, then sets `rlm.__doc__` (see below).
- A new kernel start of the same conversation replaces its server. The old server stops its requests, and the host removes its directory.
- When the server cannot start, the kernel start fails. A kernel start after the kernel servers close, while the host closes, fails with `The host is closing`: the host keeps its listener until the entries close.
- When the host closes, it stops the requests of each kernel server with `The host is closing`, before the entries close. It then closes the servers and removes their directories.

Each connection carries one request: one JSON line `{ token, action, args }`, where `action` and `args` are the arguments of the `subagent` tool: `args` has the other arguments, such as `{ handle, timeout }` for `wait`, or `{ prompts, provider, model }` for `spawn`. The host replies with one line, `{ ok: true, value }` or `{ ok: false, error }`, then ends the connection. A line that is not JSON or does not have the token of the server fails with `Invalid rlm token` and runs nothing. A line without an object `args`, or whose arguments the tool's parameters refuse, fails with `Invalid rlm request: <path> <message>`, with the path of the first field that does not match, such as `Invalid rlm request: /timeout must be >= 1`. The tool then refuses the calls that it refuses for the CLI and the model, such as `send requires message`.

The caller of each request is the conversation of the kernel, `String(conversationId)`. It is the same caller as the `subagent` tool of that conversation, so `rlm.list()`, the `list` of the tool, and `harness list` with that `PI_SESSION_ID` give the same children. The caller's model, thinking level and working directory come from the agent of the conversation, read at each request; the subagent settings come before its model and level (see [Tool](#tool)). Each call has its own request ID, `<caller>:rlm:<random hex>`, unless its `args` has the tool's `key`: then it is `<caller>:<key>`, as in the tool. The Python client sends no `key`. Each request runs as a call of the tool, in the host process. The children are children of the host, as for the tool: the conversation of the kernel is their tree parent, so they close when it closes, such as on a `stop` of the subagent that spawned them. The `spawn` and `send` requests of `rlm` have `notify: false`, whatever `args` gives: their answers come only with `wait`, and they do not hold the caller. The children stay after a cell, also after a failed cell; the model sees them on its next turn with `rlm.list()` or `rlm.wait()`. A `spawn` request of `rlm` has `kind: "rlm"`, and the host keeps it on the record of the child. The host gives it in the info of the child, so `list`, the subagents widget and the mirror sessions mark the child `rlm`.

No system prompt has an `rlm` section. The model reads the text with `print(rlm.__doc__)`, which the startup code sets, and the tool description names that command (see [Tool](#tool)). The text says that `rlm` is bound in the kernel. It gives each coroutine with its arguments and its result, and a fan-out example with `asyncio.gather`. It says that the children are those of the `subagent` tool, that their answers come only with `wait`, that they stay after a failed cell, that `stop` ends a child and its subtree, and that the answer of the conversation is plain text. It then gives each limit of [RLM limits](#rlm-limits), and what the model does at that limit: stop a child before it spawns another, split a large prompt, send a smaller task after an abort, and ask for short answers.

### RLM in Pi

In interactive Pi, the extension `@vzlentin/pi-agents` (see [Pi extension](#pi-extension)) serves `rlm` to the IPython kernel of the session, with the client, the servers and the startup code of the host. The kernel runs in Pi, and its children run in the host of the project.

- The extension listens on `ipython:kernel-starting` on `pi.events`. In Pi, pi-ipython emits it before each kernel start, restarts included, with `{ env, startupCode, waitFor }`, without `conversationId`. A payload of another shape shows the notification `The ipython:kernel-starting event has an invalid payload; its kernel gets no rlm` as a warning, and its kernel gets no `rlm`.
- In a promise that it gives to `waitFor`, the extension starts a server for that kernel start, as the host does: a Unix socket `kernel.sock` in a new directory `/tmp/harness-rlm-<random>`, with a random secret token. It sets `HARNESS_RLM_SOCKET` and `HARNESS_RLM_TOKEN` in the `env` of the payload, never in the environment of Pi, and adds the startup code. A new kernel start, such as a restart, replaces the server: the old server stops its requests, and the extension removes its directory. When the server cannot start, the kernel start fails.
- Each request goes to the host of the project as a call of the `subagent` tool, with `sendToHost`, so a request starts the host when none runs. The caller is the session ID, and the caller's model, thinking level and working directory are those of the session; the subagent settings come before its model and level (see [Tool](#tool)). The extension reads them at each request, so a request after a model change uses the new model. `rlm.list()`, the `list` of the tool, and `harness list` with that `PI_SESSION_ID` give the same children, and the subagents widget and `/subagent` show them, marked `rlm`. The `spawn` and `send` requests have `notify: false`, and the `spawn` requests have `kind: "rlm"`, as in the host, so the host applies the [RLM limits](#rlm-limits).
- A Pi session has no lineage: it is a root, at depth 0, so it is never a leaf, and its kernel always has `rlm`. Its children are the first level of their tree, and the session is the root of that tree for the pool.
- At the session end, the extension stops the requests of the server with `The host is closing`, closes the server and removes its directory. A later request of the kernel cannot reach a server, because its socket is gone. The children stay in the host.

### RLM limits

An RLM child is a child whose record has `kind: "rlm"`: the child of a `spawn` request of `rlm`, or of another `spawn` request with `kind: "rlm"`. These limits apply only to RLM children. The children of the `subagent` tool and of the CLI get none of them. Push and `stop` do not change, and `list` marks an RLM child with `rlm`.

- Live children: an RLM spawn fails with `16 RLM children are live: stop one before you spawn another` when its caller has 16 RLM children that are not closed. A `stop` frees a place. A closed child that keeps its record, such as a child whose parent closed, does not count. A repeat of a spawn with the same request ID gives the same child, and is not a new one. The host counts in the commit that creates the child, so spawns at the same time cannot pass 16.
- Request size: an RLM spawn fails with `The prompt of an RLM spawn, with its files and context, is more than 1 MiB` when its first message, with the text of its files, its prompt and its context, is more than 1 MiB in UTF-8. A `send` to an RLM child fails with `The message of an RLM send is more than 1 MiB` when its message is more than 1 MiB in UTF-8. The host checks these sizes, so they apply to each client: a kernel, the `subagent` tool that sends to an RLM child, or a socket.
- Kernel line: a request line on a kernel socket that is longer than 1 MiB + 64 KiB before its newline gets the reply `{ ok: false, error: "Invalid rlm request: the line is longer than 1 MiB plus 64 KiB" }`, and runs nothing. The server then ends the connection, and reads and ignores the data that follows. The client sends the line as UTF-8 JSON, with each character as it is, so a character counts its UTF-8 bytes. The JSON escapes count in the line, such as `\n`, `\"` and a lone surrogate, which goes as its escape: a text with many escapes can get this error under 1 MiB.
- Deadline: the host aborts a turn of an RLM child after 5 minutes, as the `abort` request does, so the queued messages of the child are aborted too. A turn is one run of the conversation, from its first input to its end: a steer goes into the turn that runs, and a follow-up starts a new turn. The deadline applies to each turn of an RLM child, also one that a mirror session or a push starts. `wait` then fails with `<handle> was aborted`. The child stays open and takes new sends. At host start, each busy RLM child gets a full new deadline.
- Answer text: `wait` cuts each answer of an RLM child, and each failure text, to 256 KiB in UTF-8, on a character boundary. It then adds the line `[The answer was cut at 256 KiB]`. When a `wait` gives several answers, it cuts each one.
- Pool: each tree runs at most 4 model requests of its RLM children at the same time. The tree of a child is the `root` of its lineage: the caller that started the tree. A request holds its slot from the start of the model request to its response, its failure or its abort. Tool calls hold no slot, so a child that waits for its own children in a cell does not stop them. When a slot frees, the waiting request with the smallest depth starts first, then the oldest. A waiting request that is aborted leaves the queue. The pool works through the hooks of the extension `harness-rlm` before and after each model request, so compaction requests and deferred polls are not in it.

## Pi extension

The Pi extension is the npm package `@vzlentin/pi-agents`, from the `pi/` folder of this repository: the `subagent` tool, the `/subagent` command, the subagents widget, the messages with the answers of the children, the `todo` tool, the todo widget, the `thread`, `rule`, `term` and `part` tools, the digest of the session, the gate on the tool calls of the session, the mirror sessions (see [Mirror sessions](#mirror-sessions)), `rlm` in the IPython kernels of the session (see [RLM in Pi](#rlm-in-pi)), and the `subagent` skill, `pi/skills/subagent/SKILL.md`, which tells the agent how to use the tool and the `harness` CLI. The `pi` manifest of the package lists the extension and the `skills/` folder. `/subagent` lists the children of the session, with the lines of `list`, and opens the one that you select in Pi, in a new herdr-app tab (see `openChildTab`); outside an hc terminal (`HC_TERMINAL_ID` is not set), it shows `Run in another terminal: harness attach <handle>`. When the tab does not open, it shows `Could not open a herdr-app tab: <reason>. Run in another terminal: harness attach <handle>`. The extension has the same version as harness. It has no copy of harness: `@vzlentin/harness` at that version is a dependency of `@vzlentin/pi-agents`, and the extension loads its `dist/` modules, so it starts the host of that install. It resolves each module from its own folder, as `@vzlentin/harness/<name>`, with the `exports` of the package. These `exports` give the public modules of the package, and only them: `answers`, `children`, `client`, `durable-entry`, `entries`, `herdr`, `host`, `inspect`, `mirror`, `overlay`, `projects`, `protocol`, `respond`, `rlm`, `tasks`, `todo`, `tool`, `trust` and `view-state`, and `package.json`. When Pi loads the extension, it also puts the `.bin` folder of the `node_modules` folder that holds `@vzlentin/harness` last on the `PATH` of Pi's process, so the agents find `harness`. It goes last because the folder also holds the commands of other dependencies, such as an older `pi`, which must not hide the user's own. It first removes that folder from `PATH`, so each load leaves it there once. When one of the `dist/` modules does not load, such as in a checkout without `npm run build`, Pi shows that the extension failed to load.

With a UI, the subagents widget below the editor shows the children of the session, `<name or handle>:<state>`, or `rlm:<name or handle>:<state>` for an RLM child, five at most, then `+<n>` for the others; it reads them every second and does not start the host. A busy child is in the warning colour, an idle child in the success colour, a child in error in the error colour and a closed child in the muted colour. Without children, or when no host runs (see [Host](#host): it exits after 5 idle minutes), the widget is hidden. When the host fails the request, it shows `subagents: <first line of the error>` in the error colour.

The `todo` tool of the extension has the parameters, the description, the text result and the structured result of the `todo` tool of the host (see [Tool](#tool)), and runs the same runner, `runTodoTool` of `@vzlentin/harness/tool`, on the list of `todoToolTarget(args)`. The call goes to the host of the project with `sendToHost`, so it starts the host when none runs. The caller is the session ID, so without `list`, the list is the list of the session, which the host keeps under the session ID (see the `todo` request in [Host](#host)). `harness todo` in the bash of the session has the session ID in `PI_SESSION_ID`, so it gives the same list. `list: "project"` is the list of the project. Each call opens its own connection, so calls at the same time could reach the host out of order: a round with a `todo` call runs all of its tool calls in order, as for the `subagent` tool, so the todos of one message get their IDs in message order.

Before each tool call of the session, the extension sends a `gate` request to the host of the project (see [Host](#host)) with `sendToHost`, so it starts the host when none runs. The caller is the session ID, the request ID is the ID of the tool call, and `messages` are the texts of the last 3 user messages of the branch of the session. A call of a read tool sends no request. With a UI, a held call shows a confirm prompt, `Held action <id>`, with the command and the reason. Yes approves the action and sends the `gate` request again, which runs the call one time. No drops the action and refuses the call with `Held as action <id>: <reason>`. Without a UI, the call is refused with that reason, and the action stays held for another client to approve. A request that fails refuses the call with its error.

The `thread`, `rule`, `term` and `part` tools of the extension have the parameters, the descriptions, the text results and the structured results of the tools of the host (see [Tool](#tool)), and run the same runners: `projectTools({ Type }, adapt)` of `@vzlentin/harness/tool` gives each tool, with its name, label, description, schemas and runner, to `adapt`, which registers it. The calls go to the host of the project with `sendToHost`, so they start the host when none runs. The caller is the session ID, which the host keeps in `by` of each object that a call writes. A round with one of these calls runs all of its tool calls in order, as for the `todo` tool.

Before each turn of the session (`before_agent_start`), the extension sends a `digest` request with the session ID as the caller to the host of the project, only when a host runs: a turn does not start a host. When the reply has a text, the turn gets it as a custom message of the type `harness-digest`, which Pi shows and gives the model. A request that fails gives no message, and a notification `harness: no digest: <error>` with a UI.

With a UI, the todo widget below the editor shows the list of the agent of the session while that list has an open or a doing todo: one line for each todo, in ID order, as `harness todo list` prints it. Otherwise the widget is hidden. Pi shows at most 10 lines of a widget. In a session that is not a mirror session, the agent is the session itself. Its list has no watch, so the widget reads it as the subagents widget reads the children: every second, without starting the host, so it is hidden when no host runs. It also reads it at once after each `todo` call of the session, before the call ends. When the host fails the request, it shows `todos: <first line of the error>` in the error colour. The extension sets each of the two widgets again only when its lines change, also in a mirror session, so the subagents widget and the todo widget keep their places below the editor until the lines of one of them change. A `todo` request with the action `list` does not keep the host running (see [Host](#host)). In a mirror session, the widget shows the list of the mirrored agent (see [Mirror sessions](#mirror-sessions)).

Each Pi session keeps one `answers` request open to the host, on a connection of its own, with the session ID as the caller (see [Push](#push)). For each answer, Pi shows a custom message of the type `subagent-answer` with the same text as the input of a push to a conversation of the host, and the answer as its details. The message starts a turn, as a follow-up when Pi works. At the session start, with or without a UI, the extension opens the request. It starts the host only when the session has a result of the `subagent` tool, so a session that spawned children gets the answers that came while Pi was closed. When the host closes the connection, the extension connects again at once, after 2 s and after 5 s, then every 5 s until a try connects. When no host runs at the session start, it tries every 5 s. When a connection closes less than 10 s after it opened, the next try is after 5 s. Only the first try at the session start can start a host. When Pi fails to show an answer, the extension shows the error as a notification, `Could not show the answer of a subagent: <error>`, and the next answers still come. At the session end, it closes the connection.

### Mirror sessions

A mirror session is a Pi session that shows a child or the agent of a project (see [Project agent](#project-agent)) in Pi's own chat, and sends what you type to it. The agent runs in the host of the project, so it continues when Pi closes. Below, the agent is the child or the project agent that the session shows. The mirror sessions work only in Pi's interactive mode. In another mode, a session with a `harness-mirror` entry, or a Pi with one of the `--harness` flags, fails at the session start with `harness: a mirror session works only in Pi's interactive mode`, and Pi's own agent does not take its input.

- `/harness <project>` opens a new Pi session that mirrors the agent of `<project>`, which is `main` or a project name. An unknown project is an error: `harness: Unknown harness project: <name>`. The command completes the project names. Without a project, it asks for one in the list `Harness project`, with one line `<name>  <dir>` for each project: the project of Pi's working directory first (as for a command), then the other projects, then `main` with `~`. When `main` is the only project, it opens `main` and does not ask. Esc cancels.
- `pi --harness <project>` mirrors the agent of the project in the session that Pi starts with, `pi --harness <project> --harness-child <handle>` mirrors a child of the project, and `pi --harness <project> --harness-conversation <id>` mirrors a conversation of the children library (see [Open in Pi](#open-in-pi)). Both `--harness-child` and `--harness-conversation` is an error: `harness: use --harness-child or --harness-conversation, not both`. Without `--harness`, or with an empty project, the project is the one of `HARNESS_PROJECT` and Pi's working directory. It refuses a session with messages, such as one of `--continue`: `harness: --harness needs a new session, not one with messages`. A session that is already a mirror session keeps its target, and at the startup Pi shows `harness: the --harness flags are not used: the session is already a mirror session`.
- The session has the title of the agent as its name, `<name> (<handle>)`, `<key>` for a conversation, or `<project> agent`, and follows a rename. It holds one custom entry, `harness-mirror`, with the target `{ project, handle }`, or `{ project, conversation }` for a conversation, and Pi draws the conversation of the agent in place of that entry: the newest entries of the conversation when the session attaches, then each new entry, which it adds below the others. It uses Pi's message and tool components and Pi's theme (adapted from the attach view of [mavam/pi-agents](https://github.com/mavam/pi-agents)): the user messages, the answers with their thinking, and a Pi tool card for each call of `read`, `bash`, `edit`, `write`, `grep`, `find` and `ls`, with its output while it runs. Other tools get Pi's generic card. A compaction shows `[compaction]` and its summary, and a reset shows `[new context]`, where they occur in the conversation; the entries before them stay. The first line is `harness │ <title> │ <working directory>`, and `harness │ <title> │ rlm │ <working directory>` for an RLM child. Pi saves a session only when it has a message, so it does not save a mirror session and `/resume` does not list it; run `/harness` again to open it.
- A message that you send goes to the agent: a new turn when it is idle, a steer when it works. Pi's own agent does not run. While the agent works, Esc aborts its turn, and the queued messages go back to the editor, steers first; Alt+Enter (`app.message.followUp`) queues the text as a follow-up. Before the connection opens and while the session connects again, Alt+Enter also sends the text as a follow-up, which waits for the connection. A conversation of the children library takes a message only while it works, always as a steer, also with Alt+Enter; when it is idle, the message goes back to the editor with `harness: not sent: <key> takes input only while it works`. The extension uses its own editor in the session for these keys.
- Above the editor, Pi's working indicator shows what the agent does (`Working...`, `Running <tool>...`, `Compacting (<reason>)...` or `Retrying (attempt <n>): <error>`), and each queued message shows as `Steer: <first line>` or `Follow-up: <first line>`.
- Below the editor, the todo widget (see [Pi extension](#pi-extension)) shows the list of todos of the agent, from the view of the watch (`harness.todos` in its `docs`, see `host.sock` in [Host](#host)), while it has an open or a doing todo. Its lines follow each change of the view, and the widget is set again only when they change. It shows the list of the last view also while the session connects again and after it failed. It does not show the list of the local Pi session. It goes away when the session ends.
- The answers of the agent follow Pi's `hideThinkingBlock` setting: Ctrl+T (`app.thinking.toggle`) hides and shows their thinking, as for Pi's own messages.
- The last line above the editor is `<title> • <usage> • <context>`, without the parts that are empty. The usage has the sums of the agent's model requests and tool results, as Pi's footer shows its own: `↑` input, `↓` output, `R` cache read, `W` cache write and `$` cost, each when it is not zero, and the cost also when Pi uses a subscription for the model, with `(sub)`. The context is `<percent>%/<window>`: the context of the last answer of the agent's active transcript (after its last compaction or reset) that did not abort or fail, against the context window of its model, when Pi knows the model. Pi's footer stays as it is, for the local Pi session: Pi's own footer, or the footer of an extension.
- Pi's model and thinking level follow the agent's. A model that you select in Pi (`/model`, Ctrl+P) and a thinking level (Shift+Tab) go to the agent with a `configure` request. A refused change gives an error, and Pi goes back to the agent's model. The model that Pi takes from the agent is not a request. When Pi does not take the agent's model, Pi shows an error: `harness: Pi has no login for <provider>/<model>` without a login for it, or the error of Pi. When the agent changes its model while Pi takes the previous one, Pi then takes the new one. A conversation of the children library refuses each change, without a request, with `harness: A conversation of the children library keeps its model and thinking level`.
- When the host closes the connection, the session connects again, which starts a new host when none runs. It shows `Connecting again to the harness host...` above the editor. It tries three times: at once, after 2 s, and after 5 s. When all tries fail, the session shows `The harness host closed the connection. Connecting again failed: <error>`. When the host closes a connection that was opened again less than 10 s before, the session does not connect again and shows `The harness host closed the connection. Run /reload to attach again`. When the child is stopped, the session shows `<name> (<handle>) was stopped`. When the connection closes, each tool card that runs shows `Interrupted: no connection to the harness host`. `/reload` attaches again, and starts the host when none runs. `/new` and `/resume` leave the mirror session; the agent keeps running.
- A message that you send while the session connects waits for the connection. When the connection closes before the host answers a message, the message goes again on the next connection with the same request ID, so the agent gets it once. A message that does not reach the agent, because the host refuses it or the session fails first, goes back to the editor, after the text there, and Pi shows `harness: not sent: <reason>`. A message that went to the host on a connection that closed before the host answered, when the session then fails, may be with the agent: it does not go back to the editor, so that a send again does not give it twice. It stays in the history of the editor, and Pi shows `harness: maybe sent: <reason>. The text is in the history of the editor`.
- Images are not sent: the agent gets only the text, with the warning `harness: the images are not sent; the agent gets only the text`. Pi does not expand skill commands and prompt templates for the agent. Pi's own session commands act on the local Pi session, which has no messages: `/compact` fails with `Nothing to compact (session too small)`, `/fork` gives `No messages to fork from`, `/tree` shows `No entries found`, and `/export` fails with `Nothing to export yet - start a conversation first`.
