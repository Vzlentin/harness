# harness reference

The behaviour of the `harness` CLI, the `subagent` tool, the Pi extension and the host. The [README](../README.md) has the install.

## Commands

Spawn with a descriptive name using the parent session's provider, model, and thinking level:

```sh
harness spawn --name review --prompt "Review the current diff independently"
```

Spawn prints `Spawned <name> (<handle>)` and `State: busy`. Names appear in the parent UI. Generated handles remain the stable identifiers used by management commands.

Override the model configuration when needed:

```sh
harness spawn \
  --provider openai-codex \
  --model gpt-5.4-mini \
  --thinking low \
  --prompt "Find the relevant implementation"
```

Provide multiple prompt fragments and files. The first message holds the text of each file, then `Task:` and the prompts:

```sh
harness spawn \
  --file /tmp/spec.md \
  --prompt "Implement this specification" \
  --prompt "Run the targeted tests"
```

Restrict tools with `--tools`, a comma-separated list. Without it, a child gets `read`, `grep`, `find`, `ls`, `write`, `edit`, `bash`, `subagent`, `codemode`, and the tools of the host's entries (see [Limits](#limits)). An unknown tool name is an error:

```sh
harness spawn --tools read,bash --prompt "Investigate the failure"
```

Manage a run by its generated handle:

```sh
harness status a1b2c3
harness rename a1b2c3 "error handling review"
harness send a1b2c3 "Focus on error handling"
harness send a1b2c3 --follow-up "Then summarize"
harness wait a1b2c3
harness stop a1b2c3
harness list
harness attach a1b2c3
```

- `status` prints `<name> (<handle>): <state> (<provider>/<model>, <thinking>)`. The state is `busy`, `idle`, `error` when the last turn failed, or `closed` when the children library closed the child outside `stop`, such as a subagent under a workflow session whose run ended. After an abort from a mirror session, the state is `idle`. A closed child stays `closed`, also while its children hold it. A child that is not closed is also `busy` while one of its notify children holds it (see [Push](#push)), at any depth, so `status`, `list`, `wait`, the widget and Herdr show it as `busy` until its subtree is quiet.
- `send` prints `Prompted`, `Steered`, or `Queued follow-up for`, then the child. A steer goes in after the current tool round. A follow-up starts after the current answer. The verb comes from the child's own turn: a child that only its children hold is `Prompted`.
- `wait` waits until the child answers its last message, up to `--timeout` seconds (default 1800), and prints `<handle> finished`, a blank line, and the answer. When the spawn or an earlier `send` has an answer that no `wait` gave, it prints `<n> unread answers, oldest first.`, a blank line, and each answer after a line `--- Answer <i> of <n> ---`, the last one last. An earlier turn that failed gives `(no answer: <error>)`. A steer shares the answer of the turn it went into, so that answer comes once. A failed or aborted last turn is an error: after an abort, it prints `<handle> was aborted`. The error gives the earlier unread answers in the same form, and does not give the failed turn twice. Each `wait` marks these answers read. A message sent while a `wait` runs stays unread for the next `wait`. Input from a mirror session is not counted. While its children hold the child, `wait` waits too, and when a push starts a turn of the child meanwhile, `wait` gives the answer of that turn. While a `wait` runs, the host pushes no answer of that child. A `wait` for a turn whose answer a push already gave prints `<handle> finished`, a blank line, and `No new answers: the last answer came as a message.`. A second `wait` without a push between still gives the last answer again. A `wait` for a closed child, or for a child that closes while the `wait` runs, fails with `The child <id> is closed`. When the host closes, a running `wait` fails with `The host is closing`.
- `stop` stops the work of the child and of the children it spawned, and removes them. A `spawn` that comes again with the request ID of a stopped child spawns a new child, with a new handle, and sends the prompt to it. A repeat of that `spawn` gives the new child.
- `list` prints one line per child of the current caller: `<name> (<handle>)  <state>  <provider>/<model>  <thinking>`.
- `attach` opens the child in Pi in this terminal, and `attach --conversation <id>` a conversation of the children library (see [Open in Pi](#open-in-pi)). Without an ID, or with more arguments, it prints the usage.

### Project agent

Each project has an agent, a conversation in its host that you talk to directly:

```sh
harness web
harness main
```

`harness <project>` opens the agent of the project in Pi in this terminal (see [Open in Pi](#open-in-pi)). It starts the host when none runs. A single word that is not `main`, a project or a command prints the usage. A `--project` before it is an error: `harness <project> takes no --project`.

- The agent works in the project directory, or in the home directory for `main`. Its system prompt, tools and bash env are the same as a child's in that directory (see [Host](#host)). Its bash commands get `PI_SESSION_ID`, the agent's conversation ID.
- When it is first opened, the agent gets Pi's default model (`defaultProvider` and `defaultModel` in Pi's `settings.json`) when it has a login, else the first model with a login, and Pi's `defaultThinkingLevel` (default `medium`), or the nearest level that the model has. Without a model with a login, Pi does not start and `harness <project>` prints `No model for the <project> agent: log in to a provider and set a default model in Pi (defaultProvider and defaultModel)`. A mirror session changes its model and thinking level as for a child.
- The children that the agent spawns have the agent as their parent: `harness list` with `PI_SESSION_ID` set to the agent's conversation ID shows them. The agent gets the answers of these children as input (see [Push](#push)). Its own state ignores its children.
- Esc stops only the agent's turn. The children that it spawned keep running.
- The agent keeps its conversation across host restarts. `status`, `send`, `wait`, `rename`, `stop` and `list` do not know the agent: it is not a subagent, and it cannot be stopped.
- Before each `input` request to the handle `agent`, the host catches the agent up. It keeps what the agent has seen in a `harness.seen` document of the agent's conversation: `{ mainSha, lastTaskId, pending, catchups, entry? }`, the head of the default branch, the highest started task ID, the IDs of the workflows runs that were still running, the count of catch-up entries, and the catch-up entry that is not written yet. The catch-ups of the agent run one at a time. A repeated input, whose request ID the conversation already has, gets no catch-up. The host then reads, in the project directory, read only:
  - The default branch: the target of `refs/remotes/origin/HEAD` without `origin/`, else `main`, and its local head `refs/heads/<branch>`. Outside a Git repository, or without that branch, there are no commits and no warning. With a head in `mainSha`, the commits are those of `git log <mainSha>..<head>`, newest first. When the head does not contain `mainSha` (`git merge-base --is-ancestor` fails), as after a force-push, a change of `origin/HEAD`, or a `mainSha` that the repository no longer has, there are no commits, the entry tells it, and `mainSha` becomes the head, with no warning. When Git fails, the host writes a warning and keeps `mainSha`.
  - The workflows runs: the started tasks of the kind `workflows.run` that are in `pending` or above `lastTaskId`. A run that is not terminal goes into `pending`. A terminal run is listed, and so is each task of a resumed run. A task that cannot be read gives a warning and stays in `pending`. A run that cannot be reported is lost, with no warning: a run whose input is not a workflows run input, and a run in `pending` whose task record is gone. A task of another kind, and a new task with no record, are left out.
  - The first time, with no `harness.seen` yet, the host only records the current state, with the running runs in `pending`, and adds no entry. When nothing is new, it adds no entry.
  - Else it records the new state with `catchups + 1` and the planned entry in one commit, then adds one passive entry of the kind `harness.catchup` before the input, with the request ID `catchup:<catchups + 1>`, then removes the planned entry from the document. A catch-up first writes a planned entry that an earlier catch-up left, such as after a crash or a failed write; its request ID makes a repeat add nothing. The entry is a user message with one line for each run, `<runId> (<workflow>): <status>; subject: <subject>; branch: <branch> @ <head>; divergence: <divergence>; lessons: <lessons as JSON>; sessions: [run <run>: <label or key> #<conversation>, ...]`, then `task <id>: <reason>` for each lost run, then the branch name and each new commit as `<short sha> <subject>`, then a line when the branch no longer contains `mainSha`. Its `data` is `{ runs, lost?, commits?, reset? }` with the same facts: each run is `{ task, runId, workflow, status, subject?, branch?, head?, divergence?, lessons?, sessions? }`, each session is `{ run, conversation, key?, label? }`, `lost` is `[{ task, reason }]`, `commits` is `{ branch, commits: [{ sha, subject }] }`, and `reset` is `{ branch, from, head }`, the old and the new head. `status` is the `status` of the result of a completed run, else the outcome status. `branch` is the branch of the result, else the branch of the run's worktree. The sessions come from the `workflows.sessions` document of the root run, with the lineage key of each session. The label is the agent profile that workflows saves with the session. The entry names a session by its label, else its lineage key, else only its ID. When the document cannot be read, the host writes a warning and the line has no sessions. A missing field is left out.
  - A failure of the catch-up is a warning: the input always goes through.

### Projects

Each project has its own host, store and children. A project is a name and a directory:

```sh
harness create web --cwd ~/Dev/web
harness projects
```

- `create <name> --cwd <dir>` prints `Created <name> (<dir>)`, where `<dir>` is the real path of the directory. A relative `--cwd` is relative to the current directory. The name has 1 to 32 characters: `a-z` first, then `a-z`, `0-9` or `-`. It cannot be `main` or a command name. A name that exists, and a directory that does not exist, are errors.
- `projects` prints `<name>  <dir>` for each project, in creation order, then `main`.
- `--version` prints the version of the package. It takes no argument and no `--project`.

The projects are in `$XDG_CONFIG_HOME/harness/projects.json` (default `~/.config/harness/projects.json`), an object of name to directory. A command that reads the file fails when a name does not follow the rule of `create` or a directory is not an absolute path.

A command goes to the project of `--project <name>`, which must come before the command (`harness --project carrefour list`), then of `HARNESS_PROJECT`, then of the current directory: the project with the longest directory that is the current directory or contains it. Without a match, the project is `main`, which has no directory. When two projects have the same directory, the first one created wins. An unknown project name is an error: `Unknown harness project: <name>`. The tool finds its project in the same way, from `HARNESS_PROJECT` and the current directory of their process.

The caller is `PI_SESSION_ID`, or `cli` when it is not set. `list` shows only the caller's children. The CLI and the tool refuse to `send` to, `rename`, or `stop` a child of another caller. A mirror session does not check the caller, because the host socket is for one user: it can show, send to, and abort the child of any caller. It sends text with an `input` request, stops a turn with an `abort` request, and changes the model or the thinking level with a `configure` request. None of these requests has a caller.

`openChildTab` of `@vzlentin/harness/herdr` opens a child in Pi in a new Herdr tab with the label `<name>` (or the handle), in the child's working directory. The tab runs `env <node> <cli> --project <project> attach <handle>`, where `<cli>` is `dist/cli.js` of the install, or `src/cli.ts` of a checkout: `harness attach` with this Node and this install's CLI, so it does not need `harness` on `PATH`, on the project of the caller. When `XDG_STATE_HOME` or `XDG_CONFIG_HOME` is set, the tab gets it too. When a `herdr` call fails, it rejects with the stderr of `herdr`, or with the reason that the call failed.

`openConversationPane` of `@vzlentin/harness/herdr` opens a children library conversation in Pi, in the conversation's working directory. It takes the conversation as a `ChildInfo`, a place, and the environment. For a conversation, `ChildInfo` gives the same ID in `handle` and in `conversation`. With `{ pane }`, it runs `herdr pane split <pane> --direction right --cwd <cwd>`, then `herdr pane rename <new pane> <key>`. With `{ workspace }`, it runs `herdr tab create --workspace <workspace> --cwd <cwd> --label <key> --focus`. The new pane then runs `env <node> <cli> --project <project> attach --conversation <id>`, on the project of the caller. When `XDG_STATE_HOME` or `XDG_CONFIG_HOME` is set, `pane split` and `tab create` get it too, with `--env`. When a `herdr` call fails, it rejects with the stderr of `herdr`, or with the reason that the call failed, and makes no more calls. When `pane split` or `tab create` gives no pane ID, it rejects with `herdr pane split gave no pane ID: <output>` or `herdr tab create gave no pane ID: <output>`.

## Open in Pi

`harness attach <handle>` opens a child in Pi in the current terminal, `harness attach --conversation <id>` opens a conversation that the children library opened, such as a child of a task, and `harness <project>` opens the agent of the project. They start the host when none runs, and check the target before Pi starts: an unknown handle is an error, `Unknown subagent: <handle>`, an unknown conversation or a root is an error, `Unknown conversation: <id>`, and so is a project agent without a model. Then they run `pi --harness <project>` for the project agent, `pi --harness <project> --harness-child <handle>` for a child, or `pi --harness <project> --harness-conversation <id>` for a conversation, which opens a mirror session (see [Mirror sessions](#mirror-sessions)), and exit with the exit code of Pi. They run the `pi` of `PATH` without the `node_modules/.bin` folders; without one, the error is `pi is not on PATH. Install Pi to open the agent`. That Pi needs the extension of the package (see [Pi extension](#pi-extension)). Closing Pi never changes the child.

In a Herdr pane (`HERDR_ENV` is set), Pi gets `HARNESS_HERDR_PANE` with the pane of `HERDR_PANE_ID`, in place of `HERDR_ENV`. Herdr's own Pi integration then does not report that pane, and the mirror session reports the state of the agent at each change: `herdr pane report-agent --source custom:harness --agent <label> --state working|idle --seq <n> <pane> -- <resume>`. The label is the name of the child, or its handle, `<key>` for a conversation, and `<project> agent` for the project agent; it is the name at the first connection, and a rename does not change it. The resume command is the command that `openChildTab` runs, `env <node> <cli> --project <project> attach <handle>`, `env <node> <cli> --project <project> attach --conversation <id>` for a conversation, or `env <node> <cli> <project>` for the project agent. A busy agent is `working`; an idle agent, an agent with an error, and an agent without a connection are `idle`. `--seq` increases with each call. A report of the same state as the last report, while it waits or after it went through, makes no call; after the last report failed, or after a release, the next report calls `herdr` again. When Pi leaves the mirror session, and when the session fails for good, it calls `herdr pane release-agent`, and a failed session reports no more. Pi leaves the session only after that call ends. A failed `herdr` call does not stop Pi. A mirror session in a Pi that you start yourself in Herdr does not report, because Herdr's Pi integration holds that pane.

In every terminal, the mirror session also reports the state of the agent to the terminal with the Program Status Protocol (OSC 7501), through Pi's `setProgramStatus`, with `app: "harness"`. It reports when it starts and at each change of the state or of the message. On an open connection, a busy agent is `working` and an agent whose last request failed is `error`. All other cases are `idle`: an idle agent, the connection before the first one opens, a connection that connects again, and a connection that failed. The message is the title of the agent (the name or the handle of a child, `<key>` for a conversation, `<project> agent` for the project agent). Before the first connection, a child has its handle and a conversation its ID. A rename changes the title. For `error`, the message is the first line of the `errorMessage` of the last assistant message with `stopReason: "error"`, trimmed, or `Error` when there is none. When Pi leaves the mirror session, it reports `idle` with the title one more time. The Herdr reports stay as they are.

## Host

The children of a project run in one host process, `harness --project <name> host` (default `main`). The host takes its project only from `--project`, not from `HARNESS_PROJECT`. The first command that needs it starts it in the background, and tries to connect for 10 s. A started host that exits with code 0 found the lock held by another host, such as one that closes after its idle time: the command then starts a host again, at most once per second. A started host that exits in another way fails the command at once with `The harness host exited with <code N or signal S>; see <host.log>`. When the started host still runs after 10 s, the command fails with `The harness host (pid <pid>) is still starting: it can wait up to 60 s for the lock of durable.sqlite. Run the command again soon; see <host.log>`; otherwise with `Could not start the harness host; see <host.log>`. It exits after 5 minutes with no connection, no running work, and no command other than `list`, `status` and `answers`. A connection with an open `answers` request does not count. An open mirror session is a connection, and a live started task is running work, so each keeps the host running. A task that no loaded entry can run, such as one of an entry that was removed, is not running work, and neither is a task that waits only on such tasks. The host waits up to 60 s for the lock of `durable.sqlite`, so a client that reads the file, such as the workflows CLI, does not make it fail. The wait is synchronous: while it lasts, the host answers no request.

The host keeps its state in `$XDG_STATE_HOME/harness/<project>/` (default `~/.local/state/harness/<project>/`):

- `durable.sqlite`: the children's conversations and records, the started tasks, and the project agent, which is the store's root conversation. Work that a host stop interrupts continues when the host starts again. A host refuses a `durable.sqlite` from a version before the children library: stop the old host, remove the file and run the command again.
- `lock.sqlite`: one host at a time.
- `host.sock`: the socket the CLI and the extension connect to. The protocol has version 12. The `spawn` and `send` requests have `notify`, a boolean: false turns off the push of the answers of that request (see [Push](#push)). An `answers` request `{ caller }` waits until the host pushes answers to `caller` (see [Push](#push)), and replies with them, `[{ handle, name?, text, failed }]`. A newer `answers` request of the same caller replaces the older one, which then fails with `A newer answers request of the same caller replaced this one`. It needs a connection of its own, because the replies of a connection come in request order. The `watch` reply is `{ view, child }`. Each event of a watch is `{ change, child }` after a commit to the conversation, `{ change: {}, child }` after a rename, or `{ stopped: true }`, which comes after the events of the commits before the stop and one event with the whole view, `{ view }`. A change gives the parts of the view that the commit changed, as whole values, so a client needs no chord: `entries` is `{ from, items }`, the entries from index `from` on; `docs` has each document that changed, by kind, and `null` for a document that was removed; `conversation` is the conversation record. After a watch that fell behind, the change is `{ view }`, the whole view. A `configure` request `{ handle, provider?, model?, thinking? }` replies with the child, and refuses an unknown model and a thinking level that the model does not have. After a `watch` reply, each event of the watch is a `{ "event": ... }` line, and every other line is a reply, in request order. A request line that is not valid fails with `Unknown or invalid request: <type>`, or `Invalid request` when it has no string `type`. When a line from the host is not valid, the client cannot match it to its request: it ends the connection, and rejects each waiting request with `The harness host sent an invalid reply: <line>`. A client refuses a host with another version, and the host refuses the `hello` of a client with another version, with the same message. When the host is older, stop it with `kill <pid>` and run the command again. When the client is older, reload Pi with `/reload`, or use the CLI of the host's install. The `watch`, `input`, `note`, `abort` and `configure` requests take the handle `agent` for the project agent; its info is a child with the handle `agent` and the name `<project> agent`, and its watch never sends `stopped`. Other requests refuse it as an unknown subagent. The `watch`, `input`, `note` and `abort` requests also take `{ conversation }` in place of `{ handle }`: the ID of a conversation that the children library opened, of any owner, such as a child of a task. A request with both keys is not valid. Its info has `handle` and `conversation` set to the ID, and the child's key as `name`, so its title and its label are `<key>`. A closed conversation is `closed`, and its watch never sends `stopped`. It takes `input` only while it works, always as a steer, so the reply verb is `Steered`; an idle conversation refuses it with `<key> takes input only while it works`. A root, an unknown ID, or text that is not an ID gives `Unknown conversation: <id>`. A `note` request `{ requestId, text, kind?, data? }` with a handle or `{ conversation }` adds a passive user message `text` to the conversation's transcript, as an entry of the kind `kind` (default `harness.note`) with `data`. It starts no turn: an idle conversation places it at once, and the model reads it with the next input; a busy one places it at its next boundary, so the model reads it on its next request. An abort keeps a note that was placed. Its request ID is in the scope `note:`, apart from the IDs of `input`, and a repeated ID, also after a host restart, adds nothing. A kind that starts with `pi.` fails with `A note kind cannot start with "pi.": <kind>`. The reply is `{ child }`, with no verb. A closed child fails with `The child <id> is closed`, and an unknown handle with `Unknown subagent: <handle>`. When the close comes while the note is admitted, the note stays in the transcript of the closed child, which never runs again, and the request still fails. A `send` in that case fails the same way, and its input is aborted. A conversation takes a note while it is idle or busy; a closed one fails with `<key> takes input only while it works`.
- `host.log`: the host's output.

The host reads Pi's settings as a Pi session in the project directory (the home directory for `main`) reads them: the settings and packages of the project's `.pi/settings.json` count only when the project is trusted, with the saved trust (see the project skills below). They give the project agent its default model, and the packages of the entries. The host loads two kinds of entries when it starts. First, the `piDurable` entries of the packages in Pi's settings, such as pi-ipython: a package lists its entry modules in its `package.json`, as `{ "piDurable": { "extensions": ["./durable/index.ts"] } }`. Second, the entries in `$XDG_CONFIG_HOME/harness/entries.json` (default `~/.config/harness/entries.json`), an object of entry name to the absolute path of a module, for packages that are not Pi packages, such as workflows. A package sets its entry there with `setEntry(name, module)` of `@vzlentin/harness/entries`, which is true when it changed the file. `setEntry` and `create` hold the lock file `<file>.lock`, with their process ID, while they change `entries.json` or `projects.json`, so processes that change the file at the same time keep each other's change. A lock whose process does not run is removed; after 5 s with a lock of a live process, they fail with `Could not lock <file>: another process holds <file>.lock. Remove it if no harness command runs`. A host that runs already loads a new or changed entry only after it starts again. Missing packages are skipped, not installed. An entry of `entries.json` whose module does not exist, such as one of an uninstalled package, is skipped with the warning `The entry <name> has no module at <path>; the host skips it`. A package whose `package.json` is not a JSON object, or has a `piDurable` field that is not valid, gives a warning and is skipped. Node does not strip types under `node_modules`, so the host loads a TypeScript entry there through jiti. It calls the default export of each entry with `{ durable, ai, events, children, place }`: the host's pi-durable and pi-ai modules, one event bus that all entries share, the children library, and the host's `place` (store, models and tools) for `children.open`. The entries load before the host opens its store, so `place.store` is usable only once the host is open, which means inside tasks. An entry returns `{ extensions, tasks?, close }`. The host installs `extensions` and `tasks`, and refuses to start when two entries give a task with the same name. An entry that returns no `tasks` loads as before.

A client starts and follows the tasks of the entries with four requests:

- `start { kind, input, key, version? }` creates a task of the kind `kind`, with the input `input`, and replies with its info `{ key, id, kind, version, status, outcome? }`. `version` is the version on the task's record: the version of the entry's task definition that last ran or migrated the task. It shows which version of the entry the host used for this task, not which version the host has loaded now. `outcome` is there only when the task is terminal. The key is the client's own name for the task. A repeated `start` with a known key gives the first task, and its new input is ignored. It refuses another kind with `The task <key> is a <kind> task, not <kind>`. An unknown kind gives `Unknown task kind: <kind>`. With `version`, a host whose loaded definition of the kind has another version creates nothing and gives `This host has version <n> of <kind>, not <version>: stop the host so it starts again with the installed version`, for a first and a repeated `start`. Before it creates the task, `start` sets up the project agent, so a child that the task opens without a model takes the agent's; when the agent has no model, the task still starts.
- `task { key }` replies with the info of the task.
- `wait-task { key }` waits until the task is terminal, and replies with its info, with the outcome. To follow the status during the run, poll `task`.
- `abort-task { key }` aborts the task and the work that it owns, such as the turns of its children, and replies with the info.

The other requests refuse a key that no `start` gave with `Unknown task: <key>`. The host keeps each key and its task in `durable.sqlite`, and no request removes a key, so the key map only grows. A started task is a background task of the root conversation, so an abort of the project agent (Esc in its mirror session) does not reach it. A task that a host stop interrupts continues when the host starts again. The children that tasks open are not in `list`, and neither is a subagent that the library closed outside `stop`, such as one under a workflow session whose run ended.

A host from before the projects kept its state in `$XDG_STATE_HOME/harness/`. To keep its children, stop that host, then move `durable.sqlite` and its `-wal` and `-shm` files into `main/` before the `main` host starts.

A child's bash commands get `PI_SESSION_ID` (the child's conversation ID), `PI_PROVIDER`, `PI_MODEL`, `PI_REASONING_LEVEL`, and `HARNESS_PROJECT`, so a child can spawn its own children with the same configuration, in the same project, down to the depth limit (see [Push](#push)). After a `configure`, the next commands get the new model and thinking level. In a project other than `main` whose directory has a `.optmem` folder, they also get `MEMORY_DIR`, the path of that folder. Otherwise they get no `MEMORY_DIR`, not even the host's own. The rule uses the project directory, not the child's working directory. Children survive `/reload` and the end of the parent Pi session. `harness stop` removes a child and the children it spawned permanently.

A child's system prompt has what a Pi session in the child's working directory gets: the `AGENTS.md` or `CLAUDE.md` of the agent directory and of the working directory and its parents, the skills, and the working directory. User skills always load. Project skills (`.pi/skills`, and `.agents/skills` in the working directory and its parents) load only for a trusted project: a directory without project resources, then the decision saved with `/trust`, then the `defaultProjectTrust` setting, where `ask` counts as not trusted. A trust decision that a Pi session made for itself without saving it does not reach its children; when the tool spawns in such a session, it adds `The child gets no project skills (.pi/skills, .agents/skills): this project is trusted for this Pi session only, and children see only the trust saved for future sessions. To give children project skills, run /trust and choose Trust.` to its output. The host checks the trust on every model request, so a decision saved later applies from the next request. The host reads the instructions and skills of a directory once per trust decision and keeps them until it exits. It skips packages that are not installed. When the instructions or skills of a directory fail to load, the child gets none for that request, the host writes a warning, and the next request tries again. A child that the children library opens with `overlay` in its spec, a map of path to content, sees that content in place of the disk. A relative path is relative to the child's working directory, lexically; without a working directory, a relative path makes `open` fail with `The overlay key <path> is relative, and the child has no working directory`. A string replaces the file, and `null` removes it. The overlay changes the instructions and the skills that Pi loaded, and the `read` tool, which gives `ENOENT` for a removed file. A `SKILL.md` path that is not on disk adds a skill. A skill whose content has no description is not loaded, as in Pi, and for a name that two skills use, the first one wins. An overlay adds no instructions file. The other tools see the disk. A child that is opened with a parent that has an overlay gets that overlay, at every depth, also through the `subagent` tool. The child's own paths win, compared after they are resolved, and its own skill comes first when two skills have the same name. A child without an overlay and without an overlaid parent saves no overlay. The overlay is set when the child is created: a second `open` of its key keeps the first one.

### Push

When a child finishes, the host sends its unread answers to its caller, so the caller does not need `wait`. A request of a `spawn` or `send` with `notify: false` is quiet: its answer is not pushed alone, and it does not hold the caller. A child is done when its own turn ended and none of its children has an unread notify request, at any depth: until then, it holds its caller. The host checks this after each commit that can end a turn or change a record of a child, at host start, at the end of a `wait` or a `send`, and when an `answers` request opens or its reply is written. For a done child, it takes the unread answers as `wait` gives them, marks them read, and delivers them:

- The text is the answers in the form of `wait`, without its first line `<handle> finished` and the blank line after it. When the last turn failed or was aborted, `failed` is true and the text is the error of `wait`, such as `<handle> failed: overloaded` or `<handle> was aborted`.
- A caller that is a conversation of the host (a child, the project agent, or another conversation of the children library, such as one of a workflow task) gets the input `subagent <name> (<handle>) finished` (`subagent <handle> finished` for a child without a name), or `failed` in place of `finished` when `failed` is true, a blank line and the text: a new turn when it is idle, a follow-up when it works. Its request ID is `push:<handle>:<read>`, so a push that runs again after a restart does not repeat. The input reaches the caller before the child stops holding it.
- Any other caller, such as a Pi session, gets the answers as the reply to its open `answers` request, oldest child first. These answers become read only once the reply is written to the socket. When the write fails, or the connection closes first, they stay unread, for a later `answers` request or a `wait`; a `wait` that runs meanwhile waits until the write ends. Without an open request, the answers stay unread too. When the host stops after it wrote the reply and before it marked the answers read, the next `answers` request gives them again.
- A turn that a mirror session started sends nothing up: when the last request is mirror input, the answer that goes up is the one of the caller's last request.

The depth of the subagent tree is the setting `agentDepthLimit` in Pi's global `settings.json`, an integer of at least 1, default 4. The host reads it again at each spawn, and it applies to the new trees: a child of a child keeps the limit of its tree. A deeper spawn fails with `Nested subagents are disabled`. A tree that a library caller of the children library starts without a limit, such as one of workflows, keeps the limit of 2, also for the spawns of the `subagent` tool in it.

## Limits

- Children get only `read`, `grep`, `find`, `ls`, `write`, `edit`, `bash`, `subagent`, `codemode`, and the tools of the host's entries (see [Host](#host)). They get no MCP tools and no Pi extensions. `codemode` runs JavaScript that calls the other tools of the child, as Pi's `codemode` does. A script that a host stop interrupts continues when the host starts again.
- A change to `AGENTS.md` or to a skill reaches children only after the host restarts.
- `--file` gives text only; images are not attached.
- The CLI sends each `spawn` once and has no `key`. If the host stops during a `spawn` and you run the command again, there can be two children.

## Tool

The `subagent` tool does what the CLI does, with one `action` and its arguments:

| `action` | Arguments |
| --- | --- |
| `spawn` | `name`, `provider`, `model`, `thinking`, `cwd`, `tools`, `prompts`, `files`, `key`, `notify` |
| `send` | `handle`, `message`, `followUp`, `key`, `notify` |
| `wait` | `handle`, `timeout` (seconds, default 1800) |
| `status`, `stop` | `handle` |
| `rename` | `handle`, `name` |
| `list` | none |

`tools`, `prompts`, and `files` are arrays. A relative `cwd` or file path is relative to the caller's working directory. A caller without a working directory cannot spawn. The text result is the output of the same CLI command. The structured result is `{ action, value }`, and the tool declares its schema, where `value` is the host's reply: the child for `spawn`, `status`, and `rename`, `{ verb, child }` for `send`, `{ answer }` for `wait`, the children for `list`, and `{ handle, name }` for `stop`. A child is `{ handle, name, state, provider, model, thinking, cwd }`, where `state` is `busy`, `idle`, `error` or `closed`, and `cwd` is its working directory.

A spawn without `provider`, `model`, or `thinking` uses the caller's. A spawn refuses a `thinking` that the model does not have with `<provider>/<model> has no thinking level <level>`. Without `thinking`, the child gets the caller's level, or the nearest level that the model has. A `spawn` or `send` that comes again with the same `key` finds the first one and does not repeat it. Without `key`, the call is the key. Each caller has its own keys. When the call is aborted, for example with Esc, a `wait` stops; the child continues.

When a child finishes, its answer comes to the caller as a message that starts a turn (see [Push](#push)). `notify: false` on a `spawn` or a `send` turns off the message for the turns of that call; the answers then come only with `wait`. The CLI has no flag for it. The tool description tells the model to use `wait` only when it needs the answer in the same turn.

`subagent` calls in one message run one after another, in message order, so a `wait` after a `send` waits for the answer to that message. A round with a `subagent` call runs all of its tool calls in order, `bash` and `read` included.

The CLI runs each command as a call of the same tool. There are two other adapters:

- In Pi, the extension `@vzlentin/pi-agents` gives the tool (see [Pi extension](#pi-extension)). The caller is the session ID, the same as `PI_SESSION_ID` for the CLI, so `harness list` in that session shows the tool's children.
- In another pi-durable host, the entry `@vzlentin/harness/durable-entry` gives the tool. The caller is `<store>:<conversation ID>`, where `<store>` is a random ID that the store keeps. A call that runs again after the host restarts uses the same key, so its spawn or send does not repeat. Such a host gets the answers only with `wait`: it opens no `answers` request.

The children get the tool too. Their caller is their conversation ID, as for their bash commands.

## Pi extension

The Pi extension is the npm package `@vzlentin/pi-agents`, from the `pi/` folder of this repository: the `subagent` tool, the `/subagent` command, the subagents widget, the messages with the answers of the children, the mirror sessions (see [Mirror sessions](#mirror-sessions)), and the `subagent` skill, `pi/skills/subagent/SKILL.md`, which tells the agent how to use the tool and the `harness` CLI. The `pi` manifest of the package lists the extension and the `skills/` folder. `/subagent` lists the children of the session and opens the one that you select in Pi, in a new Herdr tab (see `openChildTab`); outside Herdr, it shows `Run in another terminal: harness attach <handle>`. The extension has the same version as harness. It has no copy of harness: `@vzlentin/harness` at that version is a dependency of `@vzlentin/pi-agents`, and the extension loads its `dist/` modules, so it starts the host of that install. It resolves each module from its own folder, as `@vzlentin/harness/<name>`, with the `exports` of the package. When Pi loads the extension, it also puts the `.bin` folder of the `node_modules` folder that holds `@vzlentin/harness` last on the `PATH` of Pi's process, so the agents find `harness`. It goes last because the folder also holds the commands of other dependencies, such as an older `pi`, which must not hide the user's own. It first removes that folder from `PATH`, so each load leaves it there once. When one of the `dist/` modules does not load, such as in a checkout without `npm run build`, Pi shows that the extension failed to load.

Each Pi session keeps one `answers` request open to the host, on a connection of its own, with the session ID as the caller (see [Push](#push)). For each answer, Pi shows a custom message of the type `subagent-answer` with the same text as the input of a push to a conversation of the host, and the answer as its details. The message starts a turn, as a follow-up when Pi works. At the session start, with or without a UI, the extension opens the request. It starts the host only when the session has a result of the `subagent` tool, so a session that spawned children gets the answers that came while Pi was closed. When the host closes the connection, the extension connects again at once, after 2 s and after 5 s, then every 5 s until a try connects. When no host runs at the session start, it tries every 5 s. When a connection closes less than 10 s after it opened, the next try is after 5 s. Only the first try at the session start can start a host. When Pi fails to show an answer, the extension shows the error as a notification, `Could not show the answer of a subagent: <error>`, and the next answers still come. At the session end, it closes the connection.

### Mirror sessions

A mirror session is a Pi session that shows a child or the agent of a project (see [Project agent](#project-agent)) in Pi's own chat, and sends what you type to it. The agent runs in the host of the project, so it continues when Pi closes. Below, the agent is the child or the project agent that the session shows. The mirror sessions work only in Pi's interactive mode. In another mode, a session with a `harness-mirror` entry, or a Pi with one of the `--harness` flags, fails at the session start with `harness: a mirror session works only in Pi's interactive mode`, and Pi's own agent does not take its input.

- `/harness <project>` opens a new Pi session that mirrors the agent of `<project>`, which is `main` or a project name. An unknown project is an error: `harness: Unknown harness project: <name>`. The command completes the project names. Without a project, it asks for one in the list `Harness project`, with one line `<name>  <dir>` for each project: the project of Pi's working directory first (as for a command), then the other projects, then `main` with `~`. When `main` is the only project, it opens `main` and does not ask. Esc cancels.
- `pi --harness <project>` mirrors the agent of the project in the session that Pi starts with, `pi --harness <project> --harness-child <handle>` mirrors a child of the project, and `pi --harness <project> --harness-conversation <id>` mirrors a conversation of the children library (see [Open in Pi](#open-in-pi)). Both `--harness-child` and `--harness-conversation` is an error: `harness: use --harness-child or --harness-conversation, not both`. Without `--harness`, or with an empty project, the project is the one of `HARNESS_PROJECT` and Pi's working directory. It refuses a session with messages, such as one of `--continue`: `harness: --harness needs a new session, not one with messages`. A session that is already a mirror session keeps its target, and at the startup Pi shows `harness: the --harness flags are not used: the session is already a mirror session`.
- The session has the title of the agent as its name, `<name> (<handle>)`, `<key>` for a conversation, or `<project> agent`, and follows a rename. It holds one custom entry, `harness-mirror`, with the target `{ project, handle }`, or `{ project, conversation }` for a conversation, and Pi draws the conversation of the agent in place of that entry, with Pi's message and tool components and Pi's theme (adapted from the attach view of [mavam/pi-agents](https://github.com/mavam/pi-agents)): the user messages, the answers with their thinking, and a Pi tool card for each call of `read`, `bash`, `edit`, `write`, `grep`, `find` and `ls`, with its output while it runs. Other tools get Pi's generic card. A compaction shows `[compaction]` and its summary, and a reset shows `[new context]`. The first line is `harness │ <title> │ <working directory>`. Pi saves a session only when it has a message, so it does not save a mirror session and `/resume` does not list it; run `/harness` again to open it.
- A message that you send goes to the agent: a new turn when it is idle, a steer when it works. Pi's own agent does not run. While the agent works, Esc aborts its turn, and the queued messages go back to the editor, steers first; Alt+Enter (`app.message.followUp`) queues the text as a follow-up. Before the connection opens and while the session connects again, Alt+Enter also sends the text as a follow-up, which waits for the connection. A conversation of the children library takes a message only while it works, always as a steer, also with Alt+Enter; when it is idle, the message goes back to the editor with `harness: not sent: <key> takes input only while it works`. The extension uses its own editor in the session for these keys.
- Above the editor, Pi's working indicator shows what the agent does (`Working...`, `Running <tool>...`, `Compacting (<reason>)...` or `Retrying (attempt <n>): <error>`), and each queued message shows as `Steer: <first line>` or `Follow-up: <first line>`.
- The answers of the agent follow Pi's `hideThinkingBlock` setting: Ctrl+T (`app.thinking.toggle`) hides and shows their thinking, as for Pi's own messages.
- The last line above the editor is `<title> • <usage> • <context>`, without the parts that are empty. The usage has the sums of the agent's model requests and tool results, as Pi's footer shows its own: `↑` input, `↓` output, `R` cache read, `W` cache write and `$` cost, each when it is not zero, and the cost also when Pi uses a subscription for the model, with `(sub)`. The context is `<percent>%/<window>`: the context of the agent's last answer that did not abort or fail, against the context window of its model, when Pi knows the model. Pi's footer stays as it is, for the local Pi session: Pi's own footer, or the footer of an extension.
- Pi's model and thinking level follow the agent's. A model that you select in Pi (`/model`, Ctrl+P) and a thinking level (Shift+Tab) go to the agent with a `configure` request. A refused change gives an error, and Pi goes back to the agent's model. The model that Pi takes from the agent is not a request. When Pi does not take the agent's model, Pi shows an error: `harness: Pi has no login for <provider>/<model>` without a login for it, or the error of Pi. When the agent changes its model while Pi takes the previous one, Pi then takes the new one. A conversation of the children library refuses each change, without a request, with `harness: A conversation of the children library keeps its model and thinking level`.
- When the host closes the connection, the session connects again, which starts a new host when none runs. It shows `Connecting again to the harness host...` above the editor. It tries three times: at once, after 2 s, and after 5 s. When all tries fail, the session shows `The harness host closed the connection. Connecting again failed: <error>`. When the host closes a connection that was opened again less than 10 s before, the session does not connect again and shows `The harness host closed the connection. Run /reload to attach again`. When the child is stopped, the session shows `<name> (<handle>) was stopped`. When the connection closes, each tool card that runs shows `Interrupted: no connection to the harness host`. `/reload` attaches again, and starts the host when none runs. `/new` and `/resume` leave the mirror session; the agent keeps running.
- A message that you send while the session connects waits for the connection. When the connection closes before the host answers a message, the message goes again on the next connection with the same request ID, so the agent gets it once. A message that does not reach the agent, because the host refuses it or the session fails first, goes back to the editor, after the text there, and Pi shows `harness: not sent: <reason>`. A message that went to the host on a connection that closed before the host answered, when the session then fails, may be with the agent: it does not go back to the editor, so that a send again does not give it twice. It stays in the history of the editor, and Pi shows `harness: maybe sent: <reason>. The text is in the history of the editor`.
- Images are not sent: the agent gets only the text, with the warning `harness: the images are not sent; the agent gets only the text`. Pi does not expand skill commands and prompt templates for the agent. Pi's own session commands act on the local Pi session, which has no messages: `/compact` fails with `Nothing to compact (session too small)`, `/fork` gives `No messages to fork from`, `/tree` shows `No entries found`, and `/export` fails with `Nothing to export yet - start a conversation first`.
