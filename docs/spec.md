# harness reference

The behaviour of the `harness` CLI, the `subagent` tool, the Pi extension and the host. The [README](../README.md) has the install.

## Commands

Spawn with a descriptive name using the default model and thinking level (see [Tool](#tool)):

```sh
harness spawn --name review --prompt "Review the current diff independently"
```

Spawn prints `Spawned <name> (<handle>)` and `State: <state>`, the state of the child (see `status`): `busy` for a new child, and the current state when a spawn with the same key repeats. Names appear in the parent UI. Generated handles remain the stable identifiers used by management commands.

Override the model configuration when needed:

```sh
harness spawn \
  --provider openai-codex \
  --model gpt-5.4-mini \
  --thinking low \
  --prompt "Find the relevant implementation"
```

Provide multiple prompt fragments and files. The first message holds the text of each file, then `Task:` and the prompts:

```sh
harness spawn \
  --file /tmp/spec.md \
  --prompt "Implement this specification" \
  --prompt "Run the targeted tests"
```

Restrict tools with `--tools`, a comma-separated list. Without it, a child gets `read`, `write`, `edit`, `bash`, `subagent`, `todo`, `thread`, `rule`, `parley`, `item`, `codemode`, and the tools of the host's entries (see [Limits](#limits)). A child at the depth limit gets no `subagent` and no `workflow`, but keeps `todo` (see [Push](#push)). An unknown tool name is an error:

```sh
harness spawn --tools read,bash --prompt "Investigate the failure"
```

A child lives as long as what it serves (see [Agent life](#agent-life)). By default, it serves its caller. `--parley <slug>` makes it serve a parley, and `--item <id>` a work item. A spawn takes one of them: with both, or one twice, it fails with `A spawn serves one thing: give --parley or --item once`. An `--item` that is not an integer from 1 fails with `Invalid item id: <id>`:

```sh
harness spawn --parley agent-life --prompt "Run the parley"
harness spawn --item 3 --prompt "Do the work item"
```

Manage a run by its generated handle:

```sh
harness status a1b2c3
harness rename a1b2c3 "error handling review"
harness send a1b2c3 "Focus on error handling"
harness send a1b2c3 --follow-up "Then summarize"
harness wait a1b2c3
harness stop a1b2c3
harness stop --conversation 42
harness list
harness query a1b2c3 "Which files did it change?"
harness attach a1b2c3
harness inspect a1b2c3
```

- `status` prints `<name> (<handle>): <state> (<provider>/<model>, <thinking>)`. The state is `busy`, `idle`, `error` when the last turn failed, or `ended` after a `stop`, or when the children library ended the child, such as a subagent under a workflow session whose run ended. After an abort from a mirror session, the state is `idle`. An ended child stays `ended`, also while its children hold it, until a `send` resumes it. A child that is not ended is also `busy` while one of its notify children holds it (see [Push](#push)), at any depth, so `status`, `list`, `wait`, the widget and a mirror session show it as `busy` until its subtree is quiet.
- `send` prints `Prompted`, `Steered`, or `Queued follow-up for`, then the child. A `send` to an ended child resumes it: it runs a new turn with its whole history. A steer goes in after the current tool round. A follow-up starts after the current answer. The verb comes from the child's own turn: a child that only its children hold is `Prompted`.
- `wait` waits until the child answers its last message, up to `--timeout` seconds (default 1800), and prints `<handle> finished`, a blank line, and the answer. When the spawn or an earlier `send` has an answer that no `wait` gave, it prints `<n> unread answers, oldest first.`, a blank line, and each answer after a line `--- Answer <i> of <n> ---`, the last one last. An earlier turn that failed gives `(no answer: <error>)`. A steer shares the answer of the turn it went into, so that answer comes once. A failed or aborted last turn is an error: after an abort, it prints `<handle> was aborted`. The error gives the earlier unread answers in the same form, and does not give the failed turn twice. Each `wait` marks these answers read. A message sent while a `wait` runs stays unread for the next `wait`. Input from a mirror session is not counted. While its children hold the child, `wait` waits too, and when a push starts a turn of the child meanwhile, `wait` gives the answer of that turn. While a `wait` runs, the host pushes no answer of that child. A `wait` for a turn whose answer a push already gave prints `<handle> finished`, a blank line, and `No new answers: the last answer came as a message.`. A second `wait` without a push between still gives the last answer again. A `wait` for an ended child, or for a child that ends while the `wait` runs, fails with `The child <id> ended: send a message to resume it`. When the host closes, a running `wait` fails with `The host is closing`.
- `stop` stops the work of the child and of the children it spawned, and ends them. They keep their handle, their record and their conversation, and their state is `ended`. It marks each request of these children read, so they hold no caller, and an answer that no `wait` or push gave is not pushed. A repeated `stop` finishes a stop that a crash interrupted. A `send` resumes an ended child; a note leaves it ended. A `spawn` that comes again with the request ID of an ended child gives that child and sends nothing. A name is a label and not a key: a `spawn` with a new request ID and the name of an ended child starts a new child with that name, and the ended child stays ended. `stop --conversation <id>` stops the conversation whose ID is `<id>`. The caller `cli`, a command from a terminal that is not an agent (`PI_SESSION_ID` is not set), can stop any conversation of the project that works, by handle or by conversation ID: the child of any caller, a conversation of the children library with no record of a child, such as a session of a workflows run, and the project agent with the handle `agent`. A conversation with no record of a child and the project agent are not ended: the stop aborts their turn, as Esc does, and keeps the conversation and its entries. It prints `Stopped <conversation id>` or `Stopped agent`. The owner of the conversation gets the failure of an aborted turn, such as a task that then fails, and the project agent stays and takes the next input. Another caller can stop only a child that it spawned (see [Host](#host) for the details and the errors). With more arguments, or with a first argument that starts with `--` and is not `--conversation`, it prints the usage.
- `list` prints one line per child of the current caller, the ended ones too: `<name> (<handle>)  <state>  <provider>/<model>  <thinking>`.
- `attach` opens the child in Pi in this terminal, and `attach --conversation <id>` a conversation of the children library (see [Open in Pi](#open-in-pi)). `--side` after the target opens it in a new herdr-app pane to the right of the caller. Without an ID, with an argument after the target other than one `--side`, or with a first argument that starts with `--` and is not `--conversation`, it prints the usage.
- `inspect` serves a web page that shows the child live and sends what you type to it (see [Inspect](#inspect)).
- `query <handle> <question>` prints the answer of a model to one question about the child, and `query --conversation <id> <question>` about a conversation of the children library, such as a session of a workflows run. The words after the target are the question. It is the action `query` of the tool (see [Tool](#tool)). Without a target or a question, or with a first argument that starts with `--` and is not `--conversation`, it prints the usage.

### Project agent

Each project has an agent, a conversation in its host that you talk to directly:

```sh
harness web
harness main
```

`harness <project>` opens the agent of the project in Pi in this terminal (see [Open in Pi](#open-in-pi)). It starts the host when none runs. A single word that is not `main`, a project or a command prints the usage. A `--project` before it is an error: `harness <project> takes no --project`.

- The agent works in the project directory, or in the home directory for `main`. Its system prompt, tools and bash env are the same as a child's in that directory (see [Host](#host)), with its memory too (see below). Its bash commands get `PI_SESSION_ID`, the agent's conversation ID.
- When it is first opened, the agent gets Pi's default model (`defaultProvider` and `defaultModel` in Pi's `settings.json`) when it has a login, else the first model with a login, and Pi's `defaultThinkingLevel` (default `medium`), or the nearest level that the model has. Without a model with a login, Pi does not start and `harness <project>` prints `No model for the <project> agent: log in to a provider and set a default model in Pi (defaultProvider and defaultModel)`. A mirror session changes its model and thinking level as for a child.
- The agent has a memory, an OptMem store: the folder `.optmem` in the project directory when it exists, else OptMem's default folder `~/.optmem/memory`, always for `main`. The host runs `~/.optmem/memo` with `MEMORY_DIR` set to that folder, or with no `MEMORY_DIR`. Its system prompt has the section `memory` (`MEMORY_SECTION`): the line `# Memory, oldest first`, then each memory line of every part of `memo wake`, with no status line and no compression prompt. The host takes this snapshot at the first model request of the agent after the host starts, and keeps it until the host exits, so the section does not change during the life of the host. When `wake` prints `Cannot wake`, the host first does the compressions, then runs `wake` one more time. An empty memory gives no section. A snapshot that fails, such as with no `memo`, gives no section and the warning `The memory section failed: <message>`; a missing `memo` gives `~/.optmem/memo is missing: install OptMem`.
- The agent has the `memory` tool, with one `action`: `note` saves `text`, trimmed, with `memo note`, and gives its line `Saved as #<N>.`, never the rest of the output; a note that `memo` refuses, such as a text over its limit of 280 bytes, fails with the error of `memo`. `recall` gives the output of `memo recall <pattern>`, and `zoom` the output of `memo zoom <block>`. An error of `memo` is the call's error: its error output, else its output. A call goes to the host in its own process, as a `memory` request (see [Host](#host)). The gate lets each `memory` call run (see [Host](#host)).
- The host does the compressions of the memory in the background, so the agent never sees a compression prompt. A `note` whose output has a compression prompt (`Compress memories #<a>-<b> into one line of at most <N> bytes.`), and a `Cannot wake`, start a loop: `memo nap`, then for each prompt one model call and `memo nap <a>-<b> "<line>"`, until no prompt is left. The model gets the prompt without its `Run:` line and its count of the compressions left, with the thinking level `low`. The line is the first line of its answer that is not empty, trimmed, and cut to `<N>` bytes at the end of a word, else at the end of a character. The model is the setting `memoryModel` of Pi's settings, read as `queryModel` is (see [Tool](#tool)), else `subagentModel`, else Pi's default model; the errors say `a compression` and `memoryModel` in place of `a query` and `queryModel`. One loop runs for each memory folder at a time: a note while it runs makes it run one more pass. A failure ends the loop with the warning `A compression of the memory failed: <message>`. A closing host stops the loop with no warning, and waits for its end.
- The children that the agent spawns have the agent as their parent: `harness list` with `PI_SESSION_ID` set to the agent's conversation ID shows them. The agent gets the answers of these children as input (see [Push](#push)). Its own state ignores its children.
- Esc stops only the agent's turn. The children that it spawned keep running.
- The agent keeps its conversation across host restarts. `status`, `send`, `wait`, `rename` and `list` do not know the agent: it is not a subagent. `harness stop agent` from a terminal that is not an agent aborts its turn, as Esc does, and the agent stays; an agent caller cannot stop it.
- Before each `input` request to the handle `agent`, the host catches the agent up. It keeps what the agent has seen in a `harness.seen` document of the agent's conversation, version 2: `{ mainSha, catchups, hooks, entry? }`, the head of the default branch, the count of catch-up entries, what each catch-up hook of the entries said the agent saw, by hook kind, and the catch-up entry that is not written yet. A version 1 document loses its `lastTaskId` and `pending`, and its hooks start with nothing seen. The catch-ups of the agent run one at a time. A repeated input, whose request ID the conversation already has, gets no catch-up. The host then reads, in the project directory, read only:
  - The default branch: the target of `refs/remotes/origin/HEAD` without `origin/`, else `main`, and its local head `refs/heads/<branch>`. Outside a Git repository, or without that branch, there are no commits and no warning. With a head in `mainSha`, the commits are those of `git log <mainSha>..<head>`, newest first. When the head does not contain `mainSha` (`git merge-base --is-ancestor` fails), as after a force-push, a change of `origin/HEAD`, or a `mainSha` that the repository no longer has, there are no commits, the entry tells it, and `mainSha` becomes the head, with no warning. When Git fails, the host writes a warning and keeps `mainSha`.
  - The catch-up hooks of the entries, in load order (see the entries below). The host calls `run(harness, seen)` of each hook with the host's harness and the `seen` that the hook returned at the last catch-up, or `undefined` the first time. The hook returns `{ seen, lines, data? }`: the `seen` to keep in `hooks[<kind>]`, the lines for the agent, none when nothing is new, and the data of these lines. A hook that throws or returns another shape gives the warning `catch-up: <kind>: <message>` and keeps its last `seen`, and the catch-up goes on.
  - The first time, with no `harness.seen` yet, the host only records the current state, and adds no entry. When nothing is new, it adds no entry.
  - Else it records the new state with `catchups + 1` and the planned entry in one commit, then adds one passive entry of the kind `harness.catchup` before the input, with the request ID `catchup:<catchups + 1>`, then removes the planned entry from the document. A catch-up first writes a planned entry that an earlier catch-up left, such as after a crash or a failed write; its request ID makes a repeat add nothing. The entry is a user message with the line `Catch-up since your last input.`, then the lines of each hook, then the branch name and each new commit as `<short sha> <subject>`, then a line when the branch no longer contains `mainSha`. Its `data` is `{ commits?, reset?, hooks? }` with the same facts: `commits` is `{ branch, commits: [{ sha, subject }] }`, `reset` is `{ branch, from, head }`, the old and the new head, and `hooks` has the `data` of each hook that gave lines, by hook kind. A missing field is left out.
  - A failure of the catch-up is a warning: the input always goes through.

### Projects

Each project has its own host, store and children. A project is a name and a directory:

```sh
harness create web --cwd ~/Dev/web
harness projects
```

- `create <name> --cwd <dir>` prints `Created <name> (<dir>)`, where `<dir>` is the real path of the directory. A relative `--cwd` is relative to the current directory. The name has 1 to 32 characters: `a-z` first, then `a-z`, `0-9` or `-`. It cannot be `main` or a command name (`spawn`, `status`, `rename`, `send`, `wait`, `stop`, `list`, `query`, `tree`, `parley`, `rule`, `todo`, `attach`, `host`, `create`, `projects`, `inspect`, `page` or `store`); `addProject` of `@vzlentin/harness/projects` refuses these names too, with `A project cannot have the name <name>`, and `COMMAND_NAMES` gives the command names. A name that exists, and a directory that does not exist, are errors.
- `projects` prints `<name>  <dir>` for each project, in creation order, then `main`.
- `--version` prints the version of the package. It takes no argument and no `--project`.

The projects are in `$XDG_CONFIG_HOME/harness/projects.json` (default `~/.config/harness/projects.json`), an object of name to directory. `create` saves the real path of the directory; a hand-written file can have another absolute path. A command that reads the file fails when a name does not follow the rule of `create` or a directory is not an absolute path.

A command goes to the project of `--project <name>`, which must come before the command (`harness --project carrefour list`), then of `HARNESS_PROJECT`, then of the current directory: the project with the longest directory that is the current directory or contains it. The comparison uses the real paths of the current directory and of each project directory, so a path through a symbolic link finds the same project as its real path; a path that does not exist is compared as written. Without a match, the project is `main`, which has no directory. When two projects have the same real directory, the first one created wins. An unknown project name is an error: `Unknown harness project: <name>`. The tool finds its project in the same way, from `HARNESS_PROJECT` and the current directory of their process. `connect` and `request` of `@vzlentin/harness/client` take a `project` option; without it, the project comes from `HARNESS_PROJECT` and the current directory. They fail with `HostUnreachableError` when no host answers: no host could start, the connection closed before the reply, the host was closing, or the host has another protocol version. An abort keeps its own reason, and another error that the host replies is a plain `Error`. The CLI passes `--project` in this option and does not set `HARNESS_PROJECT`, so the Pi of `harness attach` and a host that the CLI starts do not get it.

The caller is `PI_SESSION_ID`, or `cli` when it is not set. `list` shows only the caller's children. The CLI and the tool refuse to `send` to, `rename`, or `stop` a child of another caller; only the caller `cli` can `stop` the child of any caller. A mirror session does not check the caller, because the host socket is for one user: it can show, send to, and abort the child of any caller. It sends text with an `input` request, stops a turn with an `abort` request, and changes the model or the thinking level with a `configure` request. None of these requests has a caller.

`openChildTab` of `@vzlentin/harness/herdr` opens a child in Pi in a new herdr-app tab, in the space of the hc terminal of the caller. It reads the labels of that terminal with `hc get --json <HC_TERMINAL_ID>`, then runs `hc run --bg --keep --no-parent --cwd <cwd> [--name <name>] --label herdr.space=<space> -- <command>`, in the child's working directory. herdr-app shows a terminal with a `herdr.space` label in that space, in a new tab, and does not move the focus. The command is `[env XDG_STATE_HOME=<state> XDG_CONFIG_HOME=<config>] <node> <cli> --project <project> attach <handle>`, where `<cli>` is `dist/cli.js` of the install, or `src/cli.ts` of a checkout: `harness attach` with this Node and this install's CLI, so it does not need `harness` on `PATH`, on the project of the caller. hc gives the program the environment of the hc server, so `env` gives it each of `XDG_STATE_HOME` and `XDG_CONFIG_HOME` that is set for the caller; without both, there is no `env`. The name is `<name>` of the child (or its handle) in lowercase, with `-` in place of each character other than `a-z`, `0-9`, `-` and `_`, without the characters before the first letter or digit, and cut to 32 characters. When nothing is left, or when the name has the shape of an hc terminal ID (`t`, a digit from 1 to 9, then digits and the letters of `bcdfghjkmnpqrstvwxyz`, such as `t7`), there is no `--name`. Before `hc run`, it rejects with `Not in an hc terminal: HC_TERMINAL_ID is not set`, with `hc get gave no labels: <output>`, or with `The hc terminal <id> has no herdr.space label` when the label is missing or empty. When an `hc` call fails, it rejects with the stderr of `hc`, or with the reason that the call failed; when a live terminal has the name, that is the `name_taken` error of hc.

`openConversationPane` of `@vzlentin/harness/herdr` opens a children library conversation in Pi in herdr-app, in the conversation's working directory. It takes the conversation as a `ChildInfo`, a place, and the environment. For a conversation, `ChildInfo` gives the same ID in `handle` and in `conversation`. It runs `hc run` as `openChildTab` does, with the name from `<key>` and the command `[env ...] <node> <cli> --project <project> attach --conversation <id>`, on the project of the caller. With `{ space }`, the terminal gets `--label herdr.space=<space>`, and it does not read the labels of the caller: herdr-app opens a new tab in that space. With `{}`, the terminal gets the `herdr.space` label of the caller: a new tab in the space of the caller. With `{ side: true }`, the terminal gets the `herdr.space` and the `herdr.tab` labels of the caller: herdr-app splits the last pane of the tab of the caller to the right. Without `space`, it rejects before `hc run` as `openChildTab` does, also with `The hc terminal <id> has no herdr.tab label` for `{ side: true }`. When an `hc` call fails, it rejects with the stderr of `hc`, or with the reason that the call failed.

### Todos

Each agent and each run keeps a list of todos (see the `todo` request in [Host](#host)). A todo can have an optional `ask`, the ID of the ask that the todo `Save to the vault` belongs to (see [Asks and parleys](#asks-and-parleys)). Only the host sets it, and the line of a todo does not show it:

```sh
harness todo add Move the config to vite.config.ts
harness todo set 1 doing
harness todo
harness todo list --handle a1b2c3
harness todo sort
```

- `harness todo [list | add <text> | set <id> <state> [--text <text>] | sort]` sends one `todo` request, or for `sort` one `classify-todos` request. Without a word, the action is `list`. The options can come before or after the words.
- `add` adds a todo with the words after it, joined with a space, as `send` does with its message. `set` sets the state of the todo `<id>` to `open`, `doing`, `done` or `dropped`, and its text to the `--text` value when it is given.
- Without a target option, the list is the list of the caller, `PI_SESSION_ID` or `cli` (see [Projects](#projects)). One target option gives another list: `--handle <handle>` the list of a child, or of the project agent with `agent`; `--conversation <id>` the list of a conversation that the children library opened; `--task <key>` the list of the task of a `start`. The project agent keeps a list of its own, as any agent: `--handle agent` gives it.
- `add` and `set` print the line of the todo. `list` prints the line of each todo, in ID order, or `No todos` for an empty list. A line is `<mark> <id> <text>`, with the mark of the state: `○` open, `◉` doing, `✓` done, `✗` dropped. A text with a line break prints as it is.
- The command refuses a state that is not one of the four with `Invalid todo state: <state>`, an ID that is not an integer from 1 with `Invalid todo id: <id>`, an unknown option, such as `--project-list`, with `Unknown todo argument: <option>`, and an empty `add` text with `add requires text`, before it sends the request. The other errors come from the host, such as `The text of a todo is empty` and `Unknown todo: <id>` (see [Host](#host)). An unknown word, more words than the action takes, `add` or `set` without its words, `--text` without `set`, two `--text` options and two target options print the usage.
- The command runs as a call of `runTodoTool(args, scope, target)` of `@vzlentin/harness/tool`, the runner of the todo tool. `args` are the parameters of the tool, `{ action, text?, id?, state? }`. `target` is the list, as the `todo` request takes it (`ListTarget` of `@vzlentin/harness/protocol`): `{ handle }`, `{ conversation }`, `{ key }`, or `{}` for the list of the caller. The command gives the target of its target option. The `todo` tool gives `{}`, the list of its caller. The runner refuses an `add` without `text`, or a `set` without `id` or `state`, with `<action> requires <argument>`. Its result is the text that the command prints, and `{ action, value }`, where `value` is the reply of the host: the todo for `add` and `set`, and `{ todos }` for `list`. The `todo` tool of the host runs `runAgentTodoTool(args, scope)` of `@vzlentin/harness/tool`, which runs this runner on `{}` and, for `add` and `set`, takes its text from a `list` call (see [Tool](#tool)).
- `sort` asks the classifier of the todos (see `classify-todos` in [Host](#host)). Without a target option, it asks about the open work items (see [Items](#items)), with their titles as their texts; a target option gives a list, as for the other actions, and it asks about the open todos of that list. It prints one line for each answer, in ID order, as `<id>  needs you: yes|no  repeats: <id>|none`, or `No open items` without a target option and `No open todos` with one when there is none. The errors come from the host, such as `No classifier: log in to <provider> or set todoClassifier`.

### Items

`harness item` sends one `item` request (see the work items in [Host](#host)), and starts the host when none runs:

```sh
harness item
harness item add Move the config to vite.config.ts
harness item set 7 done
harness item set 7 --title "Move the config" --text "Keep the lint rules."
harness item show 7
harness item link parley:vite-config shapes item:7
```

- `harness item [list [--state <state>]]` prints the line of each item in the state `<state>`, default `open`, in ID order, or `No items`. A line is `<mark> <id> <stage> <title>`, where the mark is `?` when the item needs you, else the mark of its state: `○` open, `✓` done, `✗` dropped.
- `harness item add <title> [--text <text>]` adds an open item with the words after `add`, joined with a space, as its title, and prints its line.
- `harness item set <id> [<state>] [--title <title>] [--text <text>]` changes the fields that it gives of the item `<id>`, and prints its line. The state is `open`, `done` or `dropped`. Without a state and without an option, it prints the usage.
- `harness item show <id>` prints the line of the item, its text when it is not empty, then one line `<from> <kind> <to>` for each edge, in the order of their writes, then for each `needs` edge of another item that goes to it.
- `harness item link <from> <kind> <to>` writes the edge, and prints its line `<from> <kind> <to>`. The kind is `serves`, `shapes`, `landed` or `needs`.
- The caller is `PI_SESSION_ID`, else `cli` (see [Projects](#projects)). The command refuses, before it sends the request, an ID that is not an integer from 1 with `Invalid item id: <id>`, a state with `Invalid item state: <state>`, a kind with `Invalid edge kind: <kind>`, a reference with `Invalid item reference: <reference>`, and an unknown or repeated option with `Unknown item argument: <option>`. An unknown word, more or fewer words than the action takes, and an option that the action does not take print the usage. The other errors come from the host, such as `Unknown item: <id>`.
- The command runs as a call of `runItemTool(args, scope)` of `@vzlentin/harness/project-tool`, the runner of the `item` tool (see [Tool](#tool)), with `show` as the action `read`, and prints its text.

### Tree

`harness tree [--json]` sends one `tree` request (see [Host](#host)), and starts the host when none runs:

```sh
harness tree
harness tree --json
```

- It prints one line for each node, parents first: two spaces for each level, then `<mark> <name>  <state>  <n> open`, where `<n>` counts the todos of the node in the state `open`. The mark is `◉` for `busy` and `running`, `○` for `idle` and `pending`, `✓` for `ended` and `completed`, and `✗` for `error`, `failed` and `aborted`.
- `--json` prints the reply, `{ nodes }`, as one JSON line. Another argument prints the usage.
- A started task that did not end has its child tasks and their conversations under it. A started task that ended has only its own node, and only while it is one of the 50 newest started tasks.

### Parleys

`harness parley show <slug>` prints a parley of the project as Markdown, to read or to keep. It sends one `parley read` request with the slug (see [Host](#host)), and starts the host when none runs:

```sh
harness parley show asks-store
```

- The text is `# <title>`, then the goal, then a `## <n>. <title>` section for each ask in the order of their numbers, then `## Design sense` with the design sense and `## Evidence` with one `- <item>` line for each item. A blank line separates the blocks. The sections of the design sense and of the evidence are left out when the parley does not have them.
- The title line ends with ` (done)` or ` (dropped)` for a parley with that status. An open parley and a contract have the title alone.
- The section of an ask has one state line: `Answer: <label>` when it is answered, `Open, plan <key>: <label>` while it is open, `Open` when it is open with no plan, and `Dropped` when it is dropped. The label of an answer is the `own` label, else the label of the option of the key, else the label of the answer, else the key. The label of a plan is the label of its option. After the state line, each of the words of the user is its own paragraph. The kind, the tension, the view and the options of the ask are left out.
- The read-back, the ask of the parley with no options, is left out.
- With `--json` after the slug, the command prints the reply of the host as one line of JSON in place of the Markdown: `{ parley, asks }`, with each ask of the parley in the order of their numbers, the read-back included. A script, such as the page build of the parley skill, reads it.
- An unknown slug fails with `Unknown parley: <slug>`, and the other errors come from the host. Other arguments print the usage.

`harness parley note [<slug>] <ask> <note>` records `note`, the ID of the vault note that explains an ask, and prints the line of the ask, as the `parley` tool gives it (see [Tool](#tool)). With `<slug>`, `<ask>` is the number of the ask in the parley, and the command sends `ask note { caller, slug, n, note }`. Without it, `<ask>` is the ID of an ask, and the command sends `ask note { caller, id, note }`. The caller is `PI_SESSION_ID`, or `cli` when it is not set, and it must be the asker of the ask. It starts the host when none runs:

```sh
harness parley note asks-store 2 20261115-asks-store-2
```

- An `<ask>` that is not a positive integer fails with `Invalid ask: <ask>`, before any request. The other errors come from the host. Other arguments print the usage.

### Rules

`harness rule` lists the rules of the project, and makes the changes of a rule that only the user makes (see the `rule` requests in [Host](#host)). It starts the host when none runs. The caller is `PI_SESSION_ID`, or `cli` when it is not set:

```sh
harness rule [list [--kind <kind>] [--status <status>]]
harness rule (decide | retire | delete) <id>
harness rule edit <id> [--name <name>] [--kind <kind>] [--value <text>]
harness rule create --name <name> --kind <kind> --value <text>
```

- The action is the first word, `list` when there is none. The options come after the action.
- `list` sends `rule list` with the filters that it gets, and prints the line of each rule (see [Tool](#tool)), or `No rules`.
- `decide`, `retire`, `edit`, `create` and `delete` send the `rule` request of the same name, and print the line of the rule of the reply.
- An ID that is not a positive integer fails with `Invalid rule id: <value>`, a kind that is not `conduct` or `domain` with `Invalid rule kind: <value>`, a status that is not `open`, `decided` or `retired` with `Invalid rule status: <value>`, and an unknown option with `Unknown rule argument: <option>`. Other arguments print the usage. The other errors come from the host.
- The gate holds a `bash` call of an agent that runs one of these changes, until the user approves it (see the `gate` request in [Host](#host)).

### Store

`harness store load` writes the lists and the items of a store file, such as the `store.json` of another project (see [Host](#host)), into the store of the project. The project is `--project`, then `HARNESS_PROJECT`, then the cwd. The host of the project must be down: the command takes the lock of the host, and starts no host.

```sh
harness store load <file>
```

- The command checks the file before it opens the store. A file with a `version` other than 1 and 2 fails with `<file> has the version <version>: harness store load reads only the versions 1 and 2`. A file of version 1 has no `items` and no `lastItem`: the command moves its open todos to items with the rule of the first start of a host (see [Host](#host)), so `todos` gets the moved todos as `dropped`, `items` the new items and `lastItem` the highest ID of `todos`. A file that is not JSON, that does not match the schema of `store.json`, that has an ID twice, or whose references do not resolve fails with `<file> is not a store file: <reason>`. The IDs: each ID is there once in `persons`, `threads`, `rules`, `held`, `parleys`, `asks`, `todos`, `items` and each list of `callerTodos`, each message ID is there once in all the threads together, and each caller is there once in `callerTodos`. The references: each message names its thread, the `source` of each rule names a message of the file, and the `ask` of each todo of `todos` and of `callerTodos` names an ask of the file. A todo whose `ask` names no ask fails with `the ask of the todo <id> is no ask of the file`, or `the ask of the todo <id> of <caller> is no ask of the file` for a list of `callerTodos`. Each edge of an item is an edge of that item: its kind takes its ends, and the item that stores it is the item, the `from` item for an edge from an item, else it fails with `the edge <from> <kind> <to> is not an edge of the item <id>`. Each `needs` edge goes to an item of the file, else it fails with `the edge <from> needs <to> goes to no item of the file`, and the `needs` edges of the file make no cycle, an edge from an item to itself included, else it fails with `the needs edges make a cycle through the item <id>`, where `<id>` is an item of the cycle. The schema gives each message out `changed` and no message in.
- When a host runs for the project, it fails with `A harness host runs for <project>: stop it, then run harness store load again`.
- When a list of the store has an item, it fails with `The store of <project> is not empty: harness store load writes only into an empty store`. The highest ID that a rule had and the counter of the IDs of items do not count.
- The store cannot keep the IDs of the threads and the messages. Each thread gets a new ID and each message a new ID, in file order, and the `source` of each rule gets the new ID of its message, and its `thread` the new ID of the thread of that message, whatever `thread` the file gives. Text that holds an ID, such as the command of a held action or the text of a message, does not change. The IDs of the persons, rules, held actions, parleys, asks and todos, and the callers, do not change, so a todo keeps its `ask`. Each message out gets its state in the outbox of the store: its `state`, its `at` as the time it was written, and the last change of its state from `changed`.
- The highest ID that a rule had is the higher of `lastRule` and the one of the store, so the ID of a deleted rule is never given again.
- The items keep their IDs and their edges. The `last` of the counter of the IDs of items is the highest of `lastItem`, the `last` of the store and the highest ID of `items`. The commit always writes the counter, so the next start of a host does not move the loaded todos to items.
- The command writes all the lists in one commit, also the list of each caller with no todos. When the store has no root conversation, that commit creates it.
- It prints one line `<list>: <count>` for each list, in this order: `persons`, `threads`, `messages`, `rules`, `held`, `parleys`, `asks`, `outbox`, the messages out, `todos`, `callerTodos`, the todos of all the callers, and `items`. Other arguments print the usage.

## Open in Pi

`harness attach <handle>` opens a child in Pi in the current terminal, `harness attach --conversation <id>` opens a conversation that the children library opened, such as a child of a task, and `harness <project>` opens the agent of the project. They start the host when none runs, and check the target before Pi starts: an unknown handle is an error, `Unknown subagent: <handle>`, an unknown conversation or a root is an error, `Unknown conversation: <id>`, and so is a project agent without a model. Then they run `pi --harness <project>` for the project agent, `pi --harness <project> --harness-child <handle>` for a child, or `pi --harness <project> --harness-conversation <id>` for a conversation, which opens a mirror session (see [Mirror sessions](#mirror-sessions)), and exit with the exit code of Pi. They run the `pi` of `PATH` without the `node_modules/.bin` folders; without one, the error is `pi is not on PATH. Install Pi to open the agent`. That Pi needs the extension of the package (see [Pi extension](#pi-extension)). Closing Pi never changes the child.

`harness attach (<handle> | --conversation <id>) --side` in an hc terminal (`HC_TERMINAL_ID` is set) does not start Pi in this terminal. It checks the target as above, then runs `hc run --bg --keep --no-parent` with the `herdr.space` and `herdr.tab` labels of the caller's hc terminal, so herdr-app shows the target in a new pane to the right in the caller's tab. That terminal runs `harness --project <project> attach <target>`, without `--side`, in the cwd of the target. The command exits with 0 when `hc run` succeeds. When the caller's terminal has no `herdr.space` or `herdr.tab` label, it fails with `The hc terminal <id> has no <label> label` and starts no terminal. When an `hc` call fails, it fails with the stderr of `hc`. Both exit with 1. Outside an hc terminal, `--side` runs Pi in this terminal, as without it.

In every terminal, the mirror session reports the state of the agent to the terminal with the Program Status Protocol (OSC 7501), through Pi's `setProgramStatus`, with `app: "harness"`. It reports when it starts and at each change of the state or of the message. While the session connects again to the host, the state is `blocked`, with the message `<title> (connecting again)`. On an open connection, a busy agent is `working`, an agent whose last request failed is `error`, and an idle agent after a turn is `done`, with the title as the message, until its next turn. An aborted turn also ends in `done`. `done` stays while the session connects again: an idle agent on the connection that opens again is `done`. An error, an ended agent and a connection that failed end `done`. All other cases are `idle`: an idle agent before its first turn in the session, an ended agent, the connection before the first one opens, and a connection that failed. The message is the title of the agent (the name or the handle of a child, `<key>` for a conversation, `<project> agent` for the project agent). Before the first connection, a child has its handle and a conversation its ID. A rename changes the title. For `error`, the message is the first line of the `errorMessage` of the last assistant message with `stopReason: "error"`, trimmed, or `Error` when there is none. When a dialog of Pi ends (`ui_prompt_end`), Pi writes its own state, so the session reports its state one more time, also when it did not change. When Pi leaves the mirror session, it reports `idle` with the title one more time.

## Inspect

`harness inspect` serves a web page that shows a conversation of a host live, as a mirror session does in Pi (see [Mirror sessions](#mirror-sessions)), and sends what you type to it:

```sh
harness inspect a1b2c3
harness inspect --conversation 42
harness --project web inspect --tailscale
```

- `harness inspect [<handle> | --conversation <id>] [--port <n>] [--host <ip> | --tailscale]` listens on port 7501, or on a free port with `--port 0`. It prints one URL for each address that it listens on, `http://<address>:<port>/`, with the target in the query: `?project=<project>&handle=<handle>` for a child, `?project=<project>&conversation=<id>` for a conversation, and `?project=<project>` for the handle `agent` and for `--project <name>` without a target. The project is the project of the command (see [Projects](#projects)). Without a target and without `--project`, the URL has no query, and the page shows the picker. The command runs until SIGINT or SIGTERM, then closes its connections.
- It listens on `127.0.0.1` only. `--host <ip>` listens on that address only, so it listens on `0.0.0.0` only with `--host 0.0.0.0`. `--host` takes an IP address or `localhost`, because the routes refuse another name in the `Host` header (see below); another host is an error: `The host must be an IP address or localhost: <host>`. `--tailscale` listens on `127.0.0.1` and on each IPv4 address that `tailscale ip -4` gives, on the same port. Both `--host` and `--tailscale` is an error: `Use --host or --tailscale, not both`. When `tailscale ip -4` fails, the error is `tailscale ip -4 failed: <stderr>`, and without an IPv4 address in its output, `tailscale ip -4 gave no IPv4 address`. `--port` takes an integer from 0 to 65535; another value is an error, `--port must be an integer from 0 to 65535`. An unknown option is an error, `Unknown inspect argument: <option>`, and two targets print the usage.
- With `project` in its query, the page shows the target: the project agent, the child of `handle`, or the conversation of `conversation`. Without `project`, it shows the picker: each project, then `main`, with its directory, and the project agent and the children of each running host, each with a link that has its title, as in a mirror session, then its state and its model as in the header. A project whose host does not run has only a link to its agent, `agent`, and opening it starts the host. A running host without a target to show has the line `the host runs, with no target to show`.
- The header has the title of the agent, as in a mirror session, its model and thinking level, as `<provider>/<model> • <thinking>`, its state (`busy`, `idle`, `error` or `ended`), and the connection (`connecting`, `open`, `reconnecting`, or `failed: <reason>`). The title of the page is `<title> · harness inspect`.
- The transcript has the user messages, the typed inputs (`harness.typed`) among them, the answers with their thinking, folded, each tool call with its arguments and its result, folded, with an error result in the error colour, the output of a running tool, the passive notes, catch-ups and digests, `[compaction]` with its summary, and `[new context]`.
- The footer has what the agent does, as Pi's working indicator says it, each queued message as `Steer: <first line>` or `Follow-up: <first line>`, and the usage: `↑` input, `↓` output, `R` cache read, `W` cache write and `$` cost, each when it is not zero, then `ctx <tokens>`, the context of the last answer of the active transcript. The page knows no context window, so it shows no percent. Below is a message box. While the agent is idle, `Send` starts a new turn. While it works, `Steer` and `Follow-up` queue the message, and `Stop` aborts the turn. Enter sends, Shift+Enter adds a line, Alt+Enter queues a follow-up while the agent works, and Esc stops the turn while the agent works. On the page of `harness inspect`, Esc works wherever the focus is. On a page that mounts only the view, Esc works while the focus is in the view, such as after a click in the transcript. A conversation of the children library takes a message only while it works, always as a steer: it has no `Follow-up`, and the box is off while it is idle. A message that the server refuses stays in the box, with `not sent: <error>`.
- The page puts all text in as text, never as HTML, so the output of an agent cannot run in it.

`@vzlentin/harness/inspect` gives the routes, so that another server, such as `workflows web`, can serve them on its own port. A server that mounts the handler also serves the pages of `harness page` (see [Pages](#pages)). `createInspectHandler({ start? })` gives a handler `(req, res) => Promise<boolean>`, which is false for a request that is not one of these routes. `startInspectServer({ hosts?, port?, start? })` serves the page at `/` and the routes, with one server for each address of `hosts` (default `127.0.0.1`), all on one port (default 7501, or the free port of the first address for 0), and gives `{ urls, close() }`. It refuses a host that is not an IP address or `localhost` before it listens, with `The host must be an IP address or localhost: <host>`. `close()` also closes the open connections. `resolveBindHosts({ host?, tailscale? })` gives the addresses of the CLI options, and refuses such a `host` with the same error. The routes are:

- `GET /assets/inspect.js` and `GET /assets/inspect.css`: the browser files, from the `web/` folder of the package, with no other dependency. `inspect.js` exports `mountInspect(container, { project, handle?, conversation? }, { onTitle? })`, which shows the target in `container` and gives `{ interrupt(), close() }`, and `mountPage(container)`, the page of `/`, which gives `{ close() }`. `onTitle(title)` runs each time that the title of the agent changes. `interrupt()` stops the turn while the agent works and gives true; otherwise it does nothing and gives false. The view listens to its keys on its own root, and a click in the transcript gives the focus to the view. `mountPage` also listens to Esc on the document, and gives to `interrupt()` each Esc that the view did not take. Each rule of `inspect.css` selects only elements with a class that starts with `inspect`, or elements below `.inspect` (the view), `.inspect-picker` (the picker) or `.inspect-page` (the page of `/`), so the view does not change the page that mounts it.
- `GET /api/inspect/projects`: `{ projects: [{ name, dir }, ..., { name: "main" }] }`, in creation order.
- `GET /api/inspect/targets?project=<name>`: `{ project, running, targets }`. `running` tells whether the host of the project runs. `targets` has the info of the project agent, then the children of the caller of the server process, in that host, each with `title`, its title as in a mirror session. The caller is `PI_SESSION_ID`, or `cli`, as for `harness list`. When that host does not run, `running` is false, `targets` is empty, and the route does not start the host. The agent is not in `targets` when its watch fails, such as without a model.
- `GET /api/inspect/stream?project=<name>[&handle=<handle> | &conversation=<id>]`: Server-Sent Events (`text/event-stream`) from a mirror of the target. Each event is one `data:` line with a frame `{ status, title, child, view, summary }`: the status of the mirror, the title of the agent (its handle or conversation ID before the first connection), its info, its whole conversation view, and `{ statusText, queued, usageTotals, lastAnswerUsage }`. `child`, `view` and `summary` are not there before the first connection, and `lastAnswerUsage` is not there before an answer. One frame comes at once, then one after each change. When the client reads more slowly than the frames come, only the newest frame waits. When the mirror fails, such as for an unknown child, the last frame has `status: { kind: "failed", reason }`, the stream ends, and the page does not connect again. When the client closes the connection, the mirror closes.
- `POST /api/inspect/input` with `{ project, handle?, conversation?, message, followUp? }` sends an `input` request with a new request ID, and `POST /api/inspect/abort` with `{ project, handle?, conversation? }` sends an `abort` request. Each replies `{ ok: true }`.
- `GET /api/inspect/asks?project=<name>&parley=<slug>` sends `parley read { slug }` and replies with its reply, `{ parley, asks }`, with the asks in every state.
- `POST /api/inspect/answers` with `{ project, parley, answers: [{ n, answer, label?, words? }] }` writes the answers of the user to the asks of the parley `parley`. Each answer names its ask by `n`, its number in the parley; an answer with `slug` or `id` gets 400. The route checks the answers as `ask answer` does, then sends one `ask answer { caller: "page", answers, user: true }`, with `slug` set to `parley` in each answer, and replies with the write. The caller `page` is never an asker, so each asker gets its delivery. The answers count as the answers of the user, with the limit of the mark (see [Asks and parleys](#asks-and-parleys)).
- `GET /pages/<slug>/<file>`: the files of a page of `harness page`, with the script of the Send in an HTML file whose query has a target (see [Pages](#pages)).
- Without `handle` and `conversation`, the target is the project agent, as with the handle `agent`. A stream, an input, an abort, and a read or a write of asks start the host of the project when none runs. With `start: false`, they do not: all but the stream then fail with `The harness host of <project> is not running`.
- A request that is not valid gets 400 with `{ error }`: a query or a body that does not match, such as `Invalid query: must have required properties project`, `Give handle or conversation, not both`, `The message is empty`, `Unknown harness project: <name>`, a POST that is not `application/json` (`The body must be application/json`), and a body that is not JSON (`The body is not JSON`) or is longer than 1 MiB (`The body is longer than 1 MiB`). An error of the host gets 500 with `{ error }`, such as `<key> takes input only while it works`. On the routes of the asks and the answers, a refusal of the host gets 400 with `{ error }`, such as `Unknown parley: <slug>`, `Ask <id> is dropped: it takes no answer` or `Ask <id> takes a, b or own`, and the write changes nothing; a host that does not run or does not answer gets 500. Another path under `/api/inspect/` gets 404.
- Each route under `/api/inspect/` and `/pages/` gets 403 when the `Host` header is not an IP address or `localhost`, so that the DNS name of another site that points at the server (DNS rebinding) cannot reach the routes. This refuses a Tailscale MagicDNS name too: use the address. The routes have no login: each client that reaches the address can read and steer the agents of the user. `127.0.0.1` keeps them on this machine, and `--tailscale` on the tailnet.

### Pages

`harness page` copies an HTML page, such as the classic page of a parley, to the pages of the inspect routes, and prints its link. The Send of the page posts its answer line to an agent, which takes it as a message:

```sh
harness page /tmp/parley-demo --slug demo
harness page /tmp/parley-demo --slug demo a1b2c3 --tailscale
```

- `harness page <folder> --slug <slug> [<handle> | --conversation <id>] [--port <n>] [--host <ip> | --tailscale]` copies the page to `$XDG_STATE_HOME/harness/pages/<slug>/` (default `~/.local/state/harness/pages/<slug>/`). The slug is lowercase words of letters and digits, joined with hyphens, as the parley skill gives it. The copy has the regular files at the top level of `<folder>` whose names do not start with `.`. It skips folders and symbolic links. It replaces the earlier copy of the slug. A copy that fails, such as for a file that it cannot read, keeps the earlier copy of the slug.
- The Send posts to the target of the arguments. Without a target, the command sends a `whoami` request with the caller `PI_SESSION_ID` to the host of the project (see `host.sock` in [Host](#host)): a child gets its own handle. The project agent, and a caller that the host does not run, such as a Pi session, get the project agent of the project, which comes from `--project`, `HARNESS_PROJECT` or the working directory. The command does not start the host.
- It prints one link for each address, as `harness inspect` does: `http://<address>:<port>/pages/<slug>/` with the query of the target, `?project=<project>&handle=<handle>`, `?project=<project>&conversation=<id>`, or `?project=<project>` for the project agent. The addresses come from `--host` and `--tailscale` as for `harness inspect`, and the port is 7501 without `--port`. The command starts no server. It tries a TCP connection to each address for 1 s, and when nothing listens there, the line ends with `  (no server listens: harness inspect serves the pages)`. Each server that mounts the inspect routes serves the pages, such as `harness inspect` on the same port.
- These errors stop the command with code 1 before the copy, so the earlier copy stays: the usage for a missing folder or `--slug`, two targets or an extra word; `Unknown page argument: <option>`; `The slug must be lowercase words with hyphens: <slug>`; `No index.html in <folder>` when `<folder>/index.html` is not a regular file; `Give <handle> or --conversation <id>: PI_SESSION_ID is not set`; `The harness host of <project> is not running`; and, as for `harness inspect`, the errors of `--port`, of a `--host` that is not an IP address or `localhost` (`The host must be an IP address or localhost: <host>`), of both `--host` and `--tailscale`, and of `tailscale ip -4`.
- `GET /pages/<slug>/<file>` serves the file of the copy, and `GET /pages/<slug>/` serves `index.html`. The content type comes from the extension: `.html` `text/html; charset=utf-8`, `.svg` `image/svg+xml`, `.css` `text/css; charset=utf-8`, `.js` `text/javascript; charset=utf-8`, `.png` `image/png`, `.json` `application/json; charset=utf-8`, and `application/octet-stream` for another file. Each reply has `cache-control: no-cache`.
- An HTML file whose query has `project`, `handle` or `conversation` gets one script before its first `</head>`, in any case. A file without `</head>` goes as it is. The query takes the target as the stream route does, so `?project=<project>` alone is the project agent. The script defines `window.sendPrompt(text)`, which the Send button of an artifacts page calls. It posts `{ project, handle, message }` or `{ project, conversation, message }` to `POST /api/inspect/input`, so an idle child or project agent starts a turn with the message. At its first call, it adds one line to the body of the page, at the top centre, in a 16px font. A call with the same text as the last post that succeeded posts nothing and sets the line to `already sent ✓`. Another call adds a layer that covers the page, dims it by 8% and blocks clicks, sets the line to `sending…` and posts. A call while a post runs does nothing. When both the post and a 400 ms delay end, the layer goes and the line shows `sent ✓`, or `not sent: <reason>`, where the reason is the `error` of the reply, its HTTP status, or the error of the request. A failed post does not change the last text that succeeded. The script also defines two calls for the parley whose slug is the slug of the page, so a page answers only its own parley. `window.readAsks()` gets `GET /api/inspect/asks` with the project of the query, and resolves to `{ parley, asks }`, or rejects with the `error` of the reply, its HTTP status, or the error of the request. `window.sendAnswers(answers)` posts `{ project, parley, answers }` to `POST /api/inspect/answers`, where each answer is `{ n, answer, label?, words? }`, so the asks are answered at Send, with no answer line. It shares the line and the layer of `sendPrompt`, and the same rules: a call while a post runs does nothing and resolves to undefined, and a call with the same answers, as JSON text, as the last post that succeeded posts nothing, sets the line to `already sent ✓`, and resolves to the write of that post. It resolves to the write of the host when the post succeeds, and to undefined when it fails. The script itself is ASCII. The target and the slug go into the script as JSON with each `<` escaped, so they cannot end the script. Another file, and an HTML file with no target in its query, go as their bytes.
- The route gives 404 with `{ error: "Not found: <method> <path>" }` for a method that is not GET, a path that is not `/pages/<slug>/<file>`, a slug that is not valid, a file name that does not percent-decode, a decoded file name with `/` or `..` or a leading `.`, and a file that does not exist or that is a folder. An HTML file with a query that is not valid gets 400 with `{ error }`, as the stream route does, such as `Unknown harness project: <name>` or `Give handle or conversation, not both`.

## Host

The children of a project run in one host process, `harness --project <name> host` (default `main`). The host takes its project only from `--project`, not from `HARNESS_PROJECT`. The first command that needs it starts it in the background, and tries to connect for 10 s. A started host that exits with code 0 found the lock held by another host, such as one that closes after its idle time: the command then starts a host again, at most once per second. A started host that exits in another way fails the command at once with `The harness host exited with <code N or signal S>; see <host.log>`. When the started host still runs after 10 s, the command fails with `The harness host (pid <pid>) is still starting: it can wait up to 60 s for the lock of durable.sqlite. Run the command again soon; see <host.log>`; otherwise with `Could not start the harness host; see <host.log>`. It exits after 5 minutes with no connection, no running work, no compression of the memory (see [Project agent](#project-agent)), and no command other than `list`, `status`, `answers`, `tree`, `watch-tree`, `watch-project`, `classify-todos`, a `todo`, `person`, `rule` or `ask` request with the action `list`, and a `thread`, `parley` or `item` request with the action `list` or `read`. A connection with an open `answers` request does not count. An open mirror session, an open `watch-tree` and an open `watch-project` are connections, and a live started task is running work, so each keeps the host running. A task that no loaded entry can run, such as one of an entry that was removed, is not running work, and neither is a task that waits only on such tasks. The host waits up to 60 s for the lock of `durable.sqlite`, so a client that reads the file, such as the workflows CLI, does not make it fail. The wait is synchronous: while it lasts, the host answers no request. When the host closes, it stops listening, stops each running request, such as a `wait` or an `answers` request, which then fails with `The host is closing`, and waits until the replies of all requests are written. A request that comes while the host closes fails with `The host is closing` and does not run. The host then closes the connections.

On macOS, the host holds the Mac awake while it has active work: while `wake().active` of pi-durable is true, which means a task can run now or runs. Parked work, such as a sleep that is not due or a task that waits for a child, does not count. The hold is `caffeinate -s -w <host pid>`, so it works only on AC power, and it ends with the host. The host reads `wake().active` every 5 s, and does not wait for a commit: active work can start or end without a commit, such as a sleep that falls due or the wake recompute after a failed migration, and `wake()` is synchronous and reads from memory. The host releases the hold 30 s after the last read with active work, so the release comes 30 to 35 s after the work ends. Work that comes back within the 30 s keeps the same hold. The close of the host releases the hold. When `caffeinate` cannot start, the host writes one warning, `caffeinate cannot start: <message>`, to `host.log`, and tries no more. Other systems get no hold.

The host keeps its degraded states in memory, and `watch-project` gives them (see the `watch-project` request below). A state is `{ kind, line, since }`: its kind, a line for the user, and the time of its start in epoch milliseconds. The host keeps one state for each kind and cause. A state starts when its cause starts and ends when its cause ends. A cause that continues keeps its `since` and takes the new line. A source that writes a warning to `host.log` writes it for its state too, and the `gate-classifier` and `no-classifier` states write none. `DEGRADED_KINDS`, `DegradedKind` and `DegradedState` of `@vzlentin/harness/protocol` give the kinds and the schema. The kinds, their causes, their lines and their ends:

- `gate-classifier`: the classifier of the gate failed after the host found its model. The line is the reason of the held call, such as `The classifier <provider>/<id> failed: <message>`. It ends at the next gate call whose classifier answers. It has no warning.
- `no-classifier`: one for `gateClassifier` and one for `todoClassifier`, when the setting has no classifier model with a credential. The line is `No classifier: log in to <provider> or set <setting>`. It ends when a gate call or a `classify-todos` request finds the model. It has no warning.
- `package-skipped`: one for each `package.json` that the host skipped at its start, with the line of its warning. It ends with the host.
- `entry-skipped`: one for each entry of `entries.json` with no module, with the line `The entry <name> has no module at <path>; the host skips it`. It ends with the host.
- `push-failed`: one for each delivery whose last push failed and waits, the answers of a child (its handle) or an answer of the user (`user-answer:<id>`). The line is `The push of <key> failed: <message>`, and the warning is the message. It ends when a push of the delivery works, or when the record of the child or the answer goes.
- `approve-tell`: one for each approved action whose tell to its agent failed. The line is `The tell of approved action <id> failed: <message>`, and the warning is the message. It ends when the approved command runs through the gate.
- `answer-waits`: one for each asker with answers of the user and nowhere to push them: it is not a conversation of the host and has no open `answers` request. The line is `The answers of the user wait for <asker>, which has no answers request open`. It ends when the asker gets a place for its answers, or when no answer waits for it. It has no warning.
- `awake-failed`: `caffeinate` cannot start, with the line of its warning. It stays, because the host tries no more.
- `catch-up-failed`: a catch-up of the project agent failed (the line `catch-up: <message>`), a catch-up hook threw (one for each hook kind, `catch-up: <kind>: <message>`), or Git failed (`catch-up: git: <message>`). Each ends at the next catch-up, call of the hook or read of Git that works.
- `digest-failed`: one for each conversation whose digest failed, with the line `digest: <message>`. It ends at the next digest of the conversation that works or has nothing to write.
- `resources-failed`: one for each directory whose project instructions and skills failed to load, with the line `<cwd>: <message>; no project instructions or skills`. It ends at the next load of the directory that works.

A pi-durable report and a failed pass of a watch are events, not states: a report is a warning in `host.log`, and a failed pass ends its connection with no warning. A `bash` call that the default limit stops is not a state: the model sees it in the result of the tool. Only a client sees the states where the host does not answer: no host, a host of another protocol, a store that the host cannot read, an entry that stops the start of the host, and a failed `gate` request of the Pi extension.

The host keeps its state in `$XDG_STATE_HOME/harness/<project>/` (default `~/.local/state/harness/<project>/`):

- `durable.sqlite`: the children's conversations and records, the started tasks, the lists of todos, the store of the project (persons, threads and their messages, rules, held actions, parleys and asks, and work items), and the project agent, which is the store's root conversation. A host opens a store with the `harness.terms` and `harness.parts` documents of an older version, and does not read them. Work that a host stop interrupts continues when the host starts again. A host refuses a `durable.sqlite` from a version before the children library: stop the old host, remove the file and run the command again. A host opens a `durable.sqlite` from an older version with the children library, and keeps its children and their records. A child that an older host marked `rlm` loads as any child. A child of a store from before `serves` serves its spawner.
- `lock.sqlite`: one host at a time.
- `store.json`: the lists of the store, which a program can read with no host. The host writes the whole file when it starts, and again after each commit that changes a list, through a temporary file and a rename. It is a JSON object with `version` (2) and one key for each list: `persons`; `threads`, each thread with its `messages`, oldest first, each with its state and its edits, and with no deleted message, and each message out with `changed`, `{ at, by }`, the last change of its state; `rules`; `lastRule`, the highest ID that a rule had, 0 when no rule was set; `held`; `parleys`; `asks`; `todos`, the list of the project agent, each todo with its `ask` when it has one; and `callerTodos`, `[{ caller, todos }]` for each caller that is not a conversation of the host, such as a Pi session, in caller order; `items`, every item in ID order, each with its edges; and `lastItem`, the `last` of the counter of the IDs of items, 0 when the store has no counter. The host also writes the file after each commit that changes an item or the counter. A write that fails gives the warning `Could not write <path>: <message>` in `host.log`, and does not fail the commit.
- `host.sock`: the socket the CLI and the extension connect to. The protocol has version 39. A `spawn` request has `provider` and `model` only when the spawn itself gives them, and the caller's own model in `callerProvider` and `callerModel`, next to its level in `callerThinking`; the host picks the model and the level (see [Tool](#tool)). A `whoami` request `{ caller }` replies `{ handle? }`: `agent` when the caller is the conversation ID of the project agent, and the handle of the child whose conversation ID it is. Another caller, such as a Pi session, `cli` or a conversation of a task, gets `{}`, with no handle. `harness page` sends it (see [Pages](#pages)). The `spawn` and `send` requests have `notify`, a boolean: false turns off the push of the answers of that request (see [Push](#push)). A `spawn` request can have `serves`, what the child serves: `{ parley: <slug> }` or `{ item: <id> }`, each with no other key, so a slug of digits only is never an item ID. A `serves` of another shape fails with `Invalid spawn request: serves: <rule>`. The host fixes the kind at the spawn: an open parley gives `{ kind: "parley", slug }`, a contract `{ kind: "contract", slug }`, a work item `{ kind: "item", id }`, and a spawn without `serves` `{ kind: "spawner" }`. It refuses an unknown parley with `Unknown parley: <slug>`, a parley that is done or dropped with `Parley <slug> is <status>: an agent cannot serve it`, an unknown item with `Unknown item: <id>`, and an item that is done or dropped with `Item <id> is <state>: an agent cannot serve it`. A spawn with `{ item: <id> }` writes the edge `agent:<conversation ID> serves item:<id>` into the item, with the caller as `by`, in the commit that creates the child and its record. The record keeps `{ kind: "item" }` with no ID: the edge holds the ID. A spawn that comes again with the same request ID writes no second edge. The info of a child has `serves`, as the host fixed it; for a child that serves an item, it is `{ kind: "item", id }` with the ID of the item whose `serves` edge names the child, and a child whose edge was unlinked has none. The info of the project agent has `{ kind: "project" }`, and a conversation of the children library with no record of a child has none (see [Agent life](#agent-life)). An `answers` request `{ caller }` waits until the host pushes answers to `caller` (see [Push](#push)), and replies with them: `{ source: "child", handle, name?, text, failed }` for the answers of a child, `{ source: "ask", ask, text }` for the answer of the user to an ask of the caller with no parley, and `{ source: "parley", parley, asks, text }` for the answers of the user to asks of the caller in a parley. A newer `answers` request of the same caller replaces the older one, which then fails with `A newer answers request of the same caller replaced this one`. It needs a connection of its own, because the replies of a connection come in request order. The `watch` reply is `{ view, child }`. Each event of a watch is `{ change, child }` after a commit to the conversation, or `{ change: {}, child }` after a rename, an end or a resume of the conversation. A change gives the parts of the view that the commit changed, as whole values, so a client needs no chord: `entries` is `{ from, items }`, the entries from index `from` on; `docs` has each document that changed, by kind, and `null` for a document that was removed; `conversation` is the conversation record. After a watch that fell behind, the change is `{ view }`, the whole view. When the conversation has a list of todos (see the `todo` request below), the `docs` of the reply and of each `{ view }` have it, under `harness.todos`. Each change of the list, the first `add` included, gives one event `{ change: { docs: { "harness.todos": <list> } }, child }`, with the whole list. A watch that fell behind gives only the newest list. A `configure` request `{ handle, provider?, model?, thinking? }` replies with the child, and refuses an unknown model and a thinking level that the model does not have. It takes no `conversation`. After a `watch` reply, each event of the watch is a `{ "event": ... }` line, and every other line is a reply, in request order. The host checks each request line against the schema of its type. Extra keys are allowed. A line of an unknown type fails with `Unknown request: <type>`, and a line without a string `type` with `Invalid request`. A line that does not match the schema of its type fails with `Invalid <type> request: <path>: <rule>`. `<path>` is the path of the first wrong field, with no leading slash, such as `asks/0/options/1/label`. `<rule>` is `required` for a missing field, `not allowed` for a key that the type refuses, and else the description of the schema of the field, such as `plain text, no backticks or **` for a plain text (`PLAIN_RULE` of `@vzlentin/harness/protocol`), or the message of TypeBox, such as `must be >= 1`. For example, a `spawn` needs a `cwd` that is not empty, and its `thinking` is one of pi-ai's `MODEL_THINKING_LEVELS`, as is the `thinking` of `configure`. When the type has a schema for the `action` of the line, the error comes from a schema of that action. When a line from the host is not valid, the client cannot match it to its request: it ends the connection, and rejects each waiting request with `The harness host sent an invalid reply: <line>`. A client refuses a host with another version, and the host refuses the `hello` of a client with another version, with the same message. The host does not refuse a `hello` with `external: true`: it replies `{ version, pid }` with its own version, and the external client checks that version itself. A `hello` with `external: false` or without `external` gets the exact check. When the host is older, stop it with `kill <pid>` and run the command again. When the client is older, reload Pi with `/reload`, or use the CLI of the host's install. The `watch`, `input`, `note`, `abort`, `configure` and `todo` requests take the handle `agent` for the project agent; its info is a child with the handle `agent` and the name `<project> agent`. Other requests refuse it as an unknown subagent. A `stop` request `{ caller }` with a handle or `{ conversation }` ends the child and the children it spawned, and replies `{ handle, name? }`, with the handle of the child. The caller `cli` can stop any child; another caller fails with `Subagent <handle> belongs to another session` for a child of another caller by handle, and with `The conversation <id> is not a child of this caller` by conversation ID. For the caller `cli`, a conversation of the children library with no record of a child, such as a conversation of a task, and the handle `agent` are not ended: the host aborts their turn, as an `abort` does, keeps the conversation and its entries, and replies `{ handle }`, with the conversation ID or `agent`. The owner of the conversation gets the failure of an aborted turn, such as a task whose turn then fails, and the project agent stays and takes the next input. Another caller fails with `Unknown subagent: agent` for the handle `agent`. A root, an unknown ID, or text that is not an ID fails with `Unknown conversation: <id>`. The host places the message of an `input` request as an entry of the kind `harness.typed`, whatever its target, and the message of a `send` as a `pi.user` entry. The model reads both as user messages. The gate reads only the `harness.typed` entries as the words of the user (see [Tool](#tool)). `input` is the request of the clients of the user, such as a mirror session, the inspect page and Orda. The host cannot tell who holds the socket, so an `input` from any client counts as typed by the user: this is the limit of the mark. The `watch`, `input`, `note` and `abort` requests also take `{ conversation }` in place of `{ handle }`: the ID of a conversation that the children library opened, of any owner, such as a child of a task. A request with both keys fails with `Invalid <type> request: conversation: not allowed`. Its info has `handle` and `conversation` set to the ID, and the child's key as `name`, so its title and its label are `<key>`. An ended conversation is `ended`. It takes `input` only while it works, always as a steer, so the reply verb is `Steered`; an idle conversation refuses it with `<key> takes input only while it works`. A root, an unknown ID, or text that is not an ID gives `Unknown conversation: <id>`. The info of a conversation without a model fails with `The conversation <id> has no model`, and without a working directory with `The conversation <id> has no working directory`. A `note` request `{ requestId, text, kind?, data? }` with a handle or `{ conversation }` adds a passive user message `text` to the conversation's transcript, as an entry of the kind `kind` (default `harness.note`) with `data`. It starts no turn: an idle conversation places it at once, and the model reads it with the next input; a busy one places it at its next boundary, so the model reads it on its next request. An abort keeps a note that was placed. Its request ID is in the scope `note:`, apart from the IDs of `input`, and a repeated ID, also after a host restart, adds nothing. A kind that starts with `pi.`, and the kind `harness.typed`, which only an `input` gives, fail with `Invalid note request: kind: <rule>`. The reply is `{ child }`, with no verb. A note to an ended child is placed and leaves it ended; the next input resumes the child with the note in its history. An unknown handle fails with `Unknown subagent: <handle>`. When the children library ends the child while the note is admitted, the note stays in the transcript of the ended child, and the request succeeds. A `send` in that case fails with `The child <id> ended during the submit`, and its input is aborted. A conversation takes a note in any state, and an ended one stays ended.
- `host.log`: the host's output.

The host reads Pi's settings as a Pi session in the project directory (the home directory for `main`) reads them: the settings and packages of the project's `.pi/settings.json` count only when the project is trusted, with the saved trust (see the project skills below). They give the project agent its default model, and the packages of the entries. The host loads two kinds of entries when it starts. First, the `piDurable` entries of the packages in Pi's settings, such as pi-ipython: a package lists its entry modules in its `package.json`, as `{ "piDurable": { "extensions": ["./durable/index.ts"] } }`. Second, the entries in `$XDG_CONFIG_HOME/harness/entries.json` (default `~/.config/harness/entries.json`), an object of entry name to the absolute path of a module, for packages that are not Pi packages, such as workflows. A package sets its entry there with `setEntry(name, module)` of `@vzlentin/harness/entries`, which is true when it changed the file. `setEntry` and `create` hold the lock file `<file>.lock`, with their process ID, while they change `entries.json` or `projects.json`, so processes that change the file at the same time keep each other's change. A lock with no process ID, or whose process does not run, is removed; after 5 s with a lock of a live process, they fail with `Could not lock <file>: another process holds <file>.lock. Remove it if no harness command runs`. A host that runs already loads a new or changed entry only after it starts again. Missing packages are skipped, not installed. An entry of `entries.json` whose module does not exist, such as one of an uninstalled package, is skipped with the warning `The entry <name> has no module at <path>; the host skips it`. A package whose `package.json` is not a JSON object, or has a `piDurable` field that is not valid, gives a warning and is skipped. Node does not strip types under `node_modules`, so the host loads a TypeScript entry there through jiti. It calls the default export of each entry with `{ durable, ai, events, children, place }`: the host's pi-durable and pi-ai modules, one event bus that all entries share (the host listens on it for the kernel starts and the cells of pi-ipython, see [Tools bridge](#tools-bridge)), the children library, and the host's `place` (store, models and tools) for `children.open`. A child that `children.open` opens gets the tools of the store of the project, `thread`, `rule`, `parley` and `item`, as any child does. No child that `children.open` opens, at any depth and also as a depth root, gets the extension `harness-memory` (`MEMORY_EXTENSION`), with the `memory` tool and the `memory` section: `open` removes it from the `extensions` of the child's `AgentDoc`. Only the project agent has it (see [Project agent](#project-agent)). A client of `children.open` leaves them out, in the model tools and in `codemode`, when its `setup` adds `PROJECT_EXTENSION` of `@vzlentin/harness/protocol` (`harness-project`) to the `remove` of the `extensions` of the child's `AgentDoc`. Such a child still gets the section of the decided rules (see [Host](#host)). The entries load before the host opens its store, so `place.store` is usable only once the host is open, which means inside tasks. An entry returns `{ extensions, tasks?, catchUp?, close }`. The host installs `extensions` and `tasks`, and refuses to start when two entries give a task with the same name. An entry that returns no `tasks` loads as before. `catchUp` is a catch-up hook of the project agent, `{ kind, run }`, with a `kind` that is not empty (see [Project agent](#project-agent)); the host refuses to start when two entries give a hook of the same kind, with `The entries <module> and <module> both give the catch-up hook <kind>`. An entry that returns another shape stops the host start with `The entry <module> returned an invalid result: <path> <message>`, such as `/extensions must be array`, and the entries loaded before it close.

A client starts and follows the tasks of the entries with four requests:

- `start { kind, input, key, version? }` creates a task of the kind `kind`, with the input `input`, and replies with its info `{ key, id, kind, version, status, outcome? }`. `version` is the version on the task's record: the version of the entry's task definition that last ran or migrated the task. It shows which version of the entry the host used for this task, not which version the host has loaded now. `outcome` is there only when the task is terminal. The key is the client's own name for the task. A repeated `start` with a known key gives the first task, and its new input is ignored. It refuses another kind with `The task <key> is a <kind> task, not <kind>`. An unknown kind gives `Unknown task kind: <kind>`. With `version`, a host whose loaded definition of the kind has another version creates nothing and gives `This host has version <n> of <kind>, not <version>: stop the host so it starts again with the installed version`, for a first and a repeated `start`. Before it creates the task, `start` sets up the project agent, so a child that the task opens without a model takes the agent's; when the agent has no model, the task still starts.
- `task { key }` replies with the info of the task.
- `wait-task { key }` waits until the task is terminal, and replies with its info, with the outcome. To follow the status during the run, poll `task`.
- `abort-task { key }` aborts the task and the work that it owns, such as the turns of its children, and replies with the info.

The other requests refuse a key that no `start` gave with `Unknown task: <key>`. The host keeps each key and its task in `durable.sqlite`, and no request removes a key, so the key map only grows. A started task is a background task of the root conversation, so an abort of the project agent (Esc in its mirror session) does not reach it. A task that a host stop interrupts continues when the host starts again. The children that tasks open are not in `list`. workflows starts the task `n` of the run `<runId>`, from 1, with the key `wf:<runId>#<n>`, and writes the asks of the run with the asker `workflows:<runId>`: the stage of a work item reads both (see the work items below).

A todo is a line of intent with a state: `{ id, text, state, ask? }`, where `state` is `open`, `doing`, `done` or `dropped`, and `ask` is the ID of the ask that the todo `Save to the vault` belongs to (see [Asks and parleys](#asks-and-parleys)). No `todo` request sets `ask`: the host sets it on the todo `Save to the vault`, and the replies and `store.json` give it. The host keeps lists of todos in `durable.sqlite`, in three places. Each conversation has one list, as its document `harness.todos`: the project agent, a child, or a conversation that the children library opened. Each task that `start` created has one list, keyed by its task ID: it is not a document of the task, so it stays after the task ends. Each caller that is not a conversation of the host, such as a Pi session or `cli`, has one list, keyed by the caller. A `todo` request `{ caller, action, ... }` reads or changes one list:

- `add { text }` adds a todo with the state `open` and the next ID of the list (1, 2, 3 and so on), and replies with the todo. The text stays as it is given.
- `set { id, state, text? }` sets the state of the todo `id`, and its text when `text` is given, and replies with the todo.
- `list` replies with `{ todos }`, in ID order. A list that was never changed is empty.

The list is the one of the target of the request: a handle, with `agent` for the project agent; `{ conversation }`, the ID of a conversation that the children library opened; `{ key }`, the key of a `start`; or, with none of them, the list of the caller. When the caller is the conversation ID of the project agent or of a conversation that the children library opened, such as a child of this host, the list of the caller is the list of that conversation, as for the parent of a `spawn`. The request does not check that the caller spawned the child of a handle, and it does not set up the project agent, so it works when the agent has no model. A `{ key }` target takes `add` and `set` also after the task ends, and a `{ conversation }` target also when the conversation is ended. A request with two targets fails with `Invalid todo request: <field>: not allowed`, where `<field>` is the second one in the order `handle`, `conversation`, `key`. A state that is not one of the four fails with `Invalid todo request: state: <rule>`, and an `id` that is not an integer from 1 with `Invalid todo request: id: <rule>`. A text that is empty or has only white space fails with `The text of a todo is empty`, an unknown ID with `Unknown todo: <id>`, an unknown handle with `Unknown subagent: <handle>`, a conversation that the children library did not open, the root included, with `Unknown conversation: <id>`, and an unknown key with `Unknown task: <key>`. A request that fails does not change the list. The `watch` of a conversation gives its list, and an event for each change of it (see `host.sock`). `harness todo` sends this request (see [Todos](#todos)).

`@vzlentin/harness/todo` gives the tasks of an entry the same lists and the same rules, with no socket: the schemas `Todo` and `TodoState` and their types, `TODO_STATES`, `TODO_MARKS` (the mark of each state in the line of a todo), `TODO_LIST_KIND` (`"harness.todos"`, the kind of the list of a conversation in the `docs` of a watched view), `TASK_TODO_LIST_KIND` (`"harness.task-todos"`, the kind of the lists of the started tasks), the schemas `TodoAnswer` and `ClassifyReply` of the reply of `classify-todos` and their types, the types `TodoList` and `TodoOwner` (`{ kind: "conversation", id }`, `{ kind: "task", id }` or `{ kind: "caller", caller }`), and six functions. `todoLine(todo)` gives the line of a todo as `harness todo` prints it, `<mark> <id> <text>` (see [Todos](#todos)), and `answerLine(answer)` the line of an answer as `harness todo sort` prints it. `addTodo(tx, owner, text)` and `setTodo(tx, owner, { id, state, text? })` change the list of `owner` in the commit `tx` of the caller, such as a commit of the runtime of a task, and give the todo. For an empty text or an unknown ID, they throw the error of the request, and a commit that does not catch it changes nothing. `readTodos(reader, owner, context)` gives the list from a reader such as the harness or the runtime of a task. `watchTodos(harness, id, context)` gives a chord watch of the list of the conversation `id`: its value is the list, or `null` while the conversation has none, and each stored commit that changes the list gives a call, the first `add` included. An abort of `context` or the close of the harness ends it. A task changes its own list with `{ kind: "task", id: runtime.taskId }`, also in the commit that makes it terminal.

A `classify-todos` request `{ list?, ids? }` asks a classifier model of Pi about the todos in the state `open` of a list, and stores nothing. `list` is `{ handle }`, with `agent` for the project agent, `{ conversation }` or `{ key }`, as for the `todo` request. Without `list`, it asks about the work items instead, each as a todo with its ID, its title as its text and its state: the open items are the open todos, and `earlier` has the items of every state. `ids` are the IDs of the todos to ask about; without it, every open todo. A todo of `ids` that is not open gets no answer, and an ID that is not in the list fails with `Unknown todo: <id>`. The classifier is `todoClassifier` in Pi's settings, as `<provider>/<id>`, read again at each request, from the global settings and the settings of a trusted project; the default is `typesafe/jev-latest`. When its provider has no credential in Pi, or has no classifier model with that ID, the request fails with `No classifier: log in to <provider> or set todoClassifier`, before it reads the list, so a client keeps the order of the adds. Each todo gets one call of pi-ai's `classify`, with `{ todo: { id, text }, earlier }` as the state, where `earlier` are the todos with a lower ID, in any state, and two questions: `needsYou`, a bool, true when the todo needs a call that only the user can make, which counts as yes from a probability of 0.5; and, when `earlier` is not empty, `repeats`, a choice of `none` or the ID of one todo of `earlier` that it repeats. A call that does not end with the stop reason `stop` fails the request with `The classifier <provider>/<id> failed: <errorMessage>`. The reply is `{ answers: [{ id, needsYou, repeats? }] }`, in ID order, where `repeats` is the ID that the classifier chose, absent for `none`. `harness todo sort` sends it (see [Todos](#todos)).

The host keeps the store of the project in `durable.sqlite`: the persons that the user talks with, the threads of messages with them, the rules of the project, the tool calls that the gate held (see the `gate` request below), and the parleys and their asks (see [Asks and parleys](#asks-and-parleys)). Each list is one document of the session: `harness.persons`, `harness.threads`, `harness.rules`, `harness.held`, `harness.parleys` and `harness.asks`. The state of each message out is in the document `harness.outbox`, because an entry cannot change. A person, a rule and a held action have the next ID of their list, 1, 2, 3 and so on. A delete of a rule removes it from `harness.rules`, so no list and no reply gives it again. The document keeps `last`, the highest ID that a rule had, and a new rule gets the next ID after `last` and after the ID of the last rule, so the ID of a deleted rule is never given again and the other rules keep their IDs. A document of an older version has no `last`, and needs no migration. A rule that an older version wrote can have a `source` and no `thread`: each read of the rules, `rule list`, `watch-project` and `store.json`, gives it the `thread` of its source message, with one lookup of that message, and stores nothing. A rule whose source message is not there gets no `thread`. A thread is an ownerless conversation, and its ID is the ID of the conversation. A message is an entry of the kind `harness.message` in the conversation of its thread, with the message as its `data`, without its state, and no model message, and its ID is the ID of the entry. An entry cannot change, so an edit of a message is a later entry `harness.message.edit` with the `data` `{ message, from, direction, at, text, by }`, and a delete a later entry `harness.message.delete` with the `data` `{ message, by }`, in the same conversation. Each read of a thread, and each write that looks up a message, applies them in entry order: an edit replaces the data of its message, which keeps its ID and its place, and a delete removes it. A store of an older version has none of these entries, and needs no migration. A thread is not a node of the tree. An author, `from` or `saidBy`, is the ID of a person or `"user"`. Every time is in epoch milliseconds. Each write, `message log`, `message mark`, `message edit`, `message delete` and each `rule` request but `list`, has a `caller`, as a `todo` request has: the conversation ID of a hosted agent, a Pi session ID, or another text. The host keeps it in `by` of the object that the write adds or changes. Each request has an `action`, and each reply of a list is in ID order:

- `person add { name }` adds a person `{ id, name }`, and replies with it. `person list` replies with `{ persons }`.
- `thread add { topic, persons }` adds a thread `{ id, topic, persons, last? }` with one or more persons, in a new conversation, and replies with it. `last` is the latest `at` of its messages, absent while it has none. `thread list` replies with `{ threads }`. `thread read { id }` replies with `{ thread, messages }`, the messages oldest first, in ID order. `thread join { id, person }` adds the person `person` to the thread `id`, and replies with the thread. It has no `caller`, as the other `thread` requests. A person of the thread fails with `Person <person> is already in thread <id>`.
- `message log { caller, thread, from, direction, at?, text, state? }` adds a message `{ id, thread, from, direction, state, at, text, by }` to the thread, and replies with it. `direction` is `in` or `out`. The host sets `state`: `received` for `in`, `draft` for `out`. With `state: "sent"`, a message `out` gets the state `sent` and is never a draft. `sent` is the only value of `state`: another value fails with `Invalid message request: state: <rule>`, and `sent` for a message `in` with `Only a message out can be logged as sent`. `at` defaults to the time of the write. A message `in` from a person of the thread is a reply to each message out of the thread in the state `draft` or `sent` whose `at` is not later than its own: in the same commit, a draft becomes `sent`, and a sent message `answered`. One message moves each of them one step only. A pasted message that is older than the draft moves nothing.
- `message mark { caller, message, state }` sets the state of the message out `message`, and replies with it. `state` is `sent` (the user sent it, such as after a copy), `draft` (it was not sent after all) or `dropped`. A draft takes `sent` and `dropped`, and a sent message takes `draft`. Another mark fails with `Message <id> is <state>: it cannot become <state>`, and a mark of a message in with `Message <id> is a message in: only a message out has a mark`. The states of a message out are `draft`, `sent`, `answered` and `dropped`; `messageTransition(state, event)` of `@vzlentin/harness/protocol` gives the state after a mark or a reply, or `undefined`.
- `message edit { caller, message, text, at?, from? }` changes the message `message`, and replies with it. It gets `text`, and `at` and `from` when they are given: else it keeps its own. Its ID stays the same, and `by` becomes the caller. `direction` is `out` for `user` and `in` for a person, who must be a person of the thread: another person fails with `Person <from> is not in thread <thread>`. A message that keeps its direction keeps its state, and a message out gets `at` as the time that the reply rule compares. A message out that becomes a message in leaves the outbox and is `received`. A message in that becomes a message out is a `draft`, as for `message log`. The edit moves no other message. `last` of the thread becomes the latest `at` of its messages, so an earlier `at` can lower it.
- `message delete { caller, message }` removes the message `message`, with its state in the outbox, and replies with it as it was, with its state. A rule that is not retired and has the message as its `source` fails the delete with `Message <message> is the source of rule <id>`. A retired rule with the message as its `source` loses its `source` and its `thread` in the same commit, and keeps its `at` and `by`. Two other things can name a message, and neither blocks a delete: the `data.waits` of an old `harness.digest` entry, which no read gives back, and a `draft:<id>` in the command of a held action, a plain text, whose gate then finds no draft to mark. `last` of the thread becomes the latest `at` of the messages that remain, and goes when none remains. A deleted message is an unknown message for every request.
- `rule set { caller, saidBy, source, ... }` is the request of an agent. Without `id`, it adds a rule `{ id, name, kind, value, status, saidBy, source?, thread?, replaces?, at, by }` with `name`, `kind` (`conduct` or `domain`) and `value`, in the status `open`. `replaces` names the rule that the new rule replaces, which must exist; it changes nothing until the user decides the new rule. With `id`, it changes the open rule `id`: its `name`, `kind` and `value` when they are given, and always its `saidBy`, `source` and `by`. `thread` is the ID of the thread of the message `source`: the host sets it with `source`, so a changed source gives the thread of the new source, and a rule with no source has no `thread`. `rule set` has no `status`. `at` is the time of the last change. The reply is the rule. `rule list { kind?, status? }` replies with `{ rules }`, only those of the kind `kind` and of the status `status` when they are given.
- `rule decide { caller, id }`, `rule retire { caller, id }`, `rule edit { caller, id, name?, kind?, value? }`, `rule create { caller, name, kind, value }` and `rule delete { caller, id }` are the changes that only the user makes. `decide` makes an open rule `decided`, and makes the rule that it replaces `retired` when that rule is still there and not retired, with the `at` and the `by` of the write; the retired rule keeps its own `saidBy`, `source` and `thread`. `retire` makes an open or a decided rule `retired`. `edit` changes the `name`, `kind` and `value` that it gives of a rule in any status, and keeps the status; the rule gets `saidBy` `user` and no `source` and no `thread`. `create` adds a rule in the status `decided`, with `saidBy` `user` and no `source` and no `thread`. `delete` removes the rule. The reply is the rule, for `delete` the rule as it was. No tool of an agent sends these requests: the user sends them with `harness rule` (see [Rules](#rules)) or `/rules` of the Pi extension (see [Pi extension](#pi-extension)). The host cannot tell who sends a request: a Pi session and its agent share one caller, the session ID, and any process can write to the socket of the host. The barrier is that no tool sends these requests, and that the gate holds a `bash` call of an agent that runs one (see the `gate` request below). A raw write to the socket of the host is not stopped.

`source` is the ID of a message. A write without `caller`, and a `set` without `saidBy` or `source`, fails with `Invalid <type> request: <field>: required`. A rule `set` with `id` and `replaces` fails with `A change of a rule cannot replace a rule: set replaces on a new rule`. A rule `set` with `status` fails with `Invalid rule request: status: not allowed`. A `set` with `id` or a `decide` of a rule that is not open fails with `Rule <id> is <status>, not open`, and a `retire` of a retired rule with `Rule <id> is retired`. An unknown ID fails with `Unknown person: <id>`, `Unknown thread: <id>`, `Unknown message: <id>`, or `Unknown rule: <id>`, for the persons of a thread, an author, a source, a rule that a new rule replaces, and the rule of a change. `thread join` checks its person first. An empty `name`, `topic`, `text` or `value`, or a thread with no person, fails with `Invalid <type> request: <field>: <rule>`. A request that fails changes nothing.

The host keeps the work items of the project in `durable.sqlite` too. A work item is a piece of work, `{ id, title, text?, state, edges, at, by }`: `title` is one line, `text` says in Markdown what to build, `state` is `open` (work to do), `done` (the work ended as intended) or `dropped` (given up), `edges` are its links in the order of their writes, `at` is the time of its last change and `by` the caller of that change. A reference is a text `<kind>:<value>`, where the value is the ID that the kind already has: `item:<id>`, `agent:<id>` with the ID of a conversation that the children library opened, `run:<id>` with a workflows run ID (`<8 digits>T<6 digits>-<8 hex digits>`), `parley:<slug>`, and `commit:<sha>` with a full SHA (40 lowercase hex digits). An edge `{ from, kind, to, at, by }` is a link between two references, one of them an item, and never changes after its write. Its kind fixes its ends: `serves` goes from an agent or a run to an item, `shapes` from a parley to an item, `landed` from an item to a commit, and `needs` from an item to another item, which the first item waits for. Each item is one document of the session family `harness.item`, keyed by its ID, which holds its edges, and each write stores it whole. An edge from an item, `landed` or `needs`, is stored on its `from` item, and another edge on its `to` item. The document `harness.items` is the counter `{ last }`. `item add` gives the ID after `last` and raises `last` in the same commit, so an ID is never given twice. `item add` and the commit that makes a parley a contract (see `ask answer`) add items. The first start of a host whose store has no `harness.items` creates it, in one commit with the move of the todos below, and so does `harness store load` (see [Store](#store)).

The first start of a host whose store has no `harness.items` moves the open todos of the list of the project agent to items, once. Each todo that is `open` or `doing` and has no `ask` becomes the open item with the same ID, its text as the `title`, no `text`, and `by` `migration`, and stays in the list as `dropped`, with the text `moved to item <id>: <text>`. `last` of the counter is the highest ID of the list, moved or not, so a new item never takes the ID of an old todo. An ID up to `last` that has no item, such as the ID of a todo that was done, is an unknown item. The same commit raises the document of the records of the children to version 6, which has no record that serves a todo: a record of version 5 that serves the todo `<id>` gets `{ kind: "item" }`. When the todo moved, its item gets the edge `agent:<conversation ID> serves item:<id>` with `by` `migration`. When the todo was `done` or `dropped`, the end of the child is due, and the rule that ends agents ends it (see [Agent life](#agent-life)). A child of a todo with an `ask` or of a todo that is not in the list serves an item that no edge names.

Each `item` request has an `action`:

- `item add { caller, title, text? }` adds an open item with no edge, and replies with it.
- `item set { caller, id, title?, text?, state? }` changes the fields that it gives, and replies with the item. A `text` of `""` stores an empty text: no request removes `text`. A `state` of `done` fails with `Item <id> cannot be done: run <runId> serves it and is live` while a run that serves the item is live (see below), with the first such run in the order of the edges, also for an item that is already done. A live agent that serves the item does not refuse it, so an agent can set its own item to `done`. A state of `done` or `dropped` ends the children that a spawn made to serve the item (see [Agent life](#agent-life)). In the same commit, it ends each contract that shapes the item and no open item, with the caller as its `by`: with the status `done` when one item that it shapes is `done`, else `dropped`. This also holds for an item that is already closed, so a contract whose items were all closed before ends at the next such change. An item that goes back to `open` does not reopen its contract.
- `item list { state? }` replies with `{ items }`: the items in the state `state`, default `open`, in ID order.
- `item read { id }` replies with the item, in any state, with its edges, then the `needs` edges of the other items that go to it, in the ID order of those items. The other replies, `watch-project` and `store.json` give only the edges that the item stores.
- `item link { caller, from, kind, to }` checks the edge, writes it into the document of its item, and replies with it. The host checks, in this order: the kind takes the ends, else `An edge <kind> cannot go from <from> to <to>`; a `needs` edge does not go from an item to itself, else `An edge needs cannot go from <from> to itself`; the item exists; when the item has an edge with the same `from`, `kind` and `to`, the reply is that stored edge, with its own `at` and `by`, and nothing is written, so a resumed run can send its link again; a `serves` or `shapes` edge needs an open item, else `Item <id> is <state>: an edge <kind> cannot go to it`, and a `needs` edge an open `from` item, else `Item <id> is <state>: an edge needs cannot go from it`; the `to` item of a `needs` edge exists, in any state, else `Unknown item: <id>`; a `needs` edge makes no cycle: when the `to` item needs the `from` item, through its `needs` edges and those of the items that it needs, the link fails with `Item <to> already needs item <from>: an edge needs cannot make a cycle`; a `serves` edge from an agent fails with `Only the spawn of an agent writes its edge serves`, because a spawn with `{ item: <id> }` writes it; a `serves` edge from a run that already serves an item fails with `Run <runId> already serves item <id>`, so a run serves one item at most; a parley end is a parley of the store, else `Unknown parley: <slug>`. A run end and a commit end are checked for their form only: the host keeps no runs by ID and no commits.
- `item unlink { caller, from, kind, to }` removes an edge that was written by mistake, and replies with the item. It checks the ends and the item as `link` does. An edge that the item does not have fails with `Item <id> has no edge <from> <kind> <to>`.

Each reply that gives an item, the replies of `add`, `set`, `read` and `unlink` and each item of `list`, gives it with `stage` and `needsYou`, which the host works out at each reply from the item and the other ends of its edges, and never stores. `stage` is the column of the item on a board: the first of these checks that holds gives it. The state `done` or `dropped` gives that state. An agent or a run that serves the item and is live gives `building`. A parley with the status `open` that shapes the item gives `shaping`, and a parley with the status `contract` gives `ready`. Else the stage is `inbox`. An agent is live when it is the project agent, or a conversation of the children library that did not end. A run is live while a task that `start` created with the key `wf:<runId>#<n>`, where `n` is an integer from 1, is not terminal (its node in the tree is `pending` or `running`), and while an ask with the asker `workflows:<runId>` is open: the task of a run that waits for an input of the user is terminal, and its open ask keeps the run live. `needsYou` is true when one of these holds: an ask of a parley that shapes the item is open; an open ask has as its asker an agent that serves the item, or `workflows:<runId>` of a run that serves it; an agent that serves the item has a held action in the state `held`. `needsYou` reads the same inputs for an item in any state, and for an agent that ended.

A link and an unlink do not change the `at` and the `by` of the item. An ID that no `item add` gave fails with `Unknown item: <id>`. A reference, a kind or a state of another form, an empty `title`, and an `id` below 1 fail with `Invalid item request: <field>: <rule>`. A request that fails changes nothing. `watch-project` gives the open items (see the `watch-project` request below), and `store.json` gives every item with its edges. The host keeps an index from each `agent:`, `run:` and `parley:` end to the IDs of the items whose edges come from it, and the run of each task with a key `wf:<runId>#<n>`. It builds the index from the items at its start, and keeps it current with each commit that changes an item or the started tasks. The info of a child, its node in the tree and the rule that ends agents look up the item of a child in the index, and the commit that makes a parley a contract looks up the items that the parley shapes. `WorkItem`, `StagedItem`, `Edge`, `Ref`, `ItemCounter` and `ItemList` of `@vzlentin/harness/protocol` are the TypeBox schemas of an item as the store keeps it, an item with its `stage` and `needsYou` as a reply gives it, an edge, a reference, the counter and the reply of `item list`, `ItemAdd`, `ItemSet` and `EdgeInput` the schemas of the inputs, `ItemStage` the schema of a stage, and `EDGE_KINDS`, `ITEM_STATES` and `ITEM_STAGES` the kinds of an edge, the states of an item and its stages.

A `watch-project` request `{}` replies with the whole store, `{ persons, rules, threads, held, parleys, asks, items, degraded }`, each list of the store in ID order, in `items` the open work items in ID order, each with its `stage` and `needsYou`, and in `degraded` the degraded states of the host, by `since` and then by kind (see [Host](#host)). Each thread has `waits` too: its messages in the state `draft` or `sent`, oldest first. The other messages of a thread come from `thread read`. The host reads the store again after each commit that changes a person, a rule, a thread, a message (a log, an edit or a delete), the state of a message, a held action, a parley, an ask or an item, after each change of a node of the tree at an end of an item, and after each change of its degraded states, which is not a commit, and compares it with what the client has. It then sends one `{ "event": { persons, rules, threads, held, parleys, asks, items, removed, degraded } }` with the objects that are new or changed, in `removed` the IDs of each kind of the objects that went, and in `degraded` every degraded state. Every list is there, empty when nothing of its kind changed, because the persons, the rules, the held actions, the parleys and the asks share the IDs 1, 2, 3. A read that changes no object and no degraded state sends no event. The reads run one at a time, and the commits during a read give one more read and one more event. A read gets the messages only of the threads that are new or that got an entry of a message, an edit or a delete since the last read, and the states of the messages at each read. An event has an item when a commit changes its document, whatever its new state: an item that becomes `done` or `dropped` comes once with that state, and then no more. An event also has an open item when its `stage` or its `needsYou` changes: after a change of a parley, an ask or a held action, the read works out the stage of every open item again; after a change of a node of the tree, the end of a child or a change of a task that `start` created with a key `wf:<runId>#<n>`, only the stages of the items whose `serves` edges name that agent or that run, from the index of the ends. A change of a node that is no end of an item starts no read. No request retires an item, so `removed.items` is always empty. A slow client does not hold up the host: when a write must wait for the socket to drain, only that watch waits, and its next event has every object. A read that fails ends the connection, so the client opens a new watch. A request without a connection fails with `A project watch needs a connection`. `ProjectState`, `ProjectThread`, `ProjectEvent` and `DegradedState` of `@vzlentin/harness/protocol` are the TypeBox schemas of the reply, of a thread with its waits, of an event and of a degraded state.

A `digest` request `{ caller, head? }` replies with `{ text }`, the digest of `caller`, and records it in the document `harness.digests` as the last digest of the caller. The digest has these lines: `board of <project>: <n> open`, where n counts the open items of the project, also when it is 0; then up to 10 lines `○ <id> <title>`, the open items in ID order that have no open need, where an open need is a `needs` edge of the item to an item in the state `open` (an edge to a closed or an unknown item is none); then `+<n> later` when the board does not show n > 0 open items, those with an open need and those after the first 10; then `waiting on: ` and each message out of the project in the state `draft` or `sent`, as `<persons> (<topic>, sent <day> <month> <HH:MM>)` or `<persons> (<topic>, draft not sent)`, with the names of the persons of its thread and the time of its last change of state in UTC, such as `Sam (own-brand C+P, sent 12 Nov 14:22)`; then `held: ` and each held action of the caller in the state `held`, as `<id> <tool>: <reason>`. The items are joined with `·`, and an empty list is `none`. `head` is the ID of the newest head of the context of the caller. The record keeps the `head` of every caller, and a new `head` gives the digest again, also when the text is the same, with the next count. The reply is `{}` when the text and the `head` are those of the last digest of the caller, and when the caller never got a digest, has no message that waits and no held action, and the project has no open item. The host gives each hosted agent its digest the same way, as a passive user entry of the kind `harness.digest` with `data` `{ waits, held, items }`, the IDs of the messages, of the held actions and of the items on the board, before an `input` to it (after the catch-up of the project agent), a `send` to a child, and the first message of a spawned child. For a hosted agent, `head` is the ID of the newest head marker of its conversation (a `pi.compaction` or a `pi.reset`): a newer head marker means that its context lost the last digest. The entry has the request ID `digest:<count>:<hash>`, the count of digests of the caller and a hash of the text, and goes before the record, so a repeat after a crash adds nothing. A failure is the warning `digest: <message>` in `host.log` and the degraded state `digest-failed` (see [Host](#host)), and the input goes through. The digest is not a part of the catch-up: a catch-up comes only before an input to the project agent, and its hooks do not know the agent. The input of an approve, a push of answers and a conversation of a `durable-entry` host get no digest; the next input gives it.

A `memory` request `{ action, ... }` uses the memory of the project agent (see [Project agent](#project-agent)), for the `memory` tool of the project agent and of a Pi session, and the memory section of a Pi session (see [Pi extension](#pi-extension)). `note { text }`, `recall { pattern }` and `zoom { block }` are the calls of the `memory` tool: they run `memo` as the tool says, and reply `{ text }` with the result of the call; an error of the call fails the request with its message. A `note` whose output has a compression prompt starts the compressions of the host. `snapshot` replies `{ text }` with the text of the memory section, which the host takes with `memo wake` at each request and does not keep, or with an empty `text` for an empty memory. A `snapshot` that gets `Cannot wake` first waits for the compressions. Each action has its own fields: a line without them fails with `Invalid memory request: <field>: required`. A `memory` request keeps the host running, as a `note` of the agent does.

A `gate` request `{ requestId, caller, tool, arguments, messages }` checks the tool call of the agent `caller`, the tool `tool` with the JSON object `arguments`, against the conduct rules of the project in the status `decided`. `messages` are the last messages that the user typed in the conversation of the caller, oldest first. The reply is `{ runs: true }`, or `{ runs: false, held }` with the held action. The command of a call is the `command` of a `bash` call, and `<tool> <arguments as JSON>` for another tool. The host goes through these steps, in order:

1. A call of `read`, `grep`, `find` or `ls`, of the `list` or `read` action of `thread`, `rule` or `parley`, of the `query` action of `subagent`, or of `memory`, runs, with no question.
2. When an approved action of the same caller, tool and command ran for no call, or for the call `requestId`, the call runs, and the action keeps `ran: { requestId, at }`. So an approved command runs one time, and the same call again, such as a hook after a host restart, runs again. The host finds the action and marks it in one commit, so of two calls of the command at the same time, one runs, and the other goes on to the next steps.
3. A held or dropped action of the same caller and `requestId` is the reply again, with no question.
4. A `bash` call whose command matches `\brule\s+(decide|retire|edit|create|delete)\b`, such as `harness rule decide 3`, is held with no `rule`, the reason `Only the user decides, retires, edits, creates or deletes a rule`, and no question. The match is wide on purpose: a command that only names these words is held too, and the user approves it. `harness rule` takes its action as the word right after `rule`, so the pattern matches each change that the CLI accepts. The same command in a terminal is no tool call, so no gate sees it.
5. With no decided conduct rule, the call runs.
6. Step 1 asks the classifier one bool question, `writes`, with the state `{ command }`: whether the command writes to a system outside this machine that other people see or use. A probability of 0.5 or less runs the call.
7. Step 2 asks one choice question, `rule`, with the state `{ action, last_user_messages }`, the command and `messages`: which rule the action breaks most clearly. The choices are `none` and the ID of each decided conduct rule, as `<name>: <value>`. The domain rules are not choices. `none` runs the call. Another choice holds it.

The host holds a call as a held action `{ id, requestId, agent, tool, command, rule?, reason, state, at, by }`: `agent` is the caller, `command` is the command as it runs, `rule` is the ID of the rule that it breaks, and `reason` is `It breaks rule <id> <name>: <value>`. A call held at step 4 has no `rule`. `state` is `held`, `approved` or `dropped`. `at` is the time of the last change, and `by` the caller of that change. When the classifier has no credential, has no model with that ID, fails, or gives no answer, the host holds the call with no `rule` and the error as the `reason`, such as `No classifier: log in to openrouter or set gateClassifier` or `The classifier <provider>/<id> failed: <errorMessage>`, so a call never runs unchecked. The classifier is `gateClassifier` in Pi's settings, as `<provider>/<id>`, read again at each request, as `todoClassifier` is; the default is `openrouter/typesafe/jev-1.14`. When the reply is `{ runs: true }` for a call that the gate checks (not a read), each draft that the command names as `draft:<id>`, such as in the shell comment `# draft:12`, becomes `sent`, with the caller as `by`. Another ID changes nothing, and a gate of the same call again finds the draft sent. A `held` request `{ action, caller, id }` with the action `approve` or `drop` sets the held action `id` to `approved` or `dropped`, with `by` the caller, and replies with it. An action that is not held fails with `Held action <id> is <state>, not held`, and an unknown ID with `Unknown held action: <id>`. An approve tells the agent of the action when it is a conversation of the host, with a follow-up input that starts a turn: `The user approved held action <id>: <command>. Call it again: it runs one time with no question.` A delivery that fails is a warning in `host.log`, and the action stays approved. A Pi session gets no input. `GateReply`, `HeldAction` and `HELD_STATES` of `@vzlentin/harness/protocol` are the schema of the reply, the schema of a held action and its states.

A `tree` request `{}` replies `{ nodes }` with the nodes of the project, each parent before its children, and the siblings in ID order. pi-durable takes the IDs of the tasks and the conversations from one counter, so ID order is creation order. A node is `{ id, parent?, kind, name, state, todos, serves? }`: `parent` is the `id` of the node above, absent for a root; `kind` is `agent` or `run`; `todos` is the whole list of the node (see the `todo` request), in ID order; `serves` is what an `agent` node serves, as the info of the agent gives it: the project agent and each child by handle have it, except a child of an item that no `serves` edge names, and a conversation that a task owns and a `run` node have none. The text of `harness tree` does not show it. The nodes are:

- The project agent: `id` `agent`, no parent, the name `<project> agent`, and the state `busy`, `idle` or `error` of its info. It needs no model.
- Each child by handle: `id` its handle, the name of the child or its handle, and the state that `status` gives. Its parent is the node of its caller: `agent`, the handle of a child, or `conversation:<id>` for a conversation of the children library. A child whose caller is not a conversation of the host, such as a Pi session or `cli`, is a root. A child whose caller is a conversation of the children library that is not in the tree is not in the tree either.
- Each task that `start` created: `id` `task:<key>`, `kind` `run`, no parent, and the name `<kind> <key>`.
- Each task in the root conversation of a kind that the entries give, whose owner task is a started task that did not end or a task under one, such as a child task of a started task: `id` `task:<task ID>`, `kind` `run`, the node of its owner as its parent, and the name `<kind> <task ID>`.
- Each conversation of the children library that a started task that did not end owns, or that a task under one owns: `id` `conversation:<id>`, the node of the task as its parent, the key of the conversation as its name, and the state `busy`, `idle`, `error` or `ended` of its info.

The kind of the other nodes is `agent`. The state of a `run` node comes from its task: `pending`; `running` for a task that runs, waits, sleeps or completes; and for a terminal task the status of its outcome, `completed`, `failed` (also for an orphaned or faulted task) or `aborted`. The list of a `run` node is the list of its task. A started task that ended keeps only its `run` node, and the node is left out when its ID is lower than the ID of the 50th newest task that `start` created. Under a started task that did not end, a node that ended (a terminal task, or an ended conversation) is left out when its ID is lower than that ID, and so are the nodes under it. An ended child by handle is left out by the same test. With fewer than 50 started tasks, no node is left out for its age. The host reads the tasks and the conversations of the tree from the store with no write transaction. `harness tree` sends this request (see [Tree](#tree)).

A `watch-tree` request `{}` replies as `tree` does, then sends `{ "event": { nodes } }` with the nodes that are new or changed, in tree order, and `{ "event": { removed } }` with the IDs of the nodes that went, each only when it is not empty. When a started task ends, `removed` gives the nodes that were under it. The host builds the tree again after each commit that can change a node, and compares it with what the client has: a change of a list of todos, of the records of the children by handle, of an item, of the started tasks, of a conversation of the children library or of the last request of the project agent; any change of a submission; the start and the end of a run of a conversation; and a new task of a kind of the entries, or such a task whose node state changed. The builds run one at a time, and the commits during a build give one more. A slow client does not hold up the host: when a write must wait for the socket to drain, only that watch waits, and its next `nodes` event has every node. A build that fails ends the connection, so the client opens a new watch. A request without a connection fails with `A tree watch needs a connection`. `TreeNode`, `TreeReply` and `TreeEvent` of `@vzlentin/harness/protocol` are the TypeBox schemas of a node, of the reply and of an event.

A host from before the projects kept its state in `$XDG_STATE_HOME/harness/`. To keep its children, stop that host, then move `durable.sqlite` and its `-wal` and `-shm` files into `main/` before the `main` host starts.

A child's bash commands get `PI_SESSION_ID` (the child's conversation ID), `PI_PROVIDER`, `PI_MODEL`, `PI_REASONING_LEVEL`, and `HARNESS_PROJECT`, so a child can spawn its own children with its own model and thinking level when the subagent settings do not set them (see [Tool](#tool)), in the same project, down to the depth limit (see [Push](#push)). After a `configure`, the next commands get the new model and thinking level. In a project other than `main` whose directory has a `.optmem` folder, they also get `MEMORY_DIR`, the path of that folder. Otherwise they get no `MEMORY_DIR`, not even the host's own. The rule uses the project directory, not the child's working directory. Children survive `/reload`. When a Pi session ends, the host ends its children and the children they spawned (see [Pi extension](#pi-extension)). A child also ends when what it serves ends, once its todos are done (see [Agent life](#agent-life)). `harness stop` ends a child and the children it spawned, by handle or with `--conversation <id>`; a `send` resumes one. For the project agent and a conversation with no record of a child, such as one of a task, it aborts the turn and keeps the conversation.

A child's system prompt starts with the section `rules`, before the project instructions. It has Pi's four tool-use rules, the same for every conversation: `- Use read to examine files instead of cat or sed.`, `- Use edit for targeted changes; batch changes to one file in a single call.`, `- Use write only for new files or complete rewrites.` and `- Use codemode to batch independent tool calls (Promise.allSettled), chain them, or filter large output, instead of many separate calls.`, one per line. Then it has what a Pi session in the child's working directory gets: the `AGENTS.md` or `CLAUDE.md` of the agent directory and of the working directory and its parents, the skills, and the working directory. It also has the section `project_rules` (`RULES_SECTION` of `@vzlentin/harness/protocol`), after the working directory, when the project has decided rules. A child has no `memory` section, which only the project agent has (see [Project agent](#project-agent)). The host extension `harness-rules`, which each conversation of the host selects by default, reads the decided rules of the store at each model request, so a rule that the user decides or retires reaches a running agent at its next request, with no restart. `rulesSection` of `@vzlentin/harness/protocol` gives the text: the line ``A rule is what a person of the project said that each agent follows (conduct) or knows as true (domain); only the user puts a rule in effect. Propose a rule with the `rule` tool, and never write a rule into `AGENTS.md`.``, then the decided conduct rules and the decided domain rules, each group in ID order, each rule as `<id> <name> (<kind>): <value>`. With no decided rule, the section is absent. User skills always load. Project skills (`.pi/skills`, and `.agents/skills` in the working directory and its parents) load only for a trusted project: a directory without project resources, then the decision saved with `/trust`, then the `defaultProjectTrust` setting, where `ask` counts as not trusted. A trust decision that a Pi session made for itself without saving it does not reach its children; when the tool spawns in such a session, it adds `The child gets no project skills (.pi/skills, .agents/skills): this project is trusted for this Pi session only, and children see only the trust saved for future sessions. To give children project skills, run /trust and choose Trust.` to its output. The host checks the trust on every model request, so a decision saved later applies from the next request. The host reads the instructions and skills of a directory once per trust decision and keeps them until it exits. It skips packages that are not installed. When the instructions or skills of a directory fail to load, the child gets none for that request, the host writes a warning, and the next request tries again. A child that the children library opens with `overlay` in its spec, a map of path to content, sees that content in place of the disk. A relative path is relative to the child's working directory, lexically; without a working directory, a relative path makes `open` fail with `The overlay key <path> is relative, and the child has no working directory`. A string replaces the file, and `null` removes it. The overlay changes the instructions and the skills that Pi loaded, and the `read` tool, which gives `ENOENT` for a removed file. A `SKILL.md` path that is not on disk adds a skill. A skill whose content has no description is not loaded, as in Pi, and for a name that two skills use, the first one wins. An overlay adds no instructions file. The other tools see the disk. A child that is opened with a parent that has an overlay gets that overlay, at every depth, also through the `subagent` tool. The child's own paths win, compared after they are resolved, and its own skill comes first when two skills have the same name. A child without an overlay and without an overlaid parent saves no overlay. The overlay is set when the child is created: a second `open` of its key keeps the first one.

### MCP servers

The host connects the MCP servers of Pi's config, and the `codemode` scripts of its conversations (the children, the project agent and the workflows sessions) call their tools as `tools.mcp__<server>__<tool>(args)`, as in Pi. The model never gets an MCP tool as a tool of its own: only scripts call them.

- The servers are those of `mcp.json` in Pi's agent directory, and of `.pi/mcp.json` of the project directory when the project is trusted, with the saved trust. One set serves the whole host. The rules are Pi's: a project entry replaces the global entry of the same name, and a project entry with no `command`, `url` or `type` sets only `enabled`, `exposure` and `toolExposure` of the global entry. Only the global file can set `auth`. A stdio server runs in the project directory, or in its `cwd` relative to it.
- A value that Pi resolves as `${VAR}`, `$VAR` or `!command`, in `headers`, `env` or `oauth.clientSecret`, stops that server, with the warning `MCP config: <file>: server "<name>": <field> uses ${VAR}, $VAR or !command, which the harness host does not resolve` in `host.log`. The other errors of the files are warnings of the same form.
- `exposure` and `toolExposure` work as in Pi. A `direct` tool is in the `codemode` section. A `codemode` or `deferred` tool is not: a script finds it with `searchTools()`, and the section `mcp_servers` names each server with such tools, with the first line of its `description` or of its instructions. Each server is a codemode namespace `mcp__<server>`, also before it connects: the `codemode` section lists it, and `describeNamespace("mcp__<server>")` gives its tools, the same first line as its description, and its instructions. A `hidden` tool does not exist for the host.
- The servers connect in the background when the host starts. A script that names a server, by a word that contains `mcp__<server>`, first waits for its connection. A script that uses `searchTools`, `describeNamespace`, `describeTool` or `ALL_TOOLS` waits for the connections of all servers. The tools of a script are fixed when its call starts, so a script whose server connected during the wait fails with `MCP server "<name>" connected while the script started. Run the script again.`
- A script that names a server that needs sign-in or failed tries to connect it once more, so a sign-in done in Pi applies with no restart of the host. When the server still needs sign-in, the script fails with Pi's message `MCP server "<name>" requires sign-in. Run /mcp to sign in.`, or `Run /login <provider>` for a server with `auth`. A server that failed gives `MCP server "<name>" failed to connect: <message>`. The host writes the same lines to `host.log`.
- The host never signs in. It uses the OAuth state that Pi keeps in `mcp-auth.json` of Pi's agent directory, under Pi's key `mcp__<server>|<url>` and Pi's lock of the file, and refreshes the tokens under Pi's refresh lock, so Pi and the host do not sign each other out. A server with `auth` gets the token of its provider from the host's models.
- MCP problems are warnings in `host.log`, not degraded states. The host closes the connections when it closes, after the store.

### Asks and parleys

An ask is a question that someone put to the user, with his answer. A parley is a group of asks with a frame, which ends as a contract. The host keeps both in the store of the project (see [Host](#host)), in the documents `harness.asks` and `harness.parleys`, and it is their one writer. An ask names its asker, and its parley when it has one. A parley names no asker and no ask.

An ask is `{ id, title, kind?, tension?, options?, plan?, view?, parley?, note?, asker, state, answer?, label?, words?, author?, at, by }`:

- `id` is the next ID of the one list of asks of the project.
- `title` is the question. `kind` is `your call` or `my call`. `options` is a list that is not empty of `{ key, label, gains?, costs? }`: `key` is one lowercase letter, unique in the ask, and `gains` and `costs` are lists of texts that are not empty. `plan` is the key of the option that the asker proposes. `view` is a text that explains the ask, in Markdown.
- `parley` is `{ id, n }`: the ID of its parley, and its number in that parley, 1, 2, 3 and so on. The number never changes.
- `note` is the ID of the note of the ask in the vault: the `id` of the front matter of that note, kept as it is given. Only `ask note` sets it.
- `asker` is the caller of the round that wrote it, or of the last `parley take` of its parley.
- `state` is `open`, `answered` or `dropped`. An open ask takes an answer and a drop. An answered ask takes a new answer, which replaces `answer`, `label` and `words` as one unit. A dropped ask takes nothing. `askTransition(state, event)` of `@vzlentin/harness/protocol` gives the state after an `answer` or a `drop`, or `undefined`.
- Only an answered ask has `answer`: the key of one of its options, `ok`, or `own`. `own` needs `label`, the short name of the answer of the user. `words` are the exact words of the user, a list of texts that is not empty, in Markdown.
- Only an answered ask has `author`, the author of its last answer: `{ kind: "user" }`, `{ kind: "hosted", conversation }` for the agent of a conversation of the host, with its conversation ID, or `{ kind: "agent", caller }` for another agent, which the host knows only by its caller, such as the session ID of a Pi session. A new answer writes its own author. A note keeps it.
- `at` is the time of its last change, and `by` the caller of that change.

The answer of an ask with options is the key of an option or `own`. The read-back of a parley is an ask of the parley with no options: its answer is `ok` or `own`. The answer of an ask with no options and no parley is `own`.

A parley is `{ id, slug, title, goal, evidence?, design_sense?, status, at, by }`. `slug` is lowercase words of letters and digits joined by hyphens, unique in the project. `evidence` is a list of texts that is not empty. `status` is `open`, then `contract`, then `done` or `dropped`. A parley that is not open has `design_sense`. `at` is the time of its last change, and `by` the caller of that change.

`title`, `goal`, `tension`, `design_sense`, each label, and each text of `evidence`, `gains` and `costs` are plain text: at least one character that is not white space, with no backtick and no `**`.

The requests have an `action`, and each write has a `caller`. A request names one ask as `{ id }`, its ID, or as `{ slug, n }`, its number `n` in the parley `slug`; a request with keys of both fails with `Invalid ask request: <key>: not allowed`. The reply of a write of asks, `{ parleys, asks }`, comes from the commit of the write: `parleys` has each parley that the write changed, or whose asks it changed, as `{ parley, asks }` with all of its asks, in ID order, and `asks` has the asks with no parley that the write added or changed, in ID order.

- `ask round { caller, parley?, asks }` writes one or more asks, with the state `open` and the caller as their asker. With `parley` `{ slug, title?, goal?, evidence?, design_sense? }`, the asks serve the parley `slug`, and take its next numbers. A new slug makes an open parley, which needs `title` and `goal`. A known slug must be an open parley, and the fields that `parley` gives replace its own. With `item`, the ID of an item, which needs `parley`, the round also writes the edge `parley:<slug> shapes item:<item>` with the checks and the errors of `item link`, after it writes the parley: an equal edge is not written again. A round with `item` and no `parley` fails with `Invalid ask request: parley: required`. The reply is the write: the parley with its asks, or the new asks when they have no parley.
- `ask answer { caller, answers, user? }` writes one or more answers `{ id, answer, label?, words? }` or `{ slug, n, answer, label?, words? }` in one write, each of another ask. When an answer `ok` goes to a read-back, the parley becomes `contract` in the same write, after every answer of the write. Each contract that no item has an edge `shapes` from gets a new open item, with the title of the parley, no text, and the caller as its `by`, and the edge `parley:<slug> shapes item:<id>`, in the same write. A contract that shapes an item gets no new item. The reply is the write: each parley of the answered asks, with its status after the write, and the answered asks with no parley. The host sets the `author` of each answer: `{ kind: "user" }` when `user` is `true`, else `{ kind: "hosted", conversation }` when the caller is the project agent or a conversation of the children library, else `{ kind: "agent", caller }` with the caller. The host cannot tell who holds the socket, so an `ask answer` with `user: true` from any client counts as the answers of the user, as for `input`: this is the limit of the mark. A caller that is not a conversation of the host and sends no mark, such as `cli`, `orda` or `<store>:<id>`, is written as `agent` with that caller.
- `ask drop { caller, id }` or `ask drop { caller, slug, n }` drops an open ask, and replies with the write: its parley, or the ask when it has no parley.
- `ask note { caller, id, note }` or `ask note { caller, slug, n, note }` sets `note`, the ID of the vault note of the ask (not a `note` request of a child), and replies with the ask. In the same write, it sets the todo `Save to the vault` of the ask to `done` (see below), unless that todo is `done` or `dropped`: a dropped todo stays dropped. The ask can be in any state, and its parley in any status. A second note replaces the first, and no request removes it. It sets `at` and `by`, and keeps `asker`. An answer or a drop keeps the note. Only the asker of the ask sends it: another caller fails with `Ask <id> was asked by another caller: only its asker records its note`. The `note` action of the `parley` tool and `harness parley note` send it.
- `ask read { id }` or `ask read { slug, n }` replies with the ask, in any state.
- `ask list` replies with `{ asks }`, the open asks.
- `parley take { caller, slug }` makes the caller the asker of each open ask of the parley `slug`, which is open or a contract, and replies with `{ parley, asks }`. A contract has no open ask, so its take changes no ask. The answers of the parley that wait for an asker (see [Push](#push)) leave the queue in the same write: the taker has them in the reply, and no asker gets them after.
- `parley end { caller, slug, status }` ends the contract `slug` with the status `done` or `dropped`, and replies with the parley. A contract that shapes an open item does not end: the change of its last open item to `done` or `dropped` ends it (see `item set`). So `parley end` ends only a contract that shapes no item, or whose items are all closed.
- `parley read { slug }` replies with `{ parley, asks }`, the asks in the order of their numbers. `parley list` replies with `{ parleys }`.

No request removes an ask or a parley. A request that fails changes nothing. The checks inside one request run at the request: an empty list of asks or of answers, an option key used twice, a `plan` that is not a key of the options, two answers of one ask, a text that is not plain, a slug that is not valid, and a `note` that is empty or blank fail with `Invalid ask request: <path>: <rule>` or `Invalid parley request: <path>: <rule>`, such as `Invalid ask request: asks/0/options/1/label: plain text, no backticks or **` for a label with a backtick. An answer `own` without `label` fails with `Invalid ask request: answers/<n>/label: required`, and an `ask note` without `note` with `Invalid ask request: note: required`. The checks against the store fail with:

- `Unknown ask: <id>`, `Unknown parley: <slug>`, and `Parley <slug> has no ask <n>`.
- `Ask <id> has two answers in one write`, when an answer by ID and an answer by number name the same ask.
- `Parley <slug> is new: title is required`, and the same for `goal`.
- `Parley <slug> is <status>: its asks do not change`, for a round, an answer or a drop on a parley that is not open, and for a take on a parley that is done or dropped.
- `Ask <id> takes <keys> or own`, such as `Ask 3 takes a, b or own` or `Ask 4 takes ok or own`, and `Ask <id> takes own` for an ask with no options and no parley.
- `Ask <id> is dropped: it takes no answer`, and `Ask <id> is <state>: only an open ask drops`.
- `Parley <slug> cannot be a contract: ask <n> is open`, and `Parley <slug> cannot be a contract: design_sense is not set`, for an answer `ok` to a read-back while another ask of the parley is open, or without a design sense.
- `Parley <slug> is <status>: only a contract ends`.
- `Parley <slug> shapes open items <ids>: close them, and the contract ends`, for a `parley end` of a contract that shapes open items, with their IDs in ID order, joined with `, `.
- `Ask <id> was asked by another caller: only its asker records its note`, for an `ask note` from a caller that is not the asker of the ask.
- For a round with `item`: `Unknown item: <id>`, and `Item <id> is <state>: an edge shapes cannot go to it`.

`Ask`, `Parley`, `AskRef`, `AskWrite`, `AskList`, `ParleyAsks` and `ParleyList` of `@vzlentin/harness/protocol` are the TypeBox schemas of an ask, a parley, the name of an ask and the replies.

The `ask answer` request also queues the answers for their askers, in the same write, in the document `harness.user-answers` of the store, so a restart loses none. It queues one delivery for each asker and parley of the answered asks, with the text of the parley after the write, as the `read` of the `parley` tool gives it, and one delivery for each answered ask with no parley, with the line of the ask, then each of the words of the user on its own line. Each delivery ends with the line `<mark> <id> <text>` of each todo `Save to the vault` that the same write added for one of its asks (see below). An ask whose asker is the caller of the answer gets no delivery. Each delivery has an ID from a counter that never goes down. The host pushes them (see [Push](#push)).

When the host has a vault, the `ask answer` request also adds, in the same write, the todo `Save to the vault: <title>` to the list of the asker of each answered ask (see the `todo` request in [Host](#host)), with the first line of the title of the ask, and with `ask`, the ID of the ask. The list of the asker is the list of the project agent when the asker is its conversation ID, the list of a conversation that the children library opened when the asker is its ID, and the list of the caller when the asker is a Pi session that the host knows. One ask gives one todo: the host keeps, in the document `harness.save-todos` of the store, the ID of each ask that has its todo and the list that holds it, so a second answer or a changed answer adds none, whatever the state of the todo. The host has a vault when `VAULT` of its environment is set and names a folder that exists; it reads this at each answer, and without a vault no ask gets a todo. With a vault, these asks get no todo: the read-back of a parley, an ask with a `note`, and an ask whose asker has no list, such as a session of a workflows run or `cli`. `ask note` reads a list only when that document says the list holds the todo of the ask, so a note creates no list. `harness store load` writes this document from the `ask` of the loaded todos.

### Push

When a child finishes, the host sends its unread answers to its caller, so the caller does not need `wait`. A request of a `spawn` or `send` with `notify: false` is quiet: its answer is not pushed alone, and it does not hold the caller. A child is done when its own turn ended and none of its children has an unread notify request, at any depth: until then, it holds its caller. The host checks this after each commit that can end a turn or change a record of a child, at host start, at the end of a `wait` or a `send`, and when an `answers` request opens or its reply is written. For a done child, it takes the unread answers as `wait` gives them, marks them read, and delivers them:

- The text is the answers in the form of `wait`, cut as `wait` cuts them (see [Limits](#limits)), without its first line `<handle> finished` and the blank line after it. When the last turn failed or was aborted, `failed` is true and the text is the error of `wait`, such as `<handle> failed: overloaded` or `<handle> was aborted`.
- A caller that is a conversation of the host (a child, the project agent, or another conversation of the children library, such as one of a workflow task) gets the input `subagent <name> (<handle>) finished` (`subagent <handle> finished` for a child without a name), or `failed` in place of `finished` when `failed` is true, a blank line and the text: a new turn when it is idle, a follow-up when it works. Its request ID is `push:<handle>:<read>`, so a push that runs again after a restart does not repeat. The input reaches the caller before the child stops holding it.
- Any other caller, such as a Pi session, gets the answers as the reply to its open `answers` request, oldest child first. These answers become read only once the reply is written to the socket. When the write fails, or the connection closes first, they stay unread, for a later `answers` request or a `wait`; a `wait` that runs meanwhile waits until the write ends. Without an open request, the answers stay unread too. When the host stops after it wrote the reply and before it marked the answers read, the next `answers` request gives them again.
- When a push of a child fails, such as a conversation that cannot be found or a caller that refuses the input, the host writes a warning and skips that child for 1 s, then for twice as long after each failure in a row, up to 60 s. A timer pushes again when the wait ends, also without a new commit. A push of the child that ends without an error resets the wait. While a child of a caller waits after a failed push, the later children of that caller wait too, so the answers keep their order.
- A turn that a mirror session started sends nothing up: when the last request is mirror input, the answer that goes up is the one of the caller's last request.

The host pushes the queued answers of the user to their askers (see [Asks and parleys](#asks-and-parleys)) in the same checks, after each commit that changes the queue, with the same destinations and the same waits after a failed push, oldest delivery first, after the answers of the children of the same caller. They differ from the answers of a child in these points:

- A delivery is `{ source: "ask", ask, text }` for an ask with no parley: the ID of the ask and the text of the queue. It is `{ source: "parley", parley, asks, text }` for the asks of a parley: the slug of the parley, the IDs of the answered asks, and the text of the queue. The input, and the text of the Pi message, is `the user answered ask <id>` or `the user answered the parley <slug>`, a blank line and the text.
- A conversation of the host gets it as input with the request ID `user-answer:<id>`, a new turn when it is idle and a follow-up when it works. The delivery leaves the queue after the input is sent.
- In the reply of an `answers` request, a delivery leaves the queue once the reply is written. When the write fails, or the connection closes first, it stays for a later request. When the host stops after it wrote the reply and before it removed the delivery, the next `answers` request gives it again. Without an open request, such as a Pi session that is closed, the answers stay in the queue.
- A delivery to an ended conversation of the host resumes it, as a `send` does: the answers of the user, the approval of a held action, and the answers of its children. A conversation with no record, such as a child of a task, resumes too, and the delivery does not change its last request. When the children library ends the conversation while the delivery is admitted, the delivery is aborted and fails. The unread answers of an ended child go only to the reply of an open `answers` request, such as the answers of the children of a Pi session that ended: as input, they would resume an ended conversation. A busy turn that the end aborted gives `<handle> was aborted`, with `failed` true. The answers of children to a child that the rule of what it serves ended (see [Agent life](#agent-life)), and not a `stop` or the end of its session, wait while it stays ended: the rule ends the child alone, its children keep running and end later, and their answers as input would resume it at once. The answers of the user and the approval of a held action go to it and resume it, as for any ended conversation. A message that resumes it lets the answers of its children go.
- The wait after a failed push is kept for each delivery. A delivery that waits, or a child of the same caller that waits after a failed push, makes the later deliveries of that caller wait too.
- A turn that a delivered answer starts sends nothing up to the caller of the asker, as for mirror input.

The depth of the subagent tree is the setting `agentDepthLimit` in Pi's global `settings.json`, an integer of at least 1, default 4. The host reads it again at each spawn, and it applies to the new trees: a child of a child keeps the limit of its tree. A deeper spawn fails with `Nested subagents are disabled`. A tree that a library caller of the children library starts without a limit, such as one of workflows, keeps the limit of 2, also for the spawns of the `subagent` tool in it. A library caller can open a child as a depth root (`depthRoot`): it stays under its tree parent, for the end and the viewer, and starts a new depth budget at depth 0 with its own `limit`, such as a session that a script opens in code. With `depthParent`, a child takes the depth budget of that conversation in place of its tree parent's: one deeper, with its limit; a conversation that the library did not open counts as depth 0. No child, at any depth, gets the `memory` tool. A child at the limit of its depth budget is a leaf: it gets no `subagent` and no `workflow` tool, also when `--tools` names them, so a model call to `subagent` there gives `Tool subagent is not available`. A call of `tools.subagent` in its IPython kernel gives the same error (see [Tools bridge](#tools-bridge)).

The default model and thinking level of a spawn are the settings `subagentModel` and `subagentThinkingLevel` in Pi's global `settings.json`. `subagentModel` is `<provider>/<model>`, split at the first `/`, as `subagentModel: "openai-codex/gpt-5.4-mini"`. `subagentThinkingLevel` is one of pi-ai's thinking levels. The host reads them again at each spawn, so a change applies to the next spawn without a restart. Each key works alone: a key that is missing or not valid, such as a model without `/`, counts as absent, and the caller's value applies. They apply to every spawn of the `subagent` tool and the CLI, at every depth. A model that the host does not know fails the spawn with `Unknown model: <provider>/<model>`. The children that a library opens, such as the roles of workflows, do not use them.

### Agent life

An agent lives as long as what it serves, and the host ends it when that ends. A child serves what its spawn fixed (see `host.sock` in [Host](#host)):

| `serves`                          | Ends when                                                              |
| --------------------------------- | ---------------------------------------------------------------------- |
| `{ kind: "spawner" }`             | its caller is a child of this host, by handle, and that child is ended |
| `{ kind: "parley", slug }`        | the parley is no longer open: a contract, done or dropped              |
| `{ kind: "contract", slug }`      | the contract is done or dropped, as when its last open item closes     |
| `{ kind: "item", id }`            | the item is done or dropped                                            |
| `{ kind: "project" }` (the agent) | never                                                                  |

A spawner that is not a child of this host never ends by this rule: the project agent, a Pi session (its end has its own rule, see [Pi extension](#pi-extension)), `cli`, a conversation of a task and a `<store>:<id>` caller. The item of a child is the item whose `serves` edge names the child: only its spawn writes that edge, so one item at most has it. A child that serves an item that no edge names, after an `item unlink` or the move of the todos to items, never ends by this rule. A child whose end the move of the todos to items made due, because its todo was done or dropped, ended: the host keeps the due end in its record across restarts, and ends the child once its list is clear, as below. The host checks the rule at its start and after each commit that changes the records of the children, the end of a child, the parleys, an item or a list of todos, oldest child first, so a child sees the end of its spawner in the same check. When what a child serves ended, the host waits until the list of the child has no `open` and no `doing` todo, then ends the child alone: it marks it ended and aborts its turn, a busy one too, which gives `<handle> was aborted`. The children of the child keep running, and the rule ends each of them in its turn, once its own list is clear, because they serve their spawner. The end marks each request of the child read, as a `stop` does, so it holds no caller. The rule ends a child once: a message resumes it, as after a `stop`, and the rule does not end it again; a `stop` or the end of its session still does. A message that comes between the check of the rule and the end is aborted. A child that is already ended when what it serves ends, by a `stop` or the end of its session, stays as it is: the rule only marks it, so it does not end it again after a resume, and the answers of its children do not wait: they resume it, as the answers of the user do.

The rule ends only an agent whose list has no `open` and no `doing` todo. An idle agent with such a todo is not ended: it stays as long as the todo stays open or doing, also when what it serves ended long ago. The user can end it with `stop`, or set its todos to `done` or `dropped`.

## Limits

- Children get only `read`, `write`, `edit`, `bash`, `subagent`, `todo`, `thread`, `rule`, `parley`, `item`, `codemode`, and the tools of the host's entries (see [Host](#host)). Their `codemode` scripts also call the tools of the MCP servers of the host, which the model does not get as tools (see [MCP servers](#mcp-servers)). They get no Pi extensions. A child at the depth limit also gets no `subagent` and no `workflow`, and keeps `todo`, `thread`, `rule`, `parley` and `item` (see [Push](#push)). A child of `children.open` whose `setup` removes `PROJECT_EXTENSION` gets no `thread`, `rule`, `parley` and `item` (see [Host](#host)). No child gets the `memory` tool of the project agent. `codemode` runs JavaScript that calls the other tools of the child, as Pi's `codemode` does. A script that a host stop interrupts continues when the host starts again.
- A `bash` call of a hosted conversation (a child, the project agent, or a workflows session) that sets no `timeout` stops after 300 seconds. Its result keeps the output so far, and its error is `Command stopped after 300 seconds: it set no timeout. Set a timeout to run longer.` A call that sets a `timeout` runs with it, also above 300 seconds; when it fires, the error stays `Command timed out after <timeout> seconds`. The `timeout` parameter of `bash` says `Timeout in seconds (optional, default 300 seconds)`. A `bash` call of a `codemode` script gets the same default: the `await` of the script rejects with the line, and the script gets no output. Two cases lose output or keep running: a command that pipes into `tail` shows nothing when it stops, because `tail` prints only at its end, and a process that `setsid` starts leaves the process group, so the stop does not end it.
- A change to `AGENTS.md` or to a skill reaches children only after the host restarts. A rule that the user decides or retires reaches each agent at its next model request, with no restart.
- `wait` and a push (see [Push](#push)) cut each answer of a child, and each failure text, to 256 KiB in UTF-8, on a character boundary. They then add the line `[The answer was cut at 256 KiB]`. When they give several answers, they cut each one. The answer stored in the child's conversation stays whole: the caller reads it there with `watch`, `harness attach <handle>` or the transcript of `harness inspect`.
- A query reads at most 256 KiB in UTF-8 of the transcript of its conversation: the last part, from a character boundary, of a longer one. Its answer then starts with the line `[The conversation is longer than 256 KiB: this answer reads only its last 256 KiB]`.
- `--file` gives text only; images are not attached.
- The CLI sends each `spawn` once and has no `key`. If the host stops during a `spawn` and you run the command again, there can be two children.

## Tool

The `subagent` tool does what the CLI does, with one `action` and its arguments:

| `action`         | Arguments                                                                                              |
| ---------------- | ------------------------------------------------------------------------------------------------------ |
| `spawn`          | `name`, `provider`, `model`, `thinking`, `cwd`, `tools`, `prompts`, `files`, `key`, `notify`, `serves` |
| `send`           | `handle`, `message`, `followUp`, `key`, `notify`                                                       |
| `wait`           | `handle`, `timeout` (seconds, default 1800)                                                            |
| `status`, `stop` | `handle`                                                                                               |
| `rename`         | `handle`, `name`                                                                                       |
| `list`           | none                                                                                                   |
| `query`          | `handle`, `question`                                                                                   |

`tools`, `prompts`, and `files` are arrays. `serves` is `{ parley: <slug> }` or `{ item: <id> }`, as on the socket (see [Agent life](#agent-life)). A relative `cwd` or file path is relative to the caller's working directory. A caller without a working directory cannot spawn. The text result is the output of the same CLI command. The structured result is `{ action, value }`, and the tool declares its schema, where `value` is the host's reply: the child for `spawn`, `status`, and `rename`, `{ verb, child }` for `send`, `{ answer }` for `wait` and `query`, the children for `list`, and `{ handle, name }` for `stop`. A child is `{ handle, name, state, provider, model, thinking, cwd, serves }`, where `state` is `busy`, `idle`, `error` or `ended`, `cwd` is its working directory, and `serves` is what it serves: `{ kind: "spawner" }`, `{ kind: "parley", slug }`, `{ kind: "contract", slug }`, `{ kind: "item", id }` or `{ kind: "project" }`.

A spawn without `provider` and `model` uses `subagentModel` in Pi's global `settings.json`, else the caller's model. A spawn with only one of `provider` and `model` takes the other from the caller, not from the setting. A spawn without `thinking` uses `subagentThinkingLevel`, else the caller's level, in both cases clamped to the nearest level that the model has. When no source gives a model, the spawn fails with `No provider specified and the caller has no model` or `No model specified and the caller has no model`. A spawn refuses a `thinking` that the model does not have with `<provider>/<model> has no thinking level <level>`. The CLI refuses a `--thinking` that is not one of pi-ai's levels with `Invalid thinking level: <level>`. The tool's parameter schema takes only pi-ai's levels, so Pi refuses another value before the call. On the socket, such a `thinking` fails with `Invalid spawn request: thinking: must be equal to one of the allowed values`. A `spawn` or `send` that comes again with the same `key` finds the first one and does not repeat it. Without `key`, the call is the key. Each caller has its own keys. When the call is aborted, for example with Esc, a `wait` stops; the child continues.

When a child finishes, its answer comes to the caller as a message that starts a turn (see [Push](#push)). `notify: false` on a `spawn` or a `send` turns off the message for the turns of that call; the answers then come only with `wait`. The CLI has no flag for it. The tool description tells the model to use `wait` only when it needs the answer in the same turn. Its last line says that, with the `ipython` tool, a cell has `tools`, which runs the tools of the conversation, `subagent` too, as `await tools.<name>(**args)`, and that `print(tools.__doc__)` lists them and `print(tools.<name>.__doc__)` gives the arguments of one (see [Tools bridge](#tools-bridge)).

`query` asks a model one `question` about the conversation of the child `handle`, so that the caller learns what the child did without its transcript in its context. The host sends a `query` request `{ caller, question }` with a handle or `{ conversation }`, and replies `{ answer }`; the text result is the answer. The model gets one user message: the transcript between `<transcript>` and `</transcript>`, then `Question: <question>`. The transcript has the model messages of the entries of the conversation, oldest first, separated by a blank line: each message of the user role as `User: <text>`, the notes, digests and summaries too; each text of the assistant as `Assistant: <text>`; and each tool call as `Tool call <name>: <arguments as JSON>`. It has no thinking, no tool output and no image. It is at most 256 KiB (see [Limits](#limits)). A query writes no entry, writes nothing in the store and starts no turn, so it works on a child that is busy or idle. The caller `cli`, a command from a terminal that is not an agent (`PI_SESSION_ID` is not set), can query any child, `agent` and any conversation of the children library, also after a `stop`, with `--conversation <id>`. Another caller, an agent, can query only a child that it spawned, also after a `stop`: a child of another caller with `Subagent <handle> belongs to another session`, a conversation ID that is not one of its children with `The conversation <id> is not a child of this caller`, and `agent` with `Only a terminal that is not an agent can query the project agent`. The model is the setting `queryModel` in Pi's settings, `<provider>/<model>` as `subagentModel`, read again at each query from the global settings and the settings of a trusted project; else `subagentModel` in Pi's global settings; else Pi's default model (`defaultProvider` and `defaultModel`). A key that is not valid counts as absent. A query fails with one line: `No model for a query: set queryModel, subagentModel or a default model in Pi`, `Unknown model: <provider>/<model>`, `No credential for <provider>: log in to <provider> or set queryModel`, or `The query model <provider>/<id> failed: <errorMessage>` for a call that does not end with the stop reason `stop`.

`subagent` calls in one message run one after another, in message order, so a `wait` after a `send` waits for the answer to that message. A round with a `subagent` call runs all of its tool calls in order, `bash` and `read` included.

The CLI runs `spawn`, `status`, `rename`, `send`, `wait`, `stop`, `list` and `query` as calls of the same tool, `todo` as a call of the runner of the todo tool (see [Todos](#todos)), and `item` as a call of the runner of the `item` tool (see [Items](#items)). There are two other adapters of the `subagent` tool:

- In Pi, the extension `@vzlentin/pi-agents` gives the tool (see [Pi extension](#pi-extension)). The caller is the session ID, the same as `PI_SESSION_ID` for the CLI, so `harness list` in that session shows the tool's children. When the session runs a pi virtual model, its model, which a spawn inherits, is the physical model of its latest response (see [Pi extension](#pi-extension)).
- In another pi-durable host, the entry `@vzlentin/harness/durable-entry` gives the tool. The caller is `<store>:<conversation ID>`, where `<store>` is a random ID that the store keeps. A call that runs again after the host restarts uses the same key, so its spawn or send does not repeat. Such a host gets the answers only with `wait`: it opens no `answers` request.

The children get the tool too. Their caller is their conversation ID, as for their bash commands.

The `todo` tool keeps a list of todos (see [Todos](#todos)). It takes one `action` and its arguments: `add` with `text`, `set` with `id`, `state` and an optional `text`, and `list`. The list is the caller's own: the project agent has its own list, as any agent. The text result is the whole list after the call: the line of each todo, or `No todos`, for each action. The host adds todos to the list by itself, such as the todo `Save to the vault`, so the line of one todo would hide them; `harness todo` prints the line of the todo for `add` and `set`. The structured result is `{ action, value }`, where `value` is the reply of the host: the todo `{ id, text, state }` for `add` and `set`, and `{ todos }` for `list`. The description of the tool also tells when to keep a list, in this sentence after its first line: `Use it for each task of 3 steps or more: add one todo for each step before you start, set a todo to doing when you start its step, and to done when the step is finished.` The tool declares the schema of this result. The host gives the tool to the project agent and to each child, also at the depth limit. The call runs in the host process, as a call of the `subagent` tool does, and its caller is the conversation ID, so the list is the list of that conversation. A call that a host restart interrupts does not run again. It ends with `Tool todo was interrupted and may have partially run`, so an `add` is never made twice, and `list` shows whether it was made. The entry `@vzlentin/harness/durable-entry` does not give the tool. In Pi, the extension `@vzlentin/pi-agents` gives the tool too, with the session ID as the caller (see [Pi extension](#pi-extension)).

The `thread`, `rule`, `parley` and `item` tools read and change the store of the project (see [Host](#host)). Each takes one `action` and its arguments, and sends the requests of that object:

| Tool     | `action` | Arguments                                                                        |
| -------- | -------- | -------------------------------------------------------------------------------- |
| `thread` | `list`   | none                                                                             |
| `thread` | `read`   | `thread`                                                                         |
| `thread` | `log`    | `thread`, `from`, `text`, `at`                                                   |
| `thread` | `draft`  | `thread`, `text`                                                                 |
| `thread` | `mark`   | `message`, `state`                                                               |
| `rule`   | `set`    | `saidBy`, `source`, and `name`, `kind`, `value`, `replaces`, or `id` and changes |
| `rule`   | `list`   | `kind`                                                                           |
| `parley` | `round`  | `asks`, and `slug`, `title`, `goal`, `evidence`, `design_sense`                  |
| `parley` | `answer` | `answers`, each `{ ask, answer, label?, words? }`, and `slug`                    |
| `parley` | `drop`   | `ask`, `slug`                                                                    |
| `parley` | `note`   | `ask`, `note`, `slug`                                                            |
| `parley` | `take`   | `slug`                                                                           |
| `parley` | `end`    | `slug`, `status`                                                                 |
| `parley` | `read`   | `slug`, `ask`                                                                    |
| `parley` | `list`   | none                                                                             |
| `item`   | `add`    | `title`, `text`                                                                  |
| `item`   | `set`    | `id`, and `title`, `text`, `state`                                               |
| `item`   | `list`   | `state`                                                                          |
| `item`   | `read`   | `id`                                                                             |
| `item`   | `link`   | `from`, `kind`, `to`                                                             |

- `log` adds a message `in` from the person `from`, with `at` when it is given. `draft` adds a message `out` from `user`, at the time of the write, so its state is `draft`. `mark` sends `message mark`. The `thread` tool sends no `thread join`, no `message edit`, no `message delete` and no `state` of `message log`. The description of `thread` tells the agent to put `draft:<id>` in the command of a call that sends a draft. The description of `parley` tells the agent how to write the answer line of the user, such as `[<slug>] 1a 3:"own words" 4b:"a note" ?5 ok`, with one `answer` call with `slug`: `<n><key>` is the answer `key` to the ask `n`, `:"<words>"` after it adds the words, `<n>:"<words>"` is `own` with a short label and the words, `?<n>` writes nothing, and `ok` is the plan of each open `my call` that the line does not name, and `ok` to the open read-back. The description of `parley` also gives the asker the vault flow of an ask: read the vault on the topic, write the view with `show-me` and wiki links to the notes that exist, and when the user answers and `VAULT` names a folder that exists, ask the next question first, then do the todo `Save to the vault: <title>`: write or update a note with an `id` in its front matter and record it with `note`, which closes the todo, or drop the todo with a one-line reason. `rule set` without `id` adds an open rule, and with `id` changes an open rule, as the `rule` request does. The `rule` tool has no `status`, and no action that decides, retires, edits as the user, creates or deletes a rule: an agent proposes a rule, and only the user puts it in effect. To change a decided rule, an agent adds a new rule that replaces it.
- Each `parley` call sends one request, except `list`. `parley round` sends `ask round`, with the frame `{ slug, title, goal, evidence, design_sense }` of the fields that it gives as `parley` when it has `slug`, and `item` when it gives `item`. `parley answer` sends `ask answer` with no `user`, so its answers are the answers of the agent, `{ kind: "hosted", conversation }`, `parley drop` sends `ask drop`, `parley note` sends `ask note` with `note`, and `parley read` with `ask` sends `ask read`. `parley take`, `parley end` and `parley read` with `slug` alone send the `parley` request of the action. `parley list` sends `parley list`, then `ask list`. With `slug`, `ask` is the number `n` of the ask in the parley, and the request names it as `{ slug, n }`. Without `slug`, `ask` is the ID of an ask, and the request names it as `{ id }`.
- The runner refuses a call without an argument that the action needs with `<action> requires <argument>`, before it sends a request: `read`, `log` and `draft` without `thread`, `log` without `from`, `log` and `draft` without `text`, `mark` without `message` or `state`, a `set` without `saidBy` or `source`, a new rule without `name`, `kind` or `value`, a `round` without `asks`, an `answer` without `answers`, a `drop` without `ask`, a `note` without `ask` or `note`, a `take` or an `end` without `slug`, an `end` without `status`, and a `read` with neither `slug` nor `ask`. A `round` with `title`, `goal`, `evidence`, `design_sense` or `item` and no `slug` fails with `round requires slug`. The other errors come from the host (see [Host](#host)).
- Each `item` call sends one `item` request of its action, with the caller for `add`, `set` and `link`. The tool has no `unlink`. The runner refuses an `add` without `title`, a `set` or a `read` without `id`, and a `link` without `from`, `kind` or `to`, with `<action> requires <argument>`, and a `from` or a `to` that is not a reference with `Invalid item reference: <reference>`, before it sends the request. The text of an item is its line `<mark> <id> <stage> <title>`, where the mark is `?` when the item needs you, else `○` for open, `✓` for done and `✗` for dropped. `add` and `set` give the line of the item, `list` the line of each item or `No items`, `read` the line, the text of the item when it is not empty, and one line `<from> <kind> <to>` for each edge, and `link` the line of the edge. The text of `read` has the `needs` edges that go to the item after its own edges, as the reply of `item read` has them. The description of `item` tells the agent that talks with the user to add, reword, close, drop and link items from what the chat shows, and to end its answer with one line of the change to the board, such as `board: +2, closed 3, 10 needs 8`; a message to a person stays a thread draft, not an item. `itemLine`, `itemText` and `edgeLine` of `@vzlentin/harness/protocol` give these texts.
- The text result has one line for each object. An author is `user`, or a person as `<name> (<id>)`, such as `Sam (1)`, or `person <id>` when the person has no name in the reply of `person list`. A thread is `<id> <topic> with <persons>: last message <time>`, or `no messages` in place of the time, with its persons as authors. A message is `<id> <time> <author> (<state>): <text>`. A rule is `<id> <name> (<kind>, <status>): <value> [said by <author> in message <source>; replaces <id>]`, without ` in message <source>` when it has no source, such as `[said by user]`, and without `; replaces <id>` when it replaces none. A time is in ISO 8601, in UTC. `thread read` gives the line of the thread, then the line of each message, oldest first, or `No messages`. `thread list` gives the line of each thread, or `No threads`; `rule list` gives `No rules` for no rules. Each call, except a `parley` or an `item` call, also sends a `person list` request, for the names.
- The text of `parley` joins the fields of a line with `·`. A parley is `<slug> · <status> · <title>`. An ask is `<n> · <title> · <kind> · open · plan <key> · <label>` while it is open, `<n> · <title> · <kind> · <answer> · <label>` when it is answered, and `<n> · <title> · <kind> · dropped` when it is dropped. `<n>` is its number in its parley, or its ID when it has no parley. A field that the ask does not have is left out: `<kind>`, and `plan <key> · <label>` with no plan. The label of an open ask is the label of the option of its plan. The label of an answer is the `own` label, the label of the option of the key, or the label of the answer for `ok`. The text of a parley is its line, the line of each of its asks in the order of their numbers, each open ask followed by the line of each of its options, then one last line. An option line is two spaces, then `<key> · <label>`, then `gains: <gain>; <gain>` and `costs: <cost>; <cost>` when the option has them. For an open parley, the last line is the answer line: `[<slug>]`, then `<n><plan>` for each open `your call` with a plan, then `ok` when no ask is open or when another ask is open. For any other status, the last line is `harness parley show <slug>` (see [Parleys](#parleys)). `round`, `answer` and `drop` give the text of each parley of the reply, then the line of each ask with no parley of the reply. `answer` then gives the line of each open todo of the caller's list that belongs to an ask of the reply, such as the todo `Save to the vault` that the answer added: it sends a `todo list` request for that. `take` and `read` with `slug` give the text of the parley, `end` gives the line of the parley, `note` gives the line of the ask, and `read` with `ask` gives the line of the ask, then its `view`. `list` gives the line of each parley, or `No parleys`, then the line of each open ask with no parley.
- The structured result is `{ action, value }`, where `value` is the reply of the host: the object for `log`, `draft`, `mark`, `set` and `add`, `{ thread, messages }` for `read`, and `{ threads }` or `{ rules }` for `list`. For `parley`, `value` is the write `{ parleys, asks }` for `round`, `answer` and `drop`, the ask for `note` and for `read` with `ask`, `{ parley, asks }` for `take` and `read`, the parley for `end`, and `{ parleys, asks }` with the open asks with no parley for `list`. For `item`, `value` is the item with its stage for `add`, `set` and `read`, `{ items }` for `list`, and the edge for `link`. Each tool declares the schema of this result, with the schemas `Thread`, `Message`, `Rule`, `Ask`, `Parley`, `ParleyAsks`, `ParleyList` and `AskWrite` of `src/protocol/project.ts`, and `StagedItem`, `ItemList` and `Edge` of `src/protocol/item.ts`.
- The host gives the tools to the project agent and to each child, also at the depth limit. A call runs in the host process, and its caller is the conversation ID, which the host keeps in `by` of each object that the call writes. The requests have no request ID, so a call that a host restart interrupts does not run again. It ends with `Tool <name> was interrupted and may have partially run`, so a message is never logged twice. The entry `@vzlentin/harness/durable-entry` does not give the tools. In Pi, the extension `@vzlentin/pi-agents` gives the tools too (see [Pi extension](#pi-extension)).

The host gates each tool call of the project agent and of each child, the nested calls of `codemode` and of the tools bridge included, with the `beforeTool` hook of pi-durable. The hook sends a `gate` request (see [Host](#host)) with the request ID `gate:<task ID>`, the conversation ID as the caller, and the texts of the last 3 entries of the kind `harness.typed` of the conversation, the `input` requests (see [Host](#host)), oldest first. The prompt of a spawn, a `send` of a parent agent, the input of an approve, a push of answers, a prompt of a task, the catch-ups, the digests and the notes are not typed by the user, so the gate does not read them. A child that got no `input` gives no messages: the gate holds each of its calls that a decided conduct rule makes wait for the go of the user, and the user approves it. A parent that writes "the user said go" in a `send` does not let the call pass. This is the cost of the mark. A call of a read tool sends no request. A held call does not run: its result is the error `Tool call blocked: Held as action <id>: <reason>`, and the agent goes on. A request that fails blocks the call with its error. When the user approves the action, the agent gets the input of the approve, and its next call of the same command runs one time with no question. The entry `@vzlentin/harness/durable-entry` does not gate its calls.

## Tools bridge

In the host and in interactive Pi, a cell of the IPython kernel of a conversation or of a session has `tools`: the tools of that conversation, as coroutines, as a `codemode` script has them (see [Tools bridge in Pi](#tools-bridge-in-pi) for Pi). The client is `python/harness_tools.py` of `@vzlentin/harness`. It uses the standard library only, and needs Python 3.9 or later. It has no copy of a tool schema: the text of the tools comes from the server.

- `await tools.<name>(**args)` runs the tool `<name>` of the conversation of the cell with `args`, as the cell gives them, `None` included. The bridge adds no argument and has no default of its own: a `tools.subagent(action="spawn", ...)` without `notify` sends the answer of the child as a message, as a spawn of the model does (see [Push](#push)), and `notify=False` turns it off. The tool checks the arguments against its schema.
- A call gives the structured output of the tool when the tool declares a schema for it, else the text of its output. A success of a tool with a schema that gives no structured output raises with `Tool <name> gave no structured output`.
- A refused or failed call raises `ToolError`, a `RuntimeError`, with the error text: the text of the schema check, such as `Validation failed for tool "subagent": ...`, `Tool <name> is not available` for a tool that the conversation does not have, or the error of the tool. The error of the tool is the text of its output, else the text of its error diagnostics, else `Tool <name> failed`. A result that the tool marks as an error always raises, also when it has a structured output. `from harness_tools import ToolError` gives the class.
- `print(tools.__doc__)` gives the use of `tools`, then the line `- <name>: <first line of the description>` for each tool that a cell can call. `print(tools.<name>.__doc__)` gives the description of the tool and the JSON Schema of its arguments. Each read asks the server for the list.
- A cell cannot call `ipython`: the kernel is busy with the cell, so the call would never start. The list does not have it, and a call fails with `A cell cannot run ipython: its kernel is busy with the cell`.
- A cell cannot call the internal tools of pi-durable's code mode, whose names start with `pi.codemode.`, such as `pi.codemode.models.classify`, nor a deferred tool, which a tool search must load. Code mode leaves them out of the tools that it lists to a script. The list does not have them, and a call fails with `Tool <name> is not available`, as for a tool that the conversation does not have.
- Each call opens its own connection, so `asyncio.gather` of several calls runs them at the same time. A cancelled call closes its connection, which stops the request in the server. In Pi, this also aborts the tool call. In the host, the tool call continues until it ends or its cell ends: the host cannot abort a nested call before its cell ends.

A call runs as a nested call of the `ipython` call of its cell, as a call of a `codemode` script runs inside the script. It runs only while its cell runs. A call while no cell of its kernel runs, such as a call from a thread after its cell returned, fails with `No cell of this kernel runs: tools runs a tool only while a cell runs`. When a cell ends, its calls that still run stop and fail with `The cell ended: tools runs a tool only while a cell runs`. A kernel runs one cell at a time, so a call goes to the oldest open cell of its kernel.

The host listens on three events of pi-ipython on the event bus of its entries:

- `ipython:cell-start` with `{ conversationId, api, context }`, before a cell runs. The host opens the cell. A call of the cell runs as `api.executeTool(name, args, context)`, so pi-durable checks the arguments against the schema of the tool, gates the call (see the gate in [Tool](#tool)), and aborts the call when the cell ends, not before. A tool with a schema keeps no text of its output, so its error is the text of its error diagnostics. The tools of the list are the `callable` tools of the agent of the conversation, read at each request. The host serves each conversation that has the `ipython` tool, a leaf too: a leaf has no `subagent` tool, so `tools.subagent` there fails with `Tool subagent is not available`, and its other tools run.
- `ipython:cell-end` with `{ conversationId }`, after the cell ends, also when it fails. The event does not name the cell, so the host ends the oldest open cell of the conversation. A cell that ends before an older cell of the same conversation would end the wrong cell. pi-ipython runs the cells of a kernel one at a time, so this does not occur.
- `ipython:kernel-starting` with `{ conversationId, env, startupCode, waitFor }`, before each kernel start, restarts included. On the first cell of a conversation, it comes after `ipython:cell-start`. In a promise that it gives to `waitFor`, the host starts a server for that kernel start.

A payload of another shape gives a warning, and does nothing else: `The ipython:cell-start event has an invalid payload; its cell gets no tools`, `The ipython:cell-end event has an invalid payload; its cell keeps its tools` or `The ipython:kernel-starting event has an invalid payload; its kernel gets no tools`. The server of a kernel start:

- The server is a Unix socket, `kernel.sock`, in a new directory `/tmp/harness-tools-<random>` with mode 0700. The short path keeps the socket under the 104-byte limit of macOS.
- It has a random secret token.
- The host sets `HARNESS_TOOLS_SOCKET` and `HARNESS_TOOLS_TOKEN` in the `env` of the payload, never in its own environment. The client reads them at each call.
- The host adds the startup code: it puts the folder of the client first on `sys.path`, then binds `tools`.
- A new kernel start of the same conversation replaces its server. The old server stops its requests, and the host removes its directory.
- When the server cannot start, the kernel start fails. A kernel start after the kernel servers close, while the host closes, fails with `The host is closing`: the host keeps its listener until the entries close.
- When the host closes, it stops the requests of each kernel server with `The host is closing`, before the entries close. It then closes the servers and removes their directories.
- A request line on a kernel socket that is longer than 16 MiB before its newline gets the reply `{ ok: false, error: "Invalid tools request: the line is longer than 16 MiB" }`, and runs nothing. The server then ends the connection, and reads and ignores the data that follows. This bound is for the transport only: it stops a line that has no end. The client sends the line as UTF-8 JSON, with each character as it is, so a character counts its UTF-8 bytes. The JSON escapes count in the line, such as `\n`, `\"` and a lone surrogate, which goes as its escape.

Each connection carries one request, one JSON line, of one of two shapes. `{ token, name, args }` runs the tool `name` with the object `args`. `{ token, list: true }` asks for the tools that a cell can call, as a list of `{ name, description, parameters }`. A line has only the fields of its shape. The server replies with one line, `{ ok: true, value }` or `{ ok: false, error }`, then ends the connection. A line that is not JSON or does not have the token of the server fails with `Invalid tools token` and runs nothing. A line of another shape fails with `Invalid tools request: <path> <message>`, the first error of the shape that it names: the list shape when it has `list`, else the call shape. Examples are `Invalid tools request: /name must be string`, and `Invalid tools request: /args schema is false` for a list line with `args`.

The calls of a cell are not replayed. The `ipython` tool of pi-ipython is not replay-safe, so a host restart does not run a cell again: its call ends with `Tool ipython was interrupted and may have partially run`, and pi-durable abandons the nested calls of the bridge that did not end. A call that ended before the restart keeps its effect, such as a spawned child, and does not run again. The bridge gives no key, so the nested calls of a cell take the keys `1`, `2` and so on, in the order that the cell makes them.

No system prompt has a section about `tools`. The last line of the description of the `subagent` tool names `tools`, `print(tools.__doc__)` and `print(tools.<name>.__doc__)` (see [Tool](#tool)). A leaf has no `subagent` tool, so no text tells its model about `tools`, but its kernel has them.

### Tools bridge in Pi

In interactive Pi, the extension `@vzlentin/pi-agents` (see [Pi extension](#pi-extension)) serves the bridge to the IPython kernel of the session, with the client, the servers and the startup code of the host. The kernel runs in Pi, and the calls of a cell run in Pi, as nested calls of the call of the cell.

- The extension listens on `pi.events`, from the start of the session to its end. In Pi, pi-ipython emits `ipython:kernel-starting` with `{ env, startupCode, waitFor }`, without `conversationId`, `ipython:cell-start` with `{ toolCallId, ctx }`, where `ctx` is the tool context of the call of the cell, and `ipython:cell-end` with `{ toolCallId }`. A payload of another shape shows its warning, the text of the host, as a notification, and does nothing else.
- In a promise that it gives to `waitFor`, the extension starts a server for that kernel start, as the host does: a Unix socket `kernel.sock` in a new directory `/tmp/harness-tools-<random>`, with a random secret token. It sets `HARNESS_TOOLS_SOCKET` and `HARNESS_TOOLS_TOKEN` in the `env` of the payload, never in the environment of Pi, and adds the startup code. A new kernel start, such as a restart, replaces the server: the old server stops its requests, and the extension removes its directory. When the server cannot start, the kernel start fails.
- A call of a cell runs as `ctx.executeTool(name, args, { signal })`, so Pi checks the arguments against the schema of the tool and runs the hooks of the session on it, the gate too. The signal aborts when the request stops: when the cell cancels the call, or the cell ends. Its value is the `structuredContent` of the result when the tool declares an `outputSchema`, else the text of its content. A result with `isError` raises with its text, else `Tool <name> failed`: Pi keeps no diagnostics of a nested call. The tools of the list are `ctx.tools`. `ipython:cell-end` ends the cell of its `toolCallId`, and aborts the signal of its calls that still run.
- The `subagent` tool of the session sends its requests to the host of the project. So `tools.subagent` gives the children of the session, the subagents widget and `/subagent` show them, and a child spawned without `notify: false` sends its answer to the session as a message.
- At the session end, the extension stops the requests of the server with `The host is closing`, closes the server and removes its directory. A later request of the kernel cannot reach a server, because its socket is gone. The children of the session end 30 s later, unless the session opens its `answers` request again (see [Pi extension](#pi-extension)).

## Pi extension

The Pi extension is the npm package `@vzlentin/pi-agents`, from the `pi/` folder of this repository: the `subagent` tool, the `/subagent` command, the subagents widget, the messages with the answers of the children and the answers of the user to the asks of the session, the `todo` tool, `/todo`, the todo widget, the `thread`, `rule`, `parley` and `item` tools, `/rules`, the digest of the session, the section of the decided rules, the `memory` tool and the memory section, the gate on the tool calls of the session, `/vc`, the mirror sessions (see [Mirror sessions](#mirror-sessions)), the tools bridge in the IPython kernels of the session (see [Tools bridge in Pi](#tools-bridge-in-pi)), and the `subagent` skill, `pi/skills/subagent/SKILL.md`, which tells the agent how to use the tool and the `harness` CLI, and the `parley` skill, `pi/skills/parley/SKILL.md`, which gives the conduct of a parley with the `parley` tool, and the vault flow of an ask: read the vault on the topic, write the view with `show-me` and wiki links to the notes that exist, and when the user answers, ask the next question first, write the view and the decision into a vault note with an `id` in its front matter, record that ID with `note`, which closes the todo `Save to the vault: <title>`, or drop the todo with a one-line reason. The `pi` manifest of the package lists the extension and the `skills/` folder. `/subagent` lists the children of the session, with the lines of `list`, and opens the one that you select in Pi, in a new herdr-app tab (see `openChildTab`); outside an hc terminal (`HC_TERMINAL_ID` is not set), it shows `Run in another terminal: harness attach <handle>`. When the tab does not open, it shows `Could not open a herdr-app tab: <reason>. Run in another terminal: harness attach <handle>`. The extension has the same version as harness. It has no copy of harness: `@vzlentin/harness` at that version is a dependency of `@vzlentin/pi-agents`, and the extension loads its `dist/` modules, so it starts the host of that install. It resolves each module from its own folder, as `@vzlentin/harness/<name>`, with the `exports` of the package. These `exports` give the public modules of the package, and only them: `answers`, `bridge`, `children`, `client`, `durable-entry`, `entries`, `herdr`, `host`, `inspect`, `memory-tool`, `mirror`, `overlay`, `projects`, `protocol`, `respond`, `tasks`, `todo`, `tool`, `trust` and `view-state`, and `package.json`. When Pi loads the extension, it also puts the `.bin` folder of the `node_modules` folder that holds `@vzlentin/harness` last on the `PATH` of Pi's process, so the agents find `harness`. It goes last because the folder also holds the commands of other dependencies, such as an older `pi`, which must not hide the user's own. It first removes that folder from `PATH`, so each load leaves it there once. When one of the `dist/` modules does not load, such as in a checkout without `npm run build`, Pi shows that the extension failed to load.

The model and the thinking level that a spawn of the `subagent` tool inherits from the session, when its arguments and the settings give none (see [Tool](#tool)), are the session's own or, when the session runs a pi virtual model (`api` `pi-virtual`), the physical model and the thinking level of the latest response that the branch of the session records; a failed or aborted response does not count, as it can name the virtual model, and a response without a thinking level leaves the selected one. A virtual model names no physical model the host could run, so a session that recorded no response inherits no model: the host picks `subagentModel`, and the spawn fails with the errors of [Tool](#tool) when no setting gives one.

With a UI, the subagents widget below the editor shows a dim header line `subagents`, then one line with the children of the session, `<name or handle>:<state>`, five at most, then `+<n>` for the others; it reads them every second and does not start the host. A busy child is in the warning colour, an idle child in the success colour and a child in error in the error colour. The widget leaves out the ended children. Without children that are not ended, or when no host runs (see [Host](#host): it exits after 5 idle minutes), the widget is hidden. When the host fails the request, it shows only `subagents: <first line of the error>` in the error colour, with no header.

The `todo` tool of the extension has the parameters, the description, the text result and the structured result of the `todo` tool of the host (see [Tool](#tool)), the whole list after each call, and runs the runner of the `todo` tool of the host, `runAgentTodoTool` of `@vzlentin/harness/tool`, on the caller's own list. The call goes to the host of the project with `sendToHost`, so it starts the host when none runs. The caller is the session ID, so the list is the list of the session, which the host keeps under the session ID (see the `todo` request in [Host](#host)). `harness todo` in the bash of the session has the session ID in `PI_SESSION_ID`, so it gives the same list. Each call opens its own connection, so calls at the same time could reach the host out of order: a round with a `todo` call runs all of its tool calls in order, as for the `subagent` tool, so the todos of one message get their IDs in message order.

Before each tool call of the session, the extension sends a `gate` request to the host of the project (see [Host](#host)) with `sendToHost`, so it starts the host when none runs. The caller is the session ID, the request ID is the ID of the tool call, and `messages` are the texts of the last 3 user messages of the branch of the session. A call of a read tool sends no request. With a UI, a held call shows a confirm prompt, `Held action <id>`, with the command and the reason. Yes approves the action and sends the `gate` request again, which runs the call one time. No drops the action and refuses the call with `Held as action <id>: <reason>`. Without a UI, the call is refused with that reason, and the action stays held for another client to approve. When a request of the gate fails because the host does not answer (`HostUnreachableError`: no host could start, the connection closed, the host was closing, or the host has another protocol version), a UI shows a confirm prompt, `The harness host does not answer`, with the error and `Run the tool calls of this session with no gate until the host answers?`. The calls of the session that fail at the same time share this prompt. Yes runs the call, and the later calls of the session run with no gate. No refuses the call with the error, and the next call asks again. Without a UI, the call is refused with `The harness host does not answer, and this session has no UI to let it run with no gate: <error>`. A call of a session with no gate sends its `gate` request without a start: when no host answers, the call runs. When a host answers, with a reply or an error, the gate is back: the extension shows the notification `harness: the host answers again; the gate is back` with a UI, then treats the reply as above, or refuses the call with the error. A new session or a `/reload` starts with the gate. Another request that fails, such as an error that the host replies or an abort, refuses the call with its error.

`/todo <text>` adds a todo to the list of the session, through the same runner and with the session ID as the caller. It starts the host when none runs, then refreshes the todo widget at once. With a UI, it notifies the line of the todo. `/todo` without text asks `New todo`; a cancel, or an answer that is empty or has only white space, adds nothing and shows nothing. The text loses the white space at its ends. Without a UI, the command prints the line of the todo, or `Usage: /todo <text>` on stderr without text. In a mirror session, the todo widget shows the list of the mirrored agent, not the list of the session, so `/todo` adds nothing and shows the error `harness: /todo does not work in a mirror session`. An error is the notification `harness: <error>`, or that line on stderr with no UI.

The `thread`, `rule`, `parley` and `item` tools of the extension have the parameters, the descriptions, the text results and the structured results of the tools of the host (see [Tool](#tool)), and run the same runners: `projectTools({ Type }, adapt)` of `@vzlentin/harness/project-tool` gives each tool, with its name, label, description, schemas and runner, to `adapt`, which registers it. The calls go to the host of the project with `sendToHost`, so they start the host when none runs. The caller is the session ID, which the host keeps in `by` of each object that a call writes. The answers of the `parley` tool are the answers of the agent of the session, `{ kind: "agent", caller }` with the session ID as the caller. A round with one of these calls runs all of its tool calls in order, as for the `todo` tool.

`/rules` lists the rules of the project, the open ones first, then the decided ones, then the retired ones, each as its line (see [Tool](#tool)). It sends its requests with `sendToHost`, so it starts the host when none runs, and the caller is the session ID. With a UI, a select shows `New rule` and the line of each rule. For a rule, a second select gives the actions of its status: `Decide`, `Retire`, `Edit` and `Delete` for an open rule, `Retire`, `Edit` and `Delete` for a decided rule, and `Edit` and `Delete` for a retired rule. `Edit` asks the name, with the current name as the placeholder, then the value in the editor; an empty answer keeps the field. `Delete` asks a confirm first. `New rule` asks the name, the kind and the value. The command sends the `rule` request of the action, and notifies the line of the rule of the reply. A cancel at any step sends nothing. With no UI, it writes the lines to stdout and changes nothing; in Pi's print mode, Pi sends that stdout to stderr. An error is the notification `harness: <error>`, or that line on stderr with no UI.

`/vc`, and its shortcut `ctrl+shift+y`, open the visual copy of the transcript, only in Pi's interactive mode; in another mode, it shows `/vc requires interactive mode`. The shortcut keeps the text of the editor, which a typed `/vc` replaces. The view selects the blocks of the agent messages (a paragraph, a list item, a code block, a quote, a table, a Mermaid diagram) and the images of the tool results. `j`/`k` move by block, `{`/`}` by message, `v` and `V` select a range or a message, `/` and `?` search, `n`/`N` go to the next and the previous match, `w` selects the inline code, `y` copies and `Y` copies the raw Markdown, Esc leaves the range, then the view, and `q` leaves the view. A single code block gives its code without the fences, a single quote its text without the markers, a diagram an image of it (`Y` its source) and an image the image (`Y` its file path). Images and diagrams go on the clipboard with `osascript` on macOS, with `wl-copy` or `xclip` on Linux, and with Windows PowerShell on Windows and WSL; the text copy uses Pi's clipboard. A copy shows `Copied <n> lines: <first line>`, `Copied image`, `Copied path: <path>` or `Copied diagram image (<size>)`, and a copy that fails shows `Copy failed: <error>`. After a text copy, the extension reads the threads of the project with `thread list` and `thread read`, through `sendToHost`, so it starts the host when none runs. For each message out in the state `draft` whose text the copied text holds, with each run of whitespace as one space and without whitespace at the ends, it sends `message mark` with the state `sent`, with the session ID as the caller, and shows `Draft <id> marked sent`. A read or a mark that fails shows a warning, `Could not read the drafts: <error>` or `Could not mark draft <id> sent: <error>`, and the copy stays done. Another copy sends no mark.

Before each turn of the session (`before_agent_start`), the extension sends a `digest` request with the session ID as the caller to the host of the project, and starts the host when none runs, so the first turn of a session and a turn after the host exited get the board. The request has as `head` the ID of the newest entry of the type `compaction` on the branch of the session, when it has one, so the first turn after a compaction gets the digest again also when it did not change. When the reply has a text, the turn gets it as a custom message of the type `harness-digest`, which Pi shows and gives the model. A request that fails gives no message, and a notification `harness: no digest: <error>` with a UI.

Before each turn, the extension also sends `rule list` with the status `decided` to the host, only when a host runs. When `rulesSection` gives a text for the reply, the turn has it as the system prompt section `project_rules`, as a child has it (see [Host](#host)). With no host, no decided rule, or a request that fails, the turn has no such section; a request that fails also shows the notification `harness: no rules: <error>` with a UI. Pi builds the sections again at each turn, so a rule that the user decides or retires reaches the session at its next turn.

The `memory` tool of the extension has the name, label, description and parameters of the `memory` tool of the project agent (see [Project agent](#project-agent)), from `memoryTool({ Type }, adapt)` of `@vzlentin/harness/memory-tool`. Its `run` is the runner of the host tool: `memoryRequest(args)` gives the `memory` request of a call, and refuses a call without the field of its action, such as with `note requires text`. The extension gives `run` the `sendToHost` send, so the call goes to the host of the project and starts the host when none runs, and the result is the `text` of the reply. The session uses the memory of the project agent of that host: the `MEMORY_DIR` of Pi's process has no effect. When no host answers, or the host replies an error, the call fails with that one-line error.

At the first turn of a session, the extension sends a `memory` request with the action `snapshot` to the host of the project, with a start, so this turn can start the host. It keeps the reply for the session ID, and each turn of the session gets its text as the system prompt section `memory` (`MEMORY_SECTION`), after the section of the decided rules. The section does not change during the session: a note shows only in the next session, or after a `/reload`, which takes a new snapshot. A reply with an empty text gives no section. A snapshot that fails, such as with no host that answers, gives the session no section and no new request, and the notification `harness: no memory: <error>` with a UI.

With a UI, the todo widget above the editor shows the list of the agent of the session while that list has an open or a doing todo: a dim header line `todos <done>/<total>`, such as `todos 3/10`, then one line for each open and doing todo, in ID order, as `harness todo list` prints it. The total counts the open, doing and done todos, not the dropped ones. The done and dropped todos do not show. The widget has at most 10 lines: with more than 9 open and doing todos, it shows the first 8, then a dim `+<n> more`. Each line starts with one space, and a line wider than the terminal is cut at its width with `…`. Otherwise the widget is hidden. In a session that is not a mirror session, the agent is the session itself. Its list has no watch, so the widget reads it as the subagents widget reads the children: every second, without starting the host, so it is hidden when no host runs. It also reads it at once after each `todo` call of the session and each `/todo` addition, before the call or command ends. When the host fails the request, it shows only `todos: <first line of the error>` in the error colour, with no header. The extension sets each of the two widgets one time at the session start, as a component, also in a mirror session: Pi moves a widget that is set again to the end of its side. A change of the lines draws the component again, and a hidden widget draws no line. So of these two widgets, only the todo widget is above the editor, and the subagents widget stays below it. A mirror session also has its status area above the editor, below the todo widget (see [Mirror sessions](#mirror-sessions)). Pi draws these components only in its interactive mode: an RPC client does not get the widgets. A `todo` request with the action `list` does not keep the host running (see [Host](#host)). In a mirror session, the widget shows the list of the mirrored agent (see [Mirror sessions](#mirror-sessions)).

Each Pi session keeps one `answers` request open to the host, on a connection of its own, with the session ID as the caller (see [Push](#push)). For each delivery, Pi shows a custom message with the same text as the input of a push to a conversation of the host, and the delivery as its details: of the type `subagent-answer` for the answers of a child, and `user-answer` for the answers of the user to asks of the session. The message starts a turn, as a follow-up when Pi works. At the session start, with or without a UI, the extension opens the request. It starts the host only when the session has a result of the `subagent` tool or of the `parley` tool, so a session that spawned children or asked the user gets the answers that came while Pi was closed. When the host closes the connection, the extension connects again at once, after 2 s and after 5 s, then every 5 s until a try connects. When no host runs at the session start, it tries every 5 s. When a connection closes less than 10 s after it opened, the next try is after 5 s. Only the first try at the session start can start a host. A caller that opened an `answers` request is a Pi session for the host, which keeps it in the document `subagent.sessions` of the store. When a session has no open `answers` connection for 30 s, the session ends: the host ends its children and the children they spawned, as a `stop` does, and keeps the unread answers of its own children, which the session gets when it opens an `answers` request again. A busy child gives `<handle> was aborted`. No child runs again until a `send` resumes it. `/reload` opens the request again within the 30 s, so it keeps the children; a quit, and Pi's `new`, `resume` and `fork`, close it, so the children of the old session end. A host that starts gives each saved session 30 s from its start: a session whose request does not come back in that time ends. A host that closes ends no session. `cli`, and a caller that never opened an `answers` request, keep their children. When Pi fails to show an answer, the extension shows the error as a notification, `Could not show an answer: <error>`, and the next answers still come. At the session end, it closes the connection.

### Mirror sessions

A mirror session is a Pi session that shows a child or the agent of a project (see [Project agent](#project-agent)) in Pi's own chat, and sends what you type to it. The agent runs in the host of the project, so it continues when Pi closes. Below, the agent is the child or the project agent that the session shows. The mirror sessions work only in Pi's interactive mode. In another mode, a session with a `harness-mirror` entry, or a Pi with one of the `--harness` flags, fails at the session start with `harness: a mirror session works only in Pi's interactive mode`, and Pi's own agent does not take its input.

- `/harness <project>` opens a new Pi session that mirrors the agent of `<project>`, which is `main` or a project name. An unknown project is an error: `harness: Unknown harness project: <name>`. The command completes the project names. Without a project, it asks for one in the list `Harness project`, with one line `<name>  <dir>` for each project: the project of Pi's working directory first (as for a command), then the other projects, then `main` with `~`. When `main` is the only project, it opens `main` and does not ask. Esc cancels.
- `pi --harness <project>` mirrors the agent of the project in the session that Pi starts with, `pi --harness <project> --harness-child <handle>` mirrors a child of the project, and `pi --harness <project> --harness-conversation <id>` mirrors a conversation of the children library (see [Open in Pi](#open-in-pi)). Both `--harness-child` and `--harness-conversation` is an error: `harness: use --harness-child or --harness-conversation, not both`. Without `--harness`, or with an empty project, the project is the one of `HARNESS_PROJECT` and Pi's working directory. It refuses a session with messages, such as one of `--continue`: `harness: --harness needs a new session, not one with messages`. A session that is already a mirror session keeps its target, and at the startup Pi shows `harness: the --harness flags are not used: the session is already a mirror session`.
- The session has the title of the agent as its name, `<name> (<handle>)`, `<key>` for a conversation, or `<project> agent`, and follows a rename. It holds one custom entry, `harness-mirror`, with the target `{ project, handle }`, or `{ project, conversation }` for a conversation, and Pi draws the conversation of the agent in place of that entry: the newest entries of the conversation when the session attaches, then each new entry, which it adds below the others. It uses Pi's message and tool components and Pi's theme (adapted from the attach view of [mavam/pi-agents](https://github.com/mavam/pi-agents)): the user messages, the typed inputs (`harness.typed`) among them, the answers with their thinking, and a Pi tool card for each call of `read`, `bash`, `edit` and `write`, with its output while it runs. Other tools get Pi's generic card. A compaction shows `[compaction]` and its summary, and a reset shows `[new context]`, where they occur in the conversation; the entries before them stay. The first line is `harness │ <title> │ <working directory>`. Pi saves a session only when it has a message, so it does not save a mirror session and `/resume` does not list it; run `/harness` again to open it.
- A message that you send goes to the agent: a new turn when it is idle, a steer when it works. Pi's own agent does not run. While the agent works, Esc aborts its turn, and the queued messages go back to the editor, steers first; Alt+Enter (`app.message.followUp`) queues the text as a follow-up. Before the connection opens and while the session connects again, Alt+Enter also sends the text as a follow-up, which waits for the connection. A conversation of the children library takes a message only while it works, always as a steer, also with Alt+Enter; when it is idle, the message goes back to the editor with `harness: not sent: <key> takes input only while it works`. The extension uses its own editor in the session for these keys.
- Above the editor, Pi's working indicator shows what the agent does (`Working...`, `Running <tool>...`, `Compacting (<reason>)...` or `Retrying (attempt <n>): <error>`), and each queued message shows as `Steer: <first line>` or `Follow-up: <first line>`.
- Above the editor, above the working indicator, the todo widget (see [Pi extension](#pi-extension)) shows the list of todos of the agent, from the view of the watch (`harness.todos` in its `docs`, see `host.sock` in [Host](#host)), while it has an open or a doing todo. Its lines follow each change of the view, and the widget is drawn again only when they change. It is set one time, before the status area of the session, so it stays above that area. It shows the list of the last view also while the session connects again and after it failed. It does not show the list of the local Pi session. It goes away when the session ends.
- The answers of the agent follow Pi's `hideThinkingBlock` setting: Ctrl+T (`app.thinking.toggle`) hides and shows their thinking, as for Pi's own messages.
- The last line above the editor is `<title> • <usage> • <context>`, without the parts that are empty. The usage has the sums of the agent's model requests and tool results, as Pi's footer shows its own: `↑` input, `↓` output, `R` cache read, `W` cache write and `$` cost, each when it is not zero, and the cost also when Pi uses a subscription for the model, with `(sub)`. The context is `<percent>%/<window>`: the context of the last answer of the agent's active transcript (after its last compaction or reset) that did not abort or fail, against the context window of its model, when Pi knows the model. Pi's footer stays as it is, for the local Pi session: Pi's own footer, or the footer of an extension.
- Pi's model and thinking level follow the agent's. A model that you select in Pi (`/model`, Ctrl+P) and a thinking level (Shift+Tab) go to the agent with a `configure` request. A refused change gives an error, and Pi goes back to the agent's model. The model that Pi takes from the agent is not a request. When Pi does not take the agent's model, Pi shows an error: `harness: Pi has no login for <provider>/<model>` without a login for it, or the error of Pi. When the agent changes its model while Pi takes the previous one, Pi then takes the new one. A conversation of the children library refuses each change, without a request, with `harness: A conversation of the children library keeps its model and thinking level`.
- When the host closes the connection, the session connects again, which starts a new host when none runs. It shows `Connecting again to the harness host...` above the editor. It tries three times: at once, after 2 s, and after 5 s. When all tries fail, the session shows `The harness host closed the connection. Connecting again failed: <error>`. When the host closes a connection that was opened again less than 10 s before, the session does not connect again and shows `The harness host closed the connection. Run /reload to attach again`. When the child is stopped, the session stays open and shows the state `ended`; a message resumes the child. When the connection closes, each tool card that runs shows `Interrupted: no connection to the harness host`. `/reload` attaches again, and starts the host when none runs. `/new` and `/resume` leave the mirror session; the agent keeps running.
- A message that you send while the session connects waits for the connection. When the connection closes before the host answers a message, the message goes again on the next connection with the same request ID, so the agent gets it once. A message that does not reach the agent, because the host refuses it or the session fails first, goes back to the editor, after the text there, and Pi shows `harness: not sent: <reason>`. A message that went to the host on a connection that closed before the host answered, when the session then fails, may be with the agent: it does not go back to the editor, so that a send again does not give it twice. It stays in the history of the editor, and Pi shows `harness: maybe sent: <reason>. The text is in the history of the editor`.
- Images are not sent: the agent gets only the text, with the warning `harness: the images are not sent; the agent gets only the text`. Pi does not expand skill commands and prompt templates for the agent. Pi's own session commands act on the local Pi session, which has no messages: `/compact` fails with `Nothing to compact (session too small)`, `/fork` gives `No messages to fork from`, `/tree` shows `No entries found`, and `/export` fails with `Nothing to export yet - start a conversation first`.
