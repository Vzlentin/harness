- Check: `npm run check` (Biome, oxlint, TypeScript, Vitest).
- Lint: oxlint with the anti-slop plugin, vendored in `tools/oxlint/anti-slop/` (see its `UPSTREAM.md`). Biome only formats and sorts imports. Outside data is checked with TypeBox schemas, not `typeof`.
- `docs/spec.md` is the behaviour spec: CLI commands, arguments and output lines, the tool, the host, and where state lives. Update it in the same change as the behaviour. `README.md` has only the install, a short usage and development; keep it short.
- `origin` is `Vzlentin/harness`. It continues the history of `Vzlentin/pi-subagent`, now archived, a fork of `badlogic/pi-subagent`.
- Two npm packages come from this repository: `@vzlentin/harness`, with the `harness` command, and `@vzlentin/pi-agents`, the Pi extension in `pi/` with the `subagent` skill in `pi/skills/subagent/`. They are released together, with one version. `@vzlentin/pi-agents` depends on `@vzlentin/harness` at the same exact version; release-please moves both (`extra-files` in `release-please-config.json`). Pi installs both into its own npm folder with `pi install npm:@vzlentin/pi-agents`. There is no setup and no install script. workflows depends on `@vzlentin/harness` too, so a change of the major (or of the minor before 1.0) needs a new range there.
- Release: release-please (`release-please-config.json`, `.release-please-manifest.json`) keeps one release PR open on `main`, titled `release: <version>`, with the version and `CHANGELOG.md` from the Conventional Commits since the last release. Merging a feature PR releases nothing. Merging the release PR makes `.github/workflows/publish.yml` create the tag and the GitHub release, and publish the version to npm with trusted publishing. `pi/package.json` follows the version through `extra-files` in `release-please-config.json`. The publish job publishes both packages, the root and then `pi/`, and skips each version that npm already has. Before 1.0, a breaking change bumps the minor and `feat` or `fix` the patch; a `Release-As: <version>` footer in a commit sets the version. release-please opens the release PR with the token of a GitHub App (the variable `RELEASE_APP_CLIENT_ID` and the secret `RELEASE_APP_PRIVATE_KEY`), so the check runs on it; without the app it falls back to `GITHUB_TOKEN`, whose PR runs no check. Do not change `version` by hand and do not run `npm publish` by hand.
- Dependency versions are pinned exactly. The `@earendil-works/*` packages share one version; change them together. In the root package they are plain `dependencies`.
- The root package publishes `dist/`, `python/*.py` and `web/`: `python/harness_rlm.py` is the `rlm` client of the IPython kernels, with the standard library only, for Python 3.9 or later. `web/` has the browser files of the inspect UI, plain JavaScript and CSS with no build; `src/inspect/handler.ts` reads them at `../../web/`, which is the same folder from `src/inspect/` and from `dist/inspect/`. `prepack` builds `dist/` with `tsconfig.build.json`. `dist/` is not in Git. The `exports` of `package.json` list each public subpath, `@vzlentin/harness/<name>`, and the file it maps to, such as `protocol` to `src/protocol/index.ts`, `rlm` to `src/rlm/index.ts`, `children` to `src/children/library.ts`, `mirror` to `src/client/mirror.ts`, `inspect` to `src/inspect/index.ts`, `host` to `src/host/run.ts` and `durable-entry` to `src/host/durable-entry.ts`; workflows and `pi/` import these names, so a moved module keeps its subpath. The checkout runs from source with Node type stripping, so keep to syntax that Node can strip. `cliPath()` in `src/protocol/paths.ts` gives the CLI that the host start and the hc terminals of `openChildTab` and `openConversationPane` run: `dist/cli.js`, or `src/cli.ts` in a checkout.
- `src/` has six groups and two files. `protocol/` holds the requests, targets, labels, lines and view changes, the state paths and files (`paths`, `projects`, `entries`, `json-file`), the environment variable names and the caller of a command (`env`), and `trust`. `children/` runs the children in a host. `client/` talks to a host. `host/` is the host. `rlm/` serves `rlm` to the IPython kernels: the kernel servers, the kernel startup code, the text of the `<rlm>` section, the limits of the RLM children and the pool of their model requests. `inspect/` is the inspect web UI: its routes and its standalone server. `tool.ts` is the `subagent` tool, and `cli.ts` the command. Imports go one way: `protocol/` imports nothing else from `src/`; `children/` and `client/` import only `protocol/`; `inspect/` imports only `protocol/` and `client/`; `rlm/` imports only `protocol/` and `tool.ts`, and Pi packages as types only, so that the Pi extension can load it from `dist/`; `host/` imports `protocol/`, `children/`, `rlm/` and `tool.ts`; `tool.ts` imports `protocol/` and `client/`. Type imports count too. `.oxlintrc.json` checks these rules with `no-restricted-imports`.
- The host loads the `piDurable` entries of Pi's packages (such as pi-ipython) and the entries in `entries.json` (`src/protocol/entries.ts`, for packages that are not Pi packages, such as workflows).
- The files in `pi/` run inside Pi. Pi supplies `pi-ai`, `pi-coding-agent` and `pi-tui`, so they are `peerDependencies` at `"*"` in `pi/package.json`, and the extension takes them from Pi. Code that draws with Pi's components, such as `pi/chat.ts`, goes in `pi/` for this reason. `typebox` is a peer at `"*"` too. The extension resolves its dependency `@vzlentin/harness` with `createRequire` from its own folder, puts the `.bin` folder next to it last on `PATH`, and loads `answers`, `client`, `herdr`, `mirror`, `projects`, `protocol`, `rlm`, `tool`, `trust` and `view-state` from its `dist/` into one `Harness` object (`pi/index.ts`). The other files in `pi/` take that object or a `Pick` of its functions. From `../dist/`, `pi/` has only `import type`, and loads only `protocol/`, `client/`, `rlm/` and `tool.ts`; oxlint refuses a runtime import there, and any import of another group. These modules, and the modules that they import, such as `view-change`, must not import Pi packages, `chord` or `pi-durable` at runtime (types only). The type check resolves `../dist/*.js` to `dist/*.d.ts`, so `npm run check` builds `dist/` before it. The `pi` manifest in `pi/package.json` lists `./index.ts` in `extensions` and `./skills` in `skills`: with a manifest, Pi loads only what it lists. To load the checkout's extension in Pi, run `npm run build`, link the checkout as the dependency with `mkdir -p pi/node_modules/@vzlentin && ln -s ../../.. pi/node_modules/@vzlentin/harness`, then run `pi install ./pi`. Do not run `npm link` or `npm install` in `pi/`.
- Tests must not call a real model, start tmux, use the user's Pi or Git configuration, or run the real `npm`. Use a temporary `PI_CODING_AGENT_DIR` and pi-ai's faux provider. The tests of `rlm` run the system `python3` through the fixture entry `test/fixtures/ipython`, not pi-ipython; the test of the Pi extension runs `python3` directly, with the startup code that the extension gives.
