- Check: `npm run check` (Biome, oxlint, TypeScript, Vitest).
- Lint: oxlint with the anti-slop plugin, vendored in `tools/oxlint/anti-slop/` (see its `UPSTREAM.md`). Biome only formats and sorts imports. Outside data is checked with TypeBox schemas, not `typeof`.
- `docs/spec.md` is the behaviour spec: CLI commands, arguments and output lines, the tool, the host, and where state lives. Update it in the same change as the behaviour. `README.md` has only the install, a short usage and development; keep it short.
- `origin` is `Vzlentin/harness`. It continues the history of `Vzlentin/pi-subagent`, now archived, a fork of `badlogic/pi-subagent`.
- Two npm packages come from this repository: `@vzlentin/harness`, with the `harness` command, and `@vzlentin/pi-agents`, the Pi extension in `pi/`, with the same version. `setup(packageDir, piPackage)` in `src/setup.ts` registers `npm:<piPackage>@<version>` with `pi install` for a top-level global install, with the version of `<packageDir>/package.json`. Two things run it: `scripts/postinstall.js` on a global install (npm 11; npm 12 blocks install scripts by default), which is plain JavaScript because Node does not strip types under `node_modules` and imports `dist/setup.js`; and the installed CLI, once per version (`setupOnce`). workflows calls `@vzlentin/harness/setup` too, with `@vzlentin/pi-workflows`, so keep its API as `docs/spec.md` gives it. workflows takes `@vzlentin/harness` as an optional peer, so a change of the major (or of the minor before 1.0) needs a new peer range there.
- Release: release-please (`release-please-config.json`, `.release-please-manifest.json`) keeps one release PR open on `main`, titled `release: <version>`, with the version and `CHANGELOG.md` from the Conventional Commits since the last release. Merging a feature PR releases nothing. Merging the release PR makes `.github/workflows/publish.yml` create the tag and the GitHub release, and publish the version to npm with trusted publishing. Before 1.0, a breaking change bumps the minor and `feat` or `fix` the patch; a `Release-As: <version>` footer in a commit sets the version. release-please opens the release PR with the token of a GitHub App (the variable `RELEASE_APP_CLIENT_ID` and the secret `RELEASE_APP_PRIVATE_KEY`), so the check runs on it; without the app it falls back to `GITHUB_TOKEN`, whose PR runs no check. Do not change `version` by hand and do not run `npm publish` by hand.
- Dependency versions are pinned exactly. The `@earendil-works/*` packages share one version; change them together. In the root package they are plain `dependencies`.
- The root package publishes `dist/` and `scripts/postinstall.js`. `prepack` builds `dist/` with `tsconfig.build.json`. `dist/` is not in Git. The checkout runs from source with Node type stripping, so keep to syntax that Node can strip. `cliPath()` in `src/protocol.ts` gives the CLI that the host start and the Herdr tabs run: `dist/cli.js`, or `src/cli.ts` in a checkout.
- The host loads the `piDurable` entries of Pi's packages (such as pi-ipython) and the entries in `entries.json` (`src/entries.ts`, for packages that are not Pi packages, such as workflows).
- The files in `pi/` run inside Pi. Pi supplies `pi-ai`, `pi-coding-agent` and `pi-tui`, so they are `peerDependencies` at `"*"` in `pi/package.json`, and the extension takes them from Pi. Code that draws with Pi's components, such as `pi/chat.ts`, goes in `pi/` for this reason. `typebox` is a peer at `"*"` too. The extension finds the global harness install (`harness` on `PATH`, then `npm root -g`) and loads `client`, `herdr`, `mirror`, `projects`, `protocol`, `tool` and `view-state` from its `dist/` into one `Harness` object (`pi/index.ts`). The other files in `pi/` take that object or a `Pick` of its functions. From `../dist/`, `pi/` has only `import type`; oxlint refuses a runtime import there. These modules, and the modules that they import, such as `view-change`, must not import Pi packages, `chord` or `pi-durable` at runtime (types only). The type check resolves `../dist/*.js` to `dist/*.d.ts`, so `npm run check` builds `dist/` before it. workflows implements the install lock of `docs/spec.md` too; change `pi/install-lock.ts` and the spec together. To load the checkout's extension in Pi, run `npm run build` and `npm link`, then `pi install ./pi`.
- Tests must not call a real model, start tmux, use the user's Pi or Git configuration, or run the real `npm`. Use a temporary `PI_CODING_AGENT_DIR` and pi-ai's faux provider.
