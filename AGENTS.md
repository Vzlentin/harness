- Toolchain: Vite+ (`vite-plus`, the `vp` command). The root `vite.config.ts` configures `fmt`, `lint`, `test` and `pack`.
- Before `npm run check`, run `vp check --fix`: it formats the files and autofixes the lint spacing rules, such as `anti-slop/require-readable-spacing`.
- Check: `npm run check` builds `dist/`, then runs `vp check --deny-warnings` (format, lint, type-aware lint, type check), `tsc -p tsconfig.json` and `vp test`.
- Lint: Oxlint with the anti-slop plugin, vendored in `tools/oxlint/anti-slop/` (see its `UPSTREAM.md`). Check outside data with TypeBox schemas, not `typeof`. Tests import from `vite-plus/test`.
- `docs/spec.md` is the behaviour spec (CLI, tool, host, where state lives): update it in the same change as the behaviour. Keep `README.md` short: install, usage, development.
- Two npm packages, released together with one version: `@vzlentin/harness` (the `harness` command) and `@vzlentin/pi-agents` (the Pi extension and skills in `pi/`), which depends on `@vzlentin/harness` at the exact same version. workflows depends on `@vzlentin/harness`, so a new major (or minor before 1.0) needs a new range there.
- Pin dependency versions exactly. The `@earendil-works/*` packages share one version: change them together.
- `package.json` `exports` lists each public subpath `@vzlentin/harness/<name>`. workflows and `pi/` import these names, so a moved module keeps its subpath.
- The checkout runs from source with Node type stripping: use only syntax that Node can strip.
- Most `src/` files open with a module header doc comment that says what the module holds. List them with `rg -U -m1 --no-heading -o -r '$1' '\A/\*\*\s*(?:\n \* )?([^\n]*)' src`. Keep the header true when you change what a module holds.
- Imports go one way, and type imports count: `protocol/` imports nothing else from `src/`; `children/` and `client/` only `protocol/`; `bridge/` only `protocol/`, and Pi packages as types only; `host/` imports `protocol/`, `children/`, `bridge/` and `tool.ts`; `tool.ts` only `protocol/` and `client/`.
- An external entry, such as the projects package, loads only through `loadEntries` and imports only the `package.json` `exports` subpaths. It reaches host state through the handles of the entry API (`host/entries.ts`): add a handle, not an export of a `host/` module that holds or reads host state.
- `pi/` runs inside Pi, which supplies its peers. Code that draws with Pi's components, such as `pi/chat.ts`, goes in `pi/`. From `../dist/`, `pi/` has only `import type`, and only of `protocol/`, `client/`, `bridge/` and `tool.ts`. These modules, and what they import, must not import Pi packages, `chord` or `pi-durable` at runtime. `no-restricted-imports` in `vite.config.ts` checks the `src/` and `pi/` import rules.
- To load the checkout's extension in Pi: `npm run build`, `mkdir -p pi/node_modules/@vzlentin && ln -s ../../.. pi/node_modules/@vzlentin/harness`, then `pi install ./pi`. Never run `npm link` or `npm install` in `pi/`.
- Tests must not call a real model, start tmux, use the user's Pi or Git configuration, or run the real `npm`. Use a temporary `PI_CODING_AGENT_DIR` and pi-ai's faux provider.
- Never run the tests under `git rebase -x` or in a Git hook: Git exports `GIT_DIR` and `GIT_WORK_TREE` there, and `test/setup.ts` clears the `GIT_*` variables only in the test workers.
